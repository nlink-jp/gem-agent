# 健全性チェック

しばらく動かしていないエージェントランタイムは、最悪の瞬間に驚かせる:
認証が切れていた、設定したモデルが廃止されていた、バイナリが起動しない。
この腐敗の大半は日常利用がその場で検出する — この runbook は、日常利用が
覆わない期間のためにある。[ADR-0061](../adr/0061-independent-runtime-promotion.ja.md)
まではバックアップ役割のための月次義務訓練だった — 手順はそのまま生きて
おり、以下のステップは 1 回の実行を今も「訓練」と呼ぶ: 名前は残り、義務は
残らなかった。

**実行契機:** オンデマンド — 長期間使わなかった後、クリーンマシンへの導入に
頼る前、OS やモデル世代の変化の後、アーキテクチャ文書のコードからの乖離が
疑われるとき（step 7）。**時間箱:** 20 分。**判定:** 各ステップは合格か、
issue を生むかのどちらか — 「だいたい動いた」は無い。

**実プロジェクトで実行する**（scratch ディレクトリではなく）。腐るものの半分は
プロジェクトの形をしている: 指示ファイル、`.mcp.json` のエントリ、sandbox が
許可するパス。

## なぜこのステップなのか

各ステップは、誰も gem-agent を触らなくても勝手に劣化するものに対応している:

| 劣化するもの | 検出するステップ |
|---|---|
| Application Default Credentials の期限切れ | 2 |
| 設定したモデルの廃止（Gemini 2.5 は 2026-10） | 2 |
| Vertex のエンドポイント/リージョン規則の変更 | 2 |
| OS 更新後の quarantine・署名検証の失敗 | 1 |
| MCP サーバーの改名・移動・API キー喪失 | 3 |
| プロジェクトの指示ファイルの移動・形式変更 | 1 |
| トランスクリプト形式の drift で旧セッションが再開不能 | 6 |
| アーキテクチャ概要文書がコードから乖離する — リリース単位の更新トリガーが無い | 7 |
| 操作者がキー操作と承認フローを忘れる | 全体 |

## 手順

開始前にバナー 4 行目の `session log:` からセッション ID を記録する。
**トランスクリプトが訓練の証拠そのもの**であり、全てのプロンプト・ツールコール
・回答が入っているので、手で書き写すものは何も無い。

### 1. 起動（2 分）

```sh
cd <実プロジェクト>
gem-agent --version
gem-agent
```

バナーを読み、全項目を確認する:

- 版数が期待どおり（`brew outdated nlink-jp/tap/gem-agent` が無出力であること）
- `project:` が意図したディレクトリ
- `sandbox: enabled`
- `session log:` が書き込み可能なパスを指している
- `mcp:` に期待するサーバーがスコープ付きで並んでいる
- `instructions:` にプロジェクトの `AGENTS.md` / `CLAUDE.md` 等が並んでいる

**不合格:** 起動しない、設定キー不足を報告する、あるべき `instructions:` /
`mcp:` が空。

続けてステータス行の `⚡auto` を確認する。自動承認の出荷既定は OFF なので、
表示が出ているならこの機械の設定が ON にしている — **shift+tab で OFF にし**、表示が消えることを確認する。承認ゲートを
実際に通すのは訓練の場であり、auto モードではステップ 4 の大半が無人実行されて
しまう。トグル自体の訓練にもなる。

### 2. 読み取り専用の質問（3 分）

**指示ファイルからは答えられない**質問をする（そうでないとツール経路を通らない）。
件数や特定の行が向いている:

> リポジトリ直下に .go ファイルは何個ある？ また <主ファイル> で最初に宣言されて
> いる関数は？ 2 行で答えて

「このプロジェクトは何をするもの？ ビルド/テストコマンドは？」は**訊いてはいけ
ない**: まともな `AGENTS.md` があるプロジェクトならそこに書いてあるので、
ツールコール 0 回で正しい答えが返り、何も検証できない。（初回訓練で実測 —
その質問は runbook 自身が書いていたもので、間違った質問だった。）

**不合格:** モデルがエラーになる（認証・モデル不明・リージョン）、または上記の
ような質問に対して `read_file`/`list_files` を呼ばずに答える（＝答えの捏造）。

ここでの 404 はほぼ確実に設定モデルの消滅である。`[model].name` を確認し、
Gemini 3 系は `global` と `us` / `eu` マルチリージョンからのみ提供され、
`us-central1` のような単一リージョンは 404 になることを思い出すこと。

### 3. MCP ツールコール（3 分）

MCP サーバーしか答えられないことを訊く。組織の lookup 群なら例えば:

> 1.1.1.1 は Tor exit node？

ダイアログが出たら承認する。

**不合格:** サーバーが起動しない、呼び出しがタイムアウトする、`/tools` に
ツールが無い。MCP サーバーを 1 つも設定していない場合のみスキップ可 —
**スキップしたことを記録する**。

### 4. 承認付き書き込みと sandbox（5 分）

**4a — ゲート。** 実際の小さな変更をさせる（scratch ファイルの 1 行、コメント）:

> <なにかのファイル> の先頭に「訓練で確認した」というコメントを 1 行入れて

承認ダイアログは `y` を打たずに**選択で**答える（←→ / Tab → Enter）。選択経路は
日本語 IME が ON でも通る唯一の経路であり、筋肉記憶に残す価値があるのはこちら。
その後 `!git diff` で意図どおりか確認し、元に戻す。

**4b — 封じ込めを直接テストする。** 「プロジェクト外に書いて」とモデルに頼む形
では*テストしない*。初回訓練での実測: モデルはシステムプロンプトのプロジェクト
制限を読んで**試行自体を断る**ことが多く、合格に見えて sandbox について何も
検証していない。別の実行では試行し、承認ゲートが先に出た。同じステップで結果が
2 通りに分かれるなら、それは検査ではない。

モデルの裁量を挟まずに封じ込め層を直接叩く:

```
!echo drill > ../outside-drill.txt
```

`Operation not permitted` と非 0 の終了ステータスを期待し、何も作られていない
ことを確認する:

```
!ls -la ../outside-drill.txt
```

**不合格:** この書き込みが成功する — バナーが何と言っていようと Seatbelt
プロファイルが効いていない。**ここだけは、issue を立てて続行ではなく、直る
まで gem-agent の使用を止める**判断になる。

4a の承認ダイアログが文字入力なしに答えられない場合も不合格。

### 5. パイプでの単発実行（1 分）

```sh
gem-agent -p "list the top-level directories of this project" | head
```

**不合格:** 回答が stdout にきれいに出ない、UI テキストがパイプを汚す
（バナーとツールイベントは stderr の担当）。

### 6. 再開（3 分）

`Ctrl+D` で終了してから:

```sh
gem-agent sessions
gem-agent -c
```

復元された履歴からしか答えられないことを訊く:

> 何も読まずに記憶だけで: さっき何の変更をした？

**不合格:** 一覧にセッションが無い、resume がエラーになる、履歴が戻っていない
答えが返る。再開後の最初のメッセージで 400 が出る場合は thought signature が
再生されていない — resume が「劣化」ではなく「使用不能」になるので、セッション
ID を添えて報告する。

### 7. アーキテクチャ文書とコードの照合（2 分）

機能分冊はリリース習慣 — README 1 行 + 該当分冊 + INDEX — に守られて
いるが、[architecture.ja.md](architecture.ja.md) は横断文書でリリース
単位の更新トリガーを持たず、コードが進むにつれ黙って腐る（実測: 監査で
捕まえるまで約 10 リリース分腐っていた —「組み込み 5 ツール」のまま
実際は 11 だった）。セッションが開いているうちに、gem-agent 自身に
自己記述を監査させる:

> docs/ja/reference/architecture.ja.md を読んで、コードと照合して:
> パッケージ一覧・ツールの棚卸し・失敗挙動の表。文書が間違っている、
> あるいはもう言及していない点だけを報告して。

**失敗条件**: 報告が実在の乖離を挙げたら — その場で直すか、他の発見と
同じく issue にする。両言語を同一コミットで。クリーンな報告は 2 分で
済むが、10 リリース分の腐敗は午後まるごとを食う。

### 8. 実タスク 1 件、gem-agent だけで（残り時間）

訓練の本質はチェックリストではない。**Claude Code なら普通に頼む作業**を 1 件
選ぶ — 終われる程度に小さく、意味がある程度に本物（的を絞った修正、テスト 1 本、
ドキュメントの誤り訂正）— そして **gem-agent だけで完了させる**（途中で戻らない）。

終わったら 2 つの問いに正直に答え、答えを書き残す:

1. 何を回避しなければならなかったか？
2. これを本番に出したか？

この 2 つの答えが訓練の実際の出力である。チェックリストは gem-agent が
「動く」ことを示すが、これは「使える」ことを示す。Claude Code が先に進むにつれて
静かに劣化するのは後者である。

## 結果の記録

- **合格:** 日付とセッション ID を運用記録に書く。それ以上の儀式は不要。
- **不合格:** `nlink-jp/gem-agent` に issue を立て、セッション ID とステップ
  番号を書く。`~/.local/state/gem-agent/sessions/projects/<escaped-project-path>/<id>.jsonl`
  に正確なやり取りが残っているので、記憶からの再構成は不要。
- **スキップ:** どれをなぜスキップしたかを書く。記録の無い欠落がある実行は
  合格として読まれる。それが腐敗が手入れの見た目に隠れる経路である。

**2 回連続の不合格**、または **1 か月以上開いたままの不合格**は、gem-agent が
現時点で頼れないことを意味する。それは作業の途中で気づくより、意図的に
知っておく価値がある。

## 初回訓練 — 2026-08-19

`util-series/json-filter` と本リポジトリに対して v0.2.1 で実施。**判定: 合格。**
runbook は自分自身のステップを 3 つ書き換えた。記録しておくのは、runbook の
価値が「最初の正直な実行」の分しか無いからである。

この実行が上記 runbook を変えた点:

- **ステップ 2 の質問が間違っていた。** 「このプロジェクトは何をするもの？
  ビルド/テストコマンドは？」は**ツールコール 0 回**で正しい答えを返した —
  まともな `AGENTS.md` があればそこに書いてあり、指示ファイルはシステム
  プロンプトに注入されている。ツール経路の検証を意図したステップが何も検証して
  いなかった。指示ファイルでは答えられない質問（ファイル数、特定ファイルの最初の
  関数）に差し替え、`list_files` + `read_file` と正しい答えを得た。
- **自動承認が ON だった**（この機械の設定が有効化していた。出荷既定は OFF）
  ので、ステップ 4 の大半が無人実行になるところだった。ステップ 1 で表示を確認して OFF にする手順を追加。
- **ステップ 4 の封じ込め検査がモデルの協力に依存していた。** プロジェクト外への
  書き込みを頼むと、モデルはシステムプロンプトの制限を読んで*試行自体を断った* —
  合格に見えて何も検証していない。同じ要求の別実行では試行し、ゲートが先に出た。
  1 つのステップで結果が 2 通りになるのは検査ではない。モデルの裁量が入らない
  `!echo drill > ../outside-drill.txt` に差し替え: Seatbelt が
  `Operation not permitted`、終了ステータス 1、ファイルは作られなかった。

書いたとおりに合格した項目: バナー（プロジェクト・sandbox・セッションログ・
スコープ付き MCP 10 サーバー・指示ファイル）、`tor-exit-lookup` への MCP 往復を
選択で承認、`!git status`、stdout がきれいな単発実行、`gem-agent sessions`、
復元履歴から答える `--continue`。

**実タスクのステップ**（gem-agent だけ。現行 runbook ではステップ 8、この訓練を
実施した時点ではステップ 7）は読み取り専用のレビューにした:
*`internal/tools/tools.go` でパス封じ込めを強制している関数はどれで、どのツールが
それを通り、素通りするものはあるか* — に加えてシンボリックリンクの追加質問。
`resolvePath` と補助関数 `within` / `resolveExisting` を挙げ、パスを取る 4 ツールを
正しく列挙し、`shell_exec` だけがパスを取らない（`cmd.Dir` + sandbox に委譲）
ことを正しく指摘し、シンボリックリンク検査を**逐語で引用**し、未作成ファイルの
ケースも正しく説明した。全主張をソースと照合済み。このステップが「単に動く」
ではなく「使える」ことを言う。

runbook ではなく gem-agent 側の所見 2 件 — **どちらも同日中に修正した**
（訓練はこれを出すために行うので、開いたまま放置すれば実行が無駄になる）:

- **ターン実行中の入力が無反応で捨てられていた。** TUI は実行中 Ctrl+C と
  shift+tab しか受け付けなかった。現在は入力欄が生きたままで、Enter が
  メッセージを予約する（[ADR-0007](../adr/0007-input-during-a-turn.ja.md)）。
- `!` コマンドだけのセッションは `gem-agent sessions` のプレビューが
  `I ran this shell command myself:` になっていた — 正確ではある（user ロールの
  メッセージである）が、バグのように読める。現在はコマンドを表示し、
  操作者が打ったメッセージが常にプレビューを取る。

## この順序である理由

起動と認証を最初に置く: そこで失敗すると後続すべてが無意味になるので、2 分目で
見つければ残りの 18 分が助かる。読み取り専用を破壊的操作より前に置くのは、最初の
書き込みを「正しく答えるのを既に見たモデル」に対して行うため。再開を対話ステップの
後に置くのは、再開する対象のセッションが必要だから。文書監査は再開済みセッションに
相乗りし、実タスクは残り時間を全部使えるよう最後に置く。
