# 承認・サンドボックス・安全機構

モデルが提案した操作と実行の間にある層 — 都度承認ダイアログから
Seatbelt サンドボックスまで — と、何かがロードされる前に走る起動時
ゲート。

## オペレーター pre-tool フック（ADR-0044）

以下のすべてのゲートより前 — 自動承認を含む全モードで — オペレーターが
設定したフックが最初にコールを受け取ります。グローバル設定の
`[[hooks.pre_tool_use]]` 各エントリが、コールを Claude Code PreToolUse
形式の JSON として stdin に受け取り、コマンドを実行します:

```toml
[[hooks.pre_tool_use]]
matcher = "shell_exec"           # 完全一致・"a|b"・"*"
command = "python3 /Users/you/.claude/hooks/guard-recursive-write.py"
timeout_sec = 10                 # 任意。0 = 既定（10）
```

契約は Claude Code のもので、文書からではなく**組織の実物のガードに
対して実測**しました — Claude Code のガードスクリプトは**無改修のまま**
ここに登録できます。フックは stdout の JSON
（`permissionDecision: "deny"` + 理由。組織のガードが実際に出す形式）
または exit 2 + stderr の理由で拒否します。ガードが読むのは
`tool_input.command` で、これは `shell_exec` の引数名でもあります。
matcher は Claude Code 名も受けます（`Bash` は `shell_exec` に一致。
`Write`/`Edit`/`Read` も同様）。

deny は**決定論的な床**です: 以降の階梯・モデル層・セッション
allowlist はそのコールを見ることすらなく、理由はツール結果として
モデルに返るため、モデルは修正して再試行します（実機検証済み: 組織の
相対パスガードが gem-agent 内で `sed -i` を拒否し、完全な理由文が
モデルに届き、ファイルは無傷でした）。明示的な deny 以外 —
クラッシュ・タイムアウト・解析不能な出力 — は警告つきで続行します:
フックは常に締める方向にしか働かず、壊れたガードスクリプトが
フォールバックツールを煉瓦化してはなりません。フックが覆うのは
モデルのコールだけで、オペレーター自身の `!コマンド` エスケープは
通しません。

## そのコールが何のためか（ADR-0047）

承認対象ツールはすべて必須引数 `gem_agent_purpose` を持ち（サーバ自身の
引数名と衝突しないよう接頭辞付き）、モデルが書いた一文が
引数の上に表示されます:

```
承認が必要です: shell_exec
↪ Slackへの添付準備としてレポートファイルを一時ディレクトリに配置するため
cp report.csv /tmp/share/
```

これがない状態のプロンプトは「何が実行されるか」と「なぜ訊かれているか」
には答えていましたが、「なぜエージェントがそれをしたいのか」には答えて
いませんでした。無害に見える `cp` では、それが判断のすべてです。動機が
存在しなかったのではなく到達できなかっただけで、Gemini 3 は前置きを
text ではなく思考サマリに書き（ツールコールを含む 349 ターン中 text
パートは 1 件、実測）、思考テキストは表示専用・ラウンドがコールで
終わった瞬間に消去・保存なし、という性質を持ちます。

この申告はコールを提案した当人が書いたものなので、**あなたのための文脈で
あって、何かの根拠ではありません**: リスク評価に渡る前に除去され、ルール層
の判定を動かすことはできず、ループガードのシグネチャからも除外されます。
purpose なしで届いたコールもそのまま実行でき、プロンプトは拒否ではなく
*（理由の申告なし）* と表示します — 欠落それ自体が見る価値のある情報だから
です。

同じ行は、ダイアログを開かないコール（自動承認・allowlist 済み）では `⚙`
イベント行に、`tool.call` 監査イベントには独立した `purpose` 属性として、
セッション transcript には引数の一部として残ります。

## 都度承認（MITL）

変更系ツールは実行前に確認します（ダイアログ自体は
[インターフェース](interface.ja.md)参照）。`y` = 1 回許可、`a` =
このセッション中は許可、`p` = ポリシーに永続化（`p` は TUI の回答で、
TUI を使わない plain stdin ゲートは `y`/`n`/`a` のみ）、拒否は拒否側に
倒れます。`a` は危険側には届きません: Block 判定のコール（sudo・再帰
削除・クレデンシャルパス等）と "always" ポリシーのツールは以後も必ず
確認します（ADR-0021）。

## 自動承認モード（ADR-0004）

既定は OFF。shift+tab（または `/auto`）で切り替え、ON の間は
ステータスバーに `⚡auto` が出ます。**shift+tab は実行中のターンでも
効きます** — 手動モードで始めた長いエージェントループを、終わるのを
待たずに切り替えられます（次のツールコールから反映）。ON のとき
変更系コールは次を通ります:

1. **ルール層**（モデル呼び出しなし）: *safe* → 実行、*block* → 必ず
   確認（`rm -rf`・`sudo`・`git push`・ダウンロードのシェル直
   パイプ・ディスク書き込み・認証情報パス・プロジェクト外など）、
   *不確実* → 第 2 層へ
2. **モデル層**: 別の評価ラウンドが対象コールを判定（コールはノンス
   隔離した非信頼データとして渡し、この評価ラウンドにはツールを一切
   与えない）。承認 **かつ** 高確信のときだけ自動実行、それ以外は
   確認へ

**メモリ書込は第 2 層に到達しません。** `save_memory`/`delete_memory` は
Review 層なので上の「*不確実*」に該当しますが、自動承認から除外されて
おり、評価結果によらず必ず確認に回ります（ADR-0020 §6）。評価するのは
書込を提案したのと同一の当事者なので、汚染されたツール結果がエージェント
を説得して指示を記憶させる攻撃に対する防御にはなり得ません。メモリは
永続化ベクタであり、**エージェントが何を記憶するかは利用者が決めます**。
意図的に緩める手段としてのツール別ポリシーは従来どおり使えます。

失敗系（モデルエラー・壊れた verdict）は確認へ倒れます。なお*未知の*
ツールはそもそもゲートに到達せず、ディスパッチャがエラーで弾くため
実行もされません。block 層はモデルが覆せない硬い床で、sandbox はどのモード
でも有効です。

**ターンの先頭 3 ラウンド**では、モデル層はあなたがタイプした依頼も
見ます（ADR-0038）— 同じ隔離ラップの中に証拠として引用され、
クリップ付き。添付の内容や会話履歴は決して含みません。依頼との整合は
承認を支持し、依頼に矛盾するコール — あるいはあなたの依頼ではなく
ファイル内容中の指示に仕えるコール — は矛盾を名指しして
エスカレーションします（実測: 指示が明示的に禁じた `make build` は、
コール単体視点では承認されるところをエスカレーションした）。以後の
ラウンドは従来のコール単体評価をバイト同一で実行します — ターンの
深部では、コールは依頼が名指ししないサブゴールに正当に仕えるから
です。このコンテキストが届くのはモデル層に到達するコールだけです:
Safe 層は従来どおりルールで承認され、Block はモデルに諮る前に
決まります。

**MCP コール**では、モデル層はツールの self-description — サーバーが
ツールリスティングで公開している説明（ADR-0046）— も見ます。同じ
隔離ラップの中に非信頼の証拠として引用され、クリップ付き、レジストリ
から毎回生きた値を読みます。これが無いと評価器はツール名だけから
意味論を推測することになり、そこが呼び出しごとに判定がブレていた
場所です。プロンプトは説明を事実ではなく主張として重み付けします:
正直な「読み取り専用・完全オフライン」の意味論は承認を支持し、説明と
矛盾する引数はエスカレーションし、自らの承認を主張する説明はそれ自体
がエスカレーションの証拠になります（実測: ロビーする説明は injection
の試みと名指しされてエスカレーションし、同じコールが正直な読み取り
専用の説明では承認された）。

**どちらの結果も理由が表示されます**: 自動承認されたコールは理由付き
で表示され、確認に回されたコールは承認ダイアログに `⚠` 行が付き、
**どの層が止めたのか**まで分かります — 決定論的な床なら
`blocked by rule (always asks): …`、モデルの判断なら
`escalated by risk review: …`、そもそもモデルに諮らなかったコール
（現状はメモリ書込）なら `auto-approve escalated: …`。

MCP の境界に注意: MCP ツールは承認ゲート対象で定義上 Mutating ですが、
ルール層は他所のサーバーのツールを判定できないため **Block 床には
構造的に到達しません** — auto モードではモデル層が日常的な呼び出しを
通すことがあり（サーバー公開の説明を証拠として判定します、
ADR-0046）、セッション `a` は以後の任意引数をカバーします。その
トレードが合わない場面はポリシーで `"always"` を指定してください。

## ファンクション単位の承認ポリシー（ADR-0008）

MCP ツールは呼び出しのたびに承認を求めます。サーバーのツールが何を
するのか gem-agent 側から知りようがないからです。あなたは知っている
ので、それを書けます:

```toml
# ~/.config/gem-agent/config.toml
[approval.tools]
"mcp__tor-exit-lookup__*" = "never"   # 読み取り専用の lookup サーバー
"shell_exec"              = "always"  # 自動承認モードでも必ず聞く
```

`"never"` は全モードでゲートを飛ばし、`"always"` は全モードでゲート
します（自動承認でもセッション内 `a` でも持ち上げられません）。
末尾 `*` は MCP サーバー全体にマッチ。解決は**スコープ優先、次に
特異性**（ADR-0021）: プロジェクトのルールはマッチするツールについて
global のどのルールにも勝ち、同一スコープ内では完全一致が wildcard
より優先。単独の `"*"` は拒否します — 全ゲートの無効化が 1 文字で
到達できてはいけません。

**`"never"` は「何でも実行」ではありません。** 呼び出しごとに効果が
変わるツール（`shell_exec`）では、ルール層の block パターンは引き続き
聞きます。

プロジェクト側は `<project>/.gem-agent.toml` に独自ポリシーを持てます
（`gem-agent.example.project.toml` 参照）。**向きが重要**です:

| プロジェクトファイルからの指定 | 有効になる条件 |
|---|---|
| `"always"`（承認を増やす） | 常に |
| `"never"`（承認を減らす） | **自分の**設定の `[approval].trusted_projects` にそのプロジェクトが載っているときだけ |

チェックアウトしたリポジトリは自分が書いたものとは限らず、clone
しただけでゲートを外せてはいけません。無視したエントリは起動時に
名前を出し、望むなら追記すべき行も示します。

知っておくと便利な副作用: `-p` 単発モードは「答える人がいない」ので
変更系ツールを拒否しますが、`"never"` のツールはもともと聞かないので
実行されます。読み取り専用の MCP lookup に `"never"` を付ければ、
パイプラインで使えます。

`/settings` や `p` 回答による変更は機械所有の
`~/.config/gem-agent/policy.toml` に永続化されます。並行インスタンス
はロック付き read-modify-write で書くため、2 つのセッションが互いの
決定を潰すことはありません。

## 単発モード（`-p`）— ADR-0053

単発モードには承認プロンプトに答える人がいないため、既定では
ゲート対象のコールはすべて拒否され、理由が stderr に出ます。
これを開く手段は 2 つ、リスク許容度の順に:

- **常設の `"never"` ポリシー**（上記）— パイプラインで常用する
  読み取り専用 lookup に適した形。
- **`--auto`** はこの実行に限り ADR-0004 の階梯を武装します。承認は
  TUI と完全に同じ（ルール層 → confidence 条件つきのモデル層）。
  階梯が*エスカレート*するもの — Block 層のコール・`"always"`
  ポリシーのツール・モデルの不承認・評価エラー — は代わりに拒否
  され、エスカレーションの理由が `[denied: …]` 行に載ります。
  fail-closed: どの床も動きません。

`[agent].auto_approve` は単発モードでは意図的に**無視**されます:
無人実行の付与は起動そのもの — スクリプトや cron に見えるコマンド
ライン — で可視でなければならず、常設の設定ファイルの中では
いけません。承認されたコールは `[auto-approved …]` 行を stderr に
出すので、パイプラインの監査痕跡には拒否だけでなく実行されたものも
残ります。

ここでの `--auto` の意味に注意: 人間がどこにもいない以上、Review 層
のコールの唯一の裁定者はモデル評価器です。非信頼コンテンツを読み
つつ egress 能力のあるツールを持つパイプラインでは、一般の階梯を
武装するよりツールを名指すポリシーを選んでください。

## リスクルールブック（ADR-0050）

auto モードのリスク評価器は、判定するすべてのコールで**オペレータ作の
ガイダンス** — ルールブック — を読めます。二層が積み重なります:

- **ベースルール** — `~/.config/gem-agent/risk-rules.md`。手書きで、
  gem-agent は読むだけで決して書きません。あなたの恒常的なリスク
  姿勢を、好きな言い方で:「ネットワークインストールは必ず人の目を」
  「customer export に触れるものはエスカレートする」。
- **プロジェクトルール** — `/riskbook learn`（後述）が書くか、手で
  編集します。リポジトリの外にプロジェクト単位で保存されます。
  評価器には「衝突時はプロジェクト層がより特異的な言明」と
  伝えられます。

ルールブックは**ポリシーではなくガイダンス**です: 評価器の
confidence をどちらの向きにも傾けますが、ゲートを飛ばすことは決して
ありません。決定論的に決着させた問いには、上のツール別ポリシー
（`"never"`/`"always"`）が引き続き語彙です — 1 行・機械的・モデル
不関与。ルールブックはポリシーが表現できないもののためにあります。
したがって床は不変です: Block 層のコールは評価器に諮られず、
pre-tool フックは先に走り、メモリ書込は必ず聞かれ、手動モードは
まったく変わりません。包括的承認を促す散文はそれ自体がエスカレート
理由として扱われます — 本物の包括バイパスは、機械的で可視な
ポリシーに書くべきものだからです。

`/riskbook learn` はあなた自身の判断記録からプロジェクト層を起草
します: 評価器の判定とあなたがゲートで実際に答えた内容を突き合わせ
（打鍵は個別に、セッション allowlist の `a` は 1 票として数えます）、
要約モデルにそこから含意される補正を説明させ、**保存されるものと
バイト同一の全文**をあなたに見せます。受理するまで何も効力を持ち
ません。`/riskbook` は効力中のものを表示し（毎回ディスクから読み
直し）、`/riskbook reload` は手編集を再起動なしで反映し、
`/riskbook clear` はプロジェクト層を削除します。いずれかの層が
効力を持つ間は起動バナーが告知します。

ルールブックは意図的にリポジトリから**読みません**: clone された
プロジェクトのファイルはコールを提案するモデルを操縦するもので
あり、評価器はその防御の第二層です — そのガイダンスが第一層の
供給源から届いてはなりません。

## 学習されたルール — 撤収済み（ADR-0049）

v0.46.0 から v0.47.0 の間、記録されたゲート判断から承認ルールを提案
する `/learn` コマンドが存在しました。フィールドテストの結果、撤収
されています: オペレータの想定よりはるかに多くが許可され、1 件ずつの
確認は — 完全な開示があっても — 緩和の恒久的な境界にならないことが
分かりました。設計と率直な事後検証は ADR-0045・ADR-0048・ADR-0049 に
あります。

残っているもの、使っていた場合に確認すべきもの:

- 導入されたトランスクリプト記録（回答の出所付き `gate_decision`）は
  引き続き書かれます — 診断用であり、将来のどんな設計にも必要です。
- 機械所有 `policy.toml` の `[projects."…".commands]` エントリは
  **適用されなくなりました**。存在する場合は起動時の note が報告
  します。削除しても残しても、どちらでも何もしません。
- `/learn` が書いたグローバル `[tools]` エントリ（`mcp__<server>__*`
  ワイルドカード）は通常の ADR-0008 ポリシーであり、**有効なまま**
  です — 手書きのものと区別できません。サーバ提案を受理した場合は
  `~/.config/gem-agent/policy.toml` をレビューし、不要なワイルド
  カードを削除してください。

## サンドボックス（ADR-0001）

`shell_exec`（と `!` コマンド）は macOS sandbox-exec でラップされ、
ファイル書き込みはプロジェクトディレクトリ・scratch（`TMPDIR`・
`/private/tmp`）・`/dev` に制限されます（Seatbelt による強制・実強制
テスト付き）。`--no-sandbox` はラップの
無効化（デバッグ専用）。sandbox はどの承認モードでも有効です。

## 起動時の安全機構（ADR-0023）

何かがロードされる前に 2 つのゲートが走ります:

- **広すぎるルートは先に確認。** `/`・ホームディレクトリ・その祖先で
  起動すると、file ツールと sandbox 下のシェル書き込みがそのツリー
  全域に及ぶことを説明した上で確認します（既定は No）。非対話実行
  （`-p`・パイプ）はその場でエラー拒否します。
- **初見のプロジェクトは 1 回だけ信用確認。** エージェント向け
  ファイルを提供するプロジェクトでの初回起動は、その提供物 — 指示
  ファイル（**あなたの**指示として注入）、`.mcp.json`（サーバー
  エントリごとに子プロセスを起動）、`.claude/skills` — を列挙して
  信用するか尋ねます（既定は No）。回答は機械所有の `policy.toml` に
  プロジェクト単位で永続化されます（`trust = "granted" | "declined"`。
  キーを消せば再確認）。拒否してもセッションは起動します — その
  プロジェクト自身のファイルをロードしないだけで、バナーがその旨を
  表示します。祖先の指示ファイルとグローバル設定はゲートの外です
  （clone はあなたが所有する上位ディレクトリにファイルを置けません）。
  `[approval].trusted_projects` に載せたプロジェクトは質問なしで信用
  されます。未決プロジェクトでの非対話実行は素で走ります
  （プロジェクト由来を何もロードせず、stderr に注記、記録もしない）—
  checkout したてのリポジトリへの読み取り専用 `-p` パイプラインは
  止まりません。

## 非信頼コンテンツの隔離（ADR-0018）

ツール出力はノンス XML タグ（nlk/guard。メインループはセッション
スコープ、側呼び出しは per-call）で隔離され、ツールが返す内容は常に
データであり指示ではない、という枠付けが強制されます。添付にも同じ
枠書きが付き、タグでラップできない画像・PDF には同じ立場の明示文が
当たります。

セッションスコープのタグには第二の仕事があります: リクエストの
プレフィックスがラウンド・ターンを跨いでバイト同一になり、再送される
履歴が Vertex の implicit caching でキャッシュ価格になります — 同一
