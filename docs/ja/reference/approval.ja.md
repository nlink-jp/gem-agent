# 承認・サンドボックス・安全機構

モデルが提案した操作と実行の間にある層 — 都度承認ダイアログから
Seatbelt サンドボックスまで — と、何かがロードされる前に走る起動時
ゲート。

## 都度承認（MITL）

変更系ツールは実行前に確認します（ダイアログ自体は
[インターフェース](interface.ja.md)参照）。`y` = 1 回許可、`a` =
このセッション中は許可、`p` = ポリシーに永続化（`p` は TUI の回答で、
TUI を使わない plain stdin ゲートは `y`/`n`/`a` のみ）、拒否は拒否側に
倒れます。`a` は危険側には届きません: Block 判定のコール（sudo・再帰
削除・クレデンシャルパス等）と "always" ポリシーのツールは以後も必ず
確認します（ADR-0021）。

## 自動承認モード（ADR-0004）

既定は OFF。shift+tab（または `/auto`）で切り替え、ON の間は
ステータスバーに `⚡auto` が出ます。**shift+tab は実行中のターンでも
効きます** — 手動モードで始めた長いエージェントループを、終わるのを
待たずに切り替えられます（次のツールコールから反映）。ON のとき
変更系コールは次を通ります:

1. **ルール層**（モデル呼び出しなし）: *safe* → 実行、*block* → 必ず
   確認（`rm -rf`・`sudo`・`git push`・ダウンロードのシェル直
   パイプ・ディスク書き込み・認証情報パス・プロジェクト外など）、
   *不確実* → 第 2 層へ
2. **モデル層**: 別の評価ラウンドが対象コールを判定（コールはノンス
   隔離した非信頼データとして渡し、この評価ラウンドにはツールを一切
   与えない）。承認 **かつ** 高確信のときだけ自動実行、それ以外は
   確認へ

**メモリ書込は第 2 層に到達しません。** `save_memory`/`delete_memory` は
Review 層なので上の「*不確実*」に該当しますが、自動承認から除外されて
おり、評価結果によらず必ず確認に回ります（ADR-0020 §6）。評価するのは
書込を提案したのと同一の当事者なので、汚染されたツール結果がエージェント
を説得して指示を記憶させる攻撃に対する防御にはなり得ません。メモリは
永続化ベクタであり、**エージェントが何を記憶するかは利用者が決めます**。
意図的に緩める手段としてのツール別ポリシーは従来どおり使えます。

失敗系（モデルエラー・壊れた verdict）は確認へ倒れます。なお*未知の*
ツールはそもそもゲートに到達せず、ディスパッチャがエラーで弾くため
実行もされません。block 層はモデルが覆せない硬い床で、sandbox はどのモード
でも有効です。

**ターンの先頭 3 ラウンド**では、モデル層はあなたがタイプした依頼も
見ます（ADR-0038）— 同じ隔離ラップの中に証拠として引用され、
クリップ付き。添付の内容や会話履歴は決して含みません。依頼との整合は
承認を支持し、依頼に矛盾するコール — あるいはあなたの依頼ではなく
ファイル内容中の指示に仕えるコール — は矛盾を名指しして
エスカレーションします（実測: 指示が明示的に禁じた `make build` は、
コール単体視点では承認されるところをエスカレーションした）。以後の
ラウンドは従来のコール単体評価をバイト同一で実行します — ターンの
深部では、コールは依頼が名指ししないサブゴールに正当に仕えるから
です。このコンテキストが届くのはモデル層に到達するコールだけです:
Safe 層は従来どおりルールで承認され、Block はモデルに諮る前に
決まります。

**どちらの結果も理由が表示されます**: 自動承認されたコールは理由付き
で表示され、確認に回されたコールは承認ダイアログに `⚠` 行が付き、
**どの層が止めたのか**まで分かります — 決定論的な床なら
`blocked by rule (always asks): …`、モデルの判断なら
`escalated by risk review: …`、そもそもモデルに諮らなかったコール
（現状はメモリ書込）なら `auto-approve escalated: …`。

MCP の境界に注意: MCP ツールは承認ゲート対象で定義上 Mutating ですが、
ルール層は他所のサーバーのツールを判定できないため **Block 床には
構造的に到達しません** — auto モードではモデル層が日常的な呼び出しを
通すことがあり、セッション `a` は以後の任意引数をカバーします。その
トレードが合わない場面はポリシーで `"always"` を指定してください。

## ファンクション単位の承認ポリシー（ADR-0008）

MCP ツールは呼び出しのたびに承認を求めます。サーバーのツールが何を
するのか gem-agent 側から知りようがないからです。あなたは知っている
ので、それを書けます:

```toml
# ~/.config/gem-agent/config.toml
[approval.tools]
"mcp__tor-exit-lookup__*" = "never"   # 読み取り専用の lookup サーバー
"shell_exec"              = "always"  # 自動承認モードでも必ず聞く
```

`"never"` は全モードでゲートを飛ばし、`"always"` は全モードでゲート
します（自動承認でもセッション内 `a` でも持ち上げられません）。
末尾 `*` は MCP サーバー全体にマッチ。解決は**スコープ優先、次に
特異性**（ADR-0021）: プロジェクトのルールはマッチするツールについて
global のどのルールにも勝ち、同一スコープ内では完全一致が wildcard
より優先。単独の `"*"` は拒否します — 全ゲートの無効化が 1 文字で
到達できてはいけません。

**`"never"` は「何でも実行」ではありません。** 呼び出しごとに効果が
変わるツール（`shell_exec`）では、ルール層の block パターンは引き続き
聞きます。

プロジェクト側は `<project>/.gem-agent.toml` に独自ポリシーを持てます
（`gem-agent.example.project.toml` 参照）。**向きが重要**です:

| プロジェクトファイルからの指定 | 有効になる条件 |
|---|---|
| `"always"`（承認を増やす） | 常に |
| `"never"`（承認を減らす） | **自分の**設定の `[approval].trusted_projects` にそのプロジェクトが載っているときだけ |

チェックアウトしたリポジトリは自分が書いたものとは限らず、clone
しただけでゲートを外せてはいけません。無視したエントリは起動時に
名前を出し、望むなら追記すべき行も示します。

知っておくと便利な副作用: `-p` 単発モードは「答える人がいない」ので
変更系ツールを拒否しますが、`"never"` のツールはもともと聞かないので
実行されます。読み取り専用の MCP lookup に `"never"` を付ければ、
パイプラインで使えます。

`/settings` や `p` 回答による変更は機械所有の
`~/.config/gem-agent/policy.toml` に永続化されます。並行インスタンス
はロック付き read-modify-write で書くため、2 つのセッションが互いの
決定を潰すことはありません。

## サンドボックス（ADR-0001）

`shell_exec`（と `!` コマンド）は macOS sandbox-exec でラップされ、
ファイル書き込みはプロジェクトディレクトリ・scratch（`TMPDIR`・
`/private/tmp`）・`/dev` に制限されます（Seatbelt による強制・実強制
テスト付き）。`--no-sandbox` はラップの
無効化（デバッグ専用）。sandbox はどの承認モードでも有効です。

## 起動時の安全機構（ADR-0023）

何かがロードされる前に 2 つのゲートが走ります:

- **広すぎるルートは先に確認。** `/`・ホームディレクトリ・その祖先で
  起動すると、file ツールと sandbox 下のシェル書き込みがそのツリー
  全域に及ぶことを説明した上で確認します（既定は No）。非対話実行
  （`-p`・パイプ）はその場でエラー拒否します。
- **初見のプロジェクトは 1 回だけ信用確認。** エージェント向け
  ファイルを提供するプロジェクトでの初回起動は、その提供物 — 指示
  ファイル（**あなたの**指示として注入）、`.mcp.json`（サーバー
  エントリごとに子プロセスを起動）、`.claude/skills` — を列挙して
  信用するか尋ねます（既定は No）。回答は機械所有の `policy.toml` に
  プロジェクト単位で永続化されます（`trust = "granted" | "declined"`。
  キーを消せば再確認）。拒否してもセッションは起動します — その
  プロジェクト自身のファイルをロードしないだけで、バナーがその旨を
  表示します。祖先の指示ファイルとグローバル設定はゲートの外です
  （clone はあなたが所有する上位ディレクトリにファイルを置けません）。
  `[approval].trusted_projects` に載せたプロジェクトは質問なしで信用
  されます。未決プロジェクトでの非対話実行は素で走ります
  （プロジェクト由来を何もロードせず、stderr に注記、記録もしない）—
  checkout したてのリポジトリへの読み取り専用 `-p` パイプラインは
  止まりません。

## 非信頼コンテンツの隔離（ADR-0018）

ツール出力はノンス XML タグ（nlk/guard。メインループはセッション
スコープ、側呼び出しは per-call）で隔離され、ツールが返す内容は常に
データであり指示ではない、という枠付けが強制されます。添付にも同じ
枠書きが付き、タグでラップできない画像・PDF には同じ立場の明示文が
当たります。

セッションスコープのタグには第二の仕事があります: リクエストの
プレフィックスがラウンド・ターンを跨いでバイト同一になり、再送される
履歴が Vertex の implicit caching でキャッシュ価格になります — 同一
4 ラウンドタスクの実測で per-call タグ 0% に対し **81〜95%
キャッシュ**。nlk/guard がタグ名を含むコンテンツを拒否するため健全
です — 漏れたタグは運び手を差し止めさせられるだけで、ラッパーからの
脱出には使えません。
