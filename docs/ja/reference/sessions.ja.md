# セッション・圧縮・使用量・メモリ

会話の中で、あるいは会話を跨いで永続するものすべて: トランス
クリプト、resume、コンテキスト圧縮、トークン明細、エージェント
メモリ。

## トランスクリプトと resume（ADR-0005）

```sh
gem-agent sessions        # id・経過時間・サイズ・モデル・最初の質問
gem-agent sessions --all  # このプロジェクトだけでなく全プロジェクト
gem-agent -c              # このディレクトリの最新セッション
gem-agent --resume 20260819-150102
```

再開したセッションは自分自身のトランスクリプトに追記されます — 何
プロセスにまたがろうと 1 ファイル = 1 会話 — そしてツール結果まで
含めて元のとおりに戻ります。2 つの拒否は意図的なものです: セッション
は記録されたディレクトリでのみ、そして記録したモデルでのみ再開でき
ます（再生する推論トークンがモデルに紐づくため）。それぞれの
メッセージが代わりの手を示します。圧縮済みのセッションは圧縮された
状態で戻ります（縮めた元のサイズに膨らみ直しません）。

JSONL トランスクリプトはログであると同時に resume の正本であり、完全
忠実に記録されます（API が再生時に要求する Gemini の推論トークンを
含む）。したがってエージェントが読んだ全ファイルの本文が入ります。

## 状態の置き場所（ADR-0022）

トランスクリプトは
`~/.local/state/gem-agent/sessions/projects/<エスケープ済パス>/`、
モード `0600` — メモリと同じ規約の**プロジェクト別サブディレクトリ**
です。一覧は 1 ディレクトリを読むだけになり、あるプロジェクトの
ディレクトリ内での掃除が別プロジェクトの transcript に触れることは
構造的にできません。`.project` マーカーが所有者を記録するので、パスの
エスケープが衝突する 2 プロジェクトは混ざらず大きな音で拒否します。
旧バージョンがフラットな `sessions/` 直下に記録した transcript は
その場で読み取り継続されます（一覧・resume とも可、移動はしません）。

並列起動は安全です: セッション id はタイムスタンプ + 衝突時の
アトミックなサフィックスで割り当てられ、各 transcript は排他ロック下に
あります — 同じセッションへの 2 本目の `--resume` は書き込みを混ぜる
代わりに「使用中」と言います。

環境変数 `GEMAGENT_STATE_DIR` は state ルート全体（sessions と
memory）を差し替えます — テストと訓練の隔離用です。

プロジェクトの transcript の隣には `persistent.json` があります（ADR-0074
§3/§4）: プロジェクト配下の永続ファイル — write レーンの保護名（深さ問わず、
入れ子リポジトリのフック含む）— のダイジェストで、前回セッションが残した
状態です。次の起動はこれと比較して以後の変化を注記します（「changed since
your previous session: …」、助言のみ）。起動・`/clear`・終了時に書き直されます。

## コンテキスト圧縮（ADR-0006）

モデルのウィンドウの `[agent].compact_at_pct`（既定 80%）に達すると、
会話の古い部分がその要約に置き換わり、直近はそのまま残ります。
`/compact` で任意のタイミングに同じことができます。通知には何件を
要約したかを出します — その後その半分の詳細は二次情報になるので、
忘れたモデルが最初から知らなかったモデルのように見えてはならない
からです。

身代わりメッセージはさらに、コンパクション前に読んだファイル内容
がもうコンテキスト内で逐語ではないことをモデルに警告します: 編集
や正確な引用の前に再読せよ、要約だけからファイルを書き直すな
（ADR-0051）。この警告は gem-agent 自身の枠書きで、要約器に依存し
ない決定論的なもの — 作業途中のコンパクションが後の全文 write を
「要約からの write」に変えてしまう、まさにその瞬間に届きます。

要約呼び出しが失敗した場合（エラー、コンテンツフィルタ）は、履歴を
一切変更せずターンを続行します。`auto_compact = false` で自動側を
止められます（`/compact` は動きます）。

## トークン明細: `/usage`（ADR-0019）

メインループのラウンド数とキャッシュ率、リスク評価・圧縮の側呼び
出し、トークンを使ったモデル名つきのツール別行（要約・Web・
ファイル検索エージェント）。
フッターにはライブの数字（コンテキスト占有・累計消費・`cache NN%`）
が出ており、モデル自身は `agent_info` で同じ数字を読めます。

読み方の注意を一つ: キャッシュ率は**コストとレイテンシ**の節約です —
キャッシュされたプロンプトトークンは課金が安く、ストリームも速く
なります。コンテキストウィンドウの空きは増えません。ウィンドウを
管理するのは圧縮の仕事です。

## transcript の会計レコード（ADR-0057）

API が返すのはトークン数であって金額ではない。したがってセッションの
コストは「トークン数 × カタログ単価」であり、そのカウントは発生した
その場で書き出しておく必要がある — `/usage` は in-memory で、プロセス
と共に去る。

そこで、すべてのモデル呼び出しが `usage` レコードを 1 行書く:

    {"kind":"usage","data":{"source":"risk","model":"gemini-…",
     "prompt":4183,"output":42,"thoughts":81,"cached":0,"tool_prompt":0,
     "total":4306}}

`source` は `main` / `risk` / `progress_review` / `compact` /
`summarize_file` / `web_search` / `web_fetch` / `agentic_file_search` /
`riskbook_learn` のいずれか — source で合計し、`model` で値付けし、
`total` で検算する。
単価は SKU × リージョンで解決されるので、セッションヘッダにはモデルと
並んでリージョンも記録される。

計算が依存する事実が 3 つ: thinking トークンは output とは**別の
バケツ**であり（課金上は output 扱い）、`cached` は `prompt` への加算
ではなく割引される**内訳**であり、`tool_prompt` はプロバイダの組み込み
ツール（検索グラウンディング・URL コンテキスト）の結果がモデルに入力
として戻された分である — 入力として課金され、キャッシュされず、
非ゼロになるのは `web_search` と `web_fetch` だけ（ADR-0066）。`total`
は API 自身のカウントなので、`prompt + output + thoughts + tool_prompt
== total` がどれかを忘れた集計を捕まえる — 静かに過小計上されるのでは
なく。

これ以前に書かれた transcript は古い `usage` レコード（`source` 無し・
主ループのみ）のままで、リスク評価と圧縮の消費はそもそも書かれていない。
集計側はそれらを数えたうえで、そのファイルは部分的だと報告すべきである。
`tool_prompt` キーの無いレコードは ADR-0066 以前のもの: 壊れたレコード
として扱うのではなく、チェックサムの非負の残差としてバケツを導出する。

## transcript のリモート障害（ADR-0075）

1 つの MCP ツールがターン内で連続 3 コールにバイト同一のエラー文を返したとき
— 引数が何であれ — 実行器は `mcp_fault` レコードを書き、モデル向けの注記を
付ける:

    {"kind":"mcp_fault","data":{"server":"bigquery",
     "tool":"mcp__bigquery__execute_sql_readonly","kind":"result",
     "count":3,"round":7,"error":"Required parameter is missing: query"}}

`kind` は失敗の出所 — `result`（サーバーが応答をエラーと印した）、
`rejected`（サーバーの JSON-RPC エラーオブジェクト）、`incomplete`（gem-agent が
コールを完了できなかった: 転送・タイムアウト・終了）— で、以降の同一応答ごとに
カウントを更新したレコードが繰り返される。そのツールの `message` レコードは
注記を `runtime_note` に持つ。著者が gem-agent なので（`denial` と同じ信頼）
送信時のラップはこのフィールドをノンスタグの外側に付ける。旧ビルドがこの
transcript を resume するとフィールドを無視し、注記なしで結果を再生する。

## エージェントメモリ（ADR-0020）

エージェントは短い事実をセッションを跨いで永続化できます: 決定事項、
好み、環境の癖 — プロジェクトのファイルには書かれていないが次回も
知っていてほしいこと。プロンプトは **いつ** 保存するかも述べます: 作業が
一段落したら、開始時に知っていれば手間が省けたことを学ばなかったかを
自問し、あれば指示を待たずにその場で提案します（ADR-0020 §5）。この契機が
入る前、モデルは 39 セッションで一度も自発提案していませんでした — 文面が
能力を与えるだけで、具体的な文をすべて禁止に費やしていたためです。

| スコープ | 想起される場所 | 保存先 |
|---|---|---|
| `global` | 全プロジェクト | `~/.local/state/gem-agent/memory/global/<name>.md` |
| `project` | そのプロジェクトのみ | `~/.local/state/gem-agent/memory/projects/<エスケープ済パス>/<name>.md` |

- 1 メモリ = 1 つの小さな markdown ファイル。同名で保存すると更新。
  セッション開始時に全件がシステムプロンプトへロードされ（グローバル
  が先、プロジェクトが後）、固定予算で抑えられます。切り詰めは無言
  ではなく必ず報告されます。
- **書き込みは承認ゲート付き**（`save_memory` / `delete_memory`）:
  永続化されたメモリは以後の全セッションのプロンプトに現れるため、
  メモリは注入された指示の永続化経路になり得ます — だから人間が
  書き込み 1 件ごとにレビューします。自動承認はこのレビューの代わりに
  なりません: メモリ書込は自動承認の階梯から除外され常にエスカレート
  します — 書込を評価するモデルは、それを提案したモデル自身だからです
  （ADR-0020 §6）。緩める唯一の手段は
  [承認ポリシー](approval.ja.md)による、意図的でツール単位の設定です。
- 注入されるセクションは「エージェントが記録した背景知識」として
  枠書きされます — 利用者自身の指示ファイルより明示的に一段低い地位
  で、古くなっている可能性も明記されます。
- リポジトリ内には決して書き込まず、`~/.claude` も読みません。
  ファイルは素の markdown なので、いつでも手で監査・編集・削除でき
  ます。
- `/memory` はいま保存されているもの・ファイルの置き場所・削除する 2 つの
  方法（エージェントに忘れるよう頼む / ファイルを消す）を表示します。
  引数は取りません。新しい保存が効くのは次のセッションからです。

## 作業ディレクトリ: `gem-agent workdirs`（ADR-0058・ADR-0059）

各セッションは state ルート配下に作業ディレクトリを持ち（`GEMAGENT_WORK_DIR`
として export）、大きすぎる MCP 結果やスクラッチ出力がそこに置かれます。
起動時の note が以前のセッションのディレクトリを数えます
（`N earlier session work directories hold 12 MB here`）。自動では何も削除
しません。`gem-agent workdirs` が経過時間・ファイル数・サイズで一覧し、
`gem-agent workdirs clean [id…]` はタイプした確認の後に削除します
（端末なしでは `--yes` を付けます）。稼働中のセッションのものは決して
消しません。走査は有界です: 一覧は 10,000 セッションで止まりそう告げ、
ディレクトリの件数は 50,000 ファイルで止まって `N+` と表示、起動時の note は
数値が下限のとき `N+` / `12 MB+` と表示します。`workdirs clean <id>` は
打ち切られた一覧に届かなかったセッションも見つけます。

## セッション id と `/clear`（ADR-0071）

セッション id はマシン内で一意な UUID v4 です。一覧は開始時刻の隣に先頭 8
文字を示し、`--resume` は完全な id か曖昧でない前方一致を受け付けます。旧来の
タイムスタンプ id で記録されたトランスクリプトも従来どおり一覧・resume
できます。`/clear` は新しいセッションを始めます: 旧トランスクリプトは会話が
終わった位置で閉じられ、その id で resume 可能なまま残ります。新しい id・
トランスクリプト・作業ディレクトリが引き継ぎ、子プロセスに export されます。
セッションフックには `session_end`（`clear`）の後に `session_start`
（`clear`）が見えます。作業ディレクトリを読むもの全て — sandbox プロファイル、
ファイルツールの第 2 ルート、MCP 取込、system prompt — が新しいものに従い、
エージェント自身のセッション状態（キュー済み添付、transcript 死亡マーク）は
旧セッションとともに捨てられます（ADR-0072 §2）。MCP サーバーは再接続され
（`/mcp reload` と同じ報告が出ます）、セッションごとの状態を持つサーバーは
新しい id を見ます。テレメトリも新しい id で再構成され、旧セッションの
`session.end` と新セッションの `session.start` はそれぞれ自分の id を
運びます（ADR-0071 addendum）。

旧 transcript が閉じる前 — `/clear` と終了時 — に、プロジェクト配下の永続
ファイルをセッション開始時の集合と比較し、差分があれば注記して transcript に
`persistent_changes` レコード（`reason` は `clear` か `exit`、`added`・
`changed`・`removed` の名前）を書きます — ディレクトリ差し替えが仕込める
入れ子ファイルの可視化です（ADR-0074 §3）。新セッションは内容のピンも再照合
します（ADR-0074）: 旧セッション中に変わった指示ファイル・`.mcp.json`・
プロジェクトスキルは外して名指しします。
