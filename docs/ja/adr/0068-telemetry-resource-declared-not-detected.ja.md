# ADR-0068: テレメトリクライアントは Cloud Logging のリソースを探索せず宣言する

| 項目 | 値 |
|------|----|
| ステータス | **Accepted** |
| 日付 | 2026-09-04 |
| 対象 | gem-agent |
| 意思決定者 | nlink-jp メンテナ |
| きっかけ | テレメトリ有効（`backend = "gcp"`）で `gem-agent -p 'Reply with the single word OK.' --mcp off < /dev/null` を走らせると、stdin 読み取りに到達するまで 6 回中 4 回は 0.0 秒、残る 2 回は 5.9 秒 / 7.2 秒かかり、その間 stderr には何も出なかった |
| 修正対象 | ADR-0035 §2a（GCP バックエンドの構築がネットワークに触れなくなった） |

## 背景

まず stdin 読み取り自体を追跡し、原因ではないと確定した — 読み取りの
開始が遅いのだった。そこで単発分岐より前の起動経路 — 設定、プロジェクト
信頼、セッションログ、作業ディレクトリ、ツール、MCP、スキル、メモリ、
テレメトリ、Vertex クライアント、指示ファイル、エージェント、rulebook —
に環境変数で有効化するステップ別トレースを仕込み、同じコマンドを 2 バッチ
計 24 回走らせた。どの実行でもすべてのステップは 5 ms 未満だったが、
1 つだけ例外があった: `backend = "gcp"` の `telemetry.New` は 18 回で
0 ms、残る 6 回で 4.5 秒・5.7 秒・6.1 秒・6.6 秒・7.1 秒・7.2 秒かかった。
その内側では `logging.NewClient` は毎回即座に返り、待ち時間はすべて
`client.Logger(...)` にあった。`genai.NewClient` は 24 回すべてで即座
だった — 第一容疑者だった ADC トークン取得は無関係だった。

ライブラリを読んで分かった機構:

- `CommonResource` オプション無しで呼ばれた `Logger` は、ライブラリの
  環境検出を走らせる。GCE メタデータサーバーから取得して、ホストが
  App Engine / Cloud Functions / Cloud Run / GKE / GCE のどれかを
  分類する。最初に行うのは `metadata.Get("")` — compute/metadata
  クライアント経由で `http://169.254.169.254/computeMetadata/v1/` に
  送る素の HTTP GET で、ダイヤラは 2 秒でタイムアウトする。ダイヤル
  タイムアウトは `Temporary()` なエラーなので、このクライアントは
  100 ms から倍々のバックオフで最大 5 回まで再試行する。
- macOS ではこのリンクローカルアドレスに、主インタフェース上のクローン
  されたホスト経路が付く。カーネルが存在しない隣接ノードを ARP で探索
  している間、各 connect は 2 秒のタイムアウトまでブロックする。カーネル
  が諦めると経路は数秒間 reject（"host is down"）とマークされ、以後の
  connect は即座に失敗する。その否定エントリが新しいうちに着地した
  実行は何も払わず、期限切れ後に着地した実行はタイムアウト 2〜3 回分と
  バックオフを払う — 計測した 4.5〜7.2 秒がそれである。`metadata.Get("")`
  だけを呼ぶ単独プログラムで再現した: 1 回目 6.40 秒、続く 9 回は
  0.00 秒、すべて "host is down" で終わった。

検出のどの分岐もメタデータサーバーを必要とし、gem-agent は設計上
macOS 専用である（ADR-0001）。このプラットフォームでは検出は決して
何も見つけられず、何も見つからなければライブラリはプロジェクト ID を
ラベルにした `global` リソースにフォールバックする。探索は何も
もたらさず、バナー（対話）や stdin 読み取りと最初のモデル呼び出し（`-p`）
の前に最大 7 秒の沈黙を費やす。ステータス機構が存在する前に起きるから
沈黙であり、カーネルの隣接キャッシュに依存するから間欠的である —
それがまさに「ときどき遅いが理由が分からない」と読まれた理由だった。

## 決定

### 1. リソースは検出せず宣言する

GCP エクスポーターはロガーを
`logging.CommonResource({type: global, labels: {project_id: <[gcp].project>}})`
付きで構築する — このプラットフォームで検出がフォールバックする値
そのものである。レコードは変わらず、探索だけが消える。テストは
`GCE_METADATA_HOST`（メタデータクライアントが尊重する）を到達回数を
数える偽サーバーに向けてこれを固定する: gem-agent のロガー構築は
0 回、ライブラリの既定経路 — 対照 — は 1 回以上到達する。テストは
守る対象の探索を仮定するのではなく観測する。

### 2. 通知はしない。待機がもう無いからだ

ADR-0033 §2 と ADR-0067 は、意図的な待機は告知せよと言う。この待機は
意図的ではなかった。ランタイムの何もそれを選んでおらず、通知
（「2 秒経ってもテレメトリクライアントを作成中」）は欠陥を直す代わりに
記録するだけだった — しかも ARP タイムアウトを払った実行でだけ発火し、
決して起きてはならないことを待てとオペレーターに告げることになる。
本 ADR が上の 2 本に加える規則: 起動ステップが待機通知を得るのは、
待機がその契約であるとき（stdin を EOF まで読むのはその一つ）。
ライブラリの環境自動検出が入ったままだったという理由だけで存在する
待機は、検出を切ることで取り除く。

### 3. 起動は最初のモデル呼び出しまでネットワークに触れない

修正後の計測では、12 回中 12 回が起動から 16 ms 以内（4〜16 ms）で stdin 読み取りに
到達した — 遅いモードは無い。最初のターンより前にクライアントを構築
するもの、`logging.NewClient` と `genai.NewClient` は遅延ダイヤルで
ADC をディスクから読むだけで、最初に線に乗るバイトは最初のモデル
呼び出しであり、最初の監査バッチはエクスポーター自身の goroutine で
送られる。これが保つべき性質である: 将来、ネットワークをブロックせざるを
得ない起動ステップが加わるなら ADR-0067 の形（猶予、原因と対処を
名指しする stderr 1 行、終わりの行）を取る — そしてその前に、その
ブロックが契約なのか自動検出なのかを問う。

## 検討した代替案

- **`resolveWindow` のようにシンクを非同期構築する** — 却下: 無意味な
  待機をクリティカルパスから外すだけで消しはせず、その特典に
  `SessionStart` のキューと終了 flush との競合を買うことになる。
- **探索のタイムアウトを短くする** — 却下: logging ライブラリは検出の
  つまみを公開しておらず、ダイヤルタイムアウトと再試行方針はメタデータ
  クライアントのパッケージ既定値である。
- **2 秒の猶予後に告知する** — 却下、§2。
- **起動時に `GCE_METADATA_HOST` を到達不能アドレスに向ける** — 却下:
  1 つのライブラリを操るために立てたプロセス全体の環境変数は、すべての
  子（シェルコマンド、MCP サーバー、フック）に継承され、しかも同じ
  ライブラリの `OnGCE()` にこのプロセスは Google ホストで*ある*と告げる。

## 結果

- 4.5〜7.2 秒の起動モードはすべてのモードで消えた。対話バナーと単発の
  最初の呼び出しは、もはやカーネルの隣接キャッシュに左右されない。
- monitored-resource の proto パッケージが直接依存になる。logging
  クライアント経由で既にツリーにはあった。
- 宣言は無条件である。gem-agent が Google ホストのマシンで動くことが
  あれば（無い — ADR-0001）、エントリはホストのリソースではなく `global`
  を持つ。受け入れ、秒を費やす検出に委ねる代わりにここに明記する。
- これを見つけたトレースは残さない。恒久的なタイミングトレースは誰も
  読まないつまみになる。手法 — 環境変数で有効化するステップ別トレースと、
  間欠モードを捕まえるための十数回の実行 — は、次に起動が遅く見えた
  ときのためにここに記録する。
