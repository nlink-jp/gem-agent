## Context（背景）

ADR-0089 はレーンを作り、供給源を開いたまま残した。その §5 は 3 稿と 3 度の反証、そして
3 稿すべてに対して成立した制約 1 つを記録している。**view 層はファイルを開かない。**
view 層が行う読み取りはツールコールではないので、`Agent.decide` にも ADR-0086 の sandbox 子
にも届かず、組み込みツール名で引かれる資格情報一覧 — `credentialReadTools` マップ
（[risk.go:176](../../../internal/risk/risk.go)）— からは見えない。

その制約が、いちばん素直な設計を排除する。MCP intake は既に画像をセッションの work dir へ
書き出し、モデルには `[image saved at <path> … use view_image on that path]` を渡している
（[mcpresult.go:184](../../../cmd/mcpresult.go)）。つまりパスはそこにある。しかし `write` は
`os.Stat` で短絡し（[mcpresult.go:207](../../../cmd/mcpresult.go)）、毎回の呼び出しがサーバに
work dir を `_meta[workdir.MetaKey]` で渡している（[client.go:579](../../../internal/mcp/client.go)）。
ローカルのサーバ子プロセスは自分の名前・ツール名・返すバイト列・ディレクトリを知るので、
応答の前に content-addressed の名前へ symlink を置ける。するとランタイムは何も書かず、パスは
サーバが選んだ先を指す。`view_image` 経由でそのファイルに到達する道は封じ込められている。
エージェントが強制者の判定より先に symlink を解決するからである。パスを開く view 層はそう
ではない。

### 配管は実際にどうなっているか

反証された第 3 稿は、view 層に「intake が既に保持しているバイト列」を渡すと書いた。渡せない。
`render` は `string` を返し（[mcpresult.go:53](../../../cmd/mcpresult.go)）、`mcpIntake` が
持つのは work dir の getter とバイト上限とプレビュー長だけで
（[mcpresult.go:46](../../../cmd/mcpresult.go)）、ツール契約は
`Run func(ctx, args) (string, error)` である（[tools.go:65](../../../internal/tools/tools.go)）。
`Run` が返れば blocks は消えている。

しかしランタイムに経路が無いわけではない。エージェントループはツールコールの**最中に**既に
UI へ話しかけている — `prog.Send(tui.ToolCall{…})`（[root.go:927](../../../cmd/root.go)）—
ので、ツール結果から画面への帯域外経路は新しい機構ではなく既存の働いている型である。文字列
契約は 1 ミリも動かさなくてよい。

### 画像は道中で何を要するか

この機械で、emit 経路が使うカウンタ（ANSI を除去してグラフィムを走査する `physicalRows`）に
実際の payload を通して測った:

| デコード後の画像 | payload | `physicalRows` |
|---|---|---|
| 64 KiB | 85 KiB | 0.35 ms |
| 256 KiB | 341 KiB | 1.19 ms |
| 1 MiB | 1.3 MiB | 3.7 ms |
| 4 MiB | 5.3 MiB | 14.4 ms |
| 8 MiB | 10.7 MiB | 29.2 ms |

線形で、1 MiB あたり約 3.6 ms。しかもそれは文字列が同時に存在する 3 箇所のうちの 1 つで
ある — emit 経路、Bubble Tea のキュー、端末の scrollback。今日これを縛るものは JSON-RPC の
フレーム上限だけで（`scannerMax = 10 MiB`、[client.go:28](../../../internal/mcp/client.go)）、
ブロックあたりおよそ 7.5 MiB のデコード後バイト列を許す。

## Decision（決定）

### 1. バイト列は帯域外を通る。UI が既に持っている経路で

`mcpIntake` は `workDir` の隣に任意の依存を 1 つ得る。ランタイムが供給する sink で、ブロックを
取り込む瞬間にデコード済みバイト列と MIME 型で呼ばれる。`cmd` はそれを `prog.Send` に配線する。
`ToolCall` と `ToolDone` が既に呼び出し中に UI へ届くのと同じ形である。ツール結果は `string` の
ままで、transcript・resume・エラー経路には触れない。

sink は対話的 TUI でない入口すべてで nil である。one-shot `-p` と素の REPL は「描かないと判断
する」のではなく、**バイト列をどこへも渡さない**。

### 2. 画像を描くのは、intake が保存し記述したときに限る

条件は 1 つであって 2 つではない。注記が response budget に収まらないブロックは、既に保存も
個別記述もされない — ガードは何かを書く前に `binaryNote` の大きさを測る
（[mcpresult.go:105](../../../cmd/mcpresult.go)）— そして leftovers 行に数えられる。そうした
ブロックは**描かない**。

代案（モデルが知らされていない絵を、結果が切り詰められた呼び出しから描く）は、セッションの
記録のどこにも現れないものを操作者の画面に置く。**画面はセッションが記録したものを映す。**
それは第 2 の budget ではなく、1 つの規則である。

### 3. ボックスは絵から、切り詰めは端末から

`image.DecodeConfig`（標準ライブラリ）が、絵をデコードせずにピクセル寸法を返す。行数は
アスペクト比から `maxRows` の天井に対して選び、列数はそれに従い、`termimg.Fit` が幅を端末より
狭く切り詰める。端末幅を超えるボックスは端末自身に絵を折り返させ、宣言が主張していない行を
足す（ADR-0089 §2）。

`DecodeConfig` は検証器でもある。MIME が `image/*` と言っていてもバイト列がデコードできない
ブロックは**画像ではなく**、描かない。MIME 型はブロックのうちサーバが自由に選べる唯一の部分で
あり、それが選ぶのはコンテナであってエスケープではない。payload 自体は base64 で、その
アルファベットに `ESC` も `BEL` も無いので、view 層に届いたバイト列が包まれたエスケープから
抜け出すことはできない。

### 4. 2 メガバイト、デコード後。理由は測定である

デコード後のバイト列が **2 MiB** を超えるブロックは、通常どおり保存され記述され、描かれない。
その大きさでカウンタは約 7 ms を要し、文字列は同時に 3 箇所に存在する。フレーム上限ではその
4 倍になる。上限をデコード後のバイト列に置くのは、コストがそれに比例するからであり、判定は
payload を組む前に行う。

これは天井であって目標ではない。端末に届く絵は高々 1 画面ぶんのセルのボックスへ縮小される
ので、それより大きな原本は端末が捨てるピクセルである。操作者が失うのは待ち時間だけである。

### 5. モデルが見るものは何も変わらない

注記も、パスも、`view_image` の経路もそのままである。モデルが絵に触れる道は、依然として
強制者が判定を取るツールを通り、symlink は先に解決される。本決定が足すのは第 2 の観客 —
操作者 — であり、それに**ファイルを開かない経路**を与える。

## Consequences（帰結）

- MCP サーバのスクリーンショットは撮られた時点で画面に出る。モデルが見たければ、依然として
  自分で求める必要がある。
- symlink の事前設置は本決定で修理されず、悪化もしない。ランタイムは依然としてファイルを書き、
  モデルにパスを渡し、`view_image` は強制者の判定より先に解決する。変わるのは、**そのパスを
  新たに開くものが無い**ことである。
- サーバが操作者の画面に絵を置けるようになる。もともと transcript に任意のバイト列を置くことは
  できたし、絵はこのランタイムが宣言したボックスへ描かれるが、以前は存在しなかった面であり、
  面として名指しておく。
- 2 MiB の天井は、操作者が見たかった画像をいくらか拒む。拒否は画面上では沈黙である（超過ブロック
  ごとの警告は「報告は制御ではない」の形である）。モデルが得る注記は変わらないので、絵は
  `view_image` から依然として到達可能である。
- lagent は同じ intake・同じツール契約・同じ UI 経路を持つ。ミラーは負債である。こちらを先に
  実装するのは、レーンがこちらにあるからである。

## Alternatives Considered（検討した代替案）

**A1. `Tool.Run` を構造化コンテンツを返す形に広げる。** 却下。文字列の結果は transcript が
保存し、resume が再生し、`RemoteError` が運ぶものである。表示のケース 1 つのためにそれを広げる
のは、4 つ目の都合で 3 つのサブシステムを変えることであり、ADR-0089 §5 が 3 度反証されたのは
まさにこの種の数え上げられていない波及によってである。

**A2. view 層が保存されたパスを読む。** 却下 — ADR-0089 §5 が獲得した制約そのものであり、
`os.Stat` の短絡がそのパスをサーバの選べるものにしている。

**A3. budget に関わらず全ての image block を描く。** 却下。セッションの記録に含まれない絵を
画面に置くことになり、response budget がテキストだけを縛って画像を素通しさせることになる。

**A4. バイトではなくピクセルで縛る。** 主たる上限としては却下。実測コストはピクセルではなく
バイトに比例し、寸法の小さい画像が大きなバイト列を運ぶこともある。`DecodeConfig` の寸法は
依然として読む（決定 3 がアスペクト比を要する）ので、本記録が持たない証拠が出てくれば
ピクセル上限を後から足せる。

**A5. 画像を拒んだときに警告する。** 却下。超過ブロックごとに 1 行印字するのは報告であって
制御ではなく、操作者の次の行動はそれで変わらない。モデルの注記は変わらず、絵は到達可能な
ままである。
