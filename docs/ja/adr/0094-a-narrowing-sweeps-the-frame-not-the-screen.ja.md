## Context

### 今、幅を狭めると何が起きるか

先に端末が折り返し直す: インラインの枠（入力欄・フッタ・その上のパディング行や保持行）の各行は、このランタイムが旧幅より 1 桁短く書いた行であり、狭い幅ではそれぞれがより多くの行に折り返される。その後 Bubble Tea のインライン描画器がカーソルを基準に描き直す — `linesRendered − 1` 行上がって描く — ので、描き直しは折り返された枠の上端より下から始まり、その上の行に入力欄の古い写しが残る（階段状の残骸、AGENTS.md）。

ADR-0021 は、幅が本当に縮んだときに 1 回だけ `tea.ClearScreen` でそれを掃除し、行カウンタをリセットした（`hold.printed = 0`、`hold.lastTotal = 0`）。この消去は描画器の `ESC[2J` とカーソルの左上への移動であり、枠ではなく画面全体を消す。同 ADR の §9 は拡大時の消去も却下した。ここまではすべてソース（`internal/tui/model.go`、bubbletea v1.3.10 の `standard_renderer.go`）から読んだことである。

### 何を失うか — 測定

運用者、2026-09-29、iTerm2 と kitty で（ADR-0092 §4）:

- **その時点で見えている画面上の絵が失われる。** kitty は消し、iTerm2 はそこに黒い空白を残す。文字はスクロールバックに残る。kitty では、スクロールバックのさらに上にある絵は残る。
- **黒い、または空の空白がスクロールバックに積もる。** 両方の端末で、文字だけの内容でも起きる。
- 以前、ウィンドウを広げたときにも余分な空白が見えた。

絵は文字のようには消去を生き延びない。mermaid の図（ADR-0092）も `/show` の絵（ADR-0091）も絵として画面に届くので、以前は何も失わなかった欠陥が、今は目に見える。

### 分かっていないこと、そして選ぶ前に測る理由

ソースから分かるのは、どのバイトが送られるかである。この 2 つの端末がそれをどう扱うかは分からず、以下の候補はどれもこのうちのどれかに依存している:

1. **黒い空白がどこから来るか。** 端末が `ESC[2J` で画面をスクロールバックへ移す（そういう端末はある。そうなら枠と空の行も一緒に運ばれる）のか、リセットしたカウンタが次の枠を 1 行目から下へパディングし、空の行が後で上へ流れるのか — あるいは両方か。
2. **絵が折り返し直しそのものを生き延びるか。** 端末が折り返し直すときに画面上の絵を落とす・黒くするなら、どんな掃除でも絵は残せず、決めるべきことが別のものになる。
3. **折り返された枠がどこに来るか。** 下の候補は、端末がカーソルをその論理行の上に保ち、そこから上へ枠を伸ばす、と仮定している。そうなら古い行は描画器が再開する位置のすぐ上にある。領域を下へ伸ばす端末や、その一部をスクロールバックへ押し出す端末では、掃除が届かない行が残る。
4. **ドラッグがどう届くか。** 1 回のドラッグで大きさの通知が何回も来る。2 つの通知の間に描き直しが入るかどうかで、掃除の行数が 1 回の折り返しを表せばよいのか、何回分かを表さねばならないのかが決まる。

## Candidates（測定用の切り替えとして作る）

モデルに継ぎ目 `tui.Options.Shrink` を設け、ゼロ値を今の振る舞いにする。残りの 2 つは、運用者が同じ実行の中で今の振る舞いと比べて測れるようにするためだけに存在し、本 ADR が決まったとき選ばれなかった方は取り除く。

**A. 画面を消す（今の振る舞い。対照）。** `ESC[2J`、カーソルを左上へ、カウンタをリセット — ADR-0021 §9 のまま。

**B. 何もしない（折り返しの対照）。** 何も掃除せず、カウンタにも触れない。わざと階段状の残骸を見せる: 測る対象の行に手を出さない唯一の切り替えなので、問い 2 と 3 に答えられるのはこれだけである。

**C. 枠の行だけ消す。** 幅が縮んだら、枠が折り返しで増やした行数 K を、描画器が実際に最後に描いた枠から求める: カーソルの行より上の各行について `physicalRows(line, newWidth) − 1` — カウンタがすでに使っている折り返しの計算と同じもの。描画器の次の描き直しを K 行上から始まるように延ばし、そこから下をすべて消す（`ESC[J`、下を消去）。折り返された枠の上端より上には何も触れないので、履歴もその中の絵もそのまま残る。カウンタは、新しい枠がちょうどその行を占めるように設定する: `lastTotal = n + K`（n は描かれた枠の行数。上限は高さ − 1）、`printed = height − 1 − lastTotal`。これは運用者の提案 —「折り返し後に枠が占めうる行だけを消す」— であり、行を画面の下から K 行としてではなくカーソルからの相対で求める: このランタイムが端末に尋ねずに知っている位置はカーソルだけであり、画面の下端が同じ場所になるのは問い 3 が仮定どおりのときだけだからである。

C をどう端末に届けるかも設計の一部である。すぐ思いつく 2 つの経路はどちらも失敗するからである:

- **`tea.Println` では届けない。** キューに入れた行は描画器の領域の上端から書き出され、必ず `\r\n` が続くので、そうして書いた掃除は履歴を 1 行使う — 大きさの通知 1 回ごとにスクロールバックに空行が 1 行。欠陥を少量にしただけである。
- **`View()` の中では届けない。** Bubble Tea は 1 ティックごとに最新のビューだけを書き出し、描き直しの後はすべての行を送り直す。1 回だけの前置きは、失われる（ティックの前に次のビューが置き換えた）か、繰り返される（後の描き直しがもう一度送り、実際の履歴の上へさらに K 行上がる）かのどちらかになる。

そこで C は、描画器と端末の間に置く writer（`tui.SweepWriter`、`tea.WithOutput` で渡す）で届ける。書き出しと書き出しの間、描画器はカーソルを自分の領域の最後の行の 0 桁目に置いており、1 行より高い枠の書き出しは必ず `CSI n A`（カーソルを n = linesRendered − 1 行上へ）で始まる。writer は、縮小の後の最初のそういう書き出しを `\r CSI n+K A CSI J` に書き換える。その書き出しは消去と一体であり、数は描画器自身の帳簿から来る — 最後に描かれた枠を追うのがモデルではなく writer なのも同じ理由である: モデルは、描画器が一度も書き出さないかもしれないビューを見ている。2 つの大きさの通知が間に書き出しを挟まずに届いたときは、2 つ目が 1 つ目の K に足すのではなく置き換える — 画面にはまだ両方の前に描かれた枠が、最新の幅に折り返されて残っているからである。これが問い 4 であり、それがどれだけ起きるかはプローブが報告する。

これにより C は bubbletea v1.3.10 の書き出しの形式に依存する。本物の描画器を writer 越しに動かすテストを置き、書き換えが頼るカーソル上移動で書き出しが始まらなくなったら落ちるようにする。形式を変える更新が黙って通ることはない。

## Measurement

`make resizeprobe`（`tools/resizeprobe`）は、1 つの切り替えを運用者自身の端末で走らせる。pinprobe と同じく、本物のモデル（`tui.New`）を作り、本物のインラインのプログラムで動かし、本物の出力経路（`tui.Output`、`tui.Image`）で書く — つまり `wrapForScrollback`・`physicalRows`・下端の保持・宣言した画像のボックスは製品のコードである。プローブは:

1. （運用者が Enter を押した後に — 測定を既知の状態から読むため）そのタブの画面とスクロールバックを消し、番号つきの行で画面の高さを超えるまで埋め — いくつかは幅いっぱいに近く、履歴も折り返し直るように — 入力欄に長い下書きを打ち込む。枠自身の行も折り返し直るように;
2. 端末が絵を描けるなら、`/show` の経路で絵を 2 枚、目印の行で挟んで書く: 1 枚はスクロールバックへ押し上げ、1 枚は見えている画面に残す;
3. ウィンドウを狭めるよう求め、それとドラッグが落ち着くのを待ち、リサイズの時点で画面にあったものがすべてスクロールバックへ流れるまで番号つきの行を書き、次に広げるよう求めて同じことをする;
4. 終了後、見た大きさの通知、書き出しの回数と writer が書き換えた回数、運用者が目で読むチェックリストを表示する。

各読み取りの意味:

| 読み取り | どこで | 意味 |
|---|---|---|
| 古い枠 | `PROBE-END` より上にある、フッタか下書きの目印、または番号の無い文字 | 掃除が行を取りこぼした |
| 黒い空白 | 絵の目印の外にある空行 | ED 2 かパディングが履歴に空行を入れた |
| 番号の欠け | 番号の列の抜け | 掃除が履歴を消した — 古い枠より悪い |
| 絵 | 目で: 絵ごとに、残った・黒い・消えた | 問い 2（切り替え B）と、この変更の目的（切り替え C） |

文字の読み取りは、タブの文字の写し（iTerm2: すべて選択してコピーし、`pbpaste | …`。kitty では、運用者がスクロールバックを文字として書き出せる場合）から `resizeprobe -analyze` が数える。したがってプローブが描こうとしたものではなく、端末から来る。絵には文字が無いので、絵ごとに目で読む。

`resizeprobe -drive` は 3 つの切り替えをすべて（選択の後は 2 つ: 製品の `erase` と `none`）tmux の下で走らせ、ペインの大きさを自分で変えて、文字の読み取りを表示する。tmux は折り返し直すが iTerm2 や kitty の絵は描かないので、答えられるのは tmux についての文字の問いだけである — 切り替えと解析器が働くことの対照であって、どちらの端末の読み取りでもない。

### ここまでの読み取り

tmux 3.7c、`resizeprobe -drive`、120×30 のペインを 80 に狭めて元に戻した、2026-09-29（取り込んだ画面は `tools/resizeprobe/testdata` にあり、そのテストが再生する）:

| 切り替え | 狭めた後の古い枠の行 | 黒い空白 | 欠けた行 |
|---|---|---|---|
| A 消去 | 2 — 下書きとフッタ、履歴の中に | 0 | 0 |
| B 何もしない | 1 — 下書きの折り返された最初の行 | 0 | 0 |
| C 枠の消去 | 0 | 0 | 0 |

tmux は消去した画面を履歴に残すので、今の消去は枠の写しを丸ごとそこに残す。B は tmux について問い 3 の仮定を確かめた — 古い行は描画器が再開した位置のすぐ上にある — そして C は 1 行にも触れずにそれを取り除いた。画面を見ると、A は枠を固定位置より 1 行上に描き、その下に空の行を 2 行残した。C は履歴と枠の間に、普段より 1 行多く空の行を残した — カウンタが保持する隙間（ADR-0024）である — が、取り込んだ画面の履歴にはその後の空行が無いので、次に書かれた行がそれを押し上げずに取り戻した。どれも iTerm2 や kitty の読み取りではない。

**iTerm2 と kitty、手で**（運用者、2026-09-29、各端末で切り替えごとに 1 回、ドラッグで狭めた。iTerm2 は 219×117 → 約 140、kitty は 269×77 → 約 176。古い写しは 1 つずつ数え、1 行につながったものも別々に数える）:

| 端末 | 切り替え | 絵（目で） | 古い枠の写し | 黒い空白 | 失われた文字 |
|---|---|---|---|---|---|
| iTerm2 | A 消去 | 両方残った | 7（縮む通知 1 回ごとに 1 つ） | 565 行 | なし |
| iTerm2 | B 何もしない | 両方残った | 下書き 4 つと断片、1 行につながって | 0 | なし |
| iTerm2 | C 枠の消去 | 両方残った | 下書き 2 つが 1 行につながって（2 回の実行のどちらでも） | 0 | なし |
| kitty | A 消去 | 画面上の絵は目印ごと消え、上の絵は目印から絵 1 枚分下に描かれた | 0 | 0 | 49 行 — 画面にあったものすべて |
| kitty | B 何もしない | 両方残った、正しい位置に | 下書き 1 つ | 0 | なし |
| kitty | C 枠の消去 | 両方残った、正しい位置に | 下書き 1 つ | 0 | なし |

**自動で**（`resizeprobe -auto`、160×45 の新しいウィンドウ、キーボードに誰もいない、2026-09-29）: 106 へ 1 段で — kitty の A は 23 行と PIC-2 とその目印を失い、手での結果と同じ。B は下書き 1 つを残し、C は何も残さなかった。iTerm2 の C は、描いた入力欄の行と等しい幅（158）でも 1 桁広い幅でも何も残さなかった。160 → 106 の 8 段を 200 ms 間隔（iTerm2 自身の通知の間隔）で行うと、どちらも何も残さなかった。30 ms 間隔では、kitty は 1 回の通知にまとめて何も残さず、iTerm2 は 8 回とも通知して、古い写しは残さなかったが履歴に空行を 1 行残した。1 桁ずつ 54 段を 10 ms 間隔で行うと、どちらも何も残さなかった。

読み取りが答えたこと:

1. **黒い空白は消去である。** iTerm2 は `ESC[2J` で画面をスクロールバックへ移すので、ドラッグ中の縮む通知（iTerm2 は約 200 ms ごとに送る）のたびに、枠の写しを載せたほぼ空の画面を 1 枚押し込む。kitty はその場で消すので何も積もらない — 代わりに、画面にあった文字と絵を失う。B も C も、どこにも黒い空白を入れなかった。
2. **折り返し直しだけなら絵は残る。** 両方の端末で、正しい位置に。失われた絵・ずれた絵は、すべて消去が失わせ、ずらした。
3. **古い行は、描画器が再開する位置のすぐ上にある**（仮定どおり）。B の残骸は両方の端末でそこにあり、C は自動のすべての実行でそれを取り除いた。
4. **iTerm2 はドラッグを約 200 ms ごとに通知し、kitty はドラッグ 1 回に 1 回だけ通知する。** 200 ms なら通知の間に書き出しが入るので、掃除は 1 回の折り返しを表せばよい。

ここまでの読み取りでは説明できないこと: 手では、C はどちらの端末でも古い下書きを 1〜2 つ残したが、1 段で行う自動のリサイズはどれも残さなかった。最初の推測 — iTerm2 は画面とちょうど同じ幅の行を 2 行にする — は、ちょうどその幅での自動の実行が否定した。原因は次の節で見つける。

### 原因: もう無い幅での描き直し

プローブを、マウスでウィンドウの端を引きずるように拡張した（`-auto -drag`。合成したイベントで、ドラッグの点でウィンドウが最前面でなければ押さない）。writer の記録も取るようにした: すべてのビュー、書き出しごとのカーソル上移動、構えと掃除、モデルが設定したカウンタ。

- 勘定はどの段でも一致していた: 掃除の書き出しは最後に描いた枠のカーソル上移動で始まり、K は枠と合っていた。
- kitty でのマウスのドラッグは何も残さなかった。iTerm2 では古い写しは残さなかったが、履歴に空行を 2 行残した（2 回とも）。iTerm2 はドラッグを約 200 ms ごとに通知しつつ連続して折り返し直し、kitty は最後に 1 回だけ通知する。
- kitty のように通知を止めて最後の 1 回だけを渡すと、iTerm2 は**悪くなった**: 下書き 3 つが 1 行につながった — 手での結果と同じ形。記録が理由を示した: 通知を止めている間も、描画器は約 530 ms ごとに — 入力欄のカーソルの点滅で — 最後に通知された幅で書き出しており、端末はもう狭かった。行はその古い幅と同じ長さで、端末はそれを折り返した。描画器が数えるのは自分が書いた行であって、端末が作った行ではない。

つまり古い行は、描画器が最後に知らされた幅より端末が狭いときに届くどんな描き直しからも生まれる。そして描き直しの行が幅いっぱいになる理由は、**入力欄のすべての行が、何を打ったかに関係なく、空白で幅いっぱいまで埋めて描かれている**ことにある。手のドラッグは、点滅が何回か入るだけの長さがある。

**D. 枠の行を文字の長さに保つ。** 枠のすべての行を、最後に見える文字で終わらせる（幅での切り詰めの後の `shortRows`）。背景つきの埋め草 — 入力行のハイライト — は、その背景のまま行末まで消す指示に置き換え（端末は消したセルをその背景で塗る）、続けて最後の桁へ移動する。行のリセットの後に来る描画器自身の消去は、そのセル 1 つだけを取る: ハイライトは今もウィンドウいっぱいに伸び、しかもその幅に従う。入力欄のカーソル（反転表示の空白 1 つ）は残す（最初の試作はそれを捨て、kitty では帯が反転表示になりカーソルが消えた。直して測り直した）。D の有無で両端末のスクリーンショットを撮り、同じ枠であることを確かめた。

D を入れての読み取り（自動、160×45 の新しいウィンドウ。「短い」は数語 — アイドルのセッションが持つもの。「長い」は幅の大半を埋める）:

| 条件 | iTerm2 | kitty |
|---|---|---|
| 短い、C、30 ms 間隔で 8 段（D なしでは iTerm2 が空行を残した） | きれい | — |
| 短い、C、通知を止める（D なしでは下書き 3 つ） | きれい | — |
| 短い、**B** — 何も掃除しない — 30 ms 間隔で 8 段 | きれい | — |
| 長い、C、30 ms 間隔で 8 段 | きれい | きれい |
| 短い、C、1 段 | — | きれい |
| 短い、C、**マウスのドラッグ** | きれい | きれい |
| 短い、**B**、マウスのドラッグ | きれい | きれい |
| 長い、C、マウスのドラッグ | **古い下書き 1 つ** | きれい |

「きれい」は、古い写し無し・履歴の空行無し・失われた行無し。残った 1 つ: 長い下書きは、どの通知の時点でも通知された幅とちょうど同じ長さだった（152 に 152、146 に 146）ので K は 0 だった — そして通知が届く頃には端末はもう 1〜2 桁狭く、それを折り返していた。K は通知された幅を表す。その幅に近い行は、遅れが現れる場所である。

### 遅れ、そして 5 つ目の候補

残った 1 行は遅れそのものから来るので、まず、より新しい幅を読むことを試した。プローブは iTerm2 のマウスのドラッグ中に、カーネルのウィンドウの大きさ（`TIOCGWINSZ`、ioctl、2 ms ごと）を読んだ: 値が変わったのは端末が通知したとき — 約 200 ms ごと — だけで、その間には一度も変わらなかった。iTerm2 は自分の画面を連続して動かし、プログラムには — 通知もカーネルも — 遅れて伝える。ドラッグの最中に画面を表す幅をプログラムが読む手段は無く、したがってそこから求めた K がその間に正確であることはできない。

**E. リサイズの最中は枠を狭く描く。** 幅を変える大きさの通知から、通知が 400 ms（iTerm2 の間隔の 2 倍）来なくなるまで、枠のすべての行を、モデルが扱う最も狭い幅（`minWidth − 1`、19 桁）に切り詰める。最後の通知の落ち着きの合図が、動きの止まった幅で完全な枠を描く。これだけ短い行は、端末が通知よりどれだけ先に進んでいても、モデルが扱うどの画面でも折り返せない。見た目には現れる: 端が動いている間、枠のすべての行 — 入力欄・フッタ・ダイアログ・流れている応答の末尾 — は 19 桁で切れ（ドラッグの途中で撮ったスクリーンショットに写っている）、手が止まると戻る。高さだけを変える通知では何も起きない: 遅れは幅のものだからである。

C・D・E を併せて、マウスのドラッグで（160×45 の新しいウィンドウ、1.5 秒で 3 分の 2 へ）: iTerm2 でウィンドウと同じ幅の下書き、3 回 — E が無いと 1 行残った条件 — きれい。iTerm2 で短い下書き、きれい。kitty で長い下書き、きれい。30 ms と 200 ms の自動の実行も、両方で、狭めても広げてもきれいだった。「きれい」の意味は上と同じ。

## Decision

**採用（2026-09-29、運用者）: C・D・E を併せて採る。** D は枠の行を文字の長さに保つので、ふつうの下書きは折り返さない。E は、端末が通知より先に進んでいる間、すべての行を短く保つ。C は、長い行がそれでも増やした分を消す。測る前に決めた基準 — 古い枠を残さない・絵の外に黒い空白を作らない・行を失わない・画面上の絵を残す — に照らして、測ったすべての条件が 4 つとも満たした。これより前の提案（C と D だけ）は iTerm2 のマウスのドラッグで 1 行残し、1 つ目の基準を緩めることになっていた。運用者はそれを採らず、E がそれを閉じた。

測っていないこと: ドラッグ中に、応答がスクロールバックへ流れ込んでいる場合。そのとき書き出す行は最後に通知された幅で折り返してあり、端末がそれをさらに折り返すと、カウンタが数えなかった行になる — 本記録の前と同じく、下端の固定がずれる。その間は枠が狭いので、古い枠はそこから生まれない。

測る前に決めた基準:

- 両方の端末で、C が古い枠を残さず、絵のボックスの外に黒い空白を作らず、番号を欠かさず、見えている画面にあった絵が残るなら、C を採る。
- B で、端末が折り返しだけで絵を落とすと分かったら、どんな掃除でも絵は残らない。その場合は残りの読み取りで C と A から選び、制限を端末の側に記録する。
- 端末がカーソルから上へ枠を伸ばさないために C が古い行を残すなら、その端末の振る舞いをここに書き、K に余裕を足すのではなく本節に戻って設計し直す: K を多く見積もると画面上の実際の履歴を消す。それは階段状の残骸より悪い。
- 拡大も同じ実行の中で測るが、その読み取りが揃うまでは何も変えない。拡大時の消去を却下した ADR-0021 §9 はそのまま。

## Consequences

- 縮小時に画面を消去しなくなった。`cmd` は `tea.WithOutput(sweep)` でプログラムを組み立て、同じ `tui.SweepWriter` をモデルに渡し、モデルは縮小時にそれを構える。writer が無ければ何も消さない。ビューは切り詰めてから短くし（D）、リサイズの最中は狭く切り詰める（E）。
- 測定用の継ぎ目は選択とともに撤回した: `ShrinkMode`・消去・切り替え B は製品から無くなった。プローブは 2 つの切り替えを持つ — `erase`（製品）と `none`（writer を渡さないモデル）— 消去の読み取りは本記録と `testdata/tmux-clear.txt` に残る。
- ADR-0092 §4・ADR-0003・ADR-0021 §9・インターフェースの参照文書・AGENTS.md は本記録を指すようになった。v0.85.0 の CHANGELOG の既知の制限は次のリリースで解決する。
- ADR-0089 の勘定はどの切り替えでも変わらない: `emitSegments`・宣言した行数・`physicalRows` は変更せず、C はカウンタを自分が消した行数に合わせるだけである。D が短くするのは管理領域のビューだけで、スクロールバックへ書くものは通らない。
- ウィンドウの幅が変わっている間、枠のすべての行は、最後の大きさの通知から 400 ms、19 桁で切って描かれる。
- 閉じずに記録する残りと範囲（独立レビュー、2026-09-29）: 測ったのは iTerm2・kitty・tmux だけである。背景色つきで消したセルを折り返し直しのとき中身として数える端末では、K が文字で数えるハイライトつきの入力行が折り返し直され、古い行が 1 行残りうる。折り返し直さずに切り詰める端末（xterm・st・screen）では、K が増分を多く見積もり、画面上の履歴をその行数だけ消す — そこでは消去が全部を消していた。モデルの `View()` と描画器がそのビューを受け取る間、あるいは大きさの通知での描画器の描き直しとモデルの構えの間に書き出しが入ると、1 回の縮小の K が誤りうる。その幅はマイクロ秒である。`shortRows` は背景つきの行末の埋め草を、どれでも行末までの帯にする。今それを描くのは入力欄のカーソル行だけである。コロン区切りで書いた SGR は読まず、ハイライトが落ちる（見た目だけ）。
- writer の記録（トレースと構え）は、プローブが `EnableTrace` を呼んだときだけ残す。セッションの writer は何も残さない。
- 運用者が、プローブではなく組み立てた本体で手で確かめた（2026-09-29）— gem-agent `v0.85.1-30-g096ebef` と lagent `v0.11.0-5-g14b81c0`、iTerm2 と kitty、画面に `/show` の絵: 絵は残った、古い入力欄は残らなかった、スクロールバックに空行は入らなかった、広げ直しても問題なかった。mermaid の絵はこの確認に含まれていない。
- lagent も同じ縮小時の消去を持つ（その `internal/tui/model.go`）。TUI のスクロールバックの勘定は共有の機構である（AGENTS.md「The sibling runtime」）ので、決定は同じ作業の中で、本記録を引く lagent 自身の ADR としてそちらへ移植する。

## Alternatives considered

- **リサイズの後に絵を描き直す。** すでに履歴にある絵が 2 回描かれる。スクロールバックの絵は書き出したときのボックスをすでに保っている（ADR-0092 §4）。却下。
- **端末にカーソルの位置を尋ね（`ESC[6n`）、絶対位置の行を掃除する。** Bubble Tea が stdin を持っている間の端末への問い合わせであり、返事はキー入力として届く（AGENTS.md、ADR-0089 §7）。却下。
- **代替画面。** TUI の土台であるインラインの記録を手放す（ADR-0002）。却下。
- **ドラッグが落ち着いてから 1 回だけ掃除する。** K が、途中のあらゆる幅で描かれ、さらに折り返し直された枠を覆わねばならなくなる。通知ごとに掃除すれば、K は描かれた 1 つの枠の 1 回の折り返しで済む。通知ごとのままにする。
- **Bubble Tea v2 の描画器。** 修正ではなく移行であり、ここでは範囲外。
