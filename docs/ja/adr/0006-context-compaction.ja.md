# ADR-0006: 会話履歴のコンテキスト圧縮

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-19 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | オペレータからの要望「会話履歴のコンテキスト圧縮を実装しましょう」 |

## Context

gem-agent のセッションはモデルの入力ウィンドウに当たるまで伸び続け、当たり方
が良くない。エージェントループの奥深くでターンが API エラーで落ち、復旧手段は
`/clear` — つまり全部捨てる — しか無い。先に入れたフッターは接近を可視化した
（`ctx 812k/~1.0M`）が、これは問題を解くというより鋭くした。オペレータは数字が
上がるのを眺め、止める以外に何もできない。

増加の主因はツール出力である。大きなリポジトリに対する数回の `read_file` は、
オペレータが打った全メッセージより重く、そしてその大半は数ラウンド前に意味を
失っている。

## Decision

会話の古い部分を要約して置き換え、直近はそのまま残す。

1. **いつ。** 観測されたプロンプトトークン数がモデル入力ウィンドウの
   `[agent].compact_at_pct`（既定 80）に達したとき自動的に。判定はエージェント
   ループのラウンド間 — 実際に部屋を使い切るのは長いツールループだからである。
   加えて `/compact` による手動実行。自動圧縮は既定 ON（`[agent].auto_compact`）
   とする。これはどの防御も弱めないし、ウィンドウでセッションが死ぬツールは
   バックアップツールではない。
2. **どこで切るか。** 直近 `keepRecent` 件はそのまま残し、それより古いものを
   要約する。切断点はその後、**ツール結果を越えるまで**前進させる。Gemini は
   全ての function call を同一リクエスト内で応答と対にすることを要求するため
   である。ツール結果の上で切ると、残す側が「呼び出しを要約で消された応答」
   から始まり 400 になる。それ以外のメッセージは安全な開始点である。
   assistant ターンも含む — 自分の結果は必ず直後に続くからである。

   user メッセージだけを境界にする方が整っており、ここには最初そう書いて
   いた。検証中に撤回した: 長いエージェントループには user メッセージが
   先頭に 1 件しか無く、この ADR が存在する理由そのものである事例を、その
   規則では一度も圧縮できない。
3. **どうやって。** **ツールを一切渡さない** LLM 呼び出しを 1 回。入力は
   置き換え対象メッセージを描画したトランスクリプトで、防御的な指示を先頭に
   置いた上で **nonce ラップして非信頼データとして**（nlk/guard）渡す。要約
   対象はツール出力で満ちている。それを指示として扱う要約器は、以後の全ターン
   に直結するインジェクション経路そのものになる。この呼び出し用の描画では
   個々のツール結果をクリップする — 要約にバイト列は要らないし、この呼び出しは
   買い戻す文脈より安くあるべきである。
4. **何に置き換えるか。** 要約を **添付として**持つ user ロールのメッセージ
   1 件。これにより既存の送信時ラップが、指示ではなくデータとして引用する。
   要約は非信頼入力から派生したモデル生成テキストであり、拠り所にする事実で
   あって、新しい命令ではない。
5. **fail safe であって fail small ではない。** 要約呼び出しがエラー・フィルタ
   ・空応答のいずれでも、**履歴は一切変更せず**オペレータに伝える。半分だけ
   成功した圧縮は会話を黙って削除する。同じ理由で、縮まない圧縮（メッセージが
   少なすぎる、安全な境界が無い）は実行せずメッセージで断る。
6. **記録する。** 圧縮ごとに `compaction` 記録（置き換えた先頭メッセージ数と
   要約メッセージそのもの）を書く。これにより再開セッション（ADR-0005）は
   圧縮前ではなく圧縮後の履歴を復元する。

## Consequences

- 長いセッションが生き延びる。代償は圧縮 1 回あたり LLM 呼び出し 1 回と、
  要約した側の詳細の喪失である。後者は通知に明示する。忘れたモデルが、最初
  から知らなかったモデルのように見えてはならない。
- 要約は、その日の調子が悪いかもしれない同じモデルが作る不可逆な生成物で
  ある。`/compact` を自動と併せて手動でも持つことで、思考の途中ではなく
  自然な区切り（タスクの終わり）で圧縮する余地をオペレータに残す。要約が
  最もよく効くのはそこである。
- 自動圧縮はウィンドウ値を知っていることに依存する。Vertex の publisher
  メタデータは `inputTokenLimit` を返さないので、値はフッターが既に使っている
  ファミリー既定値（1M）であることが多い。`[model].context_window` で厳密に
  できる。ウィンドウが全く不明なときは自動圧縮を止め、`/compact` は動く。
- 圧縮はシステムプロンプトや指示ファイルを縮められない。`CLAUDE.md` 群自体が
  ウィンドウに迫るプロジェクトは別の問題であり、これはそれを解くふりをしない。

## Alternatives considered

- **古いメッセージを捨てる**（要約無し）— 却下。安いが、合意した決定を
  エージェントが黙って忘れる。最も問題になる場所で失敗が不可視になる。
- **システムプロンプトに要約を入れる** — 却下。システムプロンプトは信頼
  チャネルであり、この内容は非信頼のツール出力由来である。会話側に、データ
  として引用して置くべきものである。
- **手動圧縮のみ** — 既定としては却下。オペレータが見ているのは出力であって
  トークンカウンタではないし、防ぎたい失敗はループの途中で来る。
- **ツール結果ごとの逐次圧縮**（ローリング圧縮）— 今回は却下。呼び出しが増え、
  誤りうる箇所が増え、まだ使っている詳細を捨てる。セッション 1 回の圧縮では
  足りないと分かった時点で再検討する。
