# ADR-0100: 死んだ接続を名指すのは沈黙ではなく通信層である

| 項目 | 値 |
|------|----|
| ステータス | **Accepted**（2026-11-01） — 実装済み |
| 日付 | 2026-11-01 |
| 対象 | gem-agent |
| 意思決定者 | nlink-jp メンテナ |
| きっかけ | オペレーター:「`思考中… 105 秒間データなし — 接続が失速している可能性` という表示が多発する。実際には動作しているのに、動作していないように見える」 |
| 修正対象 | ADR-0033 §1（失速警告）、ADR-0056 §1–§2（90 秒のしきい値） |
| 関連 | ADR-0021（再試行は何も消費していないときだけ）、ADR-0041 §5（`toolRunning`） |

## 背景

ADR-0033 §1 は、実行中のステータスを鼓動にし、しきい値を 1 つ持たせた。
チャンクが N 秒来ないと「N 秒間データなし — 接続が失速している可能性」に
変わる。ADR-0056 は N を 20 秒から 90 秒に移した。根拠として測ったのは、
無害な沈黙の原因 1 つだけだった。Gemini の function call は丸ごと 1 part
で届くので、モデルが大きな引数を組み立てているあいだ回線には何も流れない
（約 650 B/s、21KB で 40 秒）。そのうえで、「組み立て中」と「失速」を
クライアント側で見分ける信号は無い、と結論した。

### 現場: function call ではない沈黙

2026-11-01 のオペレーターのセッション（v0.94.0、`google/gemini-4-argon`、
thinking `high`）には、メインのラウンドが 58 回ある。そのうち 8 回が
97〜210 秒かかった。8 回ともプロンプトは 23 万〜77 万トークンで、
どれも大きな出力を生んでいない。

| ラウンド時間 | プロンプト | キャッシュ | 出力 | 思考 |
|---|---|---|---|---|
| 154.1 秒 | 247,652 | 96% | 54 | 58 |
| 210.1 秒 | 236,311 | 0% | 239 | 1,999 |
| 126.6 秒 | 754,197 | 64% | 177 | 483 |
| 101.8 秒 | 768,553 | 0% | 52 | 1,960 |

セッションの記録にあるのはラウンドの所要時間で、最初のチャンクが来た
時刻ではない。それでも、出力 54・思考 58 トークンを流すのに 150 秒は
かからない。このラウンドのほぼ全部が、サーバーを待っていた時間である。
後述のプローブでは、1.6 万トークンのプロンプトでもこの待ちが現れた。
最初のチャンクまで 90.5 秒の回があり、別の回では 180 秒を超えても
何も来なかった。待ちの長さは、しきい値として選べるどの数字にも収まらない。

### 前提: 通信層はすでに接続を確かめている

gem-agent は HTTP クライアントを自分で組み立てていない。
`genai.NewClient` がそれを `cloud.google.com/go/auth/httptransport` に
任せている。その基底トランスポートは `x/net/http2.ConfigureTransports` を
`ReadIdleTimeout = 31s` で走らせる（`PingTimeout` は既定の 15 秒のまま）。
実測に使ったツールチェーン（go1.27.3）では、x/net v0.58.0 はこの設定を
標準ライブラリの HTTP/2 実装に渡している（`transport_wrap.go`）。

振る舞いは次のとおりである。HTTP/2 の接続が 31 秒フレームを受け取らないと、
トランスポートは PING を送る。フレームが届くたびに 31 秒は数え直しになる。
PING に 15 秒以内に応答が無ければ、接続を閉じ、ストリームは
`http2: client connection lost` で失敗する。つまり死んだ接続は、
最後に届けたフレームから遅くとも 46 秒で名指しされる。

ADR-0056 の結論は中身については正しいが、接続については正しくない。
「組み立て中」と「思考中」を見分ける信号は無い。しかし「相手がそこに
いる」と分かる信号はあり、しかもすでに毎回のリクエストで動いている。
このプロジェクトの誰もそれを選んでおらず、ここでは何も固定していない。

### 実測

`internal/llm/pinghealth_live_test.go` は、それぞれの実行の前に、仮説と
反証条件をコミット 5c85c14（H1–H3）と 8b624c1（H4）で宣言した。出荷して
いる `NewVertex` と `ChatStream` をそのまま呼ぶ。差し込んだのは、認証
ライブラリが複製する `http.DefaultTransport` のダイヤラだけである。
ヘルスチェックは `GODEBUG=http2debug=1` で読み、許可した行だけを残す。
同じログに bearer トークンも出るためである。トークン取得用のクライアントは
PING しない複製なので、ヘルスチェックの行はすべて Vertex の接続のもの
である。

| 仮説 | 回数 | 結果 |
|---|---|---|
| H1 接続は HTTP/2 である | 全回 | 成立: 各回にヘルスチェックの行がある |
| H2 生きている接続の長い沈黙には PING が送られ、すべて応答され、ストリームは完了する | 有効 3 回（約 35.4 万トークン、キャッシュ 0%） | 成立: 沈黙 205.4 / 147.2 / 79.1 秒、送信 6 / 3 / 2 回、失敗 0 |
| H3 リクエスト送信後に凍結した接続は、ヘルスチェックの失敗を経て 61 秒以内に失敗する | 2 回 | 成立: 凍結から 44.0 / 44.0 秒 |
| H4 同じことが、応答が始まった後（凍結前にチャンクあり）でも成り立つ | 3 回（有効 2 回） | 成立: 凍結から 46.0 / 46.0 秒 |

数えなかったもの:

- H2 の 1 回は 31.6 秒で失敗した。テスト出力に掛けた grep の絞り込みで
  エラー文を落としたため、原因は分からない。時間は 429 の再試行 5 回の
  使い切りと合うが、推測である。
- H4 の 1 回は、中継が凍結しなかったので無効にした。サーバーは 180 秒で
  4KB 未満しか送らず、その間 PING はすべて成功した。小さなプロンプトで
  起きた、H2 と同じ種類の沈黙である。
- いくつかの回では、47〜80 秒の時点で `GOAWAY NO_ERROR
  "session_timed_out"` が来た。進行中のストリームには影響しなかった。

事前登録では凍結の実行を 2 回までとしていた。H4 は後から足し、それ自体の
事前登録をしてから 3 回走らせた。費用は全体で約 $2.3（失敗した回が
課金されていれば最大 $3.0）で、承認された上限は $3.4。

### 警告にとっての意味

出荷しているトランスポートは、死んだ接続のストリームを、最後のフレームから
遅くとも 46 秒で終わらせている。90 秒の警告は、それを早めることができない。
警告がエラーより先に出るのは、ある一つの場合だけである。フレームか PING の
応答を受けた後、90 秒の時点から 46 秒以内の過去に接続が死んだ場合である。
それ以外では、警告は接続が生きて PING に応答している間に出る。現場で
観測した事例は、すべてこちらだった。健全な作業で鳴る警告は、警告を無視する
ことをオペレーターに教える。ADR-0056 が避けようとしたのは、まさにその
結果である。

## 決定

### 1. ヘルスチェックを gem-agent 自身の設定にする

`NewVertex` は HTTP クライアントを SDK に任せず、自分で組み立てる。
新しい振る舞いを入れるのが目的ではない。上の振る舞いを、このプロジェクトが
選び、テストが固定するものにする。

- **基底トランスポート。** `http.DefaultTransport` の複製に、
  `HTTP2 = &http.HTTP2Config{SendPingTimeout: 31 * time.Second,
  PingTimeout: 15 * time.Second}` と `MaxIdleConnsPerHost = 100` を
  設定する。後者は SDK の基底も設定している値である。どちらも標準
  ライブラリで、Go 1.24 以降で使える。複製は `ForceAttemptHTTP2` を
  引き継ぐので、ALPN は h2 を交渉したままである。
- **認証。** その `BaseRoundTripper` で `httptransport.NewClient` を呼ぶ。
  資格情報は `credentials.DetectDefault`（cloud-platform スコープ）から
  取り、`X-Goog-User-Project` は資格情報のクォータプロジェクトから取る。
  クライアントを渡さないときに genai がしている組み立てと同じである。
  genai はクライアントを渡されると、自分では認証を足さない。
- **依存。** `cloud.google.com/go/auth` を直接依存にする。Google の一次
  モジュールで、すでにモジュールグラフにある。

コンストラクタは 2 つの時間を引数で受け取り、オフラインのテストが短い値を
渡す。テストはローカルの TLS HTTP/2 サーバーを立て、genai を通して
ストリームのリクエストを送り、中継で接続を凍結する。凍結は 2 回行う。
1 回は応答ヘッダの前、もう 1 回は最初のチャンクの後で、エラーが通る 2 つの
経路（包まれた `doRequest` のエラーと、ストリームの scanner）に当たる。
どちらも、§3 が認識するエラーで上限内に失敗することを求める。出荷する値は
単体テストで固定する。

### 2. 失速警告を削除する

`stallSeconds`、`heartbeatLine` の警告の分岐、`StallFmt`（en/ja）を
削除する。鼓動はそのまま残す: `1m07s · 34 チャンク · 最終 40 秒前`。
経過秒数は数え続け、中立のままで、告発には変わらない。`toolRunning` は
残す。side-call の思考を思考表示に混ぜないために、まだ使っている
（ADR-0041 §5）。

警告の代わりに画面に足すものは無い。遅いだけのターンをオペレーターが
止めたければ、Ctrl+C はすでに同じ行にある。

### 3. 接続断はオペレーターの言葉で言う

ストリームが通信層の接続断のエラーで失敗したら、ターンのエラーは、何が
起きたかと次の手だけを言う: Vertex AI との接続が切れた、メッセージを
送るとそこから続く。オペレーターのメッセージと完了したラウンドはすでに
履歴にあるので、「もう一度送って」では指示が重なる。どう検出したかは
書かない（ADR-0056: 供給側の仕組みは、オペレーターが行動に移せる情報では
ない）。文言は uitext（en/ja）に置き、生のエラーは `connection_lost` 記録
としてセッションログに残す。判定はエラー文で行う。トランスポートがこの
エラーの sentinel を公開していないためである。§1 のオフラインテストが、
両方の経路でこの文を固定するのはそのためである。

ファイル検索の子（`agentic_file_search`）は、もう 1 つのエージェント
ループである。そのエラーはオペレーターではなく主モデルに届くので、そこで
接続が切れたら、トランスポート自身の文と、モデル向けの次の手（聞き直す
か、直接探す）を返す。子はセッションログを持たないので、その文が接続断の
唯一の記録になる。

genai はストリームのエラーを、自分でも標準ロガーに出す（ストリームの
読み取りでの `log.Printf("Error %v", …)`）。gem-agent はこのロガーの
出力先を変えていないので、TUI の下ではこの生の行が画面の上に書かれて
しまう。TUI が動いている間は、標準ロガーの出力先をセッションログに変え、
1 行を 1 つの `library_log` 記録にする（genai はそこにヒントも出す。
たとえば応答が大きすぎてストリームできないという案内で、捨てると失われる）。
素の REPL と `-p` では stderr に残す。実装では、変更の前後で画面を tmux で確かめる（AGENTS.md:
TUI の行は理屈でなく実測する）。

### 4. プローブはツリーに残す

`pinghealth_live_test.go`（H1–H4）は実測の記録としてツリーに残す。
オフラインテストには確かめられないこと、つまり本物のエンドポイントが長い
沈黙の間も PING に応答することを確かめるのは、このプローブだけである。
手で走らせたときにしか動かず、費用もかかるので、関門ではなく記録である。
関門は §1 のオフラインテストである。

### 5. lagent の警告は残す

lagent にも同じ警告がある（`stallSeconds = 90`、同じ `StallFmt`）。
しかし前提が違う。lagent はローカルの OpenAI 互換サーバーと素の HTTP/1.1 で
話す。HTTP/1.1 には PING が無く、認証ライブラリも通らない。警告を消すと、
ローカルサーバーが止まったときの唯一の手がかりが消える。lagent に独自の
生存確認を持たせるかは、別の測定を伴う別の問いである。この ADR が変える
のは gem-agent だけである。

## 検討した代替案

- **しきい値をまた上げる。** 実測の沈黙は 79 秒から 200 秒超まであり、
  文脈とともに伸びるので、合う数字が無い。しかも約 46 秒より上の数字は、
  ほとんど何も足さない。そのころには通信層が死んだ接続に決着をつけて
  いるからである。
- **ラウンドの最初のチャンクまでは警告しない。** 現場の事例の大半は消える。
  しかし、ラウンド途中の生きたストリーム（function call、ADR-0056）は
  まだ告発し、通信層がすでに決着をつけている主張も残る。
- **警告の言い換え**（「サーバーの応答待ち」）。この種のステータス行は
  ADR-0056 でオペレーターが却下した。供給側のタイミングは、オペレーターが
  行動に移せる情報ではない。
- **クライアントは SDK に任せたまま、警告だけ削除する。** 最小の変更で
  ある。しかし警告を消して安全なのは、ヘルスチェックがあるからである。
  依存の更新でそれが消えても、ここでは何も気づかない。そうなると死んだ
  接続は、警告もエラーも無いまま止まり続ける。
- **SDK の組み立てを保ち、オフラインテストで固定する。** 31 秒/15 秒を
  外から短くできないので、テストは実時間で 46 秒以上かかる。TLS の
  ルートとトークンのエンドポイントの差し替えも要る。それでも設定は
  ライブラリの選択のままである。
- **PING の間隔を短くする。** 測っていない。最後のフレームから 46 秒以内の
  検出は、オペレーターが 90 秒まで許していた範囲に十分収まる。数字を
  変えると、固定した観測が、根拠の無い新しい決定に変わる。

## 影響

- 沈黙は警告を出さなくなる。鼓動の経過秒数が、待った長さを示す。死んだ
  接続の扱いは変わらない。これまでどおり、最後のフレームから遅くとも
  46 秒でエラーとしてターンを終える。変わるのは、そのとき次の手を言う
  メッセージが出ることである。エラーの経路は `-p` と素の REPL でも同じで、
  どちらにも警告は元から無かった。
- 自動タイムアウトを入れないという ADR-0033 の判断は保たれる。ヘルス
  チェックは、生きている接続の長いストリームを終わらせない（H2 で
  205 秒を実測）。終わらせるのは、応答しない接続だけである。
- ここでは決めないこと: チャンクを消費していないときの、接続断の自動
  再試行。ADR-0021 は許す。しかしオペレーターがまだ見ていない失敗に、
  もう 1 回の待ちを足すことになる。別の決定とする。

### 残余

- PING が証明するのはフロントエンドがいることで、その奥のモデルでは
  ない。ストリームを開いたまま何も返さないバックエンドは、ターンを
  待たせ続ける。鼓動の経過秒数はそれを示し続け、Ctrl+C で終えられる。
  実測にこの事例を示すものは無い。
- 基底トランスポートが、認証ライブラリの `defaultBaseTransport` を通らなく
  なる。そのため、そこが環境から適用するクライアント証明書（mTLS / S2A）の
  設定は、API 呼び出しには引き継がれない。トークン交換には引き継がれる
  ので、mTLS を強制する環境では、この 2 つが別の経路をとる。gem-agent は
  ADC で認証し、どちらも使っていない。使うようになったら、この組み立てを
  見直す。
