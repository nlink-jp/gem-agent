## 背景

ADR-0099 は、追加ディレクトリを「オペレーターがこの実行のために打ったもの」、かつ「セッションの間ずっと届くもの」として扱っている。どちらも常には成り立たない。グローバル設定の `[directories]` は一度書いたらどのプロジェクトからも読まれるし、ボリュームや共有はセッションの途中で消えることがある。古い前提で動いている箇所が 4 つある。v0.100.1 での実測は次のとおり。

1. **今のプロジェクトに合わない設定のパスが起動を止める。** `[directories].write` に、今のプロジェクトを含むディレクトリ、すでに覆われているディレクトリ、今は存在しないパス（未マウントのボリューム）を書くと、いずれも `resolveAddedDirs` がエラーを返し、そのプロジェクトでは gem-agent を起動できなかった。
2. **`/clear` が write レーンを置き去りにする。** プローブに通らなくなった書き込みのルートがあると、`rotateWorkDir` はファイルツールを新しい作業ディレクトリへ移した後で、前のサンドボックスプロファイルを保った。write レーンは新しい作業ディレクトリへの書き込みで exit 1 になり、それがセッションの終わりまで続いた。
3. **読み取りのルートが、read レーンの締め出している木を開け直せた。** `RefuseRoot("/Volumes", false, …)` はこれを受け入れ、deny の後に来る追加ルートの再許可が、確認なしの read レーンに全マウントを渡した。`ownRootsUnderReach` はプロジェクトと作業ディレクトリについて、まさにこれを拒否している（ADR-0102）。
4. **どのファイル読み取りも全追加ルートを開いていた。** ファイル読み取りの子プロセスは、ツール呼び出しごとに全ルートへ `os.OpenRoot` を行う。開けないルートが 1 つあると（止まった共有と同じく open が返らない FIFO をルートの位置に置いて測定）、プロジェクトの普通のファイルの読み取りが返らなかった。

## 決定

1. **当てはまらない設定のパスは飛ばし、理由をオペレーターに告げる。** このセッションがどこで始まったか、今何がマウントされているかで決まる拒否（`sandbox.Situational`: 今は見つからない・開けない、プロジェクトや作業ディレクトリを含む、すでに覆われている）は、`[directories]` の項目なら起動時に注記して飛ばす。同じパスを `--add-dir` や `--read-dir` で渡したときは、これまでどおり起動を止める。この実行のために打ったものだからである。それ以外の理由で拒否される設定のパス（ホーム、資格情報の場所）も起動を止める。どのプロジェクトから見ても誤りだからである。
2. **`/clear` はプローブに通らなくなったルートだけを外し、ほかは残す。** `VerifyAddedRoots` は失敗したルートを型付きのエラー（`sandbox.AddedRootError`）で名指しする。`rotateWorkDir` はそのルートを除いて作り直し（ルートごとに高々 1 回）、レジストリ（`Registry.DropAddedDirs`）、監視、トランスクリプトの記録から外して、オペレーターに告げる。`/add-dir` でまた足せる。監視からも外すのは、取り外したボリュームを次に見に行くと、中身がすべて消えたと報告してしまうからである。ルートを名指さない失敗は、これまでどおり前のプロファイルを保つ。
3. **read レーンが到達範囲として拒否している木そのもの、またはそれを含むディレクトリはルートにできない。** `RefuseRoot` は `ownRootsUnderReach` の規則を追加ルートに適用する。両方のレベルで、フラグ、設定、`/add-dir`、`request_directory` のどの経路でも同じである。`/Volumes` と `/Network` は拒否する。その内側のディレクトリこそがルートの用途である。`~/Library` は資格情報の場所を含むので、すでに拒否されている。この拒否は状況によるものではない。どのプロジェクトから見ても誤りである。
4. **ファイル読み取りの子プロセスは、呼び出しのパス引数が指すルートだけを開く**（`rootsNamedBy`）。相対パスの引数は `resolvePath` と同じく先にプロジェクトへ連結する。`../ref/x` はプロジェクトの隣の追加ルートに届くからである。`path` だけでなく文字列の引数をすべて調べる。ルートを 1 つ余計に開いても損はないが、取りこぼすと読み取りが失敗する。

## 帰結

- `--read-dir /Volumes` や `[directories]` の同じパスは、これまで起動できたが、今後は理由と代わりに足すものを告げて起動を止める。ほかに動かなくなるものはない。
- 外したルートはプロセスの終わりまで外れたままである。ボリュームを戻したら `/add-dir` を 1 回打てばよい。
- 残る限界: 止まったルートを実際に指す読み取りは止まり、起動時の判定と `/clear` のプローブも止まった共有では止まりうる。そうなるのは応答しなくなったマウントだけで、読み取りには、止まった呼び出しを見切る下限（ADR-0065）が効く。

## 検討した代替案

- **`/clear` で 1 つ失敗したら追加ルートをすべて外す**（lagent の方式）— 採らない: 取り外したボリューム 1 つのために隣のノートのディレクトリまで失うべきではなく、失敗したルートを名指しても変更は大きくならない。
- **状況による拒否をフラグでも飛ばす** — 採らない: この実行のために打ったパスが当てはまらなかったことは、オペレーターが聞くべきことである（ADR-0099 §3）。
- **子プロセスでは絶対パスだけで判定する**（lagent の方式）— 採らない: ここでは、今は動いている、追加ルートへ届く相対パスが失敗してしまう。
- **子プロセスの各 open に期限を付ける** — 採らない: タイマーではカーネルで止まった open を解放できず、すべての読み取りがその時間を待つことになる。開かないことが修正のすべてである。
