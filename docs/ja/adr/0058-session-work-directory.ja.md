# ADR-0058: セッション作業ディレクトリと、「大きすぎる」を誰が判断するか

| Decision makers | nlink-jp maintainers |
| Triggered by | 利用者「セッションごとの作業ディレクトリをプロジェクトとは別に用意し、サンドボックスを両方にまたがる構成にすべきではないか」 |
| Amends | ADR-0001（sandbox の書き込みルート）、ADR-0012 §4（file-mediated MCP 出力の落ち先）、ADR-0020/0022（state レイアウト） |

## Context

作業ディレクトリの設計中に見つかった 2 つの事実が、ディレクトリそのものより
重要だった。

**MCP の結果には上限が一度もなかった。** 組み込みツールの結果は常に
`tools.OutputCap`（20,000 bytes）で切られてきた — その定数のコメントは、
上限のないツール出力を「エージェントループにおける context 爆発の主たる
失敗モード」と書いている。MCP の結果はそれを完全に迂回していた:
`cmd/mcp.go` が `client.CallTool` の文字列をそのまま会話へ返していた。
nlink-jp の file-mediated なサーバ群 — lookup 系、splunk-mcp — が
`workspace_root` 引数を持つに至ったのは、**測りようのない context** を
溢れさせないためだった。同じガードが 7 回実装され、しかもそれを実装するのに
最も不向きな 7 プロセスで実装されていた。**サーバはモデルの context window を
知り得ない。** クライアント側は知っている。

**非テキストコンテンツは捨てられていた。** `CallTool` はテキスト以外の
ブロックをすべて `[non-text content: image]` に潰していた。
`chrome-pilot-mcp` は既に 4 MiB を上限に MCP の image コンテンツを返して
いる（`internal/tools/debug.go`）ので、gem-agent 経由のスクリーンショットは
モデルから**見えていなかった** — 劣化ではなく消失である。

その上で、元の課題は依然として立つ。セッションはプロジェクトの一部でない
ものを置く場所を必要とする。候補 2 つはどちらも誤りだ。**プロジェクト
ディレクトリ**は利用者のソースツリーであり、中間生成物を置けば git 作業
コピーが誰も頼んでいないもので汚れる。**`/tmp`** はマシン上の全プロセスと
共有された 1 つの平坦な名前空間（この機で 327 エントリ、`drwxrwxrwt`）で、
セッション隔離が無く、resume したセッションが以前の自分の成果物を見つける
手段も無い。

## Decision

### 1. セッションごとの作業ディレクトリ

`<state root>/<escaped project>/work/<session id>/`。transcript と memory と
同じ state root 上（ADR-0020/0022）なので、`GEMAGENT_STATE_DIR` による
テスト・訓練の隔離がそのまま効く。session id で採番するため `--resume` は
以前の自分が使ったディレクトリに戻る。

これはプロジェクトと並ぶ **sandbox プロファイルの書き込みルート**であり、
かつ**組み込みファイルツールの第 2 ルート**である。後半は省略できない:
パスが見えるのに開けないモデルは、シェルのリダイレクトでファイルツールを
迂回する。それはレビュー可能性が下がるだけで、封じ込めにはならない。
相対パスは従来どおりプロジェクト基準 — 作業ディレクトリはプロンプトが
示す絶対パスで到達するので、`report.md` はこれまでどおりプロジェクトの
ファイルを意味する。

### 2. 「大きすぎる」の判断はクライアント側、切らずに退避する

`internal/mcp.CallTool` はコンテンツブロックをそのまま返し、
`cmd/mcpresult.go` のアダプタが描画する。`OutputCap` を超えるテキストは
**作業ディレクトリに書き出し**、モデルには先頭とパスを渡す — 切り捨てでは
ない。非テキストブロックも同じ経路で書き出す。

ファイル名はサーバ名・ツール名・内容のハッシュから作る。同じ答えを 2 回
取っても 1 ファイルに収まり、名前の一意性に時計もカウンタも要らない。

### 3. バイナリは添付ではなくパスで返す

画像は保存し、モデルには `view_image` を呼べと伝える。機構は存在する
（ADR-0012 §5）が、バイトをインラインで返すことは意図的にしない: 添付は
会話全体とともに毎ラウンド再送され、それは ADR-0027 が媒体バケットを
作った理由そのものだからだ。「見る」を明示的な行為に保つことで、モデルが
求めるまで媒体は履歴に入らない。そしてそれは ADR-0012 が設計した IR フロー
（scan → screenshot → look）であり、作業ディレクトリが読めるようになった
ことで再び成立する。

### 4. 起動順序

session id の確定を **MCP サーバ起動より前**に移した。必然である:
作業ディレクトリは session id で採番され、sandbox プロファイルはパスを
必要とし、`mcp.json` の args にある `${GEMAGENT_WORK_DIR}` は読み込み時に
プロセス環境から展開される（`internal/mcp/config.go` が既にそうしており、
Claude Code と同じ挙動）。セッションログのブロックを `connectMCPServers`
の前へ移動した。registry にも memory にも MCP にも依存していないので、
移動は機械的である。

`GEMAGENT_WORK_DIR` は引数で渡すのではなく**プロセス環境へ export する**。
これが `shell_exec` の子プロセス、全 MCP サーバ（`internal/mcp` は
`os.Environ` を継承）、全 hook の前にパスを置く唯一の方法であり、
どれ一つ gem-agent のレイアウトを知る必要がない。

### 5. 自動削除はしない

ファイルこそが目的である — モデルが作ったレポート、見るよう指示された
スクリーンショット。起動時には以前の作業ディレクトリが何個あり何バイト
保持しているかを**報告する**だけで、削除は利用者の判断とする。唯一の例外は
セッションが空のまま残したディレクトリの非再帰 `rmdir` で、これは何も
削除できず、使われなかったセッションが痕跡を残さないようにするだけである。

## Consequences

- 大きすぎる MCP 結果が context に入らなくなり、同時に失われなくもなった。
  従来は `read_file` は上限付きで切り捨て、MCP は無制限だった。今はどちらも
  退避する。
- `chrome-pilot-mcp` のスクリーンショットが初めて到達可能になった。
- サーバ側の `workspace_root` 機構は **gem-agent にとっては**不要になった。
  lookup 系がそれを外せたのはこのためである。JSON 結果に載せられない
  成果物 — 音声・動画・ツールが描画する PDF — については依然として正しい。
- `tools.OutputCap` を export した。数値は 1 つ、参照は 2 箇所。
- 作業ディレクトリが無い場合（transcript 無効のセッション）の退避先は無く、
  **残りが失われた旨を明記した**切り捨てにフォールバックする。答えの一部を
  黙って失うことだけは、この設計が絶対に起こしてはならない結果である。

## Alternatives considered

- **`Tool.Run` を拡張して添付を運ぶ**（MCP 画像を自動でインライン part に
  する）。二重の理由で却下: 約 20 のツール定義とその中の全 return に波及
  すること、そして結果として媒体が毎ラウンド履歴で再送されること —
  ADR-0027 が避けるために存在するコストそのものである。`view_image` の
  往復 1 回で済み、判断がモデルの側に残る。
- **MCP サーバを `--workspace-root ${GEMAGENT_WORK_DIR}` で作業ディレクトリに
  向ける**（サーバ側のファイル分離は残す）。動作するし当方のコード変更も
  不要だが、「モデルにとって大きすぎる」判断がサーバに残り、全サーバが
  「クライアントが名前で指せるファイルシステムを持つこと」に依存し続け、
  フラグを持たないサーバには何も効かない。
- **sandbox から `/private/tmp` と `TMPDIR` を外し**、子プロセスを
  `<work dir>/tmp` に向ける。境界は明確に締まる — 現状の作業ディレクトリは
  既に広い許可への**追加**でしかない。意図的に見送る: `/tmp` を直書きする
  プログラムが壊れるため、実作業での実測を経てから課すべきである。
  失わないようここに記録する。
- **古い作業ディレクトリの定期削除。** 却下: 利用者がまだ見ていないかも
  しれないファイルに対する、パターン駆動の再帰削除は、エージェントが単独で
  下す判断ではない。
