# ADR-0055: 単発モードのパイプ stdin は非信頼データ — 決して指示ではない

| 項目 | 内容 |
|-------|-------|
| ステータス | **承認済み** |
| 日付 | 2026-08-29 |
| 拘束対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | 利用者: `curl -s https://ipinfo.io \| gem-agent --auto -p "IPの帰属調査を…"` — パイプした JSON は黙って捨てられていた。Claude Code の `-p` はパイプ stdin を読むので、drop-in の欠落は実在 |

## 背景

単発モードは `Run(ctx, flagPrompt, …)` を呼ぶだけで stdin に一切
触れなかった: パイプされた内容は黙って破棄され、モデルは持っていない
データについての指示を受け取っていた。Claude Code の `-p` はパイプ
stdin をコンテキストとして受け取り、drop-in 互換は gem-agent の
第一要件 — `データ生成コマンド | gem-agent -p "…"` はパイプラインの
正準形である。

設計の地雷は信頼チャネルにある。ADR-0038/0054 は 1 つの構造的事実に
立つ: `turnInput` — オペレータがタイプした依頼 — は**注入攻撃者が
書けない唯一のコンテキストチャネル**であり、リスク評価器は全コールで
それを整合性の証拠として受け取る。パイプ stdin はその正反対で、
上流コマンドが取ってきたもの（契機の例は HTTP レスポンスをそのまま
流す）である。stdin を素朴にプロンプトへ連結すると、**信頼チャネル
そのものを攻撃者に渡す** — 取得ページに仕込まれた 1 行が「operator
instruction」のラベルで評価器に届く。

正しい扱いのための機構は既に存在する: `@` 参照のテキストは
`llm.Attachment` として、タイプ文の**中ではなく隣**に保存され、
送信時にターンのノンスラップへ畳み込まれる（"Attached file (x),
quoted as data: …"）— ツール結果とまったく同じ扱い。`turnInput` は
既存設計によりタイプ文字列だけを運ぶ。

## 決定

### 1. パイプ stdin は添付になる — `@` ファイルと同じレーン

単発モードで stdin が端末でないとき、gem-agent はそれを（上限つきで）
読み、新設の `Agent.AttachData(ref, kind, content)` — `AddContext` と
同じターン間規律 — でターンの user メッセージにテキスト添付
（`kind "stdin"`・`ref "-"`）として積む。下流はすべて**構築ではなく
継承**: 送信時ノンスラップ・トランスクリプト永続化と resume・
コンパクションの `[user attached …]` 行、そして決定的なのは
`turnInput` からの除外 — リスク評価器の指示セクションはオペレータが
タイプした文だけであり続ける。指示は `-p` 文字列のみ、stdin はラップ
越しにモデルが読む引用データである。

### 2. 上限つき読み取り・開示されるクリップ・テキストのみ

- 読み取りは上限つき（256 KiB）。超過時は添付の末尾にクリップの
  事実と「残りは**読んでいない**」ことを明記する — 部分が全体の
  ふりをしてはならず（ADR-0014 の規則）、サイズ報告のために無限
  パイプを飲み干すのは何も買わない。
- バイナリ stdin（不正 UTF-8 / NUL バイト）は理由を stderr に
  警告してスキップ。このレーンはテキストパイプライン用で、
  バイナリには本物の MIME 処理を持つ `@` の media/document
  レーンがある。
- 空の stdin は何も添付しない — `-p` は従来と完全に同じ。
- 端末の stdin は決して読まない: 対話シェルからの `gem-agent -p`
  実行がプロンプトなしでハングすることはない。

### 3. 対話モードは不変

素 REPL の既存契約は維持する — `-p` **なし**の非 TTY stdin は
スクリプト入力レーンで、stdin の行はコマンドでありデータではない。
stdin をデータとして読むのは `-p` 形のみで、`-p` は REPL を完全に
迂回するので両用途は衝突しえない。

## 検討した代替案

- **stdin をプロンプトに連結**（大半のラッパーのやり方）— 即却下:
  取得コンテンツを ADR-0038/0054 の信頼チャネルに注入し、送信時
  ラップ機構も他の全所（メモリ保存プロンプト・ルールブックの
  フレーミング・トランスクリプト）でそれをオペレータ文として
  扱ってしまう。
- **`--stdin-file` 型のフラグ** — 却下: パイプ自体がオペレータの
  意図を語っている。フラグは正準形に一手を足すだけで、Claude Code
  は何も要らない。
- **無制限読み取り** — 却下: 履歴は毎ラウンド再送され
  （ADR-0018 の経済）、暴走した上流が round 1 の前にウィンドウを
  焼き尽くす。

## 帰結

- `データ | gem-agent -p "…"` が動き、`--auto` の下でも安全に動く:
  評価器はタイプされた指示に対してコールを判定し、パイプ内容は
  「データであって指示ではない」という常設フレーミングつきで
  ラップの中に留まる。
- トランスクリプトはモデルが実際に見たものを記録する（添付内容は
  永続化され、resume で再生される）。
- 将来の対話側の需要（ペーストをデータとして）は `AttachData` を
  再利用できる — API は単発専用ではなく、配線だけがそうである。
