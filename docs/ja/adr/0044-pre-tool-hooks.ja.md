# ADR-0044: オペレーター pre-tool フック — 組織のガードをフォールバック後も生かす

| 項目 | 値 |
|-------|-----|
| ステータス | **Accepted** |
| 日付 | 2026-08-25 |
| 拘束範囲 | gem-agent |
| 決定者 | nlink-jp メンテナ |
| 契機 | オペレーター: Claude Code の Hook に相当するものを gem-agent に搭載できるか。組織の PreToolUse ガードは「手順書は注意が緩んだ瞬間にこそ破られるので、制御はエージェントの外に置く」ために存在する — そしてフォールバックの瞬間にそれが消える |

## Context（背景）

組織は Claude Code の `PreToolUse` フック（`guard-recursive-write.py`）
を運用している。相対パスへの再帰的 in-place 書き換え — ワークスペース
全体を 2 度リフォーマットした事故 — を拒否するもので、現在も実際に
機能している（この ADR を書いた当日、主ツール上で 2 回発火した）。
ガード自身の存在理由は「書かれた規則は注意の緩みを防げない。制御は
エージェントの外に住む必要がある」である。

gem-agent はまさに「何かがうまくいかない瞬間」のためのフォールバック
であり、その外部制御が存在しない唯一の場所でもある。フォールバックは、
不慣れなツールで事故の確率が上がるまさにその瞬間に、ガードを外す。

設計前に実測した（文書上ではなく実物の契約）:

- stdin: `{"tool_name": …, "tool_input": {…}}`
- 判定: **stdout の JSON** — `hookSpecificOutput.permissionDecision:
  "deny"` + `permissionDecisionReason`。プロセスはどちらでも exit 0
  （Claude Code には exit 2 + stderr の形式もある）。
- ガードは `tool_name` を読まず `tool_input.command` だけを見る — そして
  gem-agent の `shell_exec` の引数名も `command` なので、**組織のガードは
  gem-agent のペイロードで無改修で動く**。gem-agent 形のコールを実物の
  ガードに流して確認済み。

## Decision（決定）

### 1. `PreToolUse` のみ、gem-agent 自身の設定から

`config.toml` の `[[hooks.pre_tool_use]]` に `matcher`・`command`・
任意の `timeout_sec` を書く。Claude Code の他イベント（PostToolUse・
Stop・SessionStart 等）は実装しない: 需要が実証されているのは
PreToolUse だけであり、契機なき能力は死重である（ADR-0020 §5 の教訓）。
需要が現れれば同じ機構にイベントを足せる。

`~/.claude/settings.json` は**読まない** — ADR-0011 の原則を維持する。
org のインストーラにも触れない（オペレーターの指示）: 登録は gem-agent
自身の設定に同じスクリプトファイルを指す 1 ブロックを書くだけで、
drift する第二のコピーは生まれない。

### 2. フックは決定論的な床であり、モデルに告げる

フックはツールディスパッチの先頭、リスク階梯の前に走る: deny はモデル
層・自動承認・セッション allowlist のいずれでも覆せない — Block 床と
同格である。拒否理由はツール結果としてモデルに返す（ADR-0043 の原則:
書いた本人に告げない拒否は正直ではない）。これは Claude Code 上での
ガードの挙動そのものであり、理由文がモデルを準拠形へ誘導することは
実証済みである。

フックが守るのは**モデルのコール**である。オペレーター自身の
`!コマンド` エスケープは意図的に通さない: この制御はエージェントの
過失を捕まえるためにあり、オペレーターを縛るためではない。

### 3. 両方の判定形式。それ以外は警告つき fail-open

deny は 2 つの契約のどちらでも成立する: stdout JSON
（`hookSpecificOutput.permissionDecision: "deny"` または旧形式の
`decision: "block"`）、あるいは exit 2 + stderr。それ以外 — 非ゼロ
exit・解析不能な出力・タイムアウト — は**非ブロッキングの失敗**で、
コールは続行しオペレーターに警告が出る。Claude Code と同じ意味論で
あり（ドロップイン互換は失敗挙動も含む）、フォールバックツールが
壊れたガードスクリプトで自分を煉瓦化してはならない。フックは sandbox
外で走り（オペレーター設定は信頼済み。ガードは任意パスを読む必要が
ある）、短い既定タイムアウトを持つ。

### 4. matcher は両方の語彙を話す

matcher は完全一致のツール名・`|` 区切りの選択・`*`。gem-agent の名前
**と** Claude Code の別名（`shell_exec` ↔ `Bash`、`write_file` ↔
`Write`、`edit_file` ↔ `Edit`、`read_file` ↔ `Read`）の両方に一致する
ので、Claude Code 設定から写した hooks ブロックが改名なしで機能する。
ペイロードの `tool_name` は gem-agent の実名 — 組織のガードには無関係と
実測済みで、実際に読むスクリプトに対して正直である。

### 5. グローバル設定のみ

プロジェクト側フックは「クローンしたリポジトリが全ツールコール時に
任意コマンドを実行する」経路になる。v1 にプロジェクト面は存在しない。
将来足すなら `.mcp.json` と同じく ADR-0023 のプロジェクト信頼の内側に
置く。

## Consequences（帰結）

- 組織の削除規則と書き換えガードが、Claude Code が実行するのと同じ
  スクリプトファイルによって、フォールバック後も維持される。
- モデルの全ツールコールが matcher 比較 1 回を払い、一致したコールは
  プロセス起動 1 回を払う。不一致のコールのコストは計測不能な程度。
- 悪意ある・壊れたフックはすべてを拒否できる（DoS だが可視）が、何も
  承認はできない: 素通りは通常の階梯へ続くので、フックは常に締める
  方向にしか働かない。
- 設定リファレンスに `[hooks]` 節が 1 つ増える。設定パネルには何も
  出ない（フックに実行時トグルはない — セキュリティ制御であり、
  トグルはバイパスになる）。
