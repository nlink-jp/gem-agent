# ADR-0047: 承認対象コールに宣言された purpose — 「何を」だけでなく「なぜ」を運用者に見せる

| 項目 | 値 |
|------|-----|
| ステータス | **Accepted** |
| 日付 | 2026-08-26 |
| 対象 | gem-agent |
| 意思決定者 | nlink-jp メンテナ |
| 発端 | 運用者からの指摘: 一時ディレクトリへの `cp` の承認を求められた（おそらく Slack へ添付するためのファイル配置）が、その旨がどこにも出ていなかった。「無言で実行しようとしていたということか。理由は Think の方に出ていたのか」 |

## 背景

承認ダイアログは 3 つの問いのうち 2 つにしか答えていない。表示されるのは
ツール名、引数（`shell_exec` ならコマンド全文）、そして auto モードが
エスカレーションした場合はその理由である。つまり運用者には
**何が実行されるか**と**なぜ自分が訊かれているか**は伝わる。
**なぜエージェントがそれをしたいのか**は伝わらない。

自明なコールならこの欠落は見えない。しかし
`cp /some/report.csv /var/folders/…/T/x/` では、それが判断のすべてになる。
コマンド単体は無害そのもので、目的だけが完全に不明だからである。

動機が存在しないのではなく、到達できない。この端末に残る 45 本の
セッション記録を実測した:

| アシスタントターン | 件数 |
|---|---|
| 合計 | 413 |
| ツールコールを含む | 349 |
| うち **text パートも伴う** | **1** |
| テキストのみ（最終回答） | 64 |

Gemini 3 はツールを呼ぶとき、前置きを **text パートとしてはまず書かない**
（唯一の例外は `ask_user`＝人に話しかけること自体が仕事のツール）。
書き先は **思考サマリ** であり、思考テキストはこの実装では構造的に
一時的である:

- ADR-0033 により表示専用。transcript に保存するのは思考
  **signature** のみで、それがリプレイを実測した形状だから。テキストを
  戻すと次ラウンドが 400 で落ちる。
- ライブ表示の末尾は、ラウンドがツールコールで終わった瞬間に消去される
  （`model.go` の `case ToolCall`）。運用者がまさにそれを必要とし始める
  瞬間である。
- そもそも思考行は running フェーズでしか描画されない。承認ダイアログは
  別フェーズなので、一切表示されない。

結果として、運用者の席から見ればエージェントは意図について**無言**である。
さらに思考テキストは永続化されないため、事後に「なぜあれを打とうとしたのか」
を transcript から追うこともできない。**コールの意図が書き留められる場所が
システム内のどこにも存在しない。**

## 決定

**承認対象（Mutating）ツールはすべて必須引数 `purpose` を取る。運用者の
言語で、なぜ今このコールが必要なのかを一文で述べる。**

これは「モデルの出力を後から補正しない」という本プロジェクトの原則における
「書き方をモデルに教える」側の解決である。コマンドから意図を推定するのでは
なく、宣言する枠をモデルに与え、その宣言を人間に見せる。

### 1. 中央で注入し、`Mutating` でスコープする

パラメータはレジストリから `llm.ToolDef` を組み立てる箇所で付与する。
各ツール定義には書かない。組み込みツールと MCP ツールが同一の扱いになり、
ボイラープレートがツールファイルに散らず、新しく読み込まれた MCP サーバも
自動的に対象になる。

スコープは実行時のツールポリシーではなく静的な `Mutating` フラグとする。
公開するスキーマはセッション途中で変わってはならない。暗黙キャッシュ
（ADR-0018）のためにリクエスト前置がバイト一致で保たれる必要があり、
ポリシー変更は実行時イベントだからである。

### 2. `purpose` は gem-agent の欄であって、ツールの契約ではない

`Run` に渡す前に引数から取り除く。MCP サーバが自身のスキーマにない引数を
受け取ることはなく、組み込みツールもこの欄の存在を知らなくてよい。
一方で履歴と transcript には purpose を含む完全な引数が残る。それが
モデルが実際に出力したものであり、リプレイが要求する形だからである。

### 3. 自己申告は決して根拠にしない

purpose はコールを提案した当人が書いたテキストである。人間への表示にのみ
使い、それ以外には一切使わない:

- **リスク評価のペイロードから除去する。** さもなければモデル層が提案者
  自身の正当化を読んで説得されてしまう。ADR-0020 §4 がメモリ書き込みで
  拒否した「評価者＝提案者」の欠陥が、全承認対象コールに適用される形に
  なる。
- **ルール層に対して不活性。** `risk.Classify` は名前付き引数
  （`path` / `command`）しか読まない。purpose の追加が判定をどちら方向にも
  動かさないことをテストで固定する。
- **ループ検出シグネチャから除外する。** ループガードは引数の正規化 JSON を
  比較する。purpose を含めると、同一コールを繰り返しながら理由の文言だけ
  変えるモデルがガードを無効化できてしまう。

### 4. purpose 欠落は「可視化」であって「制裁」ではない

スキーマ上は `required` とする（それがモデルに必須と伝える手段である）が、
purpose なしで届いたコールもそのまま実行できる。ダイアログと監査イベントは
代わりに *(理由の申告なし)* と表示する。

コールを拒否すれば、最悪のタイミング（運用者が満たしようのない承認プロンプト）
で新しい失敗モードを発明することになる。しかも purpose は安全制御ではない。
欠落それ自体が情報である — 申告のない `cp` を見た運用者は、モデルが必須欄を
飛ばしたことを知る。

### 5. 表示先

- 承認ダイアログ: エスカレーション理由の上に、独立した強調行として
- 会話中の `⚙ tool` イベント行: 承認されて実行されたコールにも同じ痕跡が残る
- `tool.call` 監査イベント（ADR-0035）: 独立した `purpose` 属性として。
  後からログで追えるようにするため
- セッション transcript: 引数の一部として、追加実装なしに記録される

## 影響

- 承認対象コール 1 件につき短い文字列 1 つ分のトークンコスト。小さいが
  実在する。スキーマ変更により、アップグレード時に暗黙キャッシュが一度
  再ウォームする。
- 運用者は `⚙` 行の並びを、コマンドの羅列ではなく物語として読めるようになる。
- `purpose` はモデルが書いたものであり、誤り・曖昧・自己都合のいい表現に
  なりうる。**何のゲートにも使ってはならない** — §3 がその歯止めであり、
  慣習ではなくテストで固定する。

## 検討した代替案

**思考の末尾をスクロールバックに残す。** 表示層のみで安全（履歴は不変）、
かつ安価。ただし主たる解決としては却下した。思考サマリは冗長で、単一コールに
スコープされず、ダイアログのフェーズには出せず、transcript にも残らない。
独立した表示オプションとしては引き続き選択可能である。

**ツール呼び出し前に text で前置きを書くようプロンプトで指示する。**
実測: ツールコールを含む 349 ターン中 text パートは 1 件。Gemini 3 は前置きを
思考へ回すため、構造的な枠のない指示だけでは発火しない — メモリ保存が自発的に
起きなかったときに記録した「トリガのない能力は発火しない」と同じパターンである。

**コマンドから意図を導出する。** それはモデルの振る舞いに対する推論を
コード側で行うことであり、ADR-0043 が diagram 経路から撤去したのと同じ手である。
理由を知っているのはモデルなのだから、モデルに訊けばよい。
