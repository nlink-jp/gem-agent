# ADR-0052: ignore を理解するナビゲーション — walk はプロジェクトが無視するものをスキャンしない

| 項目 | 内容 |
|-------|-------|
| ステータス | **承認済み** |
| 日付 | 2026-08-28 |
| 適用対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | 運用者の現場報告: 小規模プロジェクトでは問題ないが、規模が大きくなるとファイルリスト取得・検索の頻度が増え、レスポンスが低下し、ノイズで対象特定の精度が悪化する — 下記の診断に対し「可能な限り外部依存は避ける方針」「対策できることはすべてやろう」。 |

## 背景

ADR-0013 は「プロジェクト規模なら逐次スキャンで十分 — 索引不要」と
いう前提で `list_tree` と `search_files` を出荷した。前提は正しかっ
たが、分母が違った。本ワークスペースの実 Tauri プロジェクト
(19,145 ファイル) で `nav.go` の walk を忠実に再現して実測した:

| | 現行 walk | 生成物ディレクトリ除外 |
|---|---|---|
| 時間 (warm cache) | 1.4 秒 | 10ms |
| 時間 (cold cache) | 27.7 秒 | 15ms |
| 内容スキャン対象 | 11,960 ファイル | 112 ファイル |
| `fn main` のマッチ | 7 件 (5 件は `node_modules` 内 README) | 2 件 (正解のみ) |

プロジェクト自身のファイルは **130 個 — walk がスキャンする量の
0.7%**。残る 99.3% は `node_modules`・`target`・`dist`・`build`、
つまりプロジェクト自身が `.gitignore` で「プロジェクトではない」と
宣言している依存物とビルド出力である。

被害の大きい方はレイテンシではない。walk はアルファベット順で、
`node_modules` は `src` より先に来る:

- `list_tree` の 800 エントリ上限は実測で **86% が生成物に消費**さ
  れ、walk は `node_modules/aria-query` の中で死に、`src/` も
  `src-tauri/` も一度も表示されなかった。1 コールでのオリエンテー
  ションが構造的に不可能 — モデルはサブディレクトリ指定で呼び直
  し、これが観測された「コール頻度の増加」そのものである。
- 頻出識別子の検索は 200 マッチ上限が依存物の中だけで尽き、プロ
  ジェクト本体のマッチが **0 件**になり得る。ツールは正直に「パ
  ターンを絞れ」と報告するが、絞った再試行も同じゴミを再スキャン
  する。

ADR-0013 のより深い却下はこの診断に影響されない: ripgrep 前提な
し・永続索引なし・embeddings なし。修正は「賢くスキャンする」で
はなく「プロジェクト自身がプロジェクトでないと言うものをスキャン
しない」である。

運用者は修正に 2 つの制約を置いた: 可能な限り外部依存を避ける
(`.gitignore` マッチャは import ではなく本リポジトリで実装する)、
そして対策できることはすべてやる (下記 3 部は相互補強するので同時
に出荷する — ゴミを飛ばすことで上限が意味を持ち、上限の再設計が
skip を可視化する)。

## 決定

### 1. 列挙 walk は 2 つの独立した層で ignore を理解する

`list_tree` と `search_files` (および同じレジストリを使う
`agentic_file_search` の子) は walk 中に以下を skip する:

- **組み込み層**: basename が既知の依存・ビルド出力名 (`node_modules`,
  `vendor`, `.venv`, `dist`, `build`, `target`, `__pycache__`,
  `Pods`, `DerivedData`, … — `internal/ignore` の 1 つの精選リス
  ト、ツール説明文に明記) であるディレクトリ。この層は git リポジ
  トリでないプロジェクトでも効く。
- **`.gitignore` 層**: gitignore(5) の完全な意味論 — ネストした
  `.gitignore`、否定、アンカー、`**`、ディレクトリ限定パターン、
  文字クラス、最終マッチ優先、深いファイル優先 — を新規モジュール
  依存なしで `internal/ignore` に実装する。ADR-0013 の「依存ゼロ」
  は実行時バイナリ (ripgrep) の話だったが、本 ADR では運用者の制約
  によりモジュール依存にも拡張する。マッチャは自前とし、git が使え
  る環境では `git check-ignore` を ground truth としてテストする。

2 つの層は独立: どちらの層も単独でエントリを skip でき、
`.gitignore` の否定は組み込み層の skip を復活させられない。脱出
ハッチはパターンではなく `include_ignored=true` (下記) である。

### 2. ignore がフィルタするのは列挙だけ — 明示パスは常に到達可能

`read_file`・`file_info`・`view_image`・`read_document`・
`edit_file` など明示パスを取るツールは一切変更しない。敵対的また
は広すぎる `.gitignore` がファイルを隠せるのは*発見*からだけで、
名指しの読み取りからは決して隠せない。フィルタを無言にしないため
の 3 つの正直規則:

- **skip は必ず報告する。** ignore されたディレクトリはツリーに
  `name/ [ignored]` として現れる — 中身がノイズでも存在自体は情報
  である (「このプロジェクトには `node_modules` がある」)。両ツー
  ルとも、何を ignore したかとそれを含める引数名を集計行で報告す
  る。
- **`include_ignored=true`** は両ツールでその 1 コールの両層を無
  効化する。
- **ignore された領域の中を root とする walk は全部見せる。** 呼
  び出し側が明示的に `path=node_modules/foo` を渡したなら意図は
  そこを見ることであり、walk 全体を ignore して空の結果を返すの
  は不可解なだけである。この場合は層を無効にして進み、その旨を出
  力する。

セキュリティ注記: リポジトリの `.gitignore` は walk を操縦するリ
ポジトリ作者のデータである。できるのは列挙からの*隠蔽*だけで (実
行も持ち出しもできない)、隠蔽は出力内で報告され、名指しの読み取
りはバイパスする。残余リスク — 敵対的リポジトリがファイルをカジュ
アルな発見から隠す — は防御せずここに記録して受容する。同じ攻撃
者はファイルを `x.png` と名付けるだけで列挙ヒューリスティックを
無効化できるからである。

### 3. `search_files` の出力は「最初の 200 行」ではなく「どこにあるか」に答える

- **ファイルごと上限**: 1 ファイルにつき最大 5 マッチ行 + `… +N
  more in this file`。グローバル 200 行上限は最悪 1 ファイルでは
  なく 40 ファイル以上に行き渡り、上限に達した結果もアルファベッ
  ト先頭ではなく分布を運ぶ。
- **`include` フィルタ**: gitignore 構文のパターン (同じコンパイ
  ラ・同じ意味論・walk root にアンカー) で内容スキャンする*ファイ
  ル*を限定する — `include="*.go"`、`include="src/**"`。ディレク
  トリの walk 自体は行う。
- **`mode="files"`**: ファイルごとの件数のみ (`path (N matches)`)、
  マッチ行なし — 「この識別子はどのファイルにあるか」という問いに
  最小トークンで答える。説明文は広い検索をここから始めるようモデ
  ルを誘導する。
- 表示の有無に関わらず総マッチ数を要約に報告する — 上限に達した結
  果も、切ったものの真のサイズを述べる。

### 4. `list_tree` の予算はグローバルではなくディレクトリごと

- **ディレクトリごとの省略**: 1 ディレクトリにつき最大 50 エント
  リ表示 + `[+N more entries]`。巨大ディレクトリ 1 個が後続の兄弟
  を飢えさせられなくなる。グローバル 800 上限はバックストップとし
  て残る (もはや滅多に到達しない)。
- **`dirs_only=true`**: ディレクトリのみ、各ディレクトリのファイ
  ル数注記つき — 大きなツリーのオリエンテーションが 1 画面で済む。
- `list_files` (単一ディレクトリ・非再帰) は問題の一部ではないが、
  同じ ` [ignored]` 注記を得る — モデルが降りる前に降りないことを
  学べるように。

### 5. 却下を維持するもの

- **永続索引 / trigram 索引**: ADR-0013 の却下は生きている。鮮度
  不変条件 (エージェントはセッション中にファイルを編集する) に加
  え、上記実測 — ゴミを飛ばせば warm 10ms — で索引が稼げるものが
  残らない。
- **ripgrep**: 挙動が 2 つになる実行時依存フォールバックのまま。
  却下継続。
- **並列 walk**: ignore 後は実測で不要 (19k ファイルのプロジェク
  トで warm 10ms)。真のモノレポ (プロジェクト本体 10⁵ ファイル
  超) で痛んだら実測してから再訪する。投機的に作らない。
- **組み込みリストの config 面**: 新キーなし。もっと ignore した
  いプロジェクトは自分の `.gitignore` に書く (それは同ファイルを
  読む他の全ツールも直す)。組み込みリストは `.gitignore` を持たな
  いプロジェクトを覆う。

## 帰結

- 実測プロジェクトでは: `list_tree` 1 コールでオリエンテーション
  (上限に触れない)、検索は約 10ms でプロジェクトファイルのみが
  マッチし、モデルは 690 エントリの代わりに `node_modules/
  [ignored]` を見る。
- `agentic_file_search` の子はすべてを継承する — 10 ラウンド予算
  が大規模プロジェクトでも 10 回の*有効な*コールを買う。
- 各ナビゲーションツールに引数が 2 つ増え、gitignore マッチング
  (約 200 行 + テスト) の保守が増える。マッチャは gitignore(5) が
  定義する構文について `git check-ignore` に対して検証済み。後日
  見つかる乖離は我々のマッチャのバグであり、それを証明するテスト
  は `internal/ignore` に置く。
- 生成物ディレクトリを持つプロジェクトでは結果が縮小・並び替えに
  なる。旧バージョンのトランスクリプトの resume は問題ない (ツー
  ル結果はデータでありスキーマではない)。

## 修正

- ADR-0013 の前提句「索引なし — プロジェクト規模なら逐次スキャン
  で十分」を「…*プロジェクトの*逐次スキャンで十分」に修正する。
  同 ADR のステータス行は本 ADR を指す。
