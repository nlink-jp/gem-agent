| Triggered by | オペレータ:「ツリー構造のファイルリスト取得ツールがあるとよい。可能なら高速検索も — RAG までは要らない、高速 grep 検索みたいなもの」 |

## Context

モデルの探索手段は `list_files` だけで、1 回につき 1 ディレクトリしか見えない。
未知のリポジトリでの方向づけはディレクトリごとに 1 ラウンドかかり、何かを
**探す**にはファイルを丸ごと読むしかない — コンテキストウィンドウで支払う、
考えうる限り最も高価な grep である。Claude Code の対応物（Glob・Grep）は
セッションが最も頼るナビゲーション道具だが、フォールバックにはどちらも無い。

上限はオペレータの表現が明確に引いている: RAG ではない、索引も埋め込みも
要らない — 高速 grep。

## Decision

読み取り専用の組み込みを 2 つ。どちらも他のファイルツールと同じくプロジェクト
封じ込め、どちらも依存ゼロ（純 Go — バックアップツールが「必要になった日」に
ripgrep という前提条件を獲得していてはならない）。

1. **`list_tree(path?, depth?)`** — サブツリーの再帰リスト。インデント表示、
   ディレクトリは `/` 付き。VCS 内部（`.git`・`.hg`・`.svn`）はスキップし、
   ツール説明文に明記する — あれは配管であってプロジェクトの内容ではない。
   それ以外は明示的な上限（エントリ数・深さ）まで全部見せ、上限に当たったら
   「何が残っているか」と「どう見るか」（サブディレクトリを渡す）を印字する —
   組織の教訓どおり、無言の切り詰めはしない。
2. **`search_files(pattern, path?, literal?)`** — サブツリー横断の正規表現
   検索（Go 構文）。結果は `path:line: text`。`literal` は「構文ではなく
   文字列そのもの」を意図するモデル（とオペレータ）のためにパターンを
   エスケープする。バイナリは内容判別でスキップ、過大ファイルと VCS 内部も
   同様。マッチ上限に当たったら報告する。逐次スキャンとする — プロジェクト
   規模なら純 Go の grep は数ミリ〜数十ミリ秒であり、索引は RFP のスコープが
   望まない「無効化問題つきキャッシュ」である。
3. **どちらのツールも symlink を辿らない** — リンクを辿る walk は、パス単位の
   検査が見ることのないリンク経由でプロジェクトを出られる。プロジェクト内の
   特定 symlink を読みたければ従来どおり `read_file`（解決後パスの封じ込め
   検査つき）を使う。

## Consequences

- 方向づけが「ディレクトリごとに 1 ラウンド」から 1 コールに、検索が
  「全部読む」でなくなる。ここでは二重に効く — 各ラウンドは履歴全体
  （画像込み）を再送するので、**ラウンドを減らし小さくすることがこのツールに
  ある最安の最適化**である。
- プロンプトのツールが 2 つ増える（組み込み 8 個）。working-style の指針で
  誘導する: `list_tree`/`search_files` で探し、特定できたファイルを
  `read_file` する。
- 索引が無い = 鮮度問題もビルド手順も無い。コストは毎回の再スキャンだが、
  プロジェクト規模では実測上それが正しいトレードである。

## Alternatives considered

- **ripgrep があればシェルアウト** — 却下。任意依存を持つフォールバック
  ツールは挙動が 2 つになり、訓練はそのうち 1 つしか鍛えられない。
- **埋め込み / RAG 索引** — 依頼文の中でオペレータ自身が却下済み。
- **`list_files` に再帰フラグを足す** — 却下。フラットとツリーでは欲しい
  上限も形式も違い、モデルはツールを名前で選ぶ。モードスイッチより
  2 つ目の名前のほうが明確。
- **`.gitignore` の尊重** — 現時点では却下。正しい gitignore 意味論は
  それ自体が 1 プロジェクトであり、オペレータに見えるファイルを黙って
  隠すのは「なぜ X が見つからないのか」を招く。実用上は上限 +
  サブディレクトリ絞り込みで node_modules 問題は足りる。
