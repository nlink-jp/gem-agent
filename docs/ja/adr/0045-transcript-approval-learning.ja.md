# ADR-0045: トランスクリプト駆動の承認ルール学習 — `/learn` が提案し、オペレータが決める

| 項目 | 値 |
|------|----|
| Status | **Accepted** |
| 日付 | 2026-08-26 |
| 適用対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | オペレータ: auto モードは固定化された評価で動いている — オペレータの判断履歴からフィードバック学習できないか？ レビューで方向が確定: ルールセットはプロジェクト単位で構築する（逆は危険）、学習は記録済みトランスクリプトに対する明示的な `/` コマンドとして実行し、ルールを提案する。追撃: MCP 呼び出しに対するモデル層の判定が目に見えてブレており、同等の摩擦源である |

## Context

auto 承認ラダー（ADR-0004）は固定である: 純粋関数のルール層
（Safe/Review/Block）、Review のみ諮られるモデル層（approve ∧
confidence ≥ 0.8）、そして人間のゲート。ADR-0038 が唯一の適応要素
（今ターンのタイプ入力を証拠として同乗）を足したが、ラダー自体が経験
から形を変えることはない。オペレータは `go test` への同じ質問に、
100 回目も同じ `y` で答えている。

MCP 呼び出しは摩擦のもう半分であり、オペレータが直接報告して
いる: ルール層はすべての `mcp__` 呼び出しを Review に分類する
（効果はルール層には未知）ため、毎回モデル層に乗る — そしてその
判定がブレる。同じ lookup ツールがある呼び出しでは自動承認され、
次ではエスカレートされる。オペレータに予測できないエスカレー
ションは 100 回目の `go test` プロンプトと同種の摩擦であり、
調査チェーンの途中に割り込む分だけ性質が悪い。

フィードバックチャネルは存在するが、どれも 1 回の判断しか運ばない:
`a`（セッション allowlist）、`p`（永続 per-tool ポリシー、ADR-0009）、
手書きの ADR-0008 テーブル。オペレータが実際に何を判断したかの蓄積
— 数十セッション分 — は、書き込まれるだけで読まれていない。

学習設計を規定する構造的事実が 2 つある:

**信号は片側にしかない。** 人間の判断はエスカレートされた呼び出しに
しか付かない。誤った自動承認は訂正信号を一切生まない。したがって
この履歴からの学習は過剰エスカレーション（摩擦）の削減にしか使えず、
安全側を改善することはできない — そして劣化させてはならない。

**ラベルは信頼できるが、呼び出しは信頼できない。** 判断そのもの
（y/n）はオペレータ入力であり、prompt injection 攻撃者が書けない
唯一のチャネルである（ADR-0038 の議論）。しかし判断対象の呼び出しは
モデルが作文したもので、ツール出力の影響を受ける。決定論的な等価
より緩いマッチングは、敵対的な呼び出しを「承認済みパターン」に
偽装する経路を攻撃者に渡す。

トランスクリプトが現に保持しているもの（現行コードで実測）:

- **拒否**: tool ロールメッセージの `Content` が `deniedResult` 定数
  と完全一致。フックによる拒否は `denied by a pre-tool hook: ` の
  接頭辞で区別でき、除外する — オペレータの判断ではない。
- **auto モードの判定**: `auto_decision` 診断記録（name, approved,
  tier, reason, model）。これが承認した呼び出しはラダーの判断で
  あってオペレータの判断ではなく、承認カウントから除外する。
- **オペレータの承認**は 2 つの形をとる。`approved=false` の
  `auto_decision` 記録に実結果が続くもの: ラダーがエスカレートし
  オペレータが yes と答えた — MCP のブレそのものの形であり、最も
  強い証拠クラス。そして `auto_decision` 記録の無い実結果付きの
  変更系呼び出し（非 auto モード）— こちらは `y`・セッション
  allowlist・当時有効だった `"never"` ポリシーが遡及的に区別でき
  ない。§7 が今後の曖昧さを除去する。過去分については現行ポリシー
  との重複排除で緩和する。

## Decision

### 1. `/learn` — オペレータ起動のみ、常駐しない

学習はオペレータが `/learn` を打ったときだけ走る。コマンドは
**このプロジェクトのトランスクリプトのみ**を走査し（ADR-0022 の
配置 + ヘッダがこのプロジェクトを名指す旧フラットファイル）、
オペレータの判断を集計し、ルール提案を 1 件ずつの確認に掛ける。
提案が受理されるまで何も変わらない。

挙動を黙って変える常駐学習器は、監査不能な緩和チャネルになる —
ADR-0008 の非対称原則（締めるのは自由、緩めるのはオペレータの明示
的行為）が防いでいるものそのものである。すべてのルールの作者が
オペレータであり続けることは制約ではなく設計である。

### 2. 決定論的抽出 — モデルにトランスクリプトを読ませない

学習パスは構造化された記録だけを解析する: ツールコールの名前と
引数、定数との完全一致で照合する tool ロールの結果、そして
`auto_decision` 記録。トランスクリプトの本文をモデルに渡すことは
決してしない。

トランスクリプトは攻撃者が影響できる散文 — ツール出力・ファイル
内容・Web ページ — に満ちている。それを読んだモデルにポリシーを
提案させる構成は、prompt injection からポリシーへのパイプライン
であり、ADR-0020 §4 がメモリについて塞いだ永続化経路を一段上に
作り直すことになる。決定論的集計は構造的に免疫を持つ — 重みを
持つ入力はオペレータ自身の記録された判断だけである。

### 3. 集計キーは構文上の事実

- **シェル以外のツール**（MCP 含む）: ツール名 — ADR-0008 の語彙
  そのもの。引数は意図的にキーへ含めない: lookup 型ツールの
  リスクはツールが何をするかに宿るのであって、どの指標について
  問われたかには宿らない。
- **`shell_exec`**: コマンドキーは第 1 トークン。第 2 トークンが
  サブコマンド形（`^[a-z][a-z0-9-]*$` — フラグでもパスでもない）の
  ときに限り連結する。`go test`・`make build`・`git status` は
  2 トークンを保ち、`ls -la` と `touch newfile.txt` は先頭語に縮む。
- 平明でないコマンドには **学習時もマッチ時もキーを導出しない**:
  複数セグメント（`|`, `;`, `&&`, `||`, `&`）、動的構築（`$(`、
  バッククォート、`${`、`eval`）、あらゆるリダイレクト。2 トークン
  を名乗るキーは実行内容の全真実でなければならない
  （agent-skeleton の知見）。学習器とマッチャは 1 つの導出関数を
  共有し、乖離できない構造にする。
- 実装で追加した除外 2 つも同じ理由による: パス区切りを含む head
  （`./deploy.sh`・`/usr/local/bin/make`）は**ファイル**を名指し、
  その中身はキーが何も語らないまま変わりうる（素の名前はオペレータ
  自身の PATH で解決される）。環境変数代入プレフィックス
  （`FOO=bar make build`）はキーに現れないままコマンドの動作を
  変える。

意味的・曖昧な類似は明確に却下する: §Context が警告する「緩い
マッチング」そのものである。

### 4. 新語彙: コマンド単位ポリシー、プロジェクトスコープ限定

機械所有 `policy.toml` の `[projects."<path>".commands]` がコマンド
キーを `"never"` / `"always"` に対応づける — ADR-0008 と同じ 2 語
であり、第 3 の語彙は作らない。意味論も ADR-0008 と同一:

- `"never"` は全モードでゲートとモデル層を飛ばすが、ルール層の
  Block の床は**持ち上げず**、pre-tool フック（ADR-0044）は
  引き続き最初に走る。
- `"always"` は締める側の床: 全モードで必ず聞く。
- §3 の平明性検査に落ちるコマンドはどのルールにもマッチせず、
  通常のラダーを通る。

2 つのテーブルは `Policy.ForCall` で順に 2 つの規則によって合成
される。**どちらかの `"always"` が勝つ**: `shell_exec = "always"` を
指定したオペレータは「すべてのシェルコールを自分が見る」と述べて
おり、学習ルール —「繰り返し承認した」以上の意味を決して持たない —
がそれを取り消してはならない。逆向きに、学習された `"always"` は
包括的な `shell_exec = "never"` を締める方向なので自由である
（ADR-0008）。**それ以外はコマンドエントリが答える**。この呼び出し
についてより特異的な言明であり、エントリはオペレータが確認した
からこそ存在する — どちらに転んでもオペレータの決定である。

**グローバルの commands テーブルは意図的に存在しない**（オペレータ
指示）。あるリポジトリで `make build` が安全であることは別のリポ
ジトリについて何も語らない。信頼済みプロジェクトで学習された
`"never"` がグローバルに適用されれば、次の敵対的 clone の中で
自動実行される。ツール単位のグローバルポリシー（ADR-0008）は
不変。

この語彙は機械所有 `policy.toml` のみに置く。手書き `[approval]`
テーブルへの拡張は需要が実証されてからでよい — 契機なき能力は
死重である（ADR-0044）。

### 5. 提案閾値 — v1 は定数、セッション単位で数える

**票は呼び出し単位ではなくセッション単位で数える。** 初稿は
「承認 ≥ 5 回・≥ 2 セッション」としていたが、実装の過程で、
セッション allowlist（`a`）が 1 打鍵を任意の回数の承認に変えて
しまうことが表面化した — 5 件の「承認」がオペレータの 1 回の判断
でありうる。同一セッション内でのコマンド反復も、allowlist 無しで
同じ増幅を起こす。各セッションをキーと結果ごとに 1 票へ畳むこと
で両方が消え、allowlist とタイプされた `y` を区別する新しい配管も
要らない。

- `"never"` の提案: **≥ 3 の別セッションで承認・どこにも拒否なし**
  で、記録された実例が現在 Block に分類されないキー。
- `"always"` の提案: **≥ 2 セッションで拒否**されたキー — 締める側
  は低いハードルでよい（Block パターンの精神: 寛大なマッチの代償は
  プロンプト 1 回）。
- 提案しないもの: `save_memory` / `delete_memory`。リスクが
  呼び出しごとの内容に宿る場所では頻度は証拠にならない — 無害な
  保存 12 回は 13 回目について何も語らない（ADR-0020 §4）。
  コマンドキーは意味論の安定した呼び出しを束ねるが、メモリ書込は
  その正反対である。
- MCP の提案に意味論フィルタは掛けない: 学習器には lookup（リスク
  はツール単位）とメッセンジャー（リスクは呼び出し単位）の区別が
  つかない。その判断こそ確認ステップがオペレータに問うものである
  — どの分類器とも違い、オペレータはそのサーバが何をするかを
  知っている。これは ADR-0008 の元々の根拠の適用である: ポリシー
  テーブルはオペレータだけが知っていることを書き込む場所である。
- スキップするもの: いずれかのスコープの現行ポリシーが既に覆う
  キー、および記録された実例が Block に分類されるキー（`"never"`
  はその床を持ち上げないので、ルールが何も変えない）。

初稿はルール層 Safe のキーも「摩擦がない」として除外していた。
これは auto モードを前提とした仮定だった: auto オフではSafe 層の
コールもゲートに届き、オペレータがそれに繰り返し答えていることこそ
本機能が除去する摩擦である。よって削除した。

閾値は config でなく定数: 調整が必要だという証拠はまだなく、ここに
つまみを付けることは「どれだけ気前よく承認を手放すか」につまみを
付けることになる。

### 6. 確認: 証拠を見せ、ルールごとに 1 判断

各提案は証拠 — 承認/拒否カウント・セッション数・オペレータが既に
見て承認した実例呼び出し 2〜3 件、そしてそのキーをラダーが歴史的に
どう扱ったか（ルール層・モデル承認/エスカレート数）— とともに
表示する。最後の行がブレを可視化する: 「モデル層 承認 12・エスカ
レート 9」は、呼び出しごとの判定を決定論的ルールで置き換える根拠
そのものである。MCP の提案にはさらにツールの現在の
self-description をクリップして表示する（ADR-0046 §4）—「lookup
かメッセンジャーか」を判断するオペレータが記憶から思い出す必要は
ない。回答は承認ダイアログの操作文法で y/n を取る。受理された提案は `MutatePolicyFile` 経由で
書き込まれ即座に有効化される。`/settings` には `policy.toml
(project)` の出所付きで表示され、他のエントリと同様に編集・削除
できる。

### 7. `gate_decision` 記録が今後の学習を正確にする

既存のテレメトリ送出と並べて、エージェントは `gate_decision` 診断
記録をトランスクリプトに書く: ツール名・判断・`must_prompt`・
**集計キー**・証拠用のクリップ済み `detail`。`auto_decision` にも
キーを載せる。`Load` は未知の kind を既に読み飛ばすためスキーマ
更新は不要で、どちらの記録も診断面であり resume には見えない。

キーを後から導出せず記録するのは 2 つの理由による。学習器は判断を
呼び出しへ対応付ける必要がなくなる — 1 ラウンドに複数コールがある
場合、その対応付けはまさに黙って間違う種類の位置推測である。そして
将来のビルドが導出するキーが過去の判断を遡って読み替えることも
できない: 記録は「このビルドが何にマッチさせたか」を語る。

この記録はタイプされた `y` とセッション allowlist を**区別しない**
し、その必要もない: §5 のセッション単位の計数が、1 回の 'a' と
複数回のプロンプトの差を既に消しているからである。過去分は
§Context の復元で補い、この記録が蓄積するほど精度が上がる。

### 8. 宣言された purpose はこのどれにも関与しない

ADR-0047 により、ゲート対象の全コールがモデル作文の
`gem_agent_purpose` を持つ。コマンドキー導出の前に除去され（実行
内容の一部ではない）、集計されず、§6 の証拠にも表示しない。
「このコマンドは聞かなくてよいか」の証拠は、何が走るかとオペレータ
がどう答えたかであって、提案者による「なぜ欲しかったか」の弁ではな
い。恒久ルールを求める場でモデル作文の正当化を並べることは、
オペレータの判断を記録するために存在する決定に提案者の声を
持ち込むことになる。

## 却下した代替案

- **常駐学習 / 自動閾値調整** — 承認挙動を黙って緩めることは
  ADR-0008 の非対称原則に反し、「自己承認は防御ではない」という
  v0.39.0 の教訓の再演になる。
- **モデル層への履歴証拠注入**（ADR-0038 の型に過去の判断を
  載せる）: 適応が暗黙的で監査しにくい。オペレータは明示的で
  点検可能なルールを選んだ。コマンドルールのカバレッジが不足と
  判明したら将来の ADR として再訪しうる。
- **意味的類似マッチング** — 毒入れ面である（§3）。

## Consequences

- 摩擦が減るのはオペレータが既に繰り返し票を投じた場所だけで、
  真に新規のコマンドは引き続き聞かれる。その境界こそが狙いである。
- 学習されたルールは通常のポリシーである: 出所付きで可視・削除
  可能・Block の床と pre-tool フックに従属する。
- 走査は記録を部分デコードし（まず kind、次に必要なフィールド
  のみ）、添付ペイロードを読み飛ばす — base64 画像だらけの
  トランスクリプトも安価に済む。
- 過去分の不正確さ（y か allowlist か当時のポリシーか）は
  §Context に明記し、ポリシー重複排除で緩和し、`gate_decision`
  の蓄積とともに減衰する。
- テスト: キー導出テーブル（§3 の全除外を含む）、合成トランスク
  リプトに対する抽出、学習器/マッチャ共有関数、閾値ロジック
  （セッション単位の畳み込みを含む）、学習ルールのゲート側効果
  （ゲートを飛ばす・キーに限定される・Block 床を持ち上げない・
  複合行にマッチしない）、ポリシー書込経路。
- サーフェスの機構: TUI では `/learn` はスラッシュコマンドでは
  なくターンのように走る。ダイアログは Bubble Tea のイベント
  ループで応答され、同期スラッシュハンドラからそのループを呼ぶと
  unbuffered channel でデッドロックする — よって `/compact` の形
  （非同期スターター・完了は `TurnDone`）を取る。素の REPL は
  ディスパッチする goroutine が stdin を所有しているのでインライン
  で走る。`-p` では到達不能であり、これは §1（聞く相手がいない）と
  一致する。
- E2E 実測（隔離 `GEMAGENT_STATE_DIR`・実バイナリ・pty）: `go test`
  を承認する 3 セッションを仕込むと提案 1 件が生成され、ダイアログ
  が証拠つきで表示され、受理すると
  `[projects."…".commands] "go test" = "never"` が書き込まれ、
  新しいセッションではモデルの `go test ./...` が
  **`gate_decision` 記録を一切残さずに**実行された — ゲートが一度も
  諮られていない。実オペレータのポリシーファイルは終始無傷。
- 検証上の教訓: 最初の E2E は失敗を報告したが、その expect パターン
  （`approval`）がダイアログではなくバナーの "approval policy:" 行に
  マッチしていただけだった。判定はトランスクリプトに
  `gate_decision` 記録が無いことへ書き換えた — 画面文字列ではなく
  ground truth で判定する。
