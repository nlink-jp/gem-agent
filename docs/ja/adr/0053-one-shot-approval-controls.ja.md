# ADR-0053: 単発モードの承認制御 — `--auto` と `--allow`

| 項目 | 内容 |
|-------|-------|
| ステータス | **承認済み** |
| 日付 | 2026-08-29 |
| 拘束対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | 利用者: ヘッドレスの Slack 読取→要約→投稿パイプラインが単発モードの一律拒否で止まった。リスク階梯は一度も走らず、`[agent].auto_approve` は `-p` で黙って無視されていた |

## 背景

単発モード（`-p`）は承認者として `denyGate` を配線する: ゲート対象の
コールは全部拒否される。プロンプトに答える者がいないからで、ここまでは
文書化されていた。文書化も記録もされて**いなかった**のは、単発モードが
auto-approve も強制無効化していたこと — `cmd/root.go` の
`AutoApprove: cfg.Agent.AutoApprove && !oneShot`、コメントのない
連言 1 つ。ADR-0004 の階梯（ルール分類器 → モデル評価 →
エスカレーション）はヘッドレスでは一度も走らず、TUI の auto なら
通るコールがパイプラインでは一律拒否され、`auto_approve = true` と
書いた設定は黙って `false` を意味していた。

階梯自体はヘッドレスで走らせるのに再設計を要しない。終端状態
「人間へエスカレート」は、人間がいなければ「拒否」に退化する —
fail-closed であり、ADR-0004 が**対話用に**緩めた「危険層は自動拒否」
の形そのもの。対話では目の前の人間にプロンプトを出すべきだから
緩めたのであって、ヘッドレスには緩める相手がいない。すべての床
（Block 層・`"always"` ポリシー・pre-tool フック）は既に
`mustPrompt` に落ち、deny gate はそれに「no」で答える。

これとは別に、ADR-0008 の `"never"` ポリシーで読み取り専用 MCP
lookup は既にパイプラインで使える — だがそれは**常設**の付与でも
ある: すべての対話セッションでもゲートが外れ、egress 能力のある
ツール（例えば Slack への投稿）への恒久・無確認の付与は、まさに
ADR-0017 の理屈が警告するものだ。欠けていたのは**1 回の起動と同じ
寿命**を持つ付与。

ADR-0049（`/learn` 撤収）が緩和機構の基準を定めている: 列挙する・
wildcard で買わせない・付与した場所で可視・書くコストは設計の一部
（熟慮は明示的行為に宿る）。

## 決定

### 1. `--auto` が単発モードで ADR-0004 の階梯を武装する

`gem-agent -p "…" --auto` は変更系コールを通常の二層評価に通す。
承認は TUI と完全に同じ（Safe はルール層、Review はモデル層 +
confidence ≥ 0.8）。それ以外 — エスカレーション・Block 層・
`"always"` ポリシーのツール — は deny gate に落ち、**階梯の理由を
stderr に添えて**拒否される。

`[agent].auto_approve` は単発モードで引き続き無視される。今回からは
意図的にだ: 無人実行の付与は**起動そのもの**（スクリプトや cron に
見えるコマンドライン）で可視でなければならず、起動地点から遠い常設
ファイルの中ではいけない。ADR-0004 の「一次防御の弱体化は意図的な
opt-in でなければならない」を、ヘッドレスでは「起動ごとの opt-in」
に拡張する。

対話モードの `--auto` は単にセッションを auto モードで開始する —
config キーや shift+tab と同じことで、`/settings` に flag 出所で
記録される。

### 2. `--allow` は実行 1 回分の `"never"` エントリを付与する

`--allow "名前"`（繰り返し可・カンマ区切り可）は `[approval.tools]`
とまったく同じ語彙 — ツール名の完全一致、または `mcp__server__*` の
ような末尾 wildcard 前置 — を取り、各エントリをこの実行に限った
`"never"` ポリシーとして注入する。

エントリは**グローバルスコープに flag 優先順位で**合流する
（flags > 機械所有 policy ファイル > 手書き config — config 系が
既に宣言している順序）。そこから先は ADR-0008 の解決規則がすべて
無変更・自動で効く: プロジェクトの `"always"` 締めはスコープ優先で
勝ち続け、Block 床は持ち上がらず、pre-tool フックは拒否し続け、
単独の `"*"` は引き続きハードエラーで、`/tools` は実効結果を表示
する。床が知らない並行バイパス機構は存在しない。

フラグは全モードで効く（1 フラグ 1 意味論）が、存在理由は `-p`
のため: 対話セッションには既により豊かな道具（`a`・`p`・
`/settings`）がある。

### 3. deny gate は自分を説明する

`denyGate` は渡された理由 — 階梯エスカレーションの原因・Block
判定 — を印字するようになり、汎用の「mutating tools are disabled
in one-shot mode」行だけではなくなった。汎用行は救済策として
`--allow` と `--auto` を名指す。拒否で終わったパイプラインこそ、
運用者が stderr から実行を再構成するケースそのもの（ADR-0047 §5）。

### 4. テレメトリは実効の auto 状態を報告する

`SessionStart` は `[agent].auto_approve` の生の config 値を報告して
いたが、単発モードは実効値を強制 OFF にしていた — auto が武装
され得ない実行で「武装済み」を主張する監査イベント。セッションが
実際に走る値を報告するよう修正（この ADR の配線を読んでいて発見。
正直な報告の規則は ADR-0009 のもの）。

## 検討した代替案

- **`-p` で `[agent].auto_approve` を尊重する** — 却下: 無人の
  auto 承認を武装する常設 config 行は起動地点で不可視。付与は起動に
  属する。
- **ポリシー層の外に別のallowlist機構** — 却下: すべての床
  （Block・プロジェクト締め・フック・`"*"` 禁止）を再実装する必要が
  生じ、漏れ 1 つがバイパスになる。flag エントリは既存のポリシー
  構築にコンパイルする。
- **両フラグを単発モード限定にする** — 却下: 1 つのフラグ語に
  モード依存の 2 挙動（エラー vs 効果）はコストが均一意味論を上回る。
  対話では単に冗長なだけで有害ではなく、出所表示面（`/settings`・
  `/tools`）に映る。
- **ヘッドレスは「Safe 層のみ」の auto 変種**（モデル層スキップ）
  — 却下: 階梯はヘッドレスでも既に fail-closed で、第 2 の評価形は
  ADR-0004 のテストが固定する挙動行列を倍にする。

## 帰結

- Slack パイプラインの形はリスク許容度に応じて 3 通りで表現できる:
  読み取り専用 lookup には常設 `"never"`（ADR-0008）、列挙した
  実行単位付与には `--allow`、確率的な一般解には `--auto` — 最後の
  形では Review 層の唯一の裁定者がモデル評価器になる。どれに手を
  伸ばすべきかは approval ドキュメントが述べる。
- egress ツールを付与した `-p --auto` で非信頼コンテンツを読むのは
  運用者の明示的・可視の選択 — 対話 auto モードと同じ injection の
  計算から、見ている人間を引いたもの。
- 単発モードの stderr に `[auto-approved …]` 行が加わる（既存の
  素 REPL コールバックがそこでも発火する）。パイプラインの監査痕跡
  に、拒否だけでなく階梯が通したものも残る。
