# ADR-0019: 利用状況の会計と /usage

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-20 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | オペレータ:「/usage コマンド（モデルの利用状況やキャッシュの消費状況）があるとよいかもしれない」 |

## Context

ADR-0018 は「測ってから信じる」を約束し、フッターに数字を 1 つ出した。だが
セッション全体の支出は散在している: メインループの usage はログの `usage`
記録に、要約器は `summary_usage` に、Web 呼び出しはそもそもトークン数を
記録しておらず、そして最悪なのはリスク評価のトークンが**メインループと同じ
フッターコールバックに流れ込む**こと — リスク検査が一瞬「ctx」計を自分の
プロンプトサイズで踏み潰す。フッターは一瞥用であり、セッションの会計には
明細書がふさわしい。

## Decision

1. **カテゴリ別会計をメモリ上に。** エージェントが mutex 付き `UsageStats`
   を持つ: メインループのラウンド数・prompt・output・thoughts・cached、
   直近コンテキストと既知ウィンドウ。リスク評価と圧縮は別バケット。
   側呼び出しは**フッターコールバックへ流すのをやめる** — ctx 計は常に
   メイン会話を意味するようになる。自前バックエンドでトークンを使うツール
   （summarize_file・web_search・web_fetch）は cmd 側の集計簿が持ち、
   その LLM 層は結果と並んで usage を返すようになる。
2. **`/usage` が明細書を描画する**: カテゴリごとに呼び出し/ラウンド数・
   prompt（メインループはキャッシュ率つき）・output・thoughts、現在の
   コンテキスト対ウィンドウ、トークンを使ったモデル名つきのツール別行。
   プレーンテキストで、TUI でも素の REPL でも同じに動く。
3. **正直な一行をレポート自体に印字する**: キャッシュ済みトークンは割引
   価格で課金される — キャッシュが節約するのはコストとレイテンシであって
   ウィンドウではない。/usage は ADR-0018 の測定を逸話でなく点検可能に
   保つために存在する。
4. ログ解析ではなくメモリ内: 永続記録はトランスクリプトのままだが、表示
   コマンドが整数の足し算のために base64 画像で数 MB になりうるセッション
   ファイルを読み直すべきではない。

## Consequences

- 「このセッションはいくら使い、キャッシュは効いているか」がコマンド 1 つ。
- auto-approve の連続中にフッターの ctx 計が嘘をつかなくなる — カテゴリ分け
  から転がり出た小さな正しさの修正。
- Web ツールの usage が初めて可視になる（従来その LLM 呼び出しは何も報告
  していなかった）。

## Alternatives considered

- **セッションログのオンデマンド解析** — 却下（§4）。
- **フッターを育てる** — 却下。たまにしか見ないデータのための常設
  ウィジェット追加。一瞥はフッター、明細書は /usage。
