# ADR-0056: 失速警告が狼を叫んでいた — function call は丸ごと届く

| 項目 | 値 |
|------|----|
| ステータス | **Accepted** |
| 日付 | 2026-08-30 |
| 対象 | gem-agent |
| 意思決定者 | nlink-jp メンテナ |
| きっかけ | オペレーター:「モデルは明らかに動いているのに、edit_file / write_file のあたりでステータス行が『接続が失速している可能性』と言う」 |
| 修正対象 | ADR-0033 §1（単一の 20 秒しきい値）、ADR-0041 §5 |

## 背景

ADR-0033 §1 は実行中ステータスに鼓動を与え、しきい値を **1 つ**
置いた: チャンクが 20 秒来なければ「N 秒間データなし — 接続が失速
している可能性」に切り替わる。ADR-0041 §5 はその穴を 3 つ塞いだが、
いずれもツール呼び出しが**始まった後**の沈黙の話だった
（`toolRunning`・サイドコールのチャンク・ターン境界）。今回の報告は
呼び出しが**届く前** — モデルがそれを組み立てている最中の窓である。

実測 2 本（gemini-3.7-flash、`internal/llm`、`-tags live`）が答えを
確定させた。

`chunkgap_live_test.go` — content 21,761 バイトの `write_file` 1 回:

    t=  2.4s chunk #1        t=  9.4s chunk #4
    t= 42.5s chunk #5   ← 33.1 秒の沈黙
    RESULT: total=42.8s chunks=6 maxGap=33.1s contentBytes=21761

`wirebytes_live_test.go` — 同じ要求で HTTP レスポンスボディを
タップし、バイト単位の鼓動がそもそも可能かを問うたもの:

    t=  7.1s read #3 590 bytes
    t= 47.5s read #4 1024 bytes   ← 40.4 秒、1 バイトも読めていない
    t= 47.5s reads #5..#10        ← 約 37KB が一度に流れ込む

つまり:

- Gemini は function call を**丸ごと 1 つの part** として出す。引数の
  部分ストリーミングは存在しない — 序盤の 4 チャンクは thought
  サマリで、その後は完成した呼び出しまで何もない。
- この沈黙はクライアントから見えるどの層でも生存性として観測でき
  ない: チャンクでも、レスポンスのバイトでも。「大きな引数を生成中」
  と「TCP が死んだ」はここからは 1 バイトも違わない。
- 沈黙の長さは引数に比例する — 実測で約 650 B/s、100KB のファイル
  なら数分になる。

したがって 20 秒しきい値は、gem-agent が存在する理由そのもの——
ファイルの作成と編集——の最中にモデルを「死んでいる」と告発する。
健全な作業で鳴る警告は、警告がないより悪い: オペレーターは
「Ctrl+C が選択肢だ」という唯一の合図を無視するよう学習してしまう。

## 決定

### 1. しきい値を動かす: `stallSeconds` 20 → 90

画面には何も足さない。鼓動は従来どおりの表示のまま —
`1m07s · 34 chunks · last 40s` — で、90 秒を超えたときだけ警告に
変わる。`toolRunning` 中の抑止（ADR-0041 §5）は不変、自動タイム
アウトも導入しない（ADR-0033）。

最初の案は原因を画面に出すものだった: ステータス行の下に dim で
「大きな書き込み/編集は完成まで一切送信されません」。**オペレーター
レビューで却下** —「これはバックエンドの事情であって、それを説明
されても『で？』となる」。Gemini が part をどう区切るかは利用者に
とって行動に移せない情報であり、供給側の都合を説明するステータス行は
自分の都合を説明する画面である。供給側の制約はコメント・ADR・コミット
メッセージに書き、画面にはそこから導かれるしきい値だけを出す
（weather-lens で高くついた家訓）。

文字列で 1 つだけ変えたものがある: `StallFmt` は内部に
`(Ctrl+C interrupts)` を抱えていたが、`CtrlCHint` が直後に描画される
ため重複であり、80 桁では語の途中で切れていた。この複製を削り、英語
表現は "the stream may be stalled" に短縮した。ヒントが 80 桁で残る
ことを両言語で検証する回帰テストを置いた。

### 2. なぜ 90 秒か

約 21KB の引数で実測した無害な沈黙の 2.5 倍で、実際のターンが書く
ファイルサイズを覆う。導出ではなく判断である: 正直な代償は、本当に
死んだ接続がさらに 70 秒名指しされなくなること。受け入れる理由は、
経過秒数（`last 84s`）が最初の 1 秒目から画面に出て増え続けており、
Ctrl+C はいつでも使えるから。告発を遅らせて失うのは既に見えている
情報だが、誤って告発して失うのは合図そのものである。

### 3. `/riskbook learn` はフラグを `beginTurnStats` の**後**に立てる

学習パスは `m.toolRunning = true` で検出器を抑止してから
`beginTurnStats()` を呼んでいた — 後者がそのフラグをリセットする。
結果、人間の回答を待っているだけのパスが、使ってもいない接続の失速を
警告していた。順序を修正し、回帰テストを付けた（`!コマンド` の経路は
元から正しい順序だった）。

### 4. 実測はツリーに残す

上の数字の根拠として、また前提の見張りとして live テスト 2 本を残す:
Gemini が将来 function call の引数を部分ストリームするようになれば
`chunkGap` は潰れ、quiet 段は消せる死んだコードになる。
`wirebytes_live_test.go` は `golang.org/x/oauth2` を direct（テスト
専用）依存に昇格させる — `HTTPClient` を差し込んでも ADC のトークン
ソースを生かす必要があるため。

## 影響

- 最も多い「長いターン」でステータス行が嘘をつかなくなる。しかも
  そのために新しい文言を 1 つも増やしていない — 増えたのは定数だけ。
- 死んだ接続の名指しは 20 秒から 90 秒に遅れる。自動タイムアウトは
  追加しない — 長い作業を殺さないという ADR-0033 の拒否は有効。
- 新しい合図は発明していない: バイト単位の鼓動は検討し、**実測で
  不可能と確認した**。だからこの修正は仕組みではなく、しきい値である。
- 将来のモデルが function call の引数を部分ストリームするように
  なれば実測は崩れ、90 秒は下げられる — 気づく役目は live テスト。
