# ADR-0065: キャンセルは呼び出しを終わらせる（第 2 部）— 協調する走査・復帰保証の床・どこにでもある脱出はしご

| 項目 | 値 |
|------|----|
| ステータス | **承認済み** |
| 日付 | 2026-09-02 |
| 拘束対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | オペレーター: ファイル検索中の Ctrl+C が「中断中…」のまま検索が続行し、3 回目の Ctrl+C も少し待たされた |
| 拡張元 | ADR-0034 |

## 文脈

ADR-0034 は*シェル*呼び出しをキャンセルで終わらせた: プロセス
グループ kill・`WaitDelay`・TUI の 3 回押し終了である。プロセス内
ツールには同じ契約が与えられていなかった。`search_files` と
`list_tree` はターンの context を受け取るが一度も参照せず、走査は
`ReadDir`/`ReadFile` をプロジェクトの端まで回す。agent は `Tool.Run`
を同期呼び出しし、その下に床はない。したがって Ctrl+C がすることは
「誰も読まない context をキャンセルする」だけである。TUI は
「中断中…」を表示して TurnDone を待つが、それは走査が自力で完了し、
次のモデル呼び出しが死んだ context で失敗して初めて届く。委任先の
`agentic_file_search` の子も同じ context を同じツールに渡すので、
同じ形で詰まる。

走査を忠実に写したプローブで、ローカル SSD 上の 30,000 ファイルを
測った: 全走査 1.6 秒。20 ms でキャンセルすると、出荷形は 1.6 秒後
（残りの走査全部）に返り、ディレクトリとファイルごとに context を見る
走査はキャンセルの 2 ms 後、goroutine + select のラッパーは 1 ms 後に
返る。遅いファイルシステム — ネットワークマウント・コールドキャッ
シュ・巨大ツリー — では出荷形の遅れは残り走査時間そのものであり、
オペレーターが見たのはそれである。プローブの入力はローカルかつ
ウォームである。以下の設計は遅い系の実測に依存しない — syscall を
予測するのではなく、待ちを有界にするからである。

同じ調査でさらに 2 つの穴が見つかった:

- 素の REPL と `-p` は `signal.NotifyContext` を使っており、登録中は
  2 回目以降の SIGINT をすべて握り潰す。TUI の外には脱出はしごが
  一切なく、詰まった走査は別の端末から殺すしかない。
- 3 回目の Ctrl+C 後の待ちは走査ではなく終了経路である: 遅延実行され
  る監査ログの flush は 3 秒で有界だが、その間は何も言わない。有界な
  沈黙はハングに見える（ADR-0033 の教訓）。

協調チェックは blocking syscall を中断できない。ハングした NFS や
SMB マウント上の `ReadDir` はカーネルが返すときに返り、Go にそれを
キャンセルする手段はない。チェックを足すだけの修正は、その事例を
ADR-0034 が `Wait` で見つけたのと同じ場所に残す。

## 決定

### 1. 走査は context を参照する

`search_files` と `list_tree` は、すべてのディレクトリ読み取りと
ファイル読み取りの前に `ctx.Err()` を確認し、`search_files` は
ファイル内でも 1024 行ごとに確認する — 重いパターン下の 2 MB ファ
イルは単独で §2 の猶予を超え得る。キャンセル時はその場で止まり、
手元にあるものをラベル付きで返す: `search_files` は `[interrupted
after N files scanned — results above are partial]`（走査途中で切ら
れたファイルは数えない）、`list_tree` は `[interrupted — the tree
above is partial]` を末尾に付ける。部分結果はエラーではなく結果で
ある: transcript に入るので、再開したセッションは中断前に見つかった
ものを見られるし（ADR-0040 の「進捗は保存済み」の立場）、切り詰めが
無言になることはない（ADR-0052）。

### 2. すべてのツール呼び出しの下に復帰保証の床

`execCall` は `Tool.Run` を goroutine で走らせ、結果と context を
select で待つ。context がキャンセルされたら 1 秒の猶予だけ協調的な
復帰を待ち — 応答するファイルシステムでは §1 の走査は syscall 1 回分
で戻り、その部分結果がこの競争に勝たなければならない — その後は
呼び出しを放棄する: モデルは `error: interrupted — the call was
abandoned; it may still complete in the background and its result is
discarded` を受け取り、監査イベントは `outcome = abandoned` を記録
する。キャンセル後・猶予内に戻った協調的なツールは `outcome =
interrupted` として記録される。

猶予は意図してシェルの `WaitDelay` より長く、そのために ADR-0034 §2
の `WaitDelay` は 2 秒から 500 ms に下げる: 逃亡者がパイプを握った
キャンセル済みシェル呼び出しは、切断前に生成した出力を `WaitDelay`
の時点で返すので、床はそのときまだ待っていなければならない。順序は
テストで固定する。

床の外に置くものが 2 つある。承認ゲート: オペレーターを待つダイア
ログは詰まったツールではない。そして自身がオペレーターを待つツール
— `WaitsOnOperator` を付けた `ask_user` — 放棄された stdin 読み取り
は素の REPL の唯一の stdin に対する 2 人目の読み手となり、オペレー
ターの次の行を食ってしまうからである（AGENTS.md の共有 reader 規則）。
それらがいつ返るかはオペレーターが決める。

床が放棄したものは計上する。まだ実行中の放棄呼び出しの数は usage
統計に持ち、ゼロでなければ終了レシートに名指しする — syscall を
握った goroutine はプロセスが消えた後に書き込むかもしれない。放棄
した呼び出しが実際に戻ったら、`tool_late_return` セッションレコード
と `tool.late_return` 監査イベントがそれを告げる（名前・outcome・
所要時間）。どちらもセッションがログを閉じ、エクスポータを止めた
後は best-effort である。遅れて戻った**変更系**の呼び出しは、次の
ターンの冒頭でそのターンのメッセージの前に user ロールの注記として
モデルにも告げる: モデルのその呼び出しについての最後の言葉は「結果
は破棄」であり、書き込みは着地したかもしれない。遅れて戻った結果
そのものを消費するものはない。

これは ADR-0034 の規則をプロセスへ拡張したものである: 停止は
best-effort、復帰は保証。床は context を無視する将来のツールも
覆い、既に context を select している MCP 呼び出し（kill-and-
respawn）には何もしない。委任先の `agentic_file_search` の子は親の
ツールとして同じ床の下にある。子のツールが死んだ context に部分結果
を返すと、子の次のモデル呼び出しが失敗し、その発見は表に出ない —
子は設計上 transcript を持たない（ADR-0037）。

### 3. 脱出はしごは TUI の外にもある

TUI の外で走るすべてのターン — `-p` のワンショット・素の REPL の
ターン・`!` シェルエスケープ・`/compact` — は ADR-0034 §3 と同じ
3 回押しのはしごを登る: 1 回目の Ctrl+C はターンをキャンセルし、
押下が効いたと分かるよう「中断中…」を出力する（素の REPL はこれまで
ターンが戻るまで何も言わなかった）。2 回目は TUI と同じ文言で、ター
ンが応答していないこと・もう 1 回で終了することを警告する。3 回目は
ステータス 130 でプロセスを終了する。その終了では遅延 flush を飛ばす
— transcript はイベントごとに書かれているので、詰まった呼び出しまで
の全てはディスクにあり、警告がそう告げている。`-p` の 1 回目の中断は
従来どおり通常のエラー経路でステータス 1 のまま。130 は強制終了の
印である。ソース走査テストがすべての呼び出し箇所をはしごに固定する
— 共有 stdin reader を固定しているのと同じ手法である。

### 4. 終了は flush 中であることを告げる

監査ログが有効なとき、対話セッションの終了は有界な flush の前に
`sending audit events… (up to 3s)` を出力する。ワンショットモードは
終了レシートと同様、パイプラインのために黙ったままにする。文字列は
それが伴う終了レシートと同じ ADR-0029 カタログに置く。上限は不変、
沈黙だけが消える。

## 帰結

- 応答するファイルシステムであれば、Ctrl+C は猶予内に返る。ハング
  したマウントでは床が返り、goroutine 1 つとファイル記述子 1 つが
  syscall が返るかプロセスが終了するまで残る — ADR-0034 の孤児と
  同じ形であり、同じ取引である: リークした goroutine は詰まった
  セッションより遥かに安い。終了レシートがそれを数える。
- 放棄された goroutine は、次のターンが自分のツールを走らせている
  間もまだ動いているかもしれない。agent の共有状態は mutex で守られ
  るが、ツール自身の副作用（同じパスへの 2 つの書き込み）は直列化
  されない。遅れて戻った変更系の呼び出しを隠さずモデルに告げるのは
  そのためである。
- 途中で放棄された変更系ツールは完走し得る: モデルは「interrupted」
  を見るが、ファイルは書かれるかもしれない。次ターンの注記と遅延
  復帰レコードが緩和策であり、床を読み取り専用ツールに限る案は却下
  した（下記）。
- ツール作者への契約が明示された（AGENTS.md）: すべての `Tool.Run`
  は自分の context を参照する。床が保証するのは復帰であって停止では
  ない。オペレーターを待つツールは `WaitsOnOperator` でそう名乗る。
- `tool.call` 監査語彙に `interrupted` と `abandoned` の 2 つの
  outcome と、`tool.late_return` の 1 イベントが加わる。
- テスト契約: 走査は `ReadFile` を停滞させる FIFO で決定論的に切る
  （ハングしたマウントの縮図）。床は 3 つの形 — 決して返らない
  ツール・猶予内に返るツール・通常の呼び出し — を race 検出器の下で
  検証し、加えてオペレーター待ちの除外と遅延した変更系の告知を検証
  する。はしごはテストプロセスへの実際の SIGINT で駆動する。猶予が
  WaitDelay より長い順序は固定する。

## 検討した代替案

- **猶予なしの床。** キャンセルの瞬間に返るため、健全なファイル
  システムでは毎回、協調的な部分結果を競争で失う。猶予のコストは
  最大 1 秒の「中断中…」であり、見つけたマッチは残る。
- **協調チェックのみ。** blocking syscall を終わらせられない。ハング
  したマウントの事例は ADR-0034 が `Wait` で見つけた場所にそのまま
  残る。共通ケースを安く・リークなしにするために §1 として残し、
  修正の全体としては却下。
- **読み取り専用ツールだけの床。** ハングしたマウント上の
  `write_file` がセッションを詰まらせたままになる。それは ADR-0034 が
  受け入れを拒んだ失敗である。遅延復帰レコードと次ターンの注記が、
  ハングに対する正直な代替である。
- **承認ゲートも床の中に。** オペレーターを待つゲートは詰まって
  いないし、stdin 読み取りの放棄は「読み手は 1 人」の規則を破る。
  同じ理由で `ask_user` を除外する。
- **設定可能な猶予。** 既に目的を失った待ちにつまみを付けると、修正
  ではなく調整を招く。正当な作業にタイマーを掛けないという ADR-0033
  の立場が当てはまる。猶予は名前付き定数であり、唯一の実質的制約
  （シェルの `WaitDelay` より長い）をテストで固定する。
- **走査のタイムアウト。** 軸が違う: 遅くて大きいプロジェクトは正当
  かつ有限である。ADR-0033 は同じ理由で自動タイムアウトを既に
  退けている。
- **TUI の外は 2 回で終了。** ADR-0034 §3 は、慌てた二度押しが正常
  終了寸前のセッションを殺さないよう 3 回を選んだ。素の REPL にも
  別のはしごではなく同じはしごを与える。
