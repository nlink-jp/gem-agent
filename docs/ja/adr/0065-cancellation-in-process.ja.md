# ADR-0065: キャンセルは呼び出しを終わらせる（第 2 部）— 協調する走査・復帰保証の床・どこにでもある脱出はしご

|------|----|
| ステータス | **承認済み** |
| 日付 | 2026-09-02 |
| 拘束対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |

| 拡張元 | ADR-0034 |

## 文脈

ADR-0034 は*シェル*呼び出しをキャンセルで終わらせた: プロセス
グループ kill・`WaitDelay`・TUI の 3 回押し終了である。プロセス内
ツールには同じ契約が与えられていなかった。`search_files` と
`list_tree` はターンの context を受け取るが一度も参照せず、走査は
`ReadDir`/`ReadFile` をプロジェクトの端まで回す。agent は `Tool.Run`
を同期呼び出しし、その下に床はない。したがって Ctrl+C がすることは
「誰も読まない context をキャンセルする」だけである。TUI は
「中断中…」を表示して TurnDone を待つが、それは走査が自力で完了し、
次のモデル呼び出しが死んだ context で失敗して初めて届く。委任先の
`agentic_file_search` の子も同じ context を同じツールに渡すので、
同じ形で詰まる。

走査を忠実に写したプローブで、ローカル SSD 上の 30,000 ファイルを
測った: 全走査 1.6 秒。20 ms でキャンセルすると、出荷形は 1.6 秒後
（残りの走査全部）に返り、ディレクトリとファイルごとに context を見る
走査はキャンセルの 2 ms 後、goroutine + select のラッパーは 1 ms 後に
返る。遅いファイルシステム — ネットワークマウント・コールドキャッ
シュ・巨大ツリー — では出荷形の遅れは残り走査時間そのものであり、
オペレーターが見たのはそれである。

同じ調査でさらに 2 つの穴が見つかった:

- 素の REPL と `-p` は `signal.NotifyContext` を使っており、登録中は
  2 回目以降の SIGINT をすべて握り潰す。TUI の外には脱出はしごが
  一切なく、詰まった走査は別の端末から殺すしかない。
- 3 回目の Ctrl+C 後の待ちは走査ではなく終了経路である: 遅延実行され
  る監査ログの flush は 3 秒で有界だが、その間は何も言わない。有界な
  沈黙はハングに見える（ADR-0033 の教訓）。

協調チェックは blocking syscall を中断できない。ハングした NFS や
SMB マウント上の `ReadDir` はカーネルが返すときに返り、Go にそれを
キャンセルする手段はない。チェックを足すだけの修正は、その事例を
ADR-0034 が `Wait` で見つけたのと同じ場所に残す。

## 決定

### 1. 走査は context を参照する

`search_files` と `list_tree` は、すべてのディレクトリ読み取りと
ファイル読み取りの前に `ctx.Err()` を確認する。キャンセル時はその
場で止まり、手元にあるものをラベル付きで返す: `search_files` は
`[interrupted after N files scanned — results above are partial]`、
`list_tree` は `[interrupted — the tree above is partial]` を末尾に
付ける。部分結果はエラーではなく結果である: transcript に入るので、
再開したセッションは中断前に見つかったものを見られるし（ADR-0040
の「進捗は保存済み」の立場）、切り詰めが無言になることはない
（ADR-0052）。

### 2. すべてのツール呼び出しの下に復帰保証の床

`execCall` は `Tool.Run` を goroutine で走らせ、結果と context を
select で待つ。context がキャンセルされたら短い猶予（500 ms）だけ
協調的な復帰を待ち — 健全なファイルシステムでは §1 の走査は syscall
1 回分で戻り、その部分結果がこの競争に勝たなければならない — その
後は呼び出しを放棄する: モデルは `error: interrupted — the call was
abandoned; it may still complete in the background and its result is
discarded` を受け取り、監査イベントは `outcome = abandoned` を記録
する。放棄した goroutine が後で戻ったら、`tool_late_return` セッション
レコード（ツール名・outcome・所要時間）が監査の穴を閉じる。遅れて
戻った結果を消費するものは他にない。キャンセル後・猶予内に戻った
協調的なツールは `outcome = interrupted` として記録される。

これは ADR-0034 の規則をプロセスへ拡張したものである: 停止は
best-effort、復帰は保証。床は context を無視する将来のツールも
覆い、既に context を select している MCP 呼び出し（kill-and-
respawn）には何もしない。

### 3. 脱出はしごは TUI の外にもある

素の REPL と `-p` は ADR-0034 §3 と同じ 3 回押しのはしごを得る:
1 回目の Ctrl+C はターンをキャンセルし、2 回目はターンが応答して
いないこと・もう 1 回で終了することを警告し、3 回目はステータス 130
でプロセスを終了する。その終了では遅延 flush を飛ばす — transcript
はイベントごとに書かれているので、詰まった呼び出しまでの全ては
ディスクにあり、メッセージはそれも伝える。

### 4. 終了は flush 中であることを告げる

監査ログが有効なとき、終了は有界な flush の前に `sending audit
events… (up to 3s)` を出力する。上限は不変、沈黙だけが消える。

## 帰結

- 応答するファイルシステムであれば、Ctrl+C は猶予内に返る。ハング
  したマウントでは床が返り、goroutine 1 つとファイル記述子 1 つが
  syscall が返るかプロセスが終了するまで残る — ADR-0034 の孤児と
  同じ形であり、同じ取引である: リークした goroutine は詰まった
  セッションより遥かに安い。
- 途中で放棄された変更系ツールは完走し得る: モデルは「interrupted」
  を見るが、ファイルは書かれるかもしれない。遅延復帰レコードが
  緩和策であり、床を読み取り専用ツールに限る案は却下した（下記）。
- ツール作者への契約が明示された（AGENTS.md）: すべての `Tool.Run`
  は自分の context を参照する。床が保証するのは復帰であって停止では
  ない。
- `tool.call` 監査語彙に 2 つの outcome が加わる: `interrupted`
  （キャンセル後・猶予内にツールが返った）と `abandoned`（床が
  ツールを待たずに返った）。

## 検討した代替案

- **猶予なしの床。** キャンセルの瞬間に返るため、健全なファイル
  システムでは毎回、協調的な部分結果を競争で失う。猶予のコストは
  最大 500 ms の「中断中…」であり、見つけたマッチは残る。
- **協調チェックのみ。** blocking syscall を終わらせられない。ハング
  したマウントの事例は ADR-0034 が `Wait` で見つけた場所にそのまま
  残る。共通ケースを安く・リークなしにするために §1 として残し、
  修正の全体としては却下。
- **読み取り専用ツールだけの床。** ハングしたマウント上の
  `write_file` がセッションを詰まらせたままになる。それは ADR-0034 が
  受け入れを拒んだ失敗である。遅延復帰の監査レコードが、ハングに
  対する正直な代替である。
- **走査のタイムアウト。** 軸が違う: 遅くて大きいプロジェクトは正当
  かつ有限である。ADR-0033 は同じ理由で自動タイムアウトを既に
  退けている。
- **TUI の外は 2 回で終了。** ADR-0034 §3 は、慌てた二度押しが正常
  終了寸前のセッションを殺さないよう 3 回を選んだ。素の REPL にも
  別のはしごではなく同じはしごを与える。
