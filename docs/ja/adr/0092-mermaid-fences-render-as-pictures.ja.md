## Context

### 罫線表示にできなかったこと

ADR-0063 は mermaid のフェンスを返答の中に戻し、mermaid-ascii の罫線で描いた。忠実さのガード（ソースの
ラベルがすべてある・線 1 本に矢じり 1 つ）を持ち、ガードに落ちればソースを見せる。動いてはいるが、
使われていない。運用者の報告では、罫線が読みにくすぎて図を作業から外している — CJK のラベルがずれる、
横に広い flowchart が裂ける、sequence が非 ASCII を拒む。実セッションに mermaid が無いのは需要が無い
証拠ではない。mermaid を含むセッションは表示のテストだけである。

### 変わったこと

`mermaid-render`（lib-series）は flowchart / graph・erDiagram・sequenceDiagram をビットマップに描く。Go で
書かれ、標準ライブラリの他は `golang.org/x/image` だけに依存する。その約束は ADR-0063 が必要とするものに
合っている:

- **間違いは拒む。** 読めない構文・どのフォントにも無い文字・資源の上限の超過はエラーで、呼び出し側は
  ソースを見せる。無い文字を描かず、見た目の悪さで図を拒まない。
- **mermaid 12.0.0 と同じように読む。** ER と sequence の字句解析は上流の jison 文法を規則ごとに移植した
  もの。このランタイムのセッションから取った実データ 43 個（flowchart 22・ER 11・sequence 10）を原文と
  突き合わせ、運用者が回を重ねて目で確かめた。
- 配置は、種類ごとに乱数の図 20,000 個の性質テストで守られ — 箱どうしが重ならない・ラベルは箱の中に
  描かれる・矢じりの後ろには線の区間がある — 独立レビューが資源とクラッシュの経路を見つけて塞いだ
  （ソースは mermaid 自身の上限と同じ 5 万文字まで）。

ADR-0089 A3 は「罫線ではなく mermaid を PNG に描く」を却下した。ADR-0042 の忠実さのガードが描くたびに
走るのは ASCII の描画器に対してだけで、PNG にすれば罫線と一緒に検証も消える、という理由である。これは
今も本物の取引であり、性質テストだけでは答えにならない — 性質テストは手元で走るので、テストが生成
しなかった図の配置の欠陥は、拒むものが無いまま間違って描かれる。答えは §5 にある: 性質テストが守る
不変条件と同じものをエンジンが描くたびに確かめ、どれかを破る絵は他の間違いと同じく拒む。

### ボックスのための実測（mermaid-render RFP の段 0）

iTerm2 と kitty で、図の文字を端末の文字の 0.85・1.00・1.15 倍にして運用者が見比べ、両方で **1.00** を
選んだ。図は Scale 2（1 em = 28 px）で描く。セルの縦横比は端末で違う（運用者の機械で iTerm2 2.25・
kitty 1.86）ので、仮定せずに読む。既存の写真用のボックス（40 桁・画面の 3 分の 1）では図の文字が
読めない（1600×1200 の絵で約 5.6 pt）ので、ここには合わない。

## Decision

### 1. フェンスが絵になるのは、TUI が画像を描く場所だけ

TUI の画像プロトコル（ADR-0089 §7。TUI の開始前に一度だけ決まる）が iTerm2 か kitty のとき、返答の中の
mermaid フェンスを mermaid-render で描き、インライン画像として表示する。プロトコルの無い TUI —
`images = "auto"` でのマルチプレクサを含む — は ADR-0063 のレーンのまま: 忠実なら罫線、そうでなければ
ソース。単発 `-p` と素の REPL は ADR-0042 §4 の決定どおりモデルのテキストを逐語で出し、ここでは何も
変えない。どの場合もトランスクリプトはモデルのソースを逐語で保ち、絵は表示だけに使う。

payload を飲み込むマルチプレクサの中で `images = "iterm"` か `"kitty"` を強制すると、図は失われる。この
設定は「この端末は描ける」という運用者の表明であり、この残余は疑い直さずに受け入れる。

### 2. エンジンには書かれたままのソースを渡す

mermaid-render には、フェンスの中身を ADR-0042 の変換表を**通す前に**渡す。変換表は mermaid-ascii の
文法のためにあり、形を四角に揃え、ラベルの中の `&` を全角の ＆ にする。通した後を渡すと、絵から形が
消え、ラベルが変わる。

### 3. 返答の描画関数は、行数を宣言した区切りを返す

いまの返答の描画関数は `func(string) string` で、結果は文字列として数えられている。絵は、行数を宣言した
`tui.Segment`（ADR-0089 §1）として `emitSegments` に届かなければならない。ツールの画像が既に使っている
レーンである。描画関数を `func(string) []tui.Segment` にする: Markdown の区切りは glamour、罫線の区切りは
逐語（ADR-0063 §3）、画像の区切りは payload と行数を持つ。`takeLive` とその呼び出し元は、文字列に
繋げる代わりに区切りのまま渡す。描画関数を作る関数（`mkRender`。いまは幅だけを受け取る）は、
プロトコル・画面の高さ・セルの縦横比・フォントも受け取る。行数の会計はそれ以外変わらない。

### 4. ボックス: 図の文字を端末の文字と同じ大きさに

1 em = 28 px で描いた W×H ピクセルの絵を、次の大きさで宣言する。

- 行数 = H ÷ 28 ÷ 1.2
- 桁数 = W ÷ 28 ÷ 1.2 ×（セルの高さ ÷ セルの幅）

これで図の文字 1 em が端末の文字 1 行になる。1.2（セルの高さがフォントの em の何倍か）は運用者の端末で
合わせた定数で、縦横比のほうは読む。セルのピクセル寸法は `TIOCGWINSZ` で読む — 端末への問い合わせでは
なく ioctl なので、Bubble Tea が stdin を持つ間も安全 — 開始時と、リサイズのたびに。ピクセルを返さない
端末では縦横比 2.25（termimg の想定値。iTerm2 の実測値と一致）。この関数は `termimg.BoxFor` の隣に置き、
エンジンは端末を知らない。

これは ADR-0089 A2 と矛盾せず、A2 に答えるものである。A2 がピクセルから行数を導くのを却下した理由は、
宣言したボックスが縦横比を上書きすること、`ESC[16t` が応答されないことがあること、だった。ここでは
両方の寸法をやはり宣言し、計算はその値を選ぶだけで、セルの寸法は ioctl から来る。ADR-0089 の
Consequences の「アスペクト比の算術も、セルのピクセルサイズ問い合わせも、ランタイムに入らない」は
改める: セルの寸法の ioctl による読み取りは入り、問い合わせは入らない（`BoxFor` の 2.25 は既に
アスペクト比の算術だった）。

- **端末の幅 − 1 桁より広い:** 縦横比を保ってボックスを縮める。文字は小さくなる。見た目の問題であって
  間違いではなく、絵は描く。
- **入力欄とフッタより上の行数より高い:** 縮めない。上端はスクロールバックへ流れ、長い返答と同じく
  運用者がスクロールして読む（運用者の判断、2026-09-29: 高い図を縮めると文字が読めなくなり、高いものは
  スクロールして読むのが普通）。宣言する行数は全体の高さ。
  **実測（2026-09-29、運用者）:** iTerm2 は画面より高い絵を正しくスクロールする。kitty はしない —
  絵の下の部分が切れ、その上にフレームが描かれた。画面より低い絵は両方で正しくスクロールした。これは
  見た目ではなく間違いなので、kitty では高い絵を画面の半分以下の**帯に分けて描く**（`termimg.Bands`）。
  帯は同じ縮尺・ボックスの桁数で隙間なく続く。どの帯も画面に収まる絵であり、文字は縮まず、全体は変わらず
  スクロールで流れる。再び実測: 帯で kitty は直り、iTerm2 では帯の継ぎ目と右下の欠けが出た — そこで
  高い絵を正しくスクロールする iTerm2 には 1 枚のまま渡す。エンコード後の合計は `termimg.MaxBytes` を
  超えてはならない。
- **絵を出した後のリサイズ**では描き直さない。スクロールバックに出た絵は、テキストと同じく、出した
  ときのボックスのままである。**実測（2026-09-29、運用者）:** ウィンドウを狭めると、そのとき画面に
  見えていた絵が失われる — kitty は削除し、iTerm2 は黒い空白を残す。文章はスクロールバックに残る。
  どちらの端末もスクロールバックに黒い空白を積み、これは文章だけでも起きる。原因はこのレーンではなく、
  入力欄の折り返し直された残骸を掃除するために TUI が縮小時に画面全体を消去すること（ADR-0021）で、
  画像は文章のようには消去を生き延びない。`/show` の絵も同じ経路を通る。運用者はこれを**既知の制約**と
  して出荷し、縮小時の消去は端末ごとに実測しながら別の ADR で見直すと決めた — 候補は画面全体ではなく
  入力欄の行だけを消すこと。

### 5. 失敗はソースを見せる。何も無くはならない

- 未対応の図の種類（state・class・gantt など）は、ADR-0063 と同じく黙ってソースのまま通す。
- それ以外の拒否はすべて、フェンスをソースとして見せ、ADR-0063 §4 の注記 1 行で理由を名指す: 構文の
  誤り・未対応の構文（エンジンの第 1 段階では入れ子の subgraph もこれ）・どのフォントにも無い文字・
  上限・`termimg.MaxBytes`（2 MiB）を超える PNG、そして**エンジン自身の不変条件を破る配置**。
  mermaid-render は採用の前にこの確かめを持つ: 性質テストが守る不変条件（箱どうしが重ならない・箱は
  自分のラベルを収める・枠は自分のメンバーを収め他の箱を含まない・線は自分のラベルを保ち、矢じりには
  線の区間がある）を、描くたびに配置の後で確かめ、破ればエラーにする。ADR-0042 のガードに当たる、
  描画器自身の確かめであり、それと同じく間違いだけを確かめ、見た目は確かめない。

絵がソースごと消えることはない。`drawImage` は payload を黙って拒める（ADR-0090・ADR-0091 §4）が、この
レーンはその道を取れない。そこで画像の区切りはフェンスのソースを持ち、フェンスを置き換えた後の失敗
— エンコード後の PNG の大きさの確認・作れない payload・大きさ 0 のボックス — はすべて、代わりにその
ソースを注記つきで出す。描画は `recover()` の下で走る: エンジンの panic は他の拒否と同じ拒否であり、
セッションの終わりではない。

### 6. フォントは cmd 層が一度だけ、必要なときだけ読む

view 層はファイルを開かない（ADR-0089 §5）。cmd 層が開始時にフォントを読み（既定はヒラギノ角ゴシック
W3 / W6 で、約 16 MB を読む）、読んだものを TUI に渡す。ただし決まったプロトコルが画像を描くときだけで、
絵を見せられないセッションはフォントを読まない。設定はユーザ設定だけにある（プロジェクト設定には
`[tui]` の表が無い）:

```toml
[tui.diagram]
font = "/path/Font.ttc"      # 本文。既定はヒラギノ角ゴシック W3
font_name = "Font-Regular"   # ファイルの中の書体（フル名か PostScript 名）
bold_font = "/path/Font.ttc" # 太字（実体名・枠の見出し）。既定は本文の書体
bold_font_name = "Font-Bold"
```

`font` 無しの `bold_font` は、`font` 無しの `font_name` と同じく設定の誤りである。設定パネルはこれらを、
次の開始で効く読み取り専用の行として見せる。

読めないフォント（無いファイル・無い書体名・設定の誤り）でランタイムは**止まらない**（運用者の判断、2026-09-29）。開始時のバナーに
設定名とエラーを 1 行出し、図は既定のフォントで描く。表示用のフォントのためにセッションを失う価値は
無い。ヒラギノ自体が読めないときは、バナーが「図はテキストで描く」と告げ、フェンスはすべて ADR-0063 の
レーンを通る。

読み取りには上限がある（ADR-0073 §4）。mermaid-render はフォントのファイルを自分で読み、そこは
`TestReadsAreBounded` から見えない。そこで採用の前に、その読み取りは通常のファイル以外を拒み、決まった
上限（macOS の最大のシステムフォントから決める）で止まるようにする。

### 7. ランタイムは図について引き続き何も言わない

ツールもプロンプトの段落も無い（ADR-0063 §2・ADR-0089 §8）。モデルの自然な事前分布（Markdown の図は
mermaid のフェンス）がそのままこの機能の描くものであり、図が欲しいときは運用者が作業の指示に含める。
`TestSystemPromptSaysNothingAboutDiagrams` は残る。

### 8. どこで何をするか

- `internal/diagram` は罫線の経路の隣に絵の経路を持つ。`Split` は任意の描画器を受け取り、描けるフェンスは
  絵とそのソースを持つ画像の区切りになる。TUI がそれを帯に分けてエンコードする。
- `internal/tui` は画像の区切りを §4 のボックスで payload にする。ツールの画像に対する `drawImage` と
  同じである。`termimg.Payload` を呼べるのは引き続き `internal/tui` だけ（ADR-0089 §6 の archtest）。
- 描画は、流れているテキストを書き出す場所、`Update` の中で走る。書き出す場所は 4 つあり、うち 2 つは
  返答が流れている間のキー操作（承認モードの切り替えと `/auto`）なので、キー操作が描画の時間を払うことが
  ある。エンジンでの実測: 実データの図は描画 1〜9 ms・エンコード 4〜49 ms、密な図（ノード 150・線 300）で
  233 ms。フェンスの途中で書き出すとフェンスは割れ、両方の半分はソースとして見える — 罫線でも既に
  そうである。
- 実セッションで停止が体感されるなら描画を `tea.Cmd` に移す。これは局所的な変更ではなく、最初から
  決めてはおかない: `emitJoined` は書き出しとその後に続くものを順序つきの 1 回の書き込みにしているので、
  非同期の絵には後の行が後ろで待つ置き場所が要る。そうしないと、ツール呼び出しの行が、その前にあるべき
  絵より上に出る。

## Consequences

- iTerm2 と kitty では返答の図が読めるようになる。CJK のラベルも、横に広い flowchart も、非 ASCII の
  sequence のラベルも描ける。
- iTerm2 と kitty では、エンジンが拒む図は、mermaid-ascii なら描けたかもしれない場合でもソースとして
  見える — とりわけ入れ子の subgraph は、エンジンの第 2 段階まで。これを受け入れる理由は B4 である。
- 画像を描けない端末のために mermaid-ascii は残る。同じパーサに乗る文字の描画器で置き換えるのは
  mermaid-render の RFP の第 2 段階。
- gem-agent は `github.com/nlink-jp/mermaid-render`（組織のモジュール）に依存し、それを通じて
  `golang.org/x/image` に依存する。モジュールグラフで `golang.org/x/sys` と `golang.org/x/text` が
  マイナー版 1 つ上がる。mermaid-render を §5 の確かめと §6 の上限つきの読み取りとともに先に
  リリースし、gem-agent はタグつきの版を採用する。
- 既知の制約（実測、§4）: ウィンドウを狭めると、そのとき画面にある絵が失われ、スクロールバックに黒い
  空白が残る — TUI の縮小時の消去が原因で、文章は生き延び、画像は生き延びない。別の ADR で見直す。
- 返答の描画関数の型が変わり、`takeLive` の呼び出し元はすべて区切りを扱う。撤回した主張のテストで
  「stops rendering the reply as one piece」に付けた理由（描画関数は変わらなかった、と言う）は、同じ
  コミットで書き直す。

## Alternatives considered

**B1. 罫線を残して改良する。** 罫線の失敗は描画器のもの（ラベルの位置揃え・幅）で、mermaid-ascii は
組織が手を入れないコミュニティ製のモジュールである。代わりに mermaid-render の第 2 段階が、同じパーサで
罫線を置き換える。

**B2. モデル向けの図のツール。** 実測の前例がある: `render_diagram` は 76 セッションで 1 回しか
発火しなかった（ADR-0063）。ランタイムの描画は、モデルがいずれにせよ書くフェンスのたびに発火する。

**B3. ヘッドレスブラウザの mermaid.js。** 表示の経路にブラウザと JavaScript の実行環境を置き、フェンスの
たびに起動することになる。しかも端末はどのみちビットマップとして見せる。

**B4. 絵に失敗したら罫線に落とす。** 2 つの描画器の失敗が重なる。新しい描画器が「間違い」として拒んだ図を、
古い描画器が間違ったまま描きうる。ソースを見せるほうが予測できる。

**B5. 写真用のボックス（40 桁・画面の 3 分の 1）。** 図には読めないと実測済み（段 0）。
