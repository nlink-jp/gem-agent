# ADR-0051: 縮む全文書き換えは危険信号 — 要約上書きに対する 4 つの床

| 項目 | 内容 |
|------|------|
| ステータス | **採択** |
| 日付 | 2026-08-27 |
| 拘束対象 | gem-agent |
| 決定者 | nlink-jp maintainers |
| 契機 | オペレータの実地報告:「プロジェクト配下の SOP が小さいうちは良好だが、規模が大きくなってから SOP 自体の改修をさせると、既存内容をやたらと要約して破壊する傾向がある。モデル特性以外にも要因があるのではないか」— 4 要因の診断に対し「すべて入れてみよう。進行承認」。 |

## 背景

症状: 大きな既存文書の改修を頼むと、返ってくるのは短くなった文書
— 節が消え、散文が圧縮され、改修だけは死体に適用されている。長文
の逐語再現でモデルが圧縮を起こす傾向自体は実在するが、調査の結果、
その条件を*作り込んでいる*実装側の要因が 4 つ見つかった。うち 1 つ
は「文書サイズとともに悪化する」という相関まで説明する:

1. **コンテキスト節約圧が全文読みから遠ざける。** システムプロン
   プトと `read_file` の説明文の両方が、窓読みと `summarize_file`
   を推す（「読んだものは以後の全ラウンドで再送される」）。コード
   探索には正しいが、文書改修ではモデルを部分コピー・要約コピーの
   保持へ誘導し、そこから全文を再生成させる。

2. **`write_file` が全文再生成を正当化し、破壊を見えなくする。**
   説明文は「小さな変更は edit_file を」だった — 大改修は「小さな
   変更」ではないので、モデルは正当に `write_file` を選ぶ。すると
   文書全体を 1 つの関数呼び出し引数の中に出力トークンとして再現
   することになる: 長文再現がドリフトし圧縮する、まさにその形。
   42KB を 8KB で置換しても `wrote 8192 bytes` — 成功報告だった。

3. **自動コンパクションが作業途中で逐語コピーを破壊する — サイズ
   相関の正体。** コンパクションは直近以外を散文要約に置換する
   （ADR-0006、ウィンドウの 80% で自動発火）。大きな文書は
   (a) 読むだけで閾値に近づき、(b) 改修に要するラウンド数が多い
   ため、*read と write の間で*コンパクションが発火する。モデルは
   そのあと文書の要約から文書を書く。小さな文書は作業の最後まで
   逐語で生き残り、大きな文書は生き残らない — 観測された「SOP が
   育つと悪化する」はこの機構である。

4. **無言の切り詰めが不良コピーを播種する。** `read_file` は
   200KB、指示ファイルのシステムプロンプト注入は 1 ファイル 32KB
   でキャップされる。どちらも切り詰めは本文中に開示されるが、切り
   詰め版で文書を「もう知っている」モデルは、切り詰め版を書き戻す。

単一の修正では 4 要因を覆えず、修正同士は相互強化する（発火した
ガードはプロンプトが述べる規則を教え、プロンプトの規則はモデルが
突き当たるガードを説明する）ので、組織教訓（相互強化する変更は
同時出荷）に従い 1 つの ADR として同時に出荷する。

## 決定

決定論的なものから助言的なものへ、4 つの床:

### 1. 縮小ガード（決定論、tools 層）

`write_file` は、**2048 バイト以上**の既存ファイルを**現サイズの
70% 未満**の内容で上書きすることを、`allow_shrink: true` が無い
限り拒否する:

    refusing to replace docs/sop.md (42KB) with much smaller content
    (8KB): a whole-file rewrite destroys everything not reproduced
    verbatim. Use edit_file for targeted changes, or re-read the file
    and pass allow_shrink=true if this shrink is intentional
    (file unchanged)

エラーは `edit_file` の近似一致診断の伝統に沿って教示的である:
両サイズ・両方の対処・何も書かれていない事実を名指す。
`allow_shrink` は**意図の宣言**（組織教訓: 意図は推定せず宣言させ
る）— 宣言は引数なので、承認ダイアログとトランスクリプトの
`gate_decision` 記録にそのまま現れる。文書の破壊は*無言では*不可能
になる: 対象を絞った編集か、縮小が意図的であるという明示的・記録
付きの主張のどちらかが必要になる。

ガードはツール内（承認ゲートの後）で動く: ファイルシステムの知識
は tools 層が持ち、承認→拒否は可視の 1 ラウンドを消費し、その再試
行は宣言を携えて新しいゲートを通る。プロジェクト内 write がダイア
ログを出さない auto モードでは、この床が荷重を受け持つ。

閾値は定数であり config ではない。安全床の設定ノブは「なぜ存在す
るか」を読まずに切る招待状になる; 誤検知の実証が出たら ADR で再訪
する。

### 2. 作業規範（プロンプト）

システムプロンプトの edit_file 優先行を、再生成についての規則に
改める:

> 既存ファイルの変更は大改修でも edit_file を優先。write_file は
> 新規ファイル用。既存ファイルの上書きはその全体を自分のコンテキ
> ストから再生成することであり、コンパクション後を含めこの会話で
> 全文を読んでいない限り行ってはならない — 逐語で再現しなかった
> ものはすべて破壊される。

これは失敗様式を、それを養う節約指針（要因 1）と同じ息で名指す:
探索は窓読み、全文 write の前は全文読み。

### 3. コンパクション失効通知（決定論、信頼側の枠書き）

`SummaryMessage` — 圧縮済み履歴の身代わりメッセージ — の
**Content**（gem-agent が書く信頼側の枠書き。非信頼のモデル出力で
ある添付要約ではない）に 1 文を加える:

> この地点より前に表示されたファイル内容はもうコンテキスト内で
> 逐語ではない: 編集や正確な引用の前にファイルを再読し、この要約
> だけから既存ファイルを書き直してはならない。

構造上決定論的 — 要約器が指示に従うかに依存せず、要因 3 が襲う
まさにその瞬間に届く。メッセージはトランスクリプトに載るので、
記録済みコンパクションは resume でもこれを再生する。

### 4. 承認ダイアログのサイズ差分（表示）

`tools.Tool` に表示専用のオプションフック `Annotate` を追加する:
ライブなファイルシステム状態から導いた追加の詳細行を、オペレータ
が見るコール詳細に併記する。`write_file` が実装し、対象が既存の
とき、ダイアログ（と `gate_decision` トランスクリプト記録）が

    replaces existing file: 42KB → 8KB

を運ぶ。手動承認経路のオペレータ側の床 — 縮む上書きが、承認の後
ではなく**同意の瞬間に**見える。注記はログ体裁の事実記述であり
英語のまま（ADR-0029 の対象外面）。Annotate は何も変更してはなら
ず、`Describe` が詳細を組み立てる場所で参照される。

## 帰結

- 正当な大幅縮小（意図的な置換・生成物）は 1 ラウンド余計にかか
  る: 拒否 → `allow_shrink` 付き再試行。そのラウンド*こそ*が機能
  である — 意図がトランスクリプトに着地する。
- 2KB 以上のファイルを正当に縮めるテストやスクリプトは
  `allow_shrink: true` を渡す必要がある。
- プロンプト変更はセッションプレフィックスを回転させる（他のプロ
  ンプト変更と同様、アップグレードごとに 1 回のコールドキャッシュ）。
- 要因 4 の切り詰めキャップは不変 — ガードは破壊的な*結果*を捕ま
  える（切り詰めコピーの書き戻しは縮小である）のであって、それを
  播種し得る全経路を取り締まるのではない。

## 却下した代替案

- **registry で「事前の全文 read」を必須化して追跡。** 危険なケー
  スはまさに「read は起きたが、その後コンパクションが捨てた」で
  あり、tools 層はコンパクションを見られない — 追跡はまさに失効
  したコピーを認証してしまう。だいたい通る検査は、モデルが満たす
  べき規則より悪い。
- **承認ダイアログでの全文 diff プレビュー。** 端末ダイアログ内の
  文書全体の diff は読めるレビューではない（ADR-0050 の教訓: 必須
  レビューは*読める*ときだけレビューである）。サイズ差分は人間が
  一瞥で実際に評価できる正直な信号であり、本物の diff レビューは
  git の仕事。
- **既存ファイルへの `write_file` の全面禁止。** 全体再生成が正し
  い場合はある（生成物・意図的な置換）し、`edit_file` の完全一致
  契約は丸ごと再生成には不向き。ガードは操作に値札を付けるので
  あって、禁止しない。
- **ガード閾値の config 化。** §1 参照 — 安全床にノブは付けない。
