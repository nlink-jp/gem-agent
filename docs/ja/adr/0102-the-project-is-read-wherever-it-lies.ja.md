## Context

read レーンは 3 つの木の読み取りを、特定のファイルの秘匿のためではなく
**到達範囲**のために拒否している: `/Volumes` と `/Network`（外部とネットワークの
マウント — `/` からの走査はすべての共有に届く）と `~/Library`（メール、
メッセージ、Cookie、ブラウザのデータ、トークンの保管場所）で、その下の
ツールチェーンのディレクトリ 4 つは許可し直している。最後の読み取り規則である
資格情報のブロックが、そのあと資格情報をどこでも拒否する。

macOS はクラウドストレージ — File Provider 経由の Google Drive、Dropbox、
OneDrive、iCloud — を `~/Library/CloudStorage/` の下に置く。そこにある
プロジェクトは read レーンが拒否する木の中にあり、外部ディスクや `/Volumes` の
下のネットワーク共有にあるプロジェクトも同じである。

このマシンで（2026-11-02）、兄弟ランタイムの read レーンのプロファイル — ここの到達範囲の規則は
同じ行である — を使い、このランタイムのプロファイルでも `TestReadLaneRunsInAProjectUnderReach` で
確かめた。
プロジェクトの中で `pwd`、`ls`、ファイルの読み取りを実行して測った:

| プロジェクト | 現状 | プロジェクトの木を許可し直す |
|---|---|---|
| 普通のディレクトリ（対照） | 動く | 動く |
| `~/Library` の下のディレクトリ | `getcwd: Operation not permitted`、`ls .` は拒否 | 動く |
| Google Drive、`~/Library/CloudStorage/…` | 同上 | 動く |
| SMB の共有、`/Volumes/…` | 同上 | 動く |
| まだダウンロードしていない Dropbox のファイル（オンライン専用） | — | 読める。プロバイダがダウンロードする |

- そこでの read レーンは狭いのではなく使えない: コマンドが自分の作業
  ディレクトリを知ることもできない。モデルがそこへ回す読み取りはすべて失敗し、
  read レーンは自動承認なので、運用者には失敗だけが見える。
- プロジェクト自身の木を許可し直せば足りる。祖先のメタデータの読み取りも
  測ったが、不要だった。
- オンライン専用のファイルを読むのに、read レーンが拒否するものは要らない:
  プロバイダに頼むのはカーネルであって、読むプロセスではない。

このランタイムは、運用者がルートとして追加したディレクトリで同じ拒否に出会い、
ADR-0099 §1 で決着させた: 追加したルートは、到達範囲のために拒否した木の
下にあっても読める — 運用者がそれを名指したのだから。最初のルートである
プロジェクトが、そこから漏れていた。

## Decision

1. **セッション自身のルートは、どこにあっても読める。** プロジェクトの
   ディレクトリまたはセッションの作業ディレクトリが、read レーンが到達範囲の
   ために拒否する木の中にあるとき、read レーンは到達範囲の拒否の後で、そのルート
   自身の木の読み取りを許可し直す。許可し直すのはルートそのものだけである:
   `~/Library/CloudStorage` の残り、共有の残り、`~/Library` の残りは拒否のまま。

2. **拒否した木の厳密に内側にあるルートだけ。** 拒否した木そのもの
   （`~/Library` 自体）や、それを含むルート（広いルートの確認で許される、
   ホームディレクトリにあるプロジェクト）は許可し直さない: Seatbelt は最後に
   一致したものが勝つので、そうしたルートを許可し直すと、自動承認のレーンに
   `~/Library` 全体を開き直すことになる。そこでは read レーンはこれまでどおり。
   包含は `pathid.Within`（ADR-0101）で判定する。

3. **ルートの中でも資格情報は拒否のまま。** 許可し直しは資格情報のブロックより
   前に置き、そのブロックはプロファイルの最後の読み取り規則のままなので、
   プロジェクトの中の `.env` や鍵がこれまでより読めるようになることはない。

## Consequences

- Google Drive、Dropbox、OneDrive、iCloud、外部ディスク、ネットワーク共有に
  あるプロジェクトで、read レーンが動く。
- モデルが read レーンで読んだオンライン専用のファイルは、どんな読み取りでも
  そうなるように、プロバイダがダウンロードする。
- セッションのルートの外では、read レーンの到達範囲は変わらない。
- ネットワーク共有の上の read レーンは共有の速さで読む。応答しない共有は、
  運用者自身のシェルを止めるのと同じようにコマンドを止める。

## Alternatives considered

- **`~/Library/CloudStorage` を到達範囲の拒否から外す。** 却下: セッションの
  ものはプロジェクトだけなのに、すべてのアカウントの、同期しているすべての
  フォルダを自動承認のレーンに開くことになる。
- **そうしたプロジェクトではコマンドを write レーンに回す。** 却下: write レーンは
  コマンドごとに承認を求め、それこそ read レーンが避けるためにある。read レーンの
  到達範囲の拒否は、プロジェクトの周りにあるもののためで、プロジェクトのため
  ではない。
- **祖先のメタデータも許可し直す。** 不要（実測）。
