## Context（背景）

ADR-0089 はレーンを作った。描画側がボックスを宣言し、行カウンタは見えないバイト列を
測る代わりにその数を告げられ、画像行は自分の下を消す。この決定は実測・実装され実機で
検証済みであり、本記録はそれに一切触れない。

続く ADR-0090 が供給源を名指した — MCP intake が、保存し**かつ**記述した画像ブロックを
すべて描く。本記録が撤回するのはその部分である。理由は 3 つあり、届いた順に並べる。
どれも単独で成立する。

### 1. ブロックの宛先はモデルであり、他の誰かが何か言ったわけではない

MCP の画像コンテンツブロックは、ツール結果が画像を**モデルの文脈へ**運ぶための形式で
ある。MCP には「この内容が誰宛てか」を言う別の手段がある — コンテンツブロックの
`audience` 注釈で、`user`・`assistant`・その両方を名指す。このランタイムはそれを一度も
読んでいない。`Content` が持つのは `Type`・`Text`・`Data`・`MIME` だけで
（[client.go:572](../../../internal/mcp/client.go)）、注釈はパーサの時点で捨てられる。

この操作者が登録している 24 サーバを数えたところ、**画像ブロックを出せるのは 4 本**
（ブラウザのスクリーンショット、URL スキャンのスクリーンショット、データ作業空間の
成果物受け渡し、サードパーティ製の vault 読み取り）で、**そのどれも audience を
設定していない**。つまり描画の条件は「サーバが見せてくれと言った」では一度もなかった。
「画像が届いた、ゆえに操作者は見たいはずだ」というこちら側の推定であり、それは
記録済みの規則が拒む形である — 意図は推定せず宣言させる。

### 2. 操作者の画面に届くものには書き手がいる。intake は何も書いていない

その 4 本のうち 2 本は、**モデルが見るために**スクリーンショットを返す。ADR-0090 の下では
その検分のたびに、操作者のスクロールバックへ原寸の絵が 1 枚入っていた。操作者が求めた
わけでもモデルが出すと決めたわけでもない出力が、モデル自身の返答と画面を取り合う。

利用者の言い方が決着をつけている — モデルが操作者に言うことがチャットメッセージであり、
インライン画像も同じ行為である。画面上の絵には書き手がおり、intake は書き手ではない。
郵便の仕分け所が中身を読んでいるだけである。

### 3. 存在した経路は、存在する場面に応えていなかった

最も多い場面は操作者が頼んだ成果物、すなわち生成された画像である。自前の生成サーバは
**パス**を返す — 組織が決め、このランタイムの MCP クライアントも守っている work dir 契約に
従って。したがって intake 経路はそこでは発火せず、発火しようがない。

そのファイルを見せろと言われたとき、モデルには画面への経路が 1 つも無いので、表示に
見える唯一の道具へ手を伸ばす — `shell_exec` の `open` である。read レーンはそれをカーネルで
拒む（`open` は他の IPC 可能なプログラムと並んで `DefaultDenyExec` にある。
[lane.go:125](../../../internal/sandbox/lane.go)）。成功するレーンへ持ち上げれば、ターミナルの
外に窓が開き、操作者は「絵を見る」ではなく「GUI プログラムを起動する」ことを承認させられ、
ssh 越しでは何も起きない。

描けるランタイムと、見せたいモデルと、両者をつなぐ道が無い状態。これは振る舞いの誤った
モデルではなく、欠落した経路である。

## Decision（決定）

### 1. MCP intake は何も描かない

`mcpIntake` は sink を失い、ADR-0090 以前の姿へ戻る — ブロックを保存し、記述し、モデルには
パスと `view_image` を渡す。**ADR-0090 §2 は撤回する。** §1 の配管（遅延束縛の `tui.Screen`。
プログラムが存在するまで不活性）は残す。以下の供給源がまさにその経路を要るからである。

sink の本番配線を固定するアーキテクチャテストは sink に追随する。MCP 呼び出し点を主張する
のをやめ、この決定の後に sink を運ぶ呼び出し点を主張する。

### 2. モデルが操作者に画像を見せるために呼ぶツール

組み込みツール `show_image` はパスを取り、その効果は操作者が絵を見ることである。
`view_image` の対であり、両者が違うのはただ 1 点、**宛先**である。

| tool | 見るのは誰か | 何に乗るか |
|---|---|---|
| `view_image` | モデル | ツール結果に添付されたバイト列、文脈へ |
| `show_image` | 操作者 | `tui.Screen` へのバイト列、宣言したボックスで描画 |

これは ADR-0090 が守るために作られた制約 — **view 層はファイルを開かない** — をそのまま
保つ。ファイルを開くのは**ツール層**であり、そこでの読み取りはツールコールであって、
あらゆる強制者が既に見ているからである。`show_image` は `view_image` の隣で
`credentialReadTools`（[risk.go:176](../../../internal/risk/risk.go)）に加わる。これは
`JudgesPath` が読む唯一の一覧であり、引数は実行前に実パスへ解決されて分類され、
読み取りは同じ檻の子プロセスを通る。モデルが名指したパスが
**判定される** — ADR-0089 §5 が反証した各稿との違いはそこだけである。

ツールの結果は何が起きたかをモデルへ返す — 見せた、あるいは見せていないとその理由
（プロトコル無し・天井超過・画像でない・対話的 UI が無い）。これは操作者の画面への報告では
なく、ツールが呼び出し元へ答えているだけであり、モデルは次に有用なことを言うためにその
答えを要る。

### 3. 操作者は直接ファイルを指せる

`/show <path>` は**操作者**が名指したファイルを描く。ランタイムが選んだパスを退けた symlink
の危険は、操作者が打ったパスには当てはまらない。これは ADR-0012 が `@<画像>` の添付で既に
引いている信頼の線と同じで、操作者の入力がファイルを名指し、ランタイムが読む。

「さっきのをもう一度見せて」も、モデルが一度も言及していないものも、この経路で閉じる。
操作者がモデルのツールコール待ちで詰まることが無くなる。

### 4. 描画については他に何も変えない

宣言したボックス、消去、端末幅未満への列の切り詰め、2 MiB の天井、画面上の沈黙した拒否、
TUI 限定の描画、能力プローブ — すべて ADR-0020 のものであり、すべて不変である。本記録は
供給源を動かすだけで、他は動かさない。

### 5. プロンプトの段落は足さない

いつ見せるかをモデルが学ぶ場所は、ツール自身の description である。システムプロンプトの
規則はここでは足さない。このランタイムのプロンプトは ADR によってのみ、かつランタイム側の
事実が真になった後にのみ変わるからであり、誰も発火させない能力は議論の対象ではなく
**測れる結果**である。`show_image` が発火すべき場面で発火しないとベンチが示したなら、その
測定が見直しの理由になる。事前に書いた散文より小さい変更で済む。

## Consequences（帰結）

- **サーバはもう操作者の画面に絵を置けない。** ADR-0090 が新しい面として名指したものは
  再び閉じる。サーバが返すものはモデルに届き、操作者が何を見るかはモデルが決める。
- **モデルが見せたい画像はツールコール 1 回のコストを払う。** 見せることは往復を伴う行為で
  あり、だからこそ帰属がはっきりする。
- **リリース済みの 2 版は後続と挙動が違う。** こちらの v0.9.0 と gem-agent の v0.83.0 は
  intake から描く。次の版は描かない。CHANGELOG はそれを改良としてではなく、そのまま書く。
- **`view_image` と `show_image` は取り違えやすい**（モデルにとっても）。description は動詞
  ではなく宛先から書き出す必要がある。
- **画面は拒否に対して沈黙のままである。** よって拒否した `show_image` はツール結果にしか
  現れない — それを伝えるのはモデルの仕事であり、§2 が結果を明示にした理由でもある。
- **lagent ADR-0022 が反対側の同じ決定である。** どちらのランタイムも単独では持てない。

## Alternatives Considered（検討した代替案）

**A1. intake 経路を残し、`audience` に `user` が含まれるときだけ描く。** 供給源としては
不採用。MCP の読み方としては正しく、そして今日は何も決められない — クライアントは注釈を
捨てており、画像ブロックを出す 4 サーバのうち設定しているのは 0 本なので、ゲートはどこでも
閉じたままになる。さらに「操作者が何を見るか」の選択がモデルではなくサーバに残る。いずれ
audience を宣言するサーバが現れたなら、**追加の**供給源として戻ってくる。そのときはまず
クライアントが注釈をパースする必要がある。

**A2. 返答の中に印を置き、レンダラーが分割する。** モデルのテキスト中の `![](path)` を、
gem-agent のレーンが mermaid を分けるように切り出す。不採用: 読み取りを行うのは view 層で、
しかもモデルが選んだパスである。ADR-0089 §5 が二重に反証した稿そのもの — view 層の読み取りは
どの強制者にも見えず、パスは先回りされうる。§2 のツールコールは同じ意図のまま、読み取りを
判定される場所へ移したものである。

**A3. 自前サーバにパスと画像ブロックの両方を返させる。** 本件の解としては不採用。10 本の
サーバを変え、あらゆる payload を倍にし、表示の決定権をモデルではなくサーバに置いたままで、
なお 2 MiB の天井に当たる。work dir 契約は障害ではない（両方返してよい）が、これは本決定では
ない。

**A4. `view_image` にも描かせる。** 1 つのツールに 2 つの宛先。不採用: また推定に戻るうえ、
スクリーンショットを 20 枚検分するモデルは会話を 20 枚の絵で埋める。

**A5. `shell_exec` + `open` を答えとして放置する。** 不採用: read レーンが設計として拒み、
ターミナルの外へ出て、ssh 越しでは失敗し、上がる承認は「GUI プログラムの起動」である —
操作者は間違った問いに答えさせられる。
