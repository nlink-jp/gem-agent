# ADR-0018: コンテキストキャッシュ — キャッシュに乗るループにして、実測する

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-20 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | オペレータ:「コンテキストの節約のために、コンテキストキャッシュに対応したほうがよいのではなかろうか」 |

## Context

まず正直な射程の整理: キャッシュが節約するのは**課金と待ち時間**であって、
ウィンドウ占有ではない — 同じプレフィックスは相変わらずウィンドウに載る。
ただしキャッシュ価格で課金され、再処理されない。ウィンドウの圧力は引き続き
圧縮の仕事である（ADR-0006）。キャッシュが攻めるのは、エージェントループを
定義づける挙動の請求書だ: 毎ラウンド履歴全体を再送する — ADR-0014 が
「読んだものは以後の全ラウンドで再送される」と測ったまさにそれの割引である。

このリクエスト形状に対する Vertex の機構は **implicit caching**:
バイト同一のプレフィックスを共有するリクエストは自動的にキャッシュ価格になる。
キャッシュオブジェクトも TTL も保管料も無い。我々のループはほぼ理想的な客だ —
システム指示 + 追記専用の履歴 — ただし、それを完全に打ち消す設計が 1 つある:

**隔離タグを LLM 呼び出しごとに再生成している。** nonce はシステム指示
（`{{DATA_TAG}}`）と全ラップ済みツール結果に入るので、ラウンド N と N+1 の
リクエストはシステム指示の 1 バイト目から違う。implicit caching は決して
プレフィックスに一致できない。我々のインジェクション防御は、最大限に
キャッシュ敵対的だった。

## Decision

1. **メインループの隔離タグをセッションスコープにする。** エージェント生成時に
   作り、`/clear` と resume で再生成する。タグが安定すればシステム指示と
   ラップ済み履歴はラウンドを跨いでも**ターンを跨いでも**バイト同一になり、
   成長するリクエストは純粋な追記 — implicit caching が報いる形になる。
2. **なぜ隔離が弱まらないか。** 呼び出しごとの nonce が守っていたのは
   「攻撃者が既知のタグを再利用してラッパー境界を偽造する」ことだった。
   その守りには機構レベルのより強い形があり、nlk の `Wrap` が既に実装して
   いる: タグ名を含むコンテンツ — 開き・閉じ・裸のいずれも — は**拒否され
   差し止められる**（`ErrTagCollision`）。つまりタグを知っていても脱出には
   使えない。セッション再利用で実際に変わるのは: モデルが攻撃者の読める場所へ
   タグを書き出した場合、それが 1 呼び出しではなくセッションの間有効に
   なること — 攻撃者はそれをコンテンツに仕込んで、そのコンテンツを
   **差し止めさせる**ことができる。可用性の嫌がらせ（しかも差し止めは目に
   見える）であって、完全性の破れではない。128-bit nonce の推測不能性は
   どちらでも変わらない。
3. **側呼び出しは per-call タグのまま。** リスク評価（ADR-0004）、圧縮
   （ADR-0006）、summarize_file（ADR-0014）は再利用するプレフィックスの無い
   単発呼び出し — キャッシュ利益が存在しないので、より厳しい既定から動く
   理由が無い。
4. **測ってから信じる。** usage パイプラインが `cachedContentTokenCount` を
   端から端まで運ぶ: API から捕捉し、セッションログの usage 記録に書き、
   フッターに直近ラウンドのプロンプトのキャッシュ率として表示する。この
   モデル・このプレフィックスサイズ・このエンドポイントで implicit caching が
   実際に効くかどうかは、カウンタが証明または反証する主張である —
   「合格に見える検査」の runbook の教訓は最適化にも適用される。
5. **explicit caching（CachedContent API）は意図的に作らない。** 保管料が
   時間課金で、TTL 管理が要り、「セッションを跨いで再利用される固定の大きな
   プレフィックス」に適合する — 我々のプレフィックスは毎ラウンド成長するので、
   それは再利用ではなく churn である。カウンタが implicit の不発を示した
   ときだけ再訪に値する。

## Consequences

- 長いツールループの再送税が、共有プレフィックス分だけキャッシュ価格に
  下がる — gem-agent のコストが住んでいる場所そのもの。レイテンシも一緒に
  改善する。
- 圧縮と `/clear` はプレフィックスを、従ってキャッシュをリセットする:
  想定内で、カウンタに見え、それでも正味プラス（圧縮はそもそもキャッシュ
  すべき量を縮める）。
- 隔離契約の文書は「常に呼び出しごとに新しいタグ」から「側呼び出しは
  呼び出しごと・メインループはセッションごと（Wrap の衝突拒否が裏付け）」に
  変わる — 本 ADR がその文書であり、組織メモリにもこのニュアンスを載せる。

## Alternatives considered

- **per-call タグ維持・キャッシュゼロ受容** — 現状維持。却下: セキュリティの
  差分は可用性の嫌がらせ（§2）である一方、コストの差分は長いセッションの
  請求書の過半である。
- **explicit CachedContent オブジェクト** — 現時点で却下（§5）。
- **N ラウンドごとのタグローテーション** — 却下。衝突拒否が既に与えている
  もの以上を何も買わず、ローテーションのたびにキャッシュを捨てる。両方の
  曲線で最悪の点である。
