## 背景 — 何を埋めるのか

**レーンは gem-agent 自身の子プロセスで止まる。** MCP サーバーは素の
`exec.Command`（`internal/mcp/client.go`）で起動され、どの Seatbelt プロファ
イルの外にもいる。ADR-0073 が縛るのはシェルコマンドにできることであって、
リモートサーバーが依頼を受けて何をするかについては何も言っていない。MCP
ツールに対してランタイムが今持っている制御は MITL ゲート 1 枚 —— ADR-0008 の
既定「MCP ツールは毎回訊く」だけである。

その制御は、まさに懸念のある場所で最も薄い。`--auto` ではラダーが操作者の
代わりに答えうるし、`-p` には訊く相手がいない。放って走らせるセッションこそ、
「この vault は今日は読み取り専用だ」が誰も見ていない状態で真であってほしい
セッションである。

**そしてゲートは別の問いに答えている。** `[approval.tools]` が言えるのは
ツールについて*いつ訊くか*（`always` / `never` / 既定）だけで、*このツールは
このセッションの一部ではない*とは言えない。`get_*` / `search_*` の隣に
`patch_*` / `delete_*` を並べるサーバーに対して操作者が言いたいのは、後者の
文である。

**相手方を機構にはできない。** 上流サーバーに読み取り専用モードがあるなら
使う価値はある（GitHub の remote MCP は `X-MCP-Readonly` ヘッダを尊重する。
2026-08-30 実測）。ツールが本当に存在しなくなるので、クライアントにできる
どんなことより上位である。しかし大半のサーバーにはそのモードが無く、頼む
相手もいない。**相手方の実装に依存する制御は制御ではない。** 上流の
読み取り専用は問題を小さくするが、機構を所有できない。同じ境界が
`.mcp.json` への記述も排除する —— あれは Claude Code と共有する drop-in の
オリジンであり、gem-agent だけの都合を書き込む場所ではない。

**そしてプロトコルには、照合すべき「能力」が存在しない。** MCP の `Tool` は
`name`・`title`（任意）・`description`・`inputSchema`・`outputSchema`（任意）・
`annotations`（任意）で、型はそれで全部である（仕様 2025-06-18、server/tools
§Data Types）。そのツールが世界に対して何をするかを述べるフィールドは無い。
最も近いのが annotations だが、仕様自身がこの用途に対して退けている ——
クライアントは tool annotations を "untrusted unless they come from trusted
servers" として扱わなければならない。しかも任意項目であり、大半のサーバーは
設定していない。

つまり「このサーバーの write 能力を捨てる」は、ワイヤ上の何からも機械的に判定
できない。その意味を運んでいるのはファンクション名と散文の description であり、
2 つのうち鍵にできるほど安定しているのは名前だけである。**名前で照合するのは、
本 ADR が選択肢の中から選好したのではなく、操作者の意図が取りうる唯一の表現形式
である。** これを明言する価値があるのは、結果として得られるものの価値の上限も
同時に定まるからである —— 決定の冒頭の要約を参照。

**そして能力モデルがあったとしても解決しない。** ここが、やむを得ない選択を
正しい選択に変える点である。操作者の文は「read か write か」ではない。Jira
サーバーに対してであれば「チケットは作らせたくないが、コメントは書き込みたい」
であり、そのどちらも write である。あらゆるサーバーにまたがるほど一般的な語彙は
その文を言うには粗すぎ、言えるほど細かい語彙はそのサーバーの業務語彙そのもので
あって、誰かがサーバーごとに定義し、維持し、翻訳し続けることになる。それは
このプロジェクトが既に踏み、計測した罠の形である —— mcp-bridge を生んだ前身は
profile キーを約 26 個持ち、使われていたのは 5 個で、分かりづらさは誰も使わない
機構の量から来ていた。ファンクション名は、サーバーの業務領域と操作者の意図が
既に出会っている場所である —— `create_issue` と `add_comment` という区別は、
そのサーバーを書いた人間が綴ったものである。名前を鍵にするのは能力モデルからの
後退ではなく、**操作者の実際の文がそもそも言える唯一の粒度**であり、プロトコルの
沈黙は、その仕事を争う相手がいなかったことを意味するにすぎない。

したがって決定は所有境界のこちら側、gem-agent 自身に置くしかない。これは
ADR-0008 の論法の一段下である。あの ADR はこう書いた: 情報の欠落は実在し、
クライアントには埋められないが操作者には埋められる、足りないのはそれを言う
場所だ、と。あれは「このサーバーは無確認で走らせてよい」と言う場所を作った。
本 ADR は「このサーバーのうち、自分にとって存在するのはこれだけだ」と言う
場所を作る。

プロンプトサイズは実在する副次効果だが（宣言は全リクエストの固定接頭辞であり、
5 個で足りるセッションが 200 個を運ぶ必要はない）、**正当化ではない**。ここでは
計測しておらず、以下のどれもそれに依拠していない。

## 背景 — なぜ「見せて拒否」ではないのか

自明な代替は、ツールを宣言したまま全コールを「ポリシで遮断」と拒否することで
ある。3 つの実測済みの理由で採らない。

1. **それは禁止であり、しかも最悪の位置に配達される。** 拒否文は function
   response に入り、履歴に残り、モデルが具体的な目的を追っている最中に毎
   ラウンド読み直される。ADR-0063 は 2 ヶ月かけて禁止が何をするかを計測した ——
   対象を超えて一般化し、誰も書いていない経路を発明する。ここでの第 3 の経路は
   仮定ではない。MCP ツールの背後にある能力はたいていコマンドラインの綴りも
   持つので、`mcp__github__*` を拒否すれば write レーンの `gh` になる。より
   不可視になるだけで、封じ込めではない。ファイルツールが作業ディレクトリを
   到達可能に保つ理由として既に記録している事象と同型である。
2. **モデルを、対応する挙動を持たない状態に置く。** 「登録されていない
   サーバー」はどのセッションも毎日扱っている状態で、ツールは存在せず、モデルは
   別経路を選ぶか操作者に訊く。「宣言されているのに必ず失敗するツール」は
   その持ち札に無く、モデルの既定の読み —— 一過性の障害・引数の不備・自分の
   使い方が悪い —— は ADR-0075 が 56 ラウンド・6.5M プロンプトトークンを払って
   計測した誤読そのものである。宣言して拒否することは、その誤読をセッションの
   常態にすることに等しい。
3. **歪みに見合う観測が得られない。** 拒否が与える唯一のものは「モデルが何を
   使いたがったか」の記録である。それは既に、歪みのない形で、ツールが使えた
   セッションの transcript にある（`gate_decision`・`auto_decision`・コール
   そのもの）。実際の使用実績から集合を組むほうが、拒否自身が作った
   分布の下で拒否を数えるより良い証拠である。

## 決定

機構としてはこれは 1 つのものである: **ツール名に対するフィルタを、2 つの点で
適用する** —— モデルに渡す宣言を組むところと、コールを捌くところ。以下はすべて、
フィルタが照合する名前の形（§1–§2）、操作者がそれを編集する場所（§3）、既定の
理由（§4–§6）のいずれかである。実装が述語 1 つと呼び出し点 2 つを超えて育つなら、
何かが紛れ込んでいる。

こう言うことで限界も定まる。名前に対するフィルタは、「名前はそのツールが何を
するかを表す」という慣習と正確に同じ強さしか持たない。ランタイムは
`patch_vault_file` が何をするかを知らず、それが何と呼ばれているかだけを知って
いる。名前を意図に対応させるのは操作者の判断であり、だからサーバー自身の
`readOnlyHint` は参照しないし（§6）、同じファンクションが別の名前で戻ってくる
ことをこの機構は気づけない（§5）。

### 1. 宣言集合は設定であり、機構は不在である

操作者がオフにしない限りすべて宣言される。オフにできる階層は 2 つで、3 つ目は
無い。

- **サーバー。** そのサーバーはそもそも起動しない —— プロセス無し・資格情報に
  触れない・宣言にも出ない。行はパネルに残る。サーバー名は `.mcp.json` から
  来るのであってサーバーから来るのではないからであり、だからオフのサーバーは
  いつでも戻せる。オンにすれば起動し、ツールが現れる（ADR-0039 のリロード）。
  到達不能になりそうなものが、まさに一覧に残っているものである。
- **サーバー配下のファンクション。** 宣言されず、その名前を挙げたコールは
  どのゲートより前に拒否される。サーバーは他のツールのために動き続ける。最後の
  1 個をオフにしても、サーバーは動いたまま何も宣言しない状態になる。プロセスを
  止めるのは 1 つ上の階層での明示の行為であって、操作者の背後で算術が到達する
  結論ではない。

何もオフにしない操作者には今日の挙動がそのまま見え、`.mcp.json` は今持っている
意味をそのまま保つ。

**組み込みツールは選択対象にしない。** レビュー可能な組み込みを外すと同じ作業が
`shell_exec` とシェルリダイレクトに流れ、より不可視になるだけで封じ込めにならない
—— ファイルツールが作業ディレクトリの件で既に拒んだ取引である。schema がその
間違いを提供しない。

### 2. キーは 1 つ、階層は 2 つ、優先規則は 1 つ

```toml
# ~/.config/gem-agent/config.toml — 手書き。ランタイムは書き換えない
[mcp]
exclude = [
  "chrome-pilot",                    # サーバー
  "obsidian/patch_vault_file",       # サーバー配下のファンクション
  "obsidian/search_and_replace",
]
```

```toml
# ~/.config/gem-agent/policy.toml — gem-agent が書き換える
[mcp]
exclude = ["obsidian/delete_vault_file"]
```

```toml
# <project>/.gem-agent.toml — off に足すことしかできない
[mcp]
exclude = ["github"]
```

- **項目は完全一致の名前である**: `.mcp.json` が綴るサーバー名か、サーバーが
  提供する `server/function`。パターンは無い —— 階層 2 つが、パターンが代用して
  いたグループ化を供給するからである（`mcp__server__*` は平坦な一覧で「この
  サーバー全体」と言うための綴りだった）。初稿はその平坦な一覧を持ち、さらに
  部分ワイルドカード（`mcp__obsidian__search_*` は `search_and_replace` に
  当たる）を設定エラーにする規則を持っていた。操作者のレビューがその禁止を
  退け、続く再構成が問い自体を消した。
- **サーバー単位で、最も近いスコープが丸ごと決める。** `policy.toml` がある
  サーバーについて何か言っていれば —— サーバー自体でも配下のファンクションでも
  —— それがそのサーバーの答えであり、`config.toml` のそのサーバーに関する記述は
  参照しない。スコープをまたぐ集合演算は無い。操作者がパネルで最後に言ったことが、
  先月書いたファイルを**そのサーバーについてだけ**置き換える。
- **プロジェクトファイルは `exclude` に足すことしかできない。** 絞ることが唯一の
  合成なので、ADR-0008 §4 の方向規則が構造で成立し、信頼条件は一切要らない。
- **何にも当たらない名前は無視せず報告する**（ADR-0037 の規則）。上流で改名
  されたサーバーやファンクションが、黙って何もしない行を残してはならない。
- **キーは `[mcp]` の下の `exclude` である。** 初稿は `[tools] off` と綴って
  いたが、これは一覧ではなくスイッチに読め、しかも何を名指せるのかを何も言わない。
  スコープはセクションが供給する —— 組み込みは選択対象ではなく、`[mcp]` はそれを
  キーに 1 語も足さずに言う。方向は `exclude` が供給する —— `filter` だけでは
  「残す」のか「除く」のかが開いたままで、それはまさに §4 が決着させねばならな
  かった場所である。パネルの操作子は toggle のままでよい: 操作者は行をオフにし、
  ファイルは除外されたものを記録する。

### 3. 集合を決める場所はパネルである

`/tools` に 2 階層の一覧が付く。外側はサーバーで、出所は `.mcp.json`。起動して
いるか否かに関わらず存在し、オン/オフを持つ。開くと配下のファンクションが出て、
各行がオン/オフと**その出所** —— `config.toml`・`policy.toml`・プロジェクト
ファイル・既定 —— を持つ。この出所の列は ADR-0009 のものである。

階層は装飾ではない。平坦にすれば操作者の実機で 200 行になり読めないし、起動して
いないサーバーを提示できる唯一の方法でもある —— その行は、サーバーが
`tools/list` に答えたことに依存しないからである。**承認の行も同じ 2 階層に従う**
（ADR-0009 決定 1 の修正）。`[approval.tools]` は ADR-0008 §3 以来
`mcp__server__*` を受け取ってきたので、あの表にとってもサーバーは元から自然な
単位であり、パネルの部品 1 つが両方の一覧を担える。

切り替えは ADR-0039 のリロードで即座に効き、**永続化するまではセッション限り**
である。永続化すると `policy.toml` に書かれる。まず試してから確定するのが普通の
使い方であり、手書きファイルを一発で正しく書く圧力も下がる。

### 4. 除外という向きが払う代償と、それを既に覆っているもの

`exclude` は取り除くものを名指すので、サーバーが後のバージョンで得たファンクションは
**オンで**到着する。これは人手にとって正しい向きであり（サーバーを分けるとは
45 個をオンにすることではなく 6 個をオフにすることである）、その代償は、
ファンクションが存在する前に下した判断がそれを覆わない、ということである。

その代償に対して 2 つの機構を草案に書き、どちらも落とした。落とした理由のほうが、
どちらの機構よりも価値がある。

**サーバーごとの起動時 1 行**が 1 つ目だった（`obsidian: 51 個中 8 個を宣言
（前回確認時から +2）` を毎起動）。操作者がこれを退けた。その反論は本 ADR を
超えて一般化する。**報告は制御ではない。** 誰も問いを持っていない時点で印字される
行は状態表示であり、毎起動出る状態表示はどの起動でも読まれない。印字はランタイム
に「開示した」という感覚を買い与えるだけで、操作者には何も買わない。この失敗は
このリポジトリに記録済みである —— AGENTS.md が `make labels` とリリース時の通読を
維持しているのは「4 つのリリースが説明的バナーを出荷した。誰も全体を 1 箇所で見て
いなかったから」である。しかも合流先のバナーは、起動中の stderr 書き込みを丸ごと
ティーして組み立てられている（`cmd/root.go`）—— 誰も壁を建てると決めないまま壁が
積み上がる仕組みである。

**基準線の記録**が 2 つ目だった（`policy.toml` がサーバーごとに、操作者が最後に
確認した時点のファンクション名を持ち、その外への最初のコールが 1 度だけ止まる）。
これは自分の前提で崩れる。

- **比較相手である「確認」に、それが起きる瞬間が無い。** パネルを開かない操作者
  が持つのは、初日の基準線（以後すべてが「新しい」）か、一覧取得のたびに更新
  される基準線（永遠に発火しない）かのどちらかである。その中間には誰も行わない
  儀式がある —— 仕事の中から見つけた契機ではなく、機構のために発明した契機で
  あり、ADR-0062 が実測した教訓を裏から読んだものである。
- **オフのサーバーは一覧を取得できない**ので、基準線は最後に動いた時点のもので
  固まる。数ヶ月後にオンにすれば、時間が経ったという事実だけが変化として報告
  される。
- **ツール集合は名前の安定した属性ではない。** mcp-bridge が前に立つリモート
  サーバーは集合がサーバー側で変わり、ヘッダ（`X-MCP-Toolsets`）でも変わりうる
  ので、同じエントリが日によって正当に違う一覧を返す。
- **劣化した `tools/list` は大量消失に続く大量到着として読める** —— ADR-0075 が
  計測した一過性サーバー障害のクラスそのものである。通常のサーバー障害が偽陽性
  を生む検出器は無視される検出器であり、そうなれば維持費のある装飾になる。
- **プロトコル自身の `notifications/tools/list_changed` も救いにならない。**
  それが言うのは `listChanged` を宣言したサーバーについて「セッション中に一覧が
  変わった」ことであって、「操作者が先月下した判断に対して何が変わったか」では
  ない。意味を持ちうる比較は後者だけである。

よって drift の機構は持たない。立場を述べるのに機構は要らない。危険を覆っている
のは既にあるものである —— **ADR-0008 の既定は「MCP ツールは毎回訊く」** であり、
後から現れたファンクションもそのサーバーの他と同じように訊く。露出しているのは
操作者がそれを外した場合だけ、すなわちそのサーバーへの `never` か `--auto` の
場合だけであり、それは ADR-0008 が所有する `never` の性質であって、本 ADR が
開ける穴ではない。サーバーが次に足すものについて保証が欲しい操作者は、write
ファンクションをオフにし、**かつ**そのサーバーの承認既定をそのままにする。

### 5. 何を保証し、何を保証しないか

保証するのは 1 つだけで、その保証は操作者自身が検証できる: **このランタイムは、
操作者がオフにしたツールへのコールを発行しない。** 宣言にも出さないし、
モデルが名前を出してきた場合もゲート以前に拒否する。これは `internal/archtest`
の意味でテストに固定する。

**サーバーを封じ込めはしない。** 能力は向こうに存在し続け、操作者の資格情報は
今も届き、read に見えるツールが副作用で書く可能性も残る。これはセッションが
何を依頼できるかの削減であって、境界ではない。ADR-0073 の基準が適用される ——
封じ込めは計測されるものであり、ここではカーネルで何も計測していない。後続の
設計がこの設定を壁として扱ってはならない。

改名も越えられない。`exclude` が持つのは名前なので、`patch_vault_file` としてオフに
したものが `write_note` として戻ってくれば、また宣言される。本 ADR が検出しないと
決めた drift（§4）と同じクラスであり、同じ理由で検出しない。操作者が得るのは、
自分が名指したものに対する忠実なフィルタであって、サーバーに何ができるかについて
の常設の判断ではない。

聞き手が 2 人、文が 2 つ、どちらも真である:

- モデルに対して、拒否は存在の形を取る —— *その名前のツールはこのセッションに
  存在しない*。婉曲表現ではない。セッションのツール集合は操作者の一覧が残した
  ものであり、これは登録されていないサーバーについてモデルが受け取るのと同じ文
  である。「ポリシで遮断」と言えば、§「なぜ見せて拒否ではないのか」が避けるために
  存在する状態を作り直すことになる。
- 操作者に対して、削除済みツールが名指しされたことを transcript が専用の
  レコード種別で記録する。一覧を設定した本人から隠すものは何も無い。

真に未知の名前に対する既存のゲート（rule tier の `Review`、"unknown tool"）は
変更しない。この非対称は意図的である —— 操作者が外した名前はランタイムが持つ
事実であり、誰も登録したことのない名前はそうではない。

### 6. やらないこと、とその理由

- **`[approval.tools]` に `deny` 値を足さない。** 2 つの表は別の軸のままにする ——
  いつ訊くか、と、何が存在するか。融合すれば「宣言されているが拒否される」が値の
  組み合わせとして表現可能になり、それは本 ADR が防ぐために書かれている状態その
  ものである。非対称は 1 つの綴りに現れている: 裸の `"*"` は承認表では設定エラー
  （全ゲートを解除する）だが、`exclude` では無意味である
  （セッションから MCP ツールが 1 つも無くなるだけで、それはパネルがサーバー単位で
  到達する状態である）。
- **`[[hooks.pre_tool_use]]` による常設 deny を採らない。** 今日でも動くが、hook が
  コールの引数を渡されるのは 1 回ごとに判断するからである。「このツールはこの
  セッションの一部ではない」という常設の決定には読むべき引数が無く、しかも操作者が
  探す場所（パネル）の外に不可視で置かれる。可能であることは、正しい置き場所の
  論拠ではない。
- **MCP の annotations を分割の出所にしない** —— 背景を参照。仕様自身が、
  サーバーが信頼できるのでない限りクライアントは annotations を untrusted として
  扱えと要求しており、しかも任意項目で、gem-agent は今日それを読んでいない。
  せいぜいパネルの行の並びや初期チェックを提案して操作者に確認させるまでで、
  設定そのものを決めさせない。
- **mcp-bridge では filtering しない。** その RFP が masking を scope 外と決めて
  いるし、HTTP/OAuth 経由のサーバーの下にしかいない。
- **名前つき集合（プロファイル）を作らない。** `ir` と `dev` を持つ
  `[tools.profiles]` 表を名前で選ぶ案は本 ADR の初稿にあり、操作者が落とした。
  集合を名前で切り替えるのは、パネルが既に見せている集合の上にもう 1 つ命名体系を
  重ねることであり、mcp-bridge を生んだ実測はまさにこの機能についてのものである
  —— 置き換えられた前身は profile キーを約 26 個持ち、使われていたのは 5 個で、
  記録された結論は「分かりづらさの根本は個々の欠陥ではなく未使用機能の量」で
  あった。文脈の切り替えは、代わりにパネルでサーバーを切ることで払う。必要性が
  実証されたら、名前つき集合は後からこの上に重ねられる —— ここでは始めない。
- **名前の上に能力の語彙を重ねない。** `[tools.capabilities] jira = "read"` の
  ような表も、ファンクションが何をするかについての gem-agent 側の分類体系も
  作らない。理由は背景のとおり —— 操作者が必要とする区別はサーバーの業務領域
  （チケットかコメントか）にあり、一般語彙はそこに届かず、サーバーごとの語彙は
  サーバーの数だけ維持する第 2 の体系になる。再提案されたら最初に訊くべきなのは、
  「`exclude` では言えないどの文が、それによって言えるようになるのか」である。
- **サーバーごとの厳格モードを持たない。** 「このサーバーの配下は allowlist で、
  将来の追加は入れない」と言う手段は用意しない。そちらが安全な向きであり草案にも
  あったが、6 個を除くために 45 個を列挙する代償があり、その事例を代わりに何が
  覆うかは §4 が述べる。ゲートで足りないと分かったら —— つまり、あるサーバーを
  分割しつつ `never` も必要とする事例が出たら —— 最初に足すのはこれであり、
  同じキーの上への小さな追加で済む。

### 7. 何を、どう計量するか

問いは「宣言はどれだけ大きいか」ではなく「小さい集合は、実際に費やされる単位で
何を取り戻すか」である。以下のどれも本決定のゲートではない —— 機能は上の背景で
立っている —— リリースノートが何を主張してよいかを較正するだけである。

1. **プロンプトトークンを end-to-end で。** 同一の些細なプロンプトで `-p` を
   2 回、片方は何もオフにせず、片方は操作者の実運用の集合で。ADR-0057 の `usage` レコード
   が既にコール毎の `prompt`・`cached`・`thoughts`・`tool_prompt`・`total` を持って
   いるので、`prompt` の差が宣言のコストであり、それは API が課金する単位であり、
   ADR-0057 のカタログ価格を通せば金額でもある。各 3 回。プロンプトは固定なので
   変数はツール集合だけになる。
2. **初回ラウンドだけでなく cached の割合も。** 宣言はリクエストの接頭辞にあるので、
   初回の数字は長いセッションの節約を過大に見せる。`cached` は同じレコードにある ——
   初回ラウンドと定常ラウンドを分けて報告し、初回の数字を単独で引用しない。
3. **起動、サーバーをオフにできるようになった以上。** 最初のプロンプトまでの
   実時間と子プロセス数を、同じ 2 構成で。§1 のサーバー階層が追加した数字で
   あり、トークン数ではない。

計量せず、主張もしないもの: ツール選択の精度。集合が小さいほうがよく選べる、は
もっともらしいが、正直に言うには課題集合と反復が要る。ここでは何もそれに依拠して
いない。

リクエスト側の正確なバイト数がどうしても欲しくなったら、それは
`http.RoundTripper` を挟む live テストである ——
`internal/llm/wirebytes_live_test.go` が既にレスポンス側を挟んでおり、写すべき型
がある。ただし (1) の隣では余談である。課金されるのはバイトではない。

**2026-09-08 実測**（v0.71.0、実装前。縮小構成は scratch の `mcp.json` を編集して
作った —— サーバー階層の除外が行うことと同じである）。固定の些細なプロンプト 1 つ、
`gemini-3.8-flash`、同一プロジェクトディレクトリ、隔離した state、同一の
`config.toml`。変数はサーバー一覧だけである。

| 構成 | サーバー | ツール | prompt トークン（round 1） |
|---|---|---|---|
| MCP サーバー無し | 0 | 0 | 5,804 / 5,805 / 5,809 |
| 上位 3 サーバーを除外 | 21 | 130 | 32,647 |
| 操作者の一覧 | 24 | 249 | 73,143 / 73,144 / 73,151 |

- **宣言は 67,340 トークン、プロンプトの 92% である。** 実行ごとの振れは 5 トークン
  で、分散はツール集合が全てである。
- **24 サーバーのうち 3 つがそのコストの 60%**（119 ツールで 40,499 トークン）。
  `tools/list` から直接読んだ宣言バイト数 —— 249 ツールで 242,350 バイト、
  1 トークンあたり約 3.6 バイト —— はこの節約を誤差 6% で予測した。総量が分かって
  いれば、バイト数は使える推定量である。
- **初回ラウンドの数字を単独で引用してはならない。** (2) の言うとおりだった。
  同一セッションの 2 ラウンド目では prompt 73,382 に対し **cached 68,660**。宣言は
  接頭辞ごとに 1 度だけ全額を払い、以後の各ラウンドは cached 料金で払う。除外が
  節約するのはセッションごと（および接頭辞が変わるごと）の全額 1 回と、以後の
  cached 分である —— 実在するが、見出しの数字ではない。
- **起動の実時間は 3 回では使い物にならなかった**（モデルのレイテンシが支配する）。
  起動について確かなのはプロセス数で、24 対 0 である。

## 検討した代替案

- **見せて拒否** —— 却下。2 つ目の背景節のとおり。
- **平坦なパターン一覧と、それを名前で選ぶプロファイル** —— 本 ADR の初稿。
  実測の履歴を持つ複雑さとして操作者が落とした（§6）。パターンが担っていたものは
  §1 の 2 階層が、発明すべき名前無しで担う。
- **除外一覧ではなく allowlist** —— §6 の理由で却下: 安全な向きは、ほぼ全部である
  「残すもの」を列挙させる代償を伴う。
- **部分ワイルドカードの禁止** —— 操作者のレビューで却下。不可視な展開という問題を
  表現力の削減で解こうとしていた。§3 の表示が、問題のある場所で解いている。
- **上流の実装者に読み取り専用モードを求める** —— 制御ではない。大半のサーバーには
  頼む相手がおらず、実際に動いているバージョンについて何の保証も無い。
- **`.mcp.json` を編集する** —— 却下: あれは Claude Code と共有する drop-in の
  オリジンである。
- **MCP annotations から read/write を導出する** —— 設定としては却下。§6 参照。

## 影響

- キーは 1 つ、`[mcp] exclude`。グローバル設定・`policy.toml`・プロジェクト
  ファイル（足すことのみ）に置く。項目は `server` か `server/function`。他の
  全キーと同じく strict decode。
- レジストリは外した名前を保持する。そのためコールは未知名ではなく拒否になる。
  `toolDefs` は有効集合から宣言を作り、ADR-0039 のリロード経路が組み直す。
- オフにされたサーバーは起動しない。`/mcp` がそう言い、パネルは `.mcp.json` から
  いずれにせよ一覧に出す。
- `/tools` に 2 階層の一覧・出所・toggle が付く。同じ部品が `/settings` の承認の行を
  描画する（ADR-0009 修正）。
- **起動時バナーには何も足さず、サーバーが以前に提供していたものについて状態を
  記録しない。** 新たに増える起動時出力は、`exclude` にあって何にも当たらない名前
  （§2）だけである。
- 削除済みツールへのコールの transcript レコード。テレメトリは不変 —— コールは
  走らないので報告すべき `tool.call` が無い。
- テスト: 3 ファイル間のサーバー単位の優先規則、プロジェクトファイルが `exclude` に
  足すことしかできないこと、拒否経路（ゲートに到達しない）を
  `internal/archtest` で固定、drift 報告、何にも当たらない名前、**集合を変えた状態での resume**（履歴に宣言外ツールへのコールが残る）、セッション途中の
  リロード。
- ドキュメント: README / README.ja（モデルから何が見えるかの段落）、configuration・
  tools・approval・integration の各リファレンス（両言語）、RFP のセキュリティ層、
  `config.example.toml`、AGENTS.md の構造表、CHANGELOG、両 INDEX。新しい操作者向け
  文字列は `uitext` の両カタログへ。
- §7 の計量を、実装の前か同時に取る。それはリリースノートに置くものであって、
  正当化に置くものではない。
