# ADR-0035: OpenTelemetry 監査ロギング

| 項目 | 値 |
|------|----|
| ステータス | **承認済み** |
| 日付 | 2026-08-21 |
| 拘束対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | オペレーター: 実用的になってきたので職場利用にはロギングが必要な水準 — OpenTelemetry でログ取りできるとよいのでは |

## 文脈

JSONL transcript は完全忠実・会話形・ローカルの記録 — resume の正本で
あって監査証跡ではない。職場に必要なのは運用形のビューである: どの
セッションが走り、どのツールがどんな結果で実行され、何が誰に（オペ
レーター・allowlist・ポリシー・auto-approve のどの層に）承認され、
何がマシンから出て行き、いくら掛かったか — それも組織自身のコレクタ
の中、他の監視対象と同じ場所で。

## 決定

### 1. OTLP **ログ**、v1 — トレースでもメトリクスでもなく

監査イベントを OTel ログレコードとして OTLP（gRPC / HTTP）で送る。
SIEM はログをネイティブに消費し、オペレーターのスタック（Splunk 等の
前段のコレクタ）がまさに宛先だからである。トレースは美しいが別の
問いに答えるもの — 実需要が出たら自分の ADR を持つ。

イベント: `session.start` / `session.end`、`turn.start` / `turn.end`
（ラウンド数・所要・トークン合計・エラー種別）、`tool.call`（名前・
mutating・切詰め詳細・所要・結果 ok/error/denied）、
`approval.decision`（ツール・判定・経路: operator / allowlist /
policy / auto-rule / auto-model・must_prompt・切詰め理由）、
`compaction`、`media.upload`（バイト数・dedupe）。リソース属性:
サービス名/バージョン・セッション id・プロジェクトディレクトリ・
ホスト。

### 2. 既定 OFF、有効化できるのは**あなたの** config だけ

```toml
[telemetry]
enabled  = false            # 既定
backend  = "gcp"            # gcp | otlp-grpc | otlp-http
endpoint = "localhost:4317" # otlp-* のみ
insecure = false            # otlp-* のみ
```

エクスポーターはセキュリティツールからの**新しいエグレス経路**なので
opt-in であり、`[telemetry]` テーブルはオペレーターのグローバル
config にしか存在しない — プロジェクト側 `.gem-agent.toml` からは
テレメトリの有効化も宛先変更も**構造的に不可能**: clone した
リポジトリが exfil シンクを仕込めてはならない。OTLP の認証ヘッダは
`headers_file` — モード 0600 の JSON ファイル（慣例として
`~/.config/gem-agent/auth.json`、ヘッダ名 → 値）から読む: 環境変数は
launchd・cron・プロファイルを読んでいないシェルで消え、環境ごと
静かに消える認証は職場の認証ではない（オペレーターの指摘）。
所有者専用以外のパーミッションは拒否する — SSH 鍵と同じ規律である。
ファイル未設定なら標準の `OTEL_EXPORTER_OTLP_HEADERS` も従来どおり
効く。

### 2a. 既定バックエンドは GCP — 資格情報は既にそこにある

このツールはモデル呼び出しのたびに GCP プロジェクトへ認証している。
その**同じプロジェクト**の Cloud Logging が監査証跡の自然な置き場で
ある（オペレーターの観察）。`backend = "gcp"` は Vertex が使っている
ADC そのままでイベントを Cloud Logging に書く — ログ名 `gem-agent`、
イベント名と属性は構造化 JSON ペイロード、セッション/バージョン/
プロジェクトディレクトリはラベル。コレクタ基盤ゼロ:
`enabled = true` がセットアップのすべてである（加えて
`logging.googleapis.com` の有効化と `roles/logging.logWriter`）。
OTLP バックエンドは SIEM 前段の組織コレクタ向けに残る。内部的には
GCP バックエンドも同じ OTel SDK パイプライン上の一エクスポーターで
あり、バッチングも no-op ゼロ値も「決して害さない」規則（§4）も
同一である。

### 3. メタデータのみ、ペイロードは決して送らない

プロンプト・モデル応答・ファイル内容・思考サマリはこの経路から
マシンを出ない — 全文の記録はローカルの transcript のままである。
送るのは監査が求めるものである: ツール名と結果、shell のコマンド行
（切詰め — 「shell_exec が走った」だけでコマンドの無い監査証跡は
監査証跡ではない。コマンドに秘密が混ざることは有り得るが、その
トレードは隠さずここに明記する）、ファイルパス、egress URL と検索
クエリ（DLP レビューが見たいものそのもの）、トークン数、モデル名、
承認の判定と理由。

### 4. テレメトリは決してセッションを害さない

ロギングの失敗で本体が失敗するバックアップツールは優先順位が逆で
ある。レコードは SDK のバッチプロセッサ経由（fire-and-forget）、
到達不能なコレクタは stderr へ **1 回だけ**警告してその後は静かに
劣化、終了時 flush は 3 秒上限。無効時は no-op シンクがゼロ値で、
コストゼロ・呼び出し側のフラグ分岐もゼロ。

## 帰結

- 職場デプロイは `[telemetry]` を有効化するだけで（既定は同じ GCP プロジェクトの Cloud Logging）、監査証跡が他の
  すべてと同じ場所に揃う。既定の体験は不変・オフラインのまま。
- 依存ツリーに OTel log SDK と OTLP エクスポーターが加わる。
- コマンド行と URL は設計としてコレクタに行く。自組織の SIEM にすら
  それが秘匿すべき情報だと考える組織は、テレメトリを OFF のままに
  すべきである。
