# ADR-0034: キャンセルは呼び出しを終わらせる — プロセスグループ・WaitDelay・最後の脱出口

| 項目 | 値 |
|------|----|
| ステータス | **承認済み** |
| 日付 | 2026-08-21 |
| 拘束対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | オペレーター: スキルの python ツールコールが返らず、Ctrl+C は「中断中…」のままデッドロック |

## 文脈

`shell_exec` は `exec.CommandContext` + `CombinedOutput()` でコマンドを
実行していた。タイムアウトや Ctrl+C の際、Go が kill するのは**直接の
子だけ** — `sandbox-exec`（または bash）である。コマンドが起動した孫
— スキルの python — は生き残り、継承した stdout/stderr パイプを握った
ままで、`CombinedOutput` 内部の Wait はそのパイプが EOF になるまで
ブロックする。両方のキャンセル経路が同じ穴に落ちる: 120 秒タイム
アウトは発火した後 Wait でハングし、オペレーターの Ctrl+C は context
をキャンセルした後、同じ Wait でハングした。TUI は「中断中…」を正直に
表示し続けた — ターンの goroutine は二度と戻らないので TurnDone は
永遠に届かず、どのキーも効かなかった。

## 決定

### 1. 直接の子ではなく、プロセス**グループ**全体を殺す

すべてのシェルコマンドはプロセスグループリーダーとして起動し
（`Setpgid`）、context の `Cancel` はグループへ SIGKILL を送る
（`kill -pid`）: sandbox-exec・シェル・python・コマンドが起動した
その他すべてが一緒に死に、パイプは即座に閉じる。

### 2. 背後の防波堤としての `WaitDelay`

`setsid` を呼ぶ、あるいは二重 fork で新グループへ逃げるプロセスは
グループ kill を逃れる。`WaitDelay`（2 秒）が被害を限定する: context
キャンセル後・直接の子の死後、Wait は継承パイプを待つのをやめて
戻る。逃げた側は一時的に孤児として生き残るかもしれないが — オペ
レーターのセッションはそれに付き合ってハングしない。切断前の出力は
通常どおり保持・切り詰めされる。

### 3. TUI の最後の脱出口

まだ想像していない形で将来のツールが詰まったときのための多層防御:
「中断中…」表示中の 2 回目の Ctrl+C は「ツールがキャンセルに応答して
いない・もう 1 回で終了する」と警告し、3 回目で gem-agent を終了
する。transcript はイベントごとの追記なので、詰まった呼び出しまでの
すべては既にディスクにある — メッセージはそれも伝える。2 回ではなく
3 回: 慌てた二度押しが、あと 1 秒で正常に終わるはずだったセッション
を殺してはならない。

## 帰結

- 子を起動するシェルコールも、タイムアウトと中断で終わるように
  なった — 実測: バックグラウンドの子がパイプを握るコマンドが、従来
  は子の寿命いっぱいハングしたところ、キャンセル後ミリ秒で返る。
- グループ SIGKILL は設計として唐突である: キャンセルされたコマンド
  にクリーンアップの猶予はない。ここでのキャンセルは常に「いま
  止めろ」であり、graceful-then-forceful はこのバックアップツールに
  不要な複雑さである。
- まれな setsid 逃亡者は孤児プロセスとして呼び出しより長生きする。
  代替案 — セッションをハングさせる — の方が厳密に悪い。kill は
  best-effort、リターンは保証、である。
