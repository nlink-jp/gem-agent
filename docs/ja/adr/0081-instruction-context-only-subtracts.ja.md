## Context

評価器の指示文脈は**今日すでに双方向である**。ADR-0038 は「操作者の依頼
との整合は承認を支持する」と書いており、2026-09-09 にそのとおりの挙動が
計測された: 後半ラウンドの `make build` は、そのターンの入力が「続けて」
のとき confidence 0.95 で承認された — "Standard build command within
project directory"。

帰結として、この経路で評価器に届くものは verdict を承認*方向へ*動かせる。
経路は操作者の打鍵テキストであり、injection の攻撃者が直接書くことは
できない — が、ログやエラーメッセージやファイル抜粋を自分のプロンプトに
貼った操作者は、このシステムが信頼する唯一の入力に攻撃者由来のバイト列を
持ち込んでいる。1 ターン幅でも既にそうであり、何かの提案が持ち込んだ
危険ではない。

ADR-0080 §5 はそのペイロードにもう 1 つ — セッションモード — を加え、
サンドボックスを名指すことが「檻があるから承認してよい」という読みを
誘わないことを計測した。1 件の計測は証拠であって、性質ではない。以下が
性質である。

## Decision

### 1. verdict は 2 つの判断の合成である

```
approve = （指示文脈**なし**で到達した判断）
          AND
          （指示文脈を与えた評価）
```

- **Safe 層。** 合成するものが無く、ラウンドも走らない。*実装時にコード
  と突き合わせて訂正:* 本項は当初「`safe` でも aligned ラウンドが走る」と
  書いていた。それは ADR-0080 の第 2 稿 — 制約の経路が散文しか無く、
  プロジェクト内書込を評価器へ届かせる必要があった頃 — の要求である。
  採択された ADR-0080 はそれをレーン上限で答えているので、いま `safe` を
  aligned ラウンドに通しても何も買わず、コール 1 件ごとにモデル 1 ラウンド
  を払うだけになる。保証は影響を受けない: 指示文脈はそれらのコールに
  そもそも届かないので、そこで承認を作ることはできない。
- **Review 層。** baseline は指示文脈を与えないモデルラウンド、すなわち
  ADR-0038 以前にこのシステムが下していた評価である。これがエスカレート
  すればコールはエスカレートし、aligned は走らない。文脈に救済を許さない
  以上、訊くことが無い。その場合 1 ラウンド、baseline が承認したときだけ
  2 ラウンド。

baseline は文脈非依存なので、セッション内ではツール名と引数でキャッシュ
できる。

### 2. 合成が保証すること

文脈を通って評価器に届くものは、承認を**剥がす**ことしかできない。
操作者のプロンプトに紛れ込んだ攻撃者のバイト列が達成できるのは余計な
エスカレーション — 利便性の denial — であって、文脈なしの判断が下さな
かった承認を作ることはできない。下限は ADR-0038 以前の評価器そのもので
ある。

これは ADR-0080 §5 が探した「檻があるから承認してよい」の読みも縛る:
合成の下では、文脈中のどんな記述も単独で承認を生み出せない。モデルが
そこから何を結論しようとも、である。

### 3. なぜプロンプトで指示しないのか

「整合はエスカレーションの根拠にしてよいが、承認の根拠にはするな」は
文字列規則であり、この性質は指示に従わないモデルに対しても成り立たねば
ならない。合成が成り立つのは 2 つの答えの結び方によってであって、どちら
に何を訊いたかによってではない — ADR-0020 §4 がメモリ書込をモデル層から
外し、「気をつけろ」と言わなかったのと同じ理由である。

### 4. 意思変更は影響を受けない

「じゃあ直して」は、baseline が承認し、aligned がもう反対しない、という
形で通る。制約の解除に文脈が承認を*作る*ことは一度も必要ないので、
操作者に従うことが最も重要な場面で、減算規則は何も損なわない。

## Alternatives considered

- **1 ラウンドで 2 つの自己申告フィールドを返させる**（baseline verdict
  と alignment verdict）。却下: 同じ文脈が両方に影響しているので、その
  分解は合成の性質ではなくモデルの自己申告である。
- **`safe` のコールにも baseline を走らせる。** 不要: それらについては
  ルール層が既に文脈なしの判断であり、第 2 の意見は 1 ラウンドを払って
  同じ結論を導き直すだけである。
- **指示文脈を丸ごと外す。** 却下: 矛盾を可視にしているのはそれであり
  （禁じられた build をラウンド 1 と 5 でエスカレートさせたのは計測済み）、
  ADR-0080 §5 はこの経路の存在に依存している。

## Consequences

- baseline が承認する Review 層コールは、評価器 1 ラウンドではなく 2
  ラウンドになる。`safe` コールの本数は変わらない。
- 整合する指示によって承認まで運ばれていた verdict が、文脈なしの判断も
  通さなければならなくなるので、これまで走っていたコールの一部はエスカ
  レートする。CHANGELOG では *Changed*。
- **未計測。** 本 ADR が止めようとしている事例 — 操作者自身のプロンプト
  に混入した攻撃者テキストが verdict をエスカレートから承認へ動かす —
  を構成したプローブはまだ無い。合成はそれを「計測により起こりにくい」
  ではなく「構造上不可能」にするものであり、そこが眼目だが、トレードの
  コスト側は出荷前に数値を要する。
