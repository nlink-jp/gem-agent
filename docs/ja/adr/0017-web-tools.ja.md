# ADR-0017: Web アクセス — グラウンディング検索と要約フェッチ

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-19 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | オペレータ: Web サーチと Web フェッチ相当が欲しい。検索は「単純な検索 API がほとんど存在しない」ため Gemini の Grounding with Google Search を使うのがよい。フェッチは取得内容を素のままメインモデルに流すより、要約機能で要点抽出と情報整理をさせたほうがよいのでは |

## Context

フォールバックには Web を見る目が無い。検索については、オペレータの指摘は
組織の歴史でもある: 素の Web 検索 API は乏しく、その規約はエージェントに
敵対的 — 組織自身の agentic-web-search プロジェクトがまさにそれで凍結された。
**Grounding with Google Search** は Vertex の first-party 経路であり、同じ
クライアント・同じ認証・規約もクリーンである。

フェッチについては、オペレータは正しい問い（「何かよい手はあるか？」）と
答えの半分（生ページをメインモデルに注がない — 抽出と整理を先に）を出した。
残り半分は Vertex の **URL Context ツール**である: モデルが URL を
**サーバーサイドで**取得し、自分のコンテキストウィンドウの中で読む。

## Decision

ツールを 2 つ。どちらも確立済みパターン（圧縮、summarize_file）の側呼び出し —
function ツールを一切与えない LLM 呼び出しが、結果文字列を 1 つ返す。

1. **`web_search(query)`** — **メインモデル**での呼び出し。GoogleSearch
   ツールだけを有効にする。グラウンディングされた回答は、grounding metadata
   から抽出した**出典**（タイトル・ドメイン・URI）付きで返る — 主張を信じる
   のではなく確認できるように。検索グラウンディングと function calling は
   1 リクエストに同居できないが、側呼び出しアーキテクチャは元々同居させない
   ので問題にならない。
2. **`web_fetch(url, focus?)`** — **要約モデル**（`[model].summary`、軽量枠）
   での呼び出し。URL Context ツールを有効にする。プロンプトはオペレータの
   指定そのもの — 整理された抽出: そのページが何か、正確な名前・数値・日付を
   保った密度の高い要点、focus による重み付け — であって、転写ではない。
   コンテキスト経済が三層重なる: ページのバイト列はローカルプロセスに入らず、
   要約モデルの**出力**にも入らず、メイン会話にも入らない。入るのは要約だけで、
   その節約は毎ラウンド繰り返し効く（ADR-0014 の論法）。
3. **両ツールとも既定で承認ゲート（`Mutating: true`）**。効果としては
   読み取り専用だが、**リクエスト自体がエグレス経路**だからである: クエリや
   URL は、注入された指示がモデルの読めるものを外へ持ち出せる場所になる。
   緩和は ADR-0008 のツール別ポリシー（`"web_search" = "never"`）で行う —
   これで one-shot モードでも使えるようになる。オペレータ単位の意図的な
   判断であり、ADR-0008 はまさにこのために作った。
4. **Web コンテンツは非信頼であり、隔離は層について正直に。** 要約/回答は
   通常のツール結果として返り、通常の nonce ラップを受ける（ADR-0010 の
   免除なし — 非信頼由来は非信頼のまま）。側呼び出しの内側では、ページを
   nonce ラップできない（サーバーサイドで取得されるため）。だからフェッチの
   プロンプトが防御的枠書きを持つ — ADR-0012 の立場であり、それが弱い層で
   あることも同様に明言する。
5. **サーバーサイド取得は制限ではなくセキュリティ特性である。** URL を
   取得するのは Google のインフラであってこのマシンではない: localhost・
   RFC1918・オペレータの LAN は構造的に到達不能 — SSRF というクラスが
   アーキテクチャの時点で死ぬ。コストは便益の鏡像で、イントラネットや
   認証付きページは取得できない。取得失敗時はそう告げる（URL Context の
   メタデータは URL ごとの状態 — error・paywall・unsafe — を運ぶ）。
6. 取得失敗・ブロック・空回答は理由を名指す報告されるエラーであり、
   無言の空結果には決してしない。

## Consequences

- フォールバックが調査できるようになる: 出典を確認できる検索と、整理抽出
  つきのフェッチが、1 つのエージェントループの中で回る。
- エグレスゲートの既定値は、オペレータがポリシー 2 行を書くまで承認
  プロンプトが 2 つ増えることを意味する。このオペレータの脅威モデルには
  それが正しい既定であり、緩和はペースト 1 回である。
- フェッチの品質は要約モデルと URL Context のフェッチャ（JS 実行なし・
  サイズ上限）に律速される。それに敗けるページでは失敗が名指しされる。
  ローカルフェッチのフォールバックは SSRF を再開させるので、意図的に
  作らない。
- web_search はメインモデル（グラウンディング品質が眼目）、web_fetch は
  要約モデル（分量が眼目）。新しいノブは無し。

## Alternatives considered

- **サードパーティ検索 API** — 却下。乏しさと規約。オペレータの指摘であり、
  凍結された agentic-web-search の教訓でもある。
- **ローカル HTTP フェッチ + 本文抽出** — 却下。オペレータ自身のネットワーク
  への SSRF を再開させ、HTML パースが必要になり、JS には答えられず、出力は
  結局要約工程を要する。サーバーサイド取得 + 要約はそのどれも無しで仕事を
  済ませる。
- **サイズ上限つきで生テキストを返す** — 依頼文の中でオペレータ自身が却下:
  抽出と整理は切り詰めに勝る（上限は先頭 N バイトを残すが、要約は事実を残す）。
- **メインのエージェントループに GoogleSearch/URLContext を直接有効化** —
  却下。グラウンディングは function ツールと同居できないし、できたとしても
  全ターンからの無制御エグレスは、ここで選んだゲート付き既定の正反対である。
