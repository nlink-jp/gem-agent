## Context（背景）

read レーンの環境変数 scrub は ADR-0073 §6 のレビュー所見として入った。素の
`env` が操作者の export したトークンを transcript に印字したので、
`(token|secret|passw|api[_-]?key|credential|private[_-]?key|access[_-]?key|auth)`
に一致する名前の変数を read レーンの子から外した。その後 ADR-0085 のリリースで、
scrub の中にあった `GEMAGENT_` 接頭辞の免除を名前一覧に置き換えた。同じ接頭辞
免除が同居ランタイムで `LAGENT_API_KEY` を通すからである（システムリスク
レビュー 2026-09-13、R01）。

2026-09-13 に実測した 2 つの事実が、これは元から制御ではなかったと言う。

**6 つの扉のうち 1 つしか覆っていない。** 他の子はすべて操作者の環境を丸ごと
受け取る:

| 子 | 環境変数 |
|---|---|
| read レーンのシェル | scrub 済み |
| write レーンのシェル | 全部 |
| operator レーンのシェル | 全部 |
| `!` 直接シェル | 全部 |
| MCP サーバ | 全部（`cmd.Env = os.Environ()`、加えて設定自身の `env` ブロック） |
| フック | 全部（`cmd.Env` 未設定なので継承） |

**そしてその 1 つの扉も漏れる。** 出荷中の正規表現では次が素通りする:

```
OPENAI_KEY  GH_PAT  STRIPE_SK  ANTHROPIC_KEY  GPG_PASSPHRASE
SESSION_COOKIE  BEARER  LICENSE_KEY  PAT
```

`NPM_TOKEN` は捕まり `OPENAI_KEY` は捕まらない。システムリスクレビューも 10 章で
同じ結論に達し、平明に書いている。「秘密を環境変数に置けば一律に保護される、
とは説明できない」。

### 許可リストが解にならない理由

分かりやすい修理 — 拒否リストを反転し、read レーンに必要な変数だけを渡す —
は提案されたが、ここで却下する。正当なツールチェインが読む変数の集合は、秘密が
取り得る名前の集合と同じくらい open-ended である。`GOFLAGS`・`GOMODCACHE`・
`GOPRIVATE`・`PYTHONPATH`・`VIRTUAL_ENV`・`JAVA_HOME`・`CARGO_HOME`、そして
来月出るツールがもう 1 つ。許可リストは無限の一覧を「秘密らしい名前」から
「何かが必要とする名前」へ移すだけで、失敗の形を「静かな漏洩」から「一覧が
追いつくまで read レーンのビルドが壊れる」へ変える。それは ADR-0084 が取り除く
ために書かれた摩擦である。

つまり環境変数には、どちら側にも有限領域が無い。これが ADR-0086 との違いである。
あちらにはカーネルが実在し、判定をそこへ移せた。こちらにはカーネルが無い。環境
変数は親が `exec` に渡すものが全てであり、それを濾す OS の機構は無い。判定を
移すべき有限領域が無いなら、規則は存在すべきでない。

### 何が有限か

1 つだけ有限で、列挙可能で、コードを書く当事者が網羅的に知っている集合がある。
**ランタイム自身の名前空間の変数である。** `GEMAGENT_*` を読むのは他に誰も
いない。ランタイムは自分で書いたのだから全部知っている。今日の時点で、完全に:

| 用途 | 変数 |
|---|---|
| ランタイムが自分のために読む | `GEMAGENT_STATE_DIR`・`GEMAGENT_PROJECT`・`GEMAGENT_LOCATION`・`GEMAGENT_MODEL`・`GEMAGENT_MCP_STDERR` |
| ランタイムが子のために export する | `GEMAGENT_WORK_DIR`・`GEMAGENT_PROJECT_DIR`・`GEMAGENT_SESSION_ID` |

元の接頭辞規則は、領域について誤ってはいなかった。反転していたのである。
`GEMAGENT_*` を**残し**、残り全部を推測していた。同じ領域の正しい読み方は、
3 つの export 以外の `GEMAGENT_*` を**外し**、他は何も推測しないことである。

*2026-09-13 リリースレビュー後の修正: §Context の「`GEMAGENT_*` を読むのは他に
誰もいない」は偽であり、反例は org 自身のものである。`gem-usage-lens` は
`GEMAGENT_STATE_DIR` を意図的に読む（`core/platform/paths.go`）。隔離した
gem-agent を、それが実際に書く場所で測るためである。決定は維持する。この変数は
外す側のままである。隔離した state 根を使う操作者が、そのセッションのシェル
レーンから `gem-usage-lens` を起動すると、隔離先ではなく既定の sessions 根を
見るようになる。対処は兄弟ツールが既に持っているもの — `--sessions-root`、
あるいは自身の設定の `[sources]` — である。セッションについての事実を必要とする
子には、継承させるのではなく渡すべきである。入れ子のランタイムが、自分で選んで
いない環境から同一性を取らないようにするのと同じ規則である。前提として正しい
言い方はより狭い: 他の誰かが読んでいないとは仮定できないが、ゆえにランタイムは
名前空間全体に対して行動してよく、読む兄弟はそれをパラメータとして受け取る。*

## Decision（決定）

### 1. 操作者の環境変数には触れない

`sandbox.ScrubEnv`・`secretEnvRe`・`runtimeExports` を削除し、承認リファレンスの
read レーン行にある主張も併せて削除する。read レーンのコマンドは操作者が置いた
ままの環境を受け取る。そこで走るプログラムがどの変数を必要とするかは、この
ランタイムが答えられる問いではないからである。

### 2. ランタイム自身の変数はどの子にも渡らない

このランタイムが起こす子 — read・write・operator レーンのシェル、`!` シェル、
MCP サーバ、フック — は、親の環境からランタイム自身の設定変数を除いたものを
受け取る。3 つの export（ADR-0071）は今日どおり付加する。子のために存在する
ものだからである。

関数 1 つを全ての spawn 地点に適用する。子を足したときに規則を継がないことが
起きないようにするためである。

### 3. 分割はテストで閉じる。注意深さでは閉じない

非テストコードの `GEMAGENT_` 文字列リテラルは、2 つの一覧のどちらか一方に
ちょうど 1 回現れねばならない。新しい変数は、自分のものか相手のものかを分類
するまでビルドを失敗させる。

これが R01 の本来の要求である。将来の `GEMAGENT_API_KEY` は子に届かない。
正規表現が `key` という語を認識したからではない。ランタイムの名前空間に属し、
export ではないから外れるのである。クラスは構成によって閉じ、その構成は、無限の
集合についての推測ではなく、著者が列挙する集合の分割である。

### 4. 真であることを 1 回だけ言う

gem-agent が起動された環境は、それが起こす全ての子に届く。文書は保護の主張の
代わりにそれを言い、操作者が実際に持つ対処を名指す。モデルに渡したくないものを
持たないシェルから起動するか、起動時にその変数を落とす。

## Consequences（帰結）

- read レーンの素の `env` は操作者の export した変数をモデルへ印字するように
  なる。write レーン・operator レーン・MCP サーバ・フックでは既にそうだった。
  read レーンが「規則があるかのように見せる例外」であることをやめる。
- 無限領域の規則が 1 つ消え、無限領域の規則はそれを置き換えない。
- `GEMAGENT_*` が子へ届かなくなる。今日の利得は小さいが実在し
  （`GEMAGENT_PROJECT` は org 規則が共有物から外す環境固有値である）、明日の
  利得は、ランタイムが後から自分のために読むあらゆる変数について全部である。
- **シェルレーン内で入れ子に起動した `gem-agent` は、親の設定変数を継承しなく
  なる。** 別に起動されたランタイムがそうすべきように、自分の config ファイルを
  読む。子のランタイム同一性はパラメータであって、継承した環境から推定する
  ものではない。
- ambient な `GEMAGENT_*` を読んでいた MCP サーバは、MCP 設定の `env` ブロック
  から受け取る。サーバ自身の入力はそこに属する。
- lagent は同じ決定を自身の番号で取る。`LAGENT_API_KEY` はまさに §3 が構成に
  よって外す変数である。

## Alternatives considered（検討した代替案）

- **拒否リストを維持し、足りない語を足す。** 却下: 利用者が名指した道そのもので
  あり、`OPENAI_KEY` がそれが終わらないことを示している。
- **read レーン用の許可リスト。** 却下: §Context のとおり、必要な集合は秘密の
  集合と同じく無限であり、失敗が仕事を壊す形で出る。
- **read レーンだけでなく全ての子を scrub する。** 却下: 操作者が write・operator
  レーンから正当に動かす `gh`・`aws` 等を壊し、意図的に資格情報を与えられている
  MCP サーバも壊す。
- **何もせず、真実を文書化するだけ。** これが §1 と §4 であり、ADR 全体がそれで
  済んだ可能性はある。§2 を足したのは、有限な集合が 1 つ実在し、それを正しく
  扱うコストがゼロだからである。
- **操作者の秘密らしい変数を列挙する起動時警告。** 却下: 報告は制御ではなく、
  毎起動出る行は誰も読まない。
