## Context

lagent のベンチは失敗した 1 実行を逆から読み、各段がランタイムの書いた文に従って
いることを見つけた: プロンプトが write レーンでの検証を求め、read レーンの試行は
Go のビルドキャッシュが `~/Library/Caches/go-build` にあってどのレーンも書けない
ために失敗し、write レーンへの昇格は無人実行のため拒否され、拒否文はそこにいない
ユーザーに聞けと言い、モデルは行動をやめて「しようとした変更」を記述した。

gem-agent には各文がそろっている。2026-09-12 に操作者の機体で、新しい Go モジュール
に対して探針した:

```
[tool] shell_exec [read] go vet ./...
open ~/Library/Caches/go-build/dd/…-d: operation not permitted   (exit 1)
```

- **プロンプトはあらゆる build/test を write レーンに送る**（「build と test の
  ツールはキャッシュを書くので必要」）。read レーンは試されもしないが、vet や
  test は検査であり、`--auto` ではそれぞれモデル層 2 ラウンド（risk 枠で約 7 秒）、
  既定モードでは承認プロンプト 1 回を払う。このセッション自身のリリース確認でも
  そうだった。
- **拒否文はどのモードでも同じ**: "ask the user how to proceed" が `-p` でもモデルに
  届く。ADR-0065 が「尋ねる相手はいない」と既に定めている場所で。操作者向けの行は
  「nobody to ask in one-shot mode」と言うが、モデル向けの結果は何がまだ走れるかを
  言わない。
- **`list_tree dirs_only` は、ファイルがあってサブディレクトリの無いディレクトリを
  "(empty directory)" と報告し**、モデルは `list_files` に 1 ラウンドを使って
  それを知る。プロンプトは `dirs_only` から始めよと言っている。
- **プロンプトはランタイムがもう必要としない規則を保っている**:「拒否は決定で
  あって障害ではない — 再試行せず、どう進めるか聞け」。拒否が自分の経路を運ぶ
  なら、この規則はモデルが飛ばすか過剰一般化する常設の一文がもう 1 つ増えるだけ。

lagent のベンチ比較は、同じタスクで gem-agent のラウンド数が 2〜3 倍（rename 23、
read-edit 15）であることも測った。上の連鎖はその一因である。

## Decision

4 つの変更。モデルが行動できない文を、行動できる事実に置き換える。lagent
ADR-0008 を gem-agent の語彙で。

1. **ツールチェインのキャッシュは、操作者が持つ 1 つの表から、全レーンでセッション
   scratch に乗る。** `[sandbox].scratch_caches` は環境変数をディレクトリ名に対応
   づける。全 `shell_exec` は各変数を read レーン専用 scratch（`<work dir>/scratch`、
   read レーンが書ける唯一のディレクトリで、write と operator レーンも書ける）
   配下のそのディレクトリに向けて走る。同梱の行は Go の `GOCACHE = "go-build"`。
   別のツールチェインを使う操作者はコード変更なしに行を足し（`PIP_CACHE_DIR`・
   `UV_CACHE_DIR`・`npm_config_cache`）、空の値は行を消す。よって build・vet・test
   は検査と同じく read
   レーンで承認なしに走る。キャッシュはセッションに 1 回 cold で、以後 warm。
   操作者の共有キャッシュにしないのは意図的: read レーンは無人で走り、共有の
   content-addressed キャッシュは、無人のコマンドが後で sandbox 外のビルドが信用する
   オブジェクトを置ける場所である。同じ縁はセッション内にもあるので、無人のレーンと
   承認済みレーンは全行でディレクトリを分ける: read レーンのキャッシュは表の名前
   （`go-build`）、write と operator レーンは `<名前>-approved` を共有する。読んだ
   内容に誘導された read レーンのコマンドは、承認済みの `make build` がリンクし操作者
   が実行するオブジェクトを仕込めない。表は用途で有界: 行は再生成できるキャッシュを
   名指すものなので、`laneEnv` が決める変数（`TMPDIR`・`PATH`・`HOME`）とローダー
   変数（`DYLD_*`・`LD_*`）は拒む — read レーンが書くディレクトリが承認済みレーンの
   ロードするコードになってはならない — し、値はパスではなく 1 つのディレクトリ名。
   グローバル config 専用: プロジェクトファイルは `[approval.tools]` と `[mcp].exclude`
   しか持たないので、clone したリポジトリが行を足すことはできない。モジュール・
   レジストリ格納（`GOMODCACHE`・`CARGO_HOME`）はこの意味でのキャッシュではなく、
   表には入れない。read レーンの書込可能集合（ADR-0073 §2）は変わらない —
   キャッシュがその中に移った。
2. **無人の拒否は経路を名指す。** `Options.Unattended` がこの実行には尋ねる相手が
   いない（`-p`）ことをエージェントに伝え、拒否されたコールの結果は「このコールを
   承認できる者はいない」と言った上で、one-shot のどの構成でも走るもの — 読取専用の
   ファイルツールと read レーンのシェル — を名指す。または終えて残件を述べる。
   write 系ツールは名指さない: `--auto` も `--allow` も無ければそれこそが拒否された
   ものであり、2 度目の拒否へ導く経路はこの節が取り除く病理そのもの。対話時の文は
   「ユーザーに聞け」のまま。操作者の理由を運ぶ拒否（ADR-0060）と読取専用上限の
   拒否（ADR-0080、「操作者が解除できる」）は 1 行目を保ち、結びの行は同じ規則に従う。
3. **`list_tree` は見たものを言う。** `dirs_only` で、ファイルはあるがサブ
   ディレクトリの無いディレクトリは、空と読める代わりにそのファイルを列挙する
   （ディレクトリ毎の上限まで）。lagent は代替案 — 件数と「list_files を呼べ」 — を
   測り、モデルは毎回その案内に従ってラウンドが消えた。ツール自身が歩ける経路は
   名指す経路ではない。
4. **プロンプトは今真であることを言い、ランタイムが置き換えた規則を捨てる。**
   レーン段落: read レーンは検査に*加えて* compile・vet・test を走らせる —
   ツールチェインのキャッシュはレーンの scratch にある — が、バイナリをプロジェクト
   に書くビルド（main パッケージの `go build`）は依然 write レーン。write レーンは
   ファイルの変更・インストール・コミット・ネットワークのため。検証の項目は read
   レーンを名指す。「拒否は決定」の項目は消える。`shell_exec` 自身の説明も同じことを
   言う。

## Consequences

- vet と test はモデル層も承認プロンプトも払わなくなる。write レーンはプロジェクト
  を変えるかネットワークに届くもののために残る。このセッションの語彙で言えば、
  リリースチェックリストの `go test` は無確認で走る。
- sandbox 内の Go ビルドは信頼クラスごとにセッションに 1 回 cold でコンパイルする
  （read レーンのキャッシュと承認済みレーンのキャッシュは別）。操作者自身の
  キャッシュにエージェントが走らせたものは何も触れない。
- キャッシュは作業ディレクトリと共に生き、共に消える。何も削除しない: `/clear` は
  新しい作業ディレクトリに回転し古いキャッシュを残す。cold な Go キャッシュは数十〜
  数百 MB ある（1 ファイルのモジュールの `go vet` で 20 MB、実測）。起動時の「以前の作業ディレクトリ」報告がそれを数え、`gem-agent workdirs
  clean` が処方（ADR-0059）。ランタイムが自ら行う削除はここでは加えない。
- scratch が無いとき（read レーン無効、またはディレクトリを作れなかった）は何も
  向け直さず、キャッシュは `~/Library` 配下のままどのレーンでも書けない — この
  ADR 以前の状態であって新しい状態ではない。
- read レーンの `go test` はプロジェクトと依存のコードを承認なしに実行する。
  レーンが縛る — ネットワーク無し、scratch 外への書込無し、資格情報の読取無し — が、
  無人の面は `ls`・`cat`・`grep` より広く、この行はそれを記録する。
- モジュールのダウンロードは対象外: `~/go/pkg/mod` はどのレーンでも読めるが書けない
  ので、モジュールが未キャッシュのプロジェクトは実行内から取得できない。ギャップと
  して記録し、ここでは解かない。
- ゲートに当たった one-shot 実行は、可能だった作業を終え残件を述べて終わる。
  モデルが「しようとしたこと」の記述ではなく。
- Options 1 フィールド、環境変数一覧 1 つ、プロンプト段落 1 つ、項目 1 つ削除、
  `list_tree` の 1 ケース。マージ前に計測: 上の探針が read レーンで通る。フラットな
  ディレクトリがファイルを列挙する。one-shot の拒否結果が経路を名指す。

## Alternatives considered

- **「説明せず編集せよ」「one-shot では聞かずに動け」の散文規則** — 却下: ランタイム
  が招いた振る舞いに対する常設規則で、ナレッジの計測結果は「飛ばされるか過剰
  一般化される」。
- **レーンで `~/Library/Caches` への書込を許す** — read レーンでは却下（無人の
  コマンドが共有 content-addressed キャッシュを書くのは汚染経路）、したがって write
  レーンでも却下。要点は read レーンでビルドが動くこと。
- **ハードコードした一覧、ツールチェイン 1 つにつきコード変更 1 回** — 初版。
  リリース前に置き換え（操作者レビュー）: ランタイムが機体のツールチェインを知る
  理由は無く、追加のたびにリリースを要した。表は操作者のもので、ランタイムが知るのは
  全行に適用する規則（scratch への配置・レーン分離・行が名指してはならないもの）。
- **全レーンで 1 つのキャッシュディレクトリ** — レビューで却下: Go はキャッシュ
  エントリを読取時に信用するので、無人のレーンが承認済みビルドの消費するオブジェクトを
  仕込める。ディレクトリ 2 つの代価はセッションに 1 回余分な cold コンパイル。
- **`shell_exec` のレーン拒否文も経路化** — 見送り: 「名指された広いレーンが要る」は
  one-shot では無人拒否に至り、そこで経路が名指される。1 ラウンド余分だが文は真のまま。
- **one-shot では write レーンのビルドを自動承認** — 却下: write レーンはネットワーク
  とプロジェクトに届く。「build」はコマンドラインの中の単語であってレーンではなく、
  ルール層はコマンド文を意図のために読まない（ADR-0073）。
- **小さなツリーでは `dirs_only` を使わせない** — 却下: 案内は正しく、ツールの報告が
  偽だった。
