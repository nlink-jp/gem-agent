# ADR-0043: 図はツールが描く。モデルが書いたものを書き換えない

| 改訂対象 | [ADR-0042](0042-terminal-diagrams.ja.md) |
| 決定者 | nlink-jp メンテナ |
| 契機 | オペレーター: ランタイムがチャットの内容を見て書き換えているため、モデルが出した mermaid が書式エラーのとき、モデル自身がそれを認識できない。また、描けるかどうかを左右するコンソールの諸元がモデルに伝わっていない |

## Context（背景）

ADR-0042 は、確定時にアシスタントの Markdown を書き換えることで図を描く。
`diagram.Rewrite` の呼び出し箇所は 1 つだけ — TUI の Markdown レンダラ —
であり、その結果は画面にしか届かない。モデルの会話履歴には元のフェンスが
残り、**図が拒否されたことも、その理由も、モデルは知らされない**。

これは本プロジェクトが v0.38.0〜v0.39.0 で他所から取り除いてきた欠陥の、
一段深い場所での再発である。v0.38.0 は描ける方言をモデルに教え、遵守は
実測でクリーンだった。しかしそれでも間違えたモデルには学ぶ手段がない。
補正が本人に見えないからである。不完全なモデル出力への正当な応答は
「教える」「検証して拒否する」「人間に見せる」の 3 つであり、拒否は正直だ
— **しかし書いた本人に告げない拒否は正直ではない。**

後半は、モデルには不可能な算術である。図が描けるかどうかは端末幅に依存
するが、その値はプロンプトにもツール群にも存在しない。

## Decision（決定）

### 1. ツールが描き、ランタイムは書き換えをやめる

`render_diagram(source, ...)` が mermaid ソースを 1 つ描画する。成功時は
端末に図が描かれ、ツールは短いステータスを返す。失敗時は理由を返す。
いずれにせよ**モデルは何が起きたかを同じターン内で知り**、オペレーターが
壊れた図を見る前に修正して呼び直せる。

チャットの書き換えは**撤去する**。返信中の ```` ```mermaid ```` フェンスは
そのままソースとして表示される — オペレーターの言葉を借りれば、*モデルが
出してきたものを加工しない*。経路が 2 つから 1 つになり、しかもその 2 つは
対等ではなかった: 書き換えのほうが沈黙する経路だった。ソース表示は**見える**
ので、オペレーターがモデルに「ツールを使え」と言える。これは v0.37.4 で
ER 複雑さ上限をリバートしたときと同じ基準である。ファイル出力は従来どおり
一切触れない。

### 2. アートは副作用であり、モデルが復唱するものではない

モデルが受け取るツール結果はステータス行であって、アートではない。60 行の
罫線を返せばトークンは倍になり、モデルはそれを（下手に）再現しようとする。
TUI はシェル結果と同じ生出力経路（Markdown レンダラを通さない）で、専用
メッセージとして描画する。

別の会話メッセージとして届けることもできない: ADR-0012 §5 に実測が記録
されている — 関数呼び出しターンの後続コンテンツはその応答だけで構成されて
いる必要があり、さもなくば次ラウンドで 400 になる。

### 3. 描画予算はプロンプトではなく `agent_info` に置く

モデルは、拒否されて制約を知るのではなく、**書く前に**使える空間に合わせて
図を設計すべきである。よって予算は `agent_info` に加える。同ツールの採用
基準（ADR-0030）は「フィールドはモデルが取るべき行動を変えることで席を得る」
であり、これはまさに該当する。スナップショットは既に呼び出し時評価の
クロージャであり、TUI はリサイズごとに幅を追跡しているので、ADR-0039 の
live variable パターンがそのまま使え、新しい機構は要らない。

返すのは**コンソールの諸元ではなく予算**である。生の `150x50` を返すと
2 方向に誤誘導する: inline TUI はスクロールするので端末の高さは制約では
なく（固定の 80 行上限が制約）、使える幅は端末幅から Markdown レンダラの
余白を引いた値である。「50 行」と告げられたモデルは 80 行使えた図を縮め、
200 行の端末では拒否される図を書く。

プロンプトに置く案は却下した: プロンプトは ADR-0018 のキャッシュ前置を
守るためバイト安定であり（実測 81〜95% 命中）、リサイズのたびに変わる数値は
それを壊すか、セッション中に嘘になるかのどちらかである。

### 4. この誘導は fail-soft である

プロンプトは、図を書く前に予算を確認すること、フェンスではなくツールを
呼ぶことを求める。どちらも決定的な前提ではない: `agent_info` を飛ばした
モデルもツールの拒否理由で正確な予算を受け取り、そこから修正できる。これが
重要なのは、指示が確実には発火しないと実証されているからである — ADR-0020
§5 のメモリ契機は、契機として書かれる前は 39 セッションで 0 回だった。
最初の 1 発を当てるための最適化にすぎない確認は、発火しなくても機能を壊さ
ない。

## Consequences（帰結）

- 図 1 つにつき 1 ラウンド増える（予算を先に確認すれば 2）。許容する:
  一度で正しく描けた図は、ソース表示されて散文で説明し直す図より安い。
- モデルは非公開で反復できる（拒否 → 修正 → 描画）ので、オペレーターは
  試行ではなく完成した図を見る。
- `render_diagram` は ADR-0042 のプロンプト節と同じく **TUI でのみ登録**
  する。素 REPL と単発実行が、その面に無い能力を宣伝することはない。
- ツールは読み取り専用で承認ゲートを通さない。何も書かず、ネットワークにも
  触れない。
- ADR-0042 の 3 規則（変換 / 収める / 検証）は変更しない。これらがツールの
  エンジンになり、その拒否理由が**沈黙のフォールバックではなくモデルへの
  フィードバック**になる。
