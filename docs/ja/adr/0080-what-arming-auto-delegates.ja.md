## Context — 3 つの指摘、1 つの形

階梯が答えるのは*このコールは危険か*である。*このコールは操作者が
このセッションに許した範囲内か*に答える層は、階梯のどこにも無い。
3 つの指摘は、その問いが 3 方向から現れたものである。

**A-01. ルール層の `safe` が階梯を終わらせる。** プロジェクト内で
永続ファイルに当たらないパスへの `write_file`・`edit_file` は `safe`
であり、`decideAuto` はモデル層に諮らずに承認を返す。したがって
「評価だけ。書き込み禁止」で始めたセッションには、通常の編集を止める
層が 1 つも無い。主モデルに提案しないよう頼み、それでも提案されたら
承認層は「問題なし」と同意する。*どこのファイルなら編集してよいか*と
*このセッションが編集してよいか*は別の問いであり、今は前者を満たすと
後者が飛ばされる。

**A-02. 評価器から見える意図は 1 ターン分しかない。** モデル層へ渡る
指示は `a.turnInput` — *今回*操作者が打った文 — であり、
`riskInstructionCap`（2000 runes）でクリップされる。「続けて」の
ターンは何も運ばない。長い依頼の最終段落に置かれた禁止事項は、
クリップが先頭を残す仕様なので落ちる。添付と会話履歴を意図的に外して
いるのは正しい — injection が届く経路だからである。しかしその結果、
操作者の継続的な制約には経路が 1 本も無い。

**A-03. 過去の許可がモデルの異議に勝つ。** モデル層が拒否すると、
コールはゲートへ行く。ゲートは操作者 **または** セッション allowlist
であり、無条件に操作者へ届くのは must-prompt のコール — Block 層・
`operator` レーン・非封じ込めシェル・`"always"` ポリシー — だけである。
つまり、あるコールについて一度打った `a` が、評価器が今まさに異議を
唱えた別のコールに答え得る。MCP で最も広く効く: ルール層はサーバーの
作用に届かず、`a` は同じツール名への以後の任意引数を覆う。

**共通する形。** 階梯には、継続する操作者の制約を表す形が無い。
操作者の意図は散文としてしか存在せず、モデル層にしか届かず、そこまで
到達したコールにしか届かず、しかも現ターン限りである — 一方で過去の
*許可*は継続するセッション状態である。許可は残り、禁止は残らない。
3 つの指摘はいずれも、この非対称を別の側から見たものである。

## Context — 「safe 判定の前に検査する」では足りない理由

素直な修正は、`risk.Classify` の手前で明示設定を検査し、読み取り専用
なら書込を拒否することである。それ単独では見せかけにしかならない。
ADR-0077 §1 は既に組み込みツールを選択対象にすることを拒否し、理由を
述べている: *レビュー可能な組み込みを取り除くと、同じ作業が
`shell_exec` とシェルのリダイレクトへ移る — 封じ込めは強まらず、
可読性だけが落ちる。* `write_file` を止めて `write` レーンを開けた
ままの読み取り専用モードは、セッションを読み取り専用にしたのではなく、
書込をより読みにくい扉へ移しただけである。

したがって強制点はツールではなく**レーン**である。ADR-0073 は既に
そこへカーネルを置いており、`read` レーンはこのシステムで唯一、
起動時に「失敗すべきプローブ」で検証される境界である。書いてはいけない
セッションとは、シェルが `read` レーンでしか走れないセッションである
— それは gem-agent の主張ではなく、カーネルの主張である。

## Decision

### 1. 操作者が宣言し、階梯より前に評価されるセッションスコープ

新しい設定セクション 1 つとフラグ 1 つ。スコープは操作者が書くか渡す
かする設定であり、打った内容から推定されるものでは決してない。

```toml
# ~/.config/gem-agent/config.toml またはプロジェクトのもの
[scope]
# "project"（今日の挙動、既定）または "off"
writes = "off"
```

`--read-only` が実行単位の形であり、階梯に対する `--auto` と同じ位置
づけである（ADR-0053）。プロジェクトスコープが global に勝ち、かつ
2 つのうち**より厳しい方**が勝つ — `"off"` と書いたプロジェクトを
global の `"project"` が緩めることはない。層が緩められるスコープは
スコープではないからである。

`writes = "off"` のとき:

- `write_file`・`edit_file`・`save_memory`・`delete_memory` は、除外
  された MCP ファンクションと同じくゲート以前に拒否される（ADR-0077
  §1）。拒否文はスコープを名指すので、モデルは迂回を試みるのではなく
  報告できる。
- `shell_exec` は `read` レーンでしか走れない。`write` や `operator`
  を宣言したコールはエスカレートではなく拒否される。それを真にするのは
  read レーンのプロファイルであり、拒否文はそれを読めるようにする。
- MCP ツールは今日どおり毎回訊く（ADR-0008 の既定）。ルール層は他所の
  サーバーの read ツールと write ツールを見分けられず、スコープにも
  見分けられない。そこでの操作者の道具は `[mcp] exclude`（ADR-0077）
  であり、本 ADR はそれを重複させない。

### 2. スコープ外は拒否であって、エスカレーションではない

スコープ外のコールはゲートに到達してはならない。ゲートはセッション
allowlist が答え得る（§4）ので、エスカレートするスコープは過去の `a`
で使い切れるスコープである。Block 層の verdict にしてもならない:
Block は*操作者が見るべき*という意味だが、その操作者は既に「否」と
言っている。もう一度訊くのは、拒否するより悪い答えである。

これは ADR-0077 の「宣言したまま拒否する」議論を、ツールではなく作用
の水準で言い直したものである。毎ラウンド読み直される禁止は既定の読み
が漂う状態であり、拒否はそのラウンドが迂回せざるを得ない事実である。

### 3. パス単位の書込スコープは、ここで名指すが、ここでは作らない

`writes = "paths"` と `writable` 一覧は操作者が次に求める形であり、
本 ADR では意図的に決めない。理由は §「safe 判定の前では足りない
理由」と同じである: file ツール側の検査は簡単な半分でしかなく、
`write` レーンの Seatbelt プロファイルが同じ一覧から生成されるまでは
何の価値も無い。両者が 1 つの関数になる — `sandbox.PersistentFiles`
が既にプロファイルと file ツールの verdict の両方から読まれているように
— まで、パススコープはシェルが迂回できる設定であり、境界のように
読めるぶん、無いより悪い。

`writes = "off"` にはその欠落が無い。`read` レーンは既に存在し、既に
起動時に検証されており、既にシェルコマンドを縛れるプロファイルである。

### 4. モデル層の拒否は、そのコールを must-prompt にする

モデル層が走り、使える verdict を返し、それが承認でなかったとき、
続くゲートのコールは must-prompt になる。セッション allowlist は答えず、
操作者が見る。

操作者が打った `a` は、見せられたコールについての答えだった。評価器が
異議を唱えているのは*今回の引数*であり、操作者はそれを見ていない —
MCP ツールで最も鋭い。`a` は同じ名前への以後の任意引数を覆うからである。
古く粗い答えが、新しく具体的な異議に勝つのは、どちらがより多く知って
いるかを逆さにしている。

これは常に「より多く訊く」方向にしか動かない。`"never"` は従来どおり
ゲートを完全に飛ばす（ADR-0008）— それはコール単位の許可ではなく、
ツールについての操作者の継続的決定だからである。`"always"` は不変で
あり、従来の挙動が欲しい操作者は `y` と答えればよい。

**評価の失敗は拒否ではない。** 通信エラー・解析不能な verdict・
0〜1 の範囲外の confidence は今日どおりエスカレートし、allowlist が
答え得る。fail-closed は正しい勘であり、これはその例外である: そうし
なければ、不安定な回線が長時間実行中の allowlist 済みコールをすべて
プロンプトに変え、操作者を「読む」のではなく「消す」よう訓練して
しまう。2 つの場合は transcript で区別できるようになった — 本レビュー
以後の `auto_decision` は `confidence` と `evaluator_model` を持ち、
失敗はそのどちらも持たない — ので、この分岐は仮定ではなく実測できる。

### 5. 宣言されたスコープは評価器に届く。散文は証拠のままにする

評価器のペイロードにセッションスコープを機械的な 1 行として加える。
毎回の評価に存在し、クリップされない。「続けて」のターンでも操作者の
継続的制約が届く — その制約はそもそも散文ではなかったからである。

打たれた指示は現在の役割をそのまま保つ — ADR-0038 と ADR-0054 の
とおり、隔離ラップの内側の証拠である — が、1 点だけ変える:
`riskInstructionCap` は**中央**をクリップし、先頭と末尾を残す。禁止
事項は人が書く場所、すなわち末尾に書かれるのであり、先頭だけを残す
クリップは評価器が最も必要とする文を正確に落とす。クリップ標識は
残すので、何かが取り除かれたことは評価器に伝わる。

**制約をモデルに散文から抽出させることはしない。** 操作者の文を読んで
規則を導く層は作らない。提案者が自分の檻を書くことになり、それは
ADR-0020 §4 がモデルによるメモリ書込承認を拒んだ理由であり、ADR-0050
が rulebook を guidance に留めた理由である。加えて、導出が緩める方向に
外れた瞬間、導出された制約は導出された*許可*になる。宣言されていない
ものは強制されない — 本 ADR はそれを、コードに無い網羅を匂わせるので
はなく、はっきり書く。

## Alternatives considered

- **`write_file` と `edit_file` を ADR-0077 の `[mcp] exclude` 型の
  集合に加える。** ADR-0077 §1 自身の論法で却下: 作業が `shell_exec`
  とリダイレクトへ移る。スコープはツール一覧ではなく作用でなければ
  ならない。
- **スコープを Block 層の verdict にする。** §2 で却下: Block は操作者
  に訊くが、その操作者は既に答えている。
- **モデルのラウンドで会話から制約を導出する。** §5 で却下。最も静かに
  失敗する設計でもある — 網羅しているように見えるからである。
- **直近 N ターンの操作者テキストを評価器へ運ぶ。** 却下: 毎コールで
  ペイロードが膨らみ、制約の寿命が「以後どれだけ打ったか」に依存し、
  しかも強制はモデルの読みに委ねられたままである。宣言されたスコープ
  は固定費で同じ仕事をする。
- **モデルの拒否がそのセッションの allowlist 項目を取り消す。** 却下:
  1 組の引数についての 1 回の異議が、操作者が意図して与えた許可を
  使い切ってしまう。当該コールを must-prompt にするのが、この逆転を
  直す最小の手当である。
- **引数単位の allowlist 項目**（ツール *かつ* 引数の形に対する `a`）。
  ここでは決めない。ADR-0035 はツール名粒度を選んでおり、引数の形を
  キーにする案は MCP サーバーをまたいで安定した形を持たない。引数が
  効くツールに対する道具は `"always"` のままである。

## Consequences

- 既存の操作者に届く挙動変更は 2 つ: `a` がモデル層の拒否したコールに
  答えなくなること（§4）と、スコープを宣言したときに限り、これまで
  走っていたコールが拒否されること。どちらも「より多く訊き、より少なく
  許す」方向である。CHANGELOG では *Changed* に入る。
- `save_memory` と `delete_memory` は §4 と同じクラスにある: 確認では
  なくエスカレートなので、`a` 1 回がそのセッションの以後の保存を覆う。
  ADR-0020 §6 は "always escalate" と書き、意図的な緩和はツール
  ポリシーの仕事だとしている。これらを must-prompt にすべきかは、本
  ADR から意図的に外してある。
- §4 の分岐が拠り所にする実測は、本レビューと同時に入った記録であって
  ハーネスではない。モデル版ごとの固定評価セット — 危険コールの誤承認
  率・通常コールの不要な確認率・遅延・費用 — は未着手であり、
  `minConfidence` を定数から較正済みの値に変えるのはそれである。
