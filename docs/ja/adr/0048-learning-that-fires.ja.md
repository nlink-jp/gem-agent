# ADR-0048: 実利用で発火する学習へ — MCP はサーバ単位グローバル、そして人が実際に出した回答を数える

| 項目 | 値 |
|------|----|
| Status | **Accepted** |
| 日付 | 2026-08-26 |
| 適用対象 | gem-agent |
| 意思決定者 | nlink-jp maintainers |
| 契機 | オペレータ、別マシンで v0.46.0 を使用: auto モードのセッションで約 25 回エスカレーションが起き、そのすべてを承認したのに、直後の `/learn` は何ひとつ提案しなかった |

## Context

ADR-0045 の `/learn` は出荷され、自分のテストと自分の E2E では動き、
それ以外では動かなかった。最初の実セッションは 25 件の承認から提案
ゼロを生んだ。独立した原因が 2 つあり、どちらも私のものである。

**診断の前に再現した**（合成トランスクリプト、1 セッション内に
25 件のエスカレーションとその承認）: `ApproveSessions=1`・
`ModelEscalated=25`・提案 `0`。

### 原因 1: セッション単位に畳んだ票が、実在の判断を捨てている

ADR-0045 §5 はキーとセッションごとに 1 票へ畳む。セッション
allowlist（`a`）が 1 打鍵を任意の回数の承認記録に変えてしまうから
である。その論拠は健全だが、実装がそうではなかった: ゲートは、
オペレータが 25 回目の `y` を押したのか `a` を 1 回押したのかに
関わらず `approved` を同一に記録する（`internal/approve` も
`internal/tui` も allowlist をゲートの内部で消費している）。1 打鍵と
25 打鍵を区別できないので全部を畳んだ — つまり「人間が繰り返し
決めた」の**計測が、計測しようとしている反復そのものを捨てていた**。

### 原因 2: MCP の摩擦は頻度では見えない形をしている

オペレータのエスカレーションは「ほぼ MCP・別々のツールに分散」で、
少数のサーバに集中していた。ここでの調査業務はまさにその形である:
19 サーバ・136 ツールが構成され、トリアージの連鎖は `asn-lookup` →
`whois-lookup` → `abuse-lookup` と進み、各ツールは 1〜2 回しか
呼ばれない。

ツール単位の頻度学習はそこに届かない。摩擦は「同じ質問を繰り返し」
ではなく「毎回違う質問を 1 回ずつ」である。ツール単位カウンタ上の
閾値は、安全かつ到達可能にはならない: 3 セッションは到達不能で、
1 回承認は 1 打鍵で買える恒久的権限である。

### 記録が既に知っていること、知らないこと

`auto_decision` はラダーの判定を、`gate_decision` はオペレータの
回答を、どちらもキー付きで運ぶ。しかしどちらも、`gate_decision` が
打鍵由来か allowlist 由来かを語らない。さらに ADR-0045 の §Context
は、`gate_decision` 以前のトランスクリプトについて「エスカレート後に
実行された」形からのバックフィルを謳ったが、実装は一度もそれを
行っていない — よって v0.46.0 以前のセッションは何も寄与しない。
この欠落を黙って直さずここに記録するのは、最初の実運用が見かけより
証拠を持っていなかった理由がこれだからである。

## Decision

### 1. ゲートが「どう答えたか」を報告する

`Approver.Approve` は bool ではなく `Answer{Approved, FromAllowlist}`
を返す。`gate_decision` は `source: "operator" | "allowlist"` を記録
する。

この区別があれば、§5 の畳み込みは正当化される範囲にだけ適用できる:
**allowlist の回答はキーとセッションごとに 1 票へ畳み、オペレータの
打鍵は個別に数える。** 25 回タイプされた `y` は 25 個の判断である —
それが事実だからである。

閾値はこうなる: `"never"` の提案は **オペレータ承認 ≥ 5 回 または
承認セッション ≥ 3・かつどこにも拒否なし**。どちらの経路でも同じ
ハードル。セッション経路は「同じことに何日もかけて答える」場合の
ために残す。

### 2. MCP の提案はサーバ単位・グローバルスコープ

`mcp__` ツールの提案は `mcp__<server>__*` — ADR-0008 の
ワイルドカードであって新語彙ではない — であり、機械所有ポリシー
ファイルの**グローバル** `[tools]` 表へ書く。

これを支える論拠は 2 つあり、どちらも「MCP はシェルコマンドとは
違う」という話である。

**サーバ単位が正直な単位である。** ある lookup ツールだけ never にし
兄弟 5 つは聞き続ける、という状態は、オペレータが下すどんな判断も
記述していない。彼らが信頼しているのは**サーバ**であり、それは自分で
導入したものである。ツール単位のルールは「モデルがどのツールに先に
手を伸ばしたか」という偶然についてのルールにすぎない。

**グローバルが正直なスコープである。** ADR-0045 §4 がグローバルの
コマンド表を拒んだのは、`make build` がリポジトリごとに別のプログラム
だからである — Makefile はプロジェクトのものだ。この論拠は移らない:
MCP サーバは `~/.config/gem-agent/mcp.json` 由来で、そのバイナリと
挙動はどのプロジェクトでも同一であり、敵対的な clone がサーバを
持ち込むことはできない（プロジェクトの `.mcp.json` は ADR-0023 の
trust ゲートの背後にある）。`asn-lookup` をプロジェクトごとに学習し
直させることは、答えが変わりようのない問いに何度も答えさせることで
ある。

**プロジェクトの `.mcp.json` 由来のサーバは除外する** — そちらは
まさにプロジェクト供給物であり、`mcp.Merge` が既にスコープを
ラベルしている。

閾値: **そのサーバの異なるツールを 2 個以上承認、かつそのサーバの
どのツールにも拒否なし**。ここではツールの**多様性**が正しい
カウンタであり、原因 1 を生んだ allowlist 問題に構造的な免疫を持つ:
allowlist はツール名でキーされるので、1 回の `a` はカウントを
1 ツールしか増やせない。

### 3. サーバ提案は、覆うものをすべて開示する

このルールは根拠より多くを与える: `mcp__urlscan-lookup__*` は、
読み取り専用の lookup を 2 つ承認した実績を根拠に、第三者へ URL を
送信する `scan_url` まで覆う。それはルールを拒む理由には**ならない**
— オペレータはこれらのサーバを自分で書いており、何をするか知って
いる。それこそ ADR-0008 が書き留めさせようとしている知識である。
理由になるのは、**盲目のまま同意させないこと**の方である。

そこで提案は、**ルールが覆う全ツール**を、既に承認済みのものと
**まだ使っていない**ものに分けて列挙し、サーバ自身による各ツールの
説明を添える（ADR-0046: 主張であり、出所を明記する）。長い一覧は
隠した件数とともにクリップし、決して黙って切らない。

### 4. ツール単位の MCP 提案は取り下げる

MCP キーはもはやツール単位・プロジェクトスコープの提案を生まない。
同じコールに対する 2 つの提案形は重複するか矛盾するかのどちらかで
あり、§2 の論拠は「ツール単位のプロジェクトルールはそもそも形が
間違っていた」と述べている。シェルコマンド（プロジェクト・コマンド
キー）と組み込みツール（プロジェクト・ツール名）は不変である:
それらについては ADR-0045 §4 の理由付けが今も成り立つ。

### 5. バックフィルは未実装のまま、そう明記する

v0.46.0 以前のトランスクリプトから判断を復元するには、記録された
キーなしで `auto_decision` とその後のツール結果を位置で対応付ける
必要がある。ADR-0045 はこれを最強の証拠クラスと呼び、実装は
飛ばした。時間に追われて中途半端にやるより、コストを明示して
先送りする。ここから蓄積される記録で不足だと判明したら、独立した
ADR として戻ってくる。

## Consequences

- オペレータが報告したセッションは提案を生むようになる: 承認済み
  ツールを複数持つ数個のサーバが §2 のハードルを越える。
- 学習された MCP ルールはどこでも効く。これは ADR-0045 と比べて
  実際に広がっている — その境界は: オペレータが覆うツール一覧を
  目の前にして 1 件ずつ確認する・pre-tool フックは依然として走る・
  `/settings` が表示し削除できる。
- `Approve` の形が変わることは両方のゲート実装とすべてのテスト
  ダブルに波及する。それだけの価値がある: この区別がなければ、
  票を畳む安全上の論拠と、機能が発火する能力とが真っ向から衝突する。
- テストの教訓（これを引き起こしたので記録する）: ADR-0045 の E2E は
  自分の閾値を満たすために 3 セッションを仕込んでおり、機構は測った
  が**到達可能性は測っていなかった**。利用から学ぶ機能は、実利用の
  形をしたトランスクリプト — ここでは 1 セッション・多数の 1 回限り
  ツール — に対してテストしなければならない。§Context の再現は回帰
  テストとして保存する。
