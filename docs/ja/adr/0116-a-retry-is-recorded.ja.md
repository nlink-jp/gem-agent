# ADR-0116: 再試行を記録する — transcript が「待ち」と「遅い応答」を分ける

| Relates to | ADR-0033（ターンの可観測性。再試行は表示され、何も残らなかった）、ADR-0057（usage レコード）、ADR-0071（`/clear` は新しい transcript を開く）、ADR-0100（`connection_lost` レコード） |

## Context

モデル呼び出しは 429 か 5xx に当たると、待ってからやり直す。試行は最大 5 回
（再試行と画面の表示を入れたのは ADR-0033 §2 で、当時は 3 回だった）。待っている間、
TUI のステータス行がそれを表示する。書き残されるものは無い。transcript にあるのは
呼び出しの前のメッセージと後の `usage` レコードで、その間の秒数が応答に掛かった
時間のすべてである。

その秒数を埋めるものは 2 種類ある。エンドポイントが大きなリクエストへの応答に
時間を掛けたか、リクエストを 1 回以上断り、ランタイムが試行の間を待ったかである。
プロバイダーの従量課金の文書は、組織ごとのスループットのしきい値を説明しており、
それを超えた分は空きがあるときだけ処理され、超過分が受けるものとして遅延と 429
を挙げている。長いセッションのリクエストは、1 回でそのしきい値の大きな割合に
なりうる。あるセッションが遅い理由がそれなのかは、再試行についての問いであり、
それに答える記録が存在しない。プレーン REPL と one-shot モードは、再試行を
表示もしない。

## Decision

1. **モデル呼び出しのバックオフ再試行は、毎回 `model_retry` レコードを書く。**
   持つのは、呼んだモデル、呼び出しの種類（`source`。usage レコードと同じ語）、
   これから始まる試行の番号と上限、直前の試行を失敗させた HTTP ステータス、
   それに対するエンドポイントのステータスの語、バックオフのミリ秒数である。
   待つ前に書くので、レコードの時刻は失敗した試行が返った時点になる。どの項目も
   必ず書く。
2. **すべてのモデル枠が同じ記録先に報告する。** risk・summary・librarian の枠は
   主バックエンドの複製である。観測者と思考レベルは共有しない（ADR-0033 §3、
   ADR-0098 §5）が、これは共有する。枠の再試行も同じエンドポイントへの待ちで
   あり、主ループの分だけを持つ記録は、残りについて「再試行なし」と読めて
   しまうからである。Web ツールの裏の単発呼び出しは独自のループで再試行するが、
   これも同じ記録先に報告する。
3. **呼び出し箇所が種類を名乗る。** リスク評価と主ループが同じモデルを使うとき —
   既定の構成がそうである — バックエンドには両者の区別がつかない。各呼び出し箇所が、
   自分の usage レコードが使う名前でコンテキストを包む。いちばん外側の名前が
   残るので、ファイル検索の子が行う呼び出しは、そのツールの名前を持つ。名乗らない
   モデル呼び出しは、構造テストが落とす。
4. **エンドポイントの応答から残すのは語だけである。** ステータスコードと
   ステータスの語は、API エラーの値から読む。メッセージ文は記録しない。これは
   ランタイムが管理しない自由記述で、上流のメッセージは送ったものを書き戻す
   ことがあり、転送エラーはリクエストの宛先を引用する。
5. **レコードは診断用である。** 会話の状態ではない。resume は読み飛ばし、中身は
   モデルに届かず、書き込みの失敗は呼び出しに影響しない。`/clear` をまたいでも、
   使用中の transcript に書かれる。
6. **再試行の方針の形は変えず、そこにあった欠陥を 2 つ直す。** どのステータスを
   何回再試行するかはそのままである。このレコードのリリース前の検証で、Web ツールの
   ループがエラーのステータスではなく文面から判定していたために「502」を引用した
   だけのエラーを再試行していたこと、バックオフのゆらぎのせいで最初の再試行の
   4 回に 1 回が待たずに送られていたことが分かった。どちらも直す。直さなければ、
   このレコードが推測の原因と 0 の待ち時間を書き残すことになるからである。

ADR-0033 は思考テキストを transcript の外に置き（§3）、ほかのイベントについても
何も書き残さなかった。コードとアーキテクチャの文書は、それらがすべて表示だけだと
述べていた。それは鼓動と思考テキストについては今も成り立つ。再試行は、この ADR が
設ける例外である。

## Consequences

- transcript が、「呼び出しがレート制限を待った」と「エンドポイントがこれだけ
  掛かった」を分けるようになる。セッションが行ったすべてのモデル呼び出しについて、
  画面に何も出さない 2 つのモードも含めて。
- v0.102.0 より前のビルドは、このレコードを書かない。そのビルドの transcript での
  不在は「記録なし」であり、「再試行なし」ではない。再開されたセッションは最初の
  ヘッダを持ち続けるので、transcript のある区間を書いたビルドは、その前の
  `resumed` レコードの `version` である。
- レコードが言うのは、再試行があったこと、どの種類の呼び出しか、どのステータスか
  である。どのクォータやしきい値が関わったかは言わない。それはエンドポイントの
  メッセージ文にあり、メッセージ文は残さないからである。
- transcript はモデル呼び出しの開始時点を記録しないので、断られた試行に掛かった
  時間が読めるのは、メッセージの直後に来る主ループの呼び出しであり、ほかの
  呼び出しでは一般に読めない。試行の間の待ち時間は、どれについても正確である。
- 記録先を取り付けているのは `cmd/root.go` の 1 行で、テストがその行を固定する。
  リリース前に、ビルドしたバイナリを 429 を返すローカルのエンドポイントに向けて、
  このレコードを 1 回書かせて確かめた。

## Alternatives considered

- **`usage` レコードに再試行回数を足す。** 採らない。最後の試行でも失敗した
  呼び出しは usage レコードを書かないので、いちばん重要な再試行が失われる。
  また usage レコードの形は、他のツールが読む会計上の契約である（ADR-0057、
  ADR-0066）。
- **主ループだけを記録する。** 採らない。理由は §2。
- **エンドポイントのエラー文を、長さを切って残す。** 最初の案はそうしていた。
  検証で採らないことにした。上流がエラー文に資格情報の一部を書き戻した、という
  組織自身の記録が、上流の文面を素通しにしない理由であり、長さの上限は、そこに
  何が入りうるかを変えない。
- **呼び出しごとに最初のチャンクまでの時間を記録する。** ここでは採らない。
  これは別の問い — 遅い応答がどこで時間を使うか — に答えるもので、沈黙のうち
  再試行がどれだけかをこのレコードが示した後で問う価値がある。
- **transcript ではなくテレメトリに出す。** 採らない。テレメトリは任意で、
  機械の外へ出る。この問いは、既に走ったセッションに対して、残されたファイル
  から問うものである。
