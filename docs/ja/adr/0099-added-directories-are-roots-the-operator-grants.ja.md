## 背景

いまのセッションのルートは、プロジェクトとセッション作業ディレクトリ
（ADR-0058）の 2 つである。サンドボックスが有効なとき、その両方の外に
あるディレクトリには、どの書き込み経路も届かない:

| 経路 | ルートの内側 | どのルートの外（例: `~/vault`） |
|---|---|---|
| ファイルツール（`read_file`・`write_file` など） | 使える | **Block**（「absolute path outside the project …」） |
| `shell_exec` の read レーン | 読める | 読める。ただし `/Volumes`・`/Network`・`~/Library`（ツールチェーンのキャッシュを除く）は読めない |
| `shell_exec` の write レーン | 書ける（永続ファイルは除く） | **拒否** |
| `shell_exec` の operator レーン | 書ける（永続ファイルも含む） | **拒否** — operator レーンは ADR-0001 のプロファイルで、書けるのはプロジェクト・作業ディレクトリ・scratch ルートだけである |

つまりサンドボックスの下では、2 つ目のツリーに書く方法がまったくない。
唯一の経路は `--no-sandbox` で、これはセッション全体の保護をすべて捨てる。
ノート・vault・隣のチェックアウトをプロジェクトの横に置いているオペレータ
には、その中間がない。

追加ルートを安く作れる理由が 3 つある:

- **プロファイルはセッション中にもう作り直せる。** `rotateWorkDir` は
  `/clear` のときに `buildExecFn` を呼び直し、`liveExec` はロックの下で
  シェルの実行器を差し替える。
- **Seatbelt は拒否したツリーの下のサブパスを許可し直せる。** 2026-10-29
  に `sandbox-exec` で測った。`(subpath "/Volumes")` の `file-read*` を
  拒否するプロファイルでは、`ls /Volumes/<vol>` は失敗する（exit 1）。
  その拒否の後に `(allow file-read* (subpath "/Volumes/<vol>"))` を置くと
  同じコマンドは成功し（exit 0）、隣のボリュームは拒否のままだった
  （exit 1）。後に一致した規則が勝つので、外付けボリューム上の追加ルートは、
  `/Volumes` の残りを開けずに読めるようにできる。
- **資格情報のブロックは、いまはプロファイルの最後の読み取り規則である。**
  この ADR のレビューで、read レーンの `~/Library` のツールチェーン再許可が
  資格情報の拒否の後にあり、`~/Library/Caches` の中の `.env` が聞かれずに
  読めることが分かった。これは先に別の変更として直した（コミット
  `47146b1`、`TestCredentialBlockIsTheLastReadRule`）。この ADR が足す
  再許可はそのブロックより前に書くので、やはり資格情報の名前を開け直せない。

ただし、ルートの集合は 1 つの一覧ではない。「プロジェクトと作業
ディレクトリ」は複数の消費者に書き込まれており、どれも追加ルートを知る
必要がある（§6）。1 つ漏らしても穴は開かない。その消費者で機能が失敗
するか、実装者に迂回させるだけである。ただし、ファイル読み取りの子
プロセスを迂回すると、カーネルの資格情報ガード（ADR-0086）を失う。

オペレータからは、モデルがディレクトリを*要請*でき、ランタイムが必ず
その要請をオペレータに諮る形にしたい、という依頼もあった。これは
ADR-0085/0086 の資格情報の読み取りと同じ型である: モデルが提案し、
ランタイムが止め、人間が答える。

## 決定

### 1. 追加ディレクトリは、アクセスレベルを持つルートである

セッションには、プロジェクト・作業ディレクトリに加えて、0 個以上の
**追加ディレクトリ**がある。それぞれのアクセスレベルは `read` か `write`
である:

- **`read`** — ファイルツールがそのディレクトリを読める（「プロジェクト外」
  ではなくなる）。拒否しているツリー（`/Volumes`・`/Network`・
  `~/Library`）の下にあっても、read レーンが読める。**どのレーンも書かない。
  operator レーンも書かない。** read ルートへの書き込みは、どのルートの外
  への書き込みとまったく同じに判定する。
- **`write`** — `read` に加えて、ファイルツールが書け、write レーンと
  operator レーンがプロジェクトと同じように書ける。

どちらのレベルでも、プロジェクトが持つ床はすべて保つ:

- 資格情報フィルタは、どのルートでも、ファイルツールの判定でもプロファイル
  でも効いたままである。
- 永続ファイルの名前（`sandbox.PersistentFiles`、write ルートごとに
  起点を置く）は write レーンに拒否され、ファイルツールでは `OperatorOnly`
  になる。
- `.git/` への書き込みは Block のままである。

read レーンは、プロジェクトと同じく、追加ディレクトリに書かない。

### 2. 追加ディレクトリの中のものは何も読み込まない

追加ディレクトリの `AGENTS.md`・`CLAUDE.md`・`GEMINI.md`・`.mcp.json`・
`.gem-agent.toml`・skill は、指示・サーバ・ポリシー・skill として**読み
込まない**（オペレータの決定、2026-10-29）。そのツリーは、後のセッションが
信頼する別のプロジェクトかもしれないので保護はする（§1）が、ここでは信頼
しない。したがって、追加ディレクトリには信頼確認もピンも読み込み経路の
変更もない。ADR-0023/0074 は従来どおりプロジェクトだけに適用される。

これが最も効くのは §4 である。読み込むなら、モデルの要請で追加した
ディレクトリが、モデルの選んだ指示を持ち込む経路になってしまう。

### 3. オペレータは起動時にディレクトリを追加する

- `--add-dir PATH`（write）と `--read-dir PATH`（read）。どちらも繰り返し
  指定できる。
- グローバル設定ファイルも同じ一覧を取る:
  ```toml
  [directories]
  write = ["~/notes"]
  read  = ["/Volumes/Archive/reference"]
  ```
- プロジェクトの `.gem-agent.toml` はディレクトリを追加できず、そのために
  作るものは何もない。`LoadProject` は `[approval.tools]` と
  `[mcp].exclude` 以外のキーをすでにエラーで拒否している（`internal/config`）
  ので、そこに書いた `[directories]` 表は、他の未知のキーと同じく読み込みに
  失敗する。リポジトリが自分の外への書き込みを自分に与えることはできない。

起動時に与えたパスは実パスに解決し、§5 で判定してから `os.Root` として
開く。プロファイルが名指すのはその実パスである。§4 の手順 1 の記述子からの
読み戻しは、ここでは繰り返さない: 起動時にはモデルの動かすコマンドがまだ
1 つも走っていないので、判定から open までの間に gem-agent の中でパスを
差し替えられる者がいない。オペレータのディレクトリを書き換えられる外部の
プロセスは、これで得られる以上のものをすでに持っている。§4 で要るのは、
オペレータが答えている間に write レーンのコマンドが走っていうるからである。
§5 に通らないパスは注記ではなく起動エラーにする: オペレータが打ったもの
なので、効かなかったことをオペレータが知らなければならない。`-p` でも、起動時の
ディレクトリは他のフラグと同じく使える。

### 4. モデルはディレクトリを要請できる。答えるのは必ずオペレータである

組み込みツール:

```
request_directory(path, access, reason)
```

- **常に `OperatorOnly`。** どの承認モードでも必ずプロンプトを出す。
  セッションの許可リストもモデル層も答えない。人間がいない `-p` では拒否
  する。read-only の上限の下では、他の変更系の呼び出しと同じく、上限を外すかの
  上限自身の問いが先に出る（ADR-0080）*（最初の文では write の要請をそこで断って
  いた。上限の既存の経路が、頼まれていないものをすでに止める）*。委譲先の子レジストリ（`Registry.Subset`）はこの
  ツールを持たない。子は、そのとき有効なルートを親を通して見る。
- **§5 は付与の時点で判定し、承認はそれを覆さない。** 通らないパスは回答の後に規則で
  断るので、`~` を書けるようにするかどうかを承認疲れに決めさせない。*（実装の注記、
  2026-10-29: 最初の文では §5 をプロンプトの前に走らせていた。承認のゲートには
  プロンプトの前に差し込む口がなく、順序は断ることで守るものを何も変えない — 断られる
  パスはどちらの順でも断られる。）*
- **プロンプトは承認のゲートのもので**、判定の理由が、書かれたままのパス・レベル・
  自動承認での意味（「以後そこへの書き込みは聞かずに走る」）を名指し、制御文字と
  双方向上書き文字は TUI の入口で除く（ADR-0093 §2）。モデルの `reason` は呼び出しの
引数にある。モデルの書いた
  パスがリンクを通って解決するなら、付与の時点で実パスとともに断るので、操作者が
  承認したものが別の場所になることはない。
- **オペレータの答え**はゲートのもの: 承認か拒否。read で足したいディレクトリは、
  拒否して `/read-dir`（§11）で足す — 操作者の入口があるので 3 つ目の答えは要らない
  *（最初の文の「read として承認」から 2026-10-29 に変更）*。すでに `read` ルートである
  ディレクトリへの `write` の要請は昇格であり、同じように聞く。
- **承認の後、付与は §12 を通る** — この要請と操作者の `/add-dir`（§11）が共有する、
  ただ 1 つの付与の経路である。その最初の手順でディレクトリを開き、記述子から
  実パスを読み戻す。表示したパスと違えば断る。
- **検証に失敗したら要請を断り、セッションはそのままにする。** 起動時
  （と、いまの `/clear`）は、検証できない write レーンはセッションを
  無制限モードにする（ADR-0073 §7）。ここでその落ち方を使うと、モデルの
  要請 1 つでセッション全体のサンドボックスを下げられる。なので要請に
  できるのは、検証済みの檻にルートを足すことだけで、檻と引き換えにする
  ことはできない。
- **ツールの結果**は、付与したパスとレベル、または断った事実と理由を言う。
  システムプロンプトのルートの一覧は、呼び出しの中ではなく、次のターンの
  区切りで作り直す（§12）。
- **`-p` では広告しない。** そこでは拒否しかありえないからである。
- **プロセスが続く限り。ファイルには何も書かない。** 付与したディレクトリは、
  起動時のものと同じく `/clear` をまたいで残る: 外すには、この ADR が対象外に
  している取り外し（§8）が要り、操作者はパスを見たうえで承認している。新しい
  プロセスや `--resume` はフラグと設定から始め直す。前の付与に触れる再開した
  会話はルート外の拒否に当たり、その理由が「前の付与は復元しない」と言う。
- 付与はすべて、出どころ（`flag`・`config`・`slash`・`request`）・実パス・レベルとともに
  `added_directories` 記録として transcript に書く。要請の記録にはモデルの理由も載せる。
  拒否は承認のゲート自身の記録であり、断った付与や捨てた付与は、理由とともにツールの
  結果として transcript に残る。呼び出しとその答えは、他のゲート付きの呼び出しと同じく
  監査記録に届く。

### 5. ルートにしてよいかは 1 つの規則で決める

`sandbox.RefuseRoot(path, access)` を §3 と §4 の両方が読む。判定するのは
実パスで、次のディレクトリは断る:

- 存在しない、または解決後にディレクトリでない。
- `/`、オペレータのホーム、またはそのどちらかの祖先。
- プロジェクト・作業ディレクトリ・設定ホーム（`~/.config/gem-agent`）・
  状態ディレクトリのいずれかを含む。または設定ホームか状態ディレクトリの
  内側にある。
- ホームを起点とする資格情報の置き場所（ホーム下の `credentialDirs` と
  `credentialFiles`）そのもの、その内側、またはそれを含む。どこにあっても
  一致する資格情報の*名前*（`.env`・`credentials.json` など）はこの判定に
  入れない。`.env` を持つツリーもルートにでき、そのファイルは §1 によって
  中で拒否されたままである。
- 共有の scratch ルート（`sandbox.ScratchDirs()`: `TMPDIR`・`/private/tmp`）
  の内側にある。そこでは write レーンのどのコマンドも、ルートそのものを
  退避して別のディレクトリと入れ替えられる。プロファイルはパスを名指し、
  ファイルツールは記述子を持つので、両者が食い違う。プロジェクトが既に
  従っている規則と同じである（`LaneProfile` は scratch ルートにプロジェクトの
  親を覆わせない）。
- 共有の scratch ルート・`/private/var/tmp`・`/dev` を含む。ルートがレーン自身の
  許可を巻き込むからである: write と operator レーンは、ファイルツールが断る
  read ルートの下の scratch に書き、`/dev` の上の読み取りの再許可は、どの
  レーンも拒否する端末デバイスを開け直す（実装レビュー、2026-10-29）。
- `write` に限り: 使っている設定ファイルを含む — `--config` は
  `~/.config/gem-agent` の外のファイルを名指せる。そうでないとモデルが、
  以後のすべてのセッションのフック・承認・ルートを書き換えられる（実装レビュー）。
- `write` に限り: `~/Library` の内側にある。read レーンはそのツリーをもう
  拒否しており、`LaunchAgents` や `Application Support` などには、他の
  プログラムがサンドボックスの外で走らせるファイルがある。
- 同じかより高いレベルのルートの内側にすでにある。起動時は 2 つの設定が
  矛盾しているのでエラーにする。要請のときは、どのルートが覆っているかを
  言う、何もしない注記にする。セッションの途中では、read ルートを含むことに
  なる write ルートは、それを吸収する（§12）。

システムディレクトリの一覧は置かない。肝心なものは SIP が守っており、
ホーム外のそれ以外の場所に書くかはオペレータが選べることである。

### 6. ルートの集合を使うすべての消費者が追加ルートを知る

次の箇所が、いまは「プロジェクトと作業ディレクトリ」を持っている。どれも
追加ルートをレベルつきで受け取る:

- **ファイルツールのレジストリ** — `internal/tools` の `rootState`・
  `rootFor`・`roots()`。ルートごとに `os.Root` を持ち、書き込みツールは
  レベルを見る。
- **ファイル読み取りの子プロセス** — `fileChildRequest`（`cmd/filechild.go`）
  は `ProjectDir` と `WorkDir` しか運ばない。ルートの一覧をレベルつきで
  運び、カーネルに閉じ込めた読み取り（ADR-0086）が追加ルートも覆うように
  する。追加ルートの読み取りを、プロセス内の読み取りに逃がしてはならない。
- **判定** — `risk.Classify` は 2 つの文字列ではなく、ルートをレベルつきで
  受け取る。write ルートへの書き込みはプロジェクト内の書き込みと同じに
  判定する。read ルートへの書き込みと、どのルートの外への書き込みは Block
  である。`persistentTarget` と `.git` は、そのパスを持つ write ルートを
  起点に判定する。
- **自動承認のレビュアー** — 渡す内容にルートを載せ、write ルートへの正当な
  書き込みを「プロジェクト外」と判定させない。
- **`@` メンション** — `mention.resolve` はどのルートの下のパスも受け付ける。
- **組み立て直しの経路** — `buildExecFn`・`rotateWorkDir`・プロファイルの
  `Spec` が起動時のルートを運び、`/clear` の組み立て直しがそれを保つ。
- **文言** — write レーンの拒否の注記、シェルツールの説明、ルート外の理由、
  システムプロンプトのルートの段落が追加ディレクトリを名指す。ルートが
  もっとあるのに「プロジェクトと作業ディレクトリ」と言うものは残さない。

### 7. プロファイルの順序とルートごとのプローブも規則のうちである

Seatbelt は後に一致した規則が勝つので、順序は組み立てる側に任せず、
ここで定める:

1. read レーンでの追加ルートの再許可は、`readLaneReadDenies` と
   `~/Library` の拒否の後、そして `writeCredentialBlock` の**前**に置く。
   `writeCredentialBlock` は最後の読み取り規則のままである。
2. read レーンでの各追加ルートへの書込拒否は、共有の `/private/var/tmp`
   の許可の後、プロジェクトの拒否と並べて置く。
3. write レーンと operator レーンは、書込許可に write ルートをプロジェクトと
   並べて書く。read ルートはどの書込許可にも出てこない。

起動時の検証（`VerifyReadLane` / `VerifyWriteLane`）が試すのはプロジェクトと
ホームである。それが証明するのは檻であって、新しいルートではない。なので
追加ルートごとに、起動時と付与のたびに、本物のプロファイルの下で専用の
プローブを走らせる:

- read レーンはそこにファイルを作れない。
- そこに作った資格情報の名前のファイルは、read レーンが読めない。
- `write` ルートなら、write レーンはそこにファイルを作れ、そこでの永続
  ファイル名は拒否される。
- `read` ルートなら、write レーンはそこにファイルを作れない。

プローブのファイルは、既存のプローブと同じくランダムな名前で作って
消す。起動時にプローブを通らないルートは、§3 と同じ理由で起動を止める。
このプロセス自身がまったく書けない read ルート（読み取り専用のボリューム）は
プローブのファイルを置けない。何もそこに書けないので、注記を出してプローブを
飛ばし、資格情報のブロックは順序のテストが覆う。同じ場合を、パッケージの
テストが本物の `sandbox-exec` で確かめる（`TestAddedRootEnforcement`）。

### 8. 一覧

`/dirs` はルートを、レベルと出どころ（`flag`・`config`・`slash`・`request`）
とともに一覧する。セッション中にルートを外すことはこの ADR に含めない。
§4 と同じ組み立て直しを使うので、新しい仕組みなしに後から足せる。

### 9. 2 段階で出す

1. §1–§3・§5–§7・§10: ルートとすべての消費者、起動時のフラグと設定、断る規則、
   順序とプローブ、write ルートの永続ファイルの見張り。
2. §4・§8・§11・§12: 要請ツール・`/dirs`・操作者の `/add-dir` / `/read-dir`。
   段階 1 の「組み立て直し・検証・差し替え」の上に乗る、1 つの付与の経路を通る。

段階 2 は段階 1 に依存し、段階 1 で作ったものを段階 2 でやり直すことは
ない。

### 10. write ルートの永続ファイルは見張って知らせる

*2026-10-29 追加。実装のレビューで、下の残余が最初に書いたより広いと
分かったため。*

`instructions.Load` が信頼の付与で絞るのは、プロジェクト自身のファイル
だけである。プロジェクトの**祖先**（ホームまで）の指示ファイルは、
「プロジェクトより上に書くのは操作者だけ」という前提で、確認なしに読み
込まれる。write ルートはこの前提を崩す。write レーンのコマンドは scratch で
`d/AGENTS.md` を作って `d` をルートへ移せ、後で `<root>/d/...` の下で
起動したセッションは、それを祖先のファイルとして確認なしに読み込む。
移し込んだチェックアウトは、操作者が次にそこで `git commit` したときに
サンドボックスの外で走る `.git/hooks` のスクリプトを持ちこめる。名前の
拒否はどちらも止めない。改名が名指すのはファイルではなくディレクトリだから
である。

そこで write ルートにも、ADR-0074 §3 以来プロジェクトが持つのと同じ
変化の検出を与える。何も止めはしない。変化を、それが起きたときに見える
ようにする:

- **見張るもの**: すべての `write` ルート。`read` ルートにはどのレーンも
  書かないので走査しない。
- **走査**: `trustpin.Snapshot` — プロジェクト自身の走査。`sandbox.PersistentFile`
  が守る名前（指示ファイル・`.mcp.json`・`.gem-agent.toml`・`.claude/`・
  `.git/hooks` など）をどの深さでもダイジェストで記録し、リンクはたどらず、
  `trustpin.WalkEntries` 項目で止まる。打ち切った走査は、起動時にルートごとに
  1 度言う。
- **いつ**: 起動時は、このプロジェクトの前回のセッションが同じルートについて
  記録したものと比べる。セッションの間に — 何によってであれ — 起きた変化が
  知らされる。`/clear` と終了時は、そのセッション自身の始まりと比べる。
  このセッションが足したり変えたりしたものが、操作者がそのツリーを他所で
  開く前に知らされる。
- **知らせ方**: 変化のあったルートごとに注記を 1 つ出し、ルートと、追加・
  変更・削除されたファイルを名指す。`/clear` と終了時の報告は、プロジェクト
  自身の記録と並べて、`root`（走査が上限で止まったときは `cut` も）つきの
  `persistent_changes` 記録を transcript に書く。起動時の報告は、プロジェクトの
  ものと同じく記録を書かない — 記録はセッションがしたことの記録だからである。
  打ち切られた走査は、打ち切りより先のものを削除とは言わない: そこは分からない
  のであって、無くなったのではない。
- **誰に知らせるか**: そのルートを足したプロジェクトのセッション。状態はその
  プロジェクトの状態ディレクトリにあるので、ルートの下で開いた別のプロジェクト
  — 置かれたファイルを読み込む側 — には知らされない。その場合の手当ては、下の
  残余にある助言である。
- **状態**: プロジェクトの状態ディレクトリにファイルを 1 つ、
  `added-persistent.json` を置き、このプロジェクトが足した write ルートごとに
  最後のスナップショットを持つ。ルートの中には何も書かない。

走査はルートごとで上限つきなので、コストは最悪でもその上限である:
`WalkEntries` より大きいルートは最初の項目だけを見張り、注記がそう言う。

セッションの途中で付与した write ルート（§4・§11）は、付与の時点で取った
スナップショットとともに見張りに加わる。その後にセッションが置いたものは、
他の write ルートと同じく、次の `/clear` か終了時に知らされる。

### 11. 操作者はセッションの途中でディレクトリを足せる

*2026-10-29、操作者の依頼により段階 2 とともに追加。*

起動時のフラグでは、ディレクトリを足すのに操作者が起動し直す必要がある。
モデルの要請（§4）では、操作者がすでに足したいと分かっているものを、モデルに
頼ませることになる。そこで操作者はプロンプトで足せる:

```
/add-dir <path>     write のルート。--add-dir と同じ
/read-dir <path>    read のルート。--read-dir と同じ
```

名前はフラグと同じで、`/add-dir` は Claude Code が同じ操作に使う名前である。

- **承認のプロンプトは出さない。** パスを打ったのは操作者である: `--add-dir` と
  `@<path>` がすでに引いている信頼の線と同じである。§4 のプロンプトがあるのは
  モデルが提案するからで、ここでは誰も提案していない。
- **同じ規則と同じ付与の経路。** 判定は `RefuseRoot`（§5）で、断るときは理由を
  言う。通ったパスは、承認された要請とまったく同じく §12 を通る。検証に失敗
  したら追加を断り、セッションはそのままにする。
- **リンクを通って解決するパスは、実パスで確かめる。** モデルはプロジェクトに
  `notes -> ~/Documents` を仕込み、`/add-dir notes` を勧められる。そうすると、打った
  パスは 1 つの場所を名指し、別の場所を与えることになる。実パスが、整えた打った
  パスと（ボリュームと同じく大文字小文字を区別せずに比べて）違うときは、何も足さず、
  注記が実パスを名指す。その実パスを打てば足される。それ以外ではプロンプトを
  出さない。注記はいつも実パスを名指す。
- **文法**（ADR-0098 の前例）: 行の残りがパスなので、空白を含むパスも引用符が
  要らない。先頭の `~` はホーム。相対パスはプロジェクトからの相対である。引数の
  ない `/add-dir` と `/read-dir` は、`/dirs` と同じくルートを一覧する。
- **使える場所**: 対話の面（TUI と素の REPL）で、他のスラッシュコマンドと同じく
  ターンの合間に。`-p` にはスラッシュコマンドがないので、フラグを使う。
- **既にあるルート**: read ルートへの `/add-dir` は write に上げる（§12 がその項目を
  置き換える）。すでに覆われているルートへの `/read-dir` と、write ルートへの
  `/add-dir` は、何も変えない注記になる。
- **read-only の上限**（ADR-0080）は外さない: 上限の下で足した write ルートには、
  上限が外れるまで何も書かない。
- **寿命**: §4 と同じ — `/clear` をまたいで残り、ファイルには何も書かない。恒久に
  する方法（`[directories]` かフラグ）を注記で言う。
- **記録**: `source: "slash"` の `added_directories` 記録。

### 12. 付与の経路は 1 つ。要請にも操作者にも

*2026-10-29、段階 2 の設計レビューから追加。*

セッションの途中の付与は、同時に読まれる 4 つのもの — シェルの実行器・レジストリの
ルート・見張り・システムプロンプト — を変える。その間も、床が見放した呼び出し
（ADR-0065）は走り続けうるし、`/clear` は独自に実行器を作り直す。そこで 2 つの
入口はどちらも 1 つの関数を呼び、それは次の順で進む:

1. **判定。** 今のルートで `RefuseRoot`。「すでに覆われている」はエラーではなく型の
   ついた結果で、注記として示す。判定するパスは、大文字小文字も含めてカーネルの
   名前（`CanonicalDir`）である: 包含の判定は文字列で比べるので、大文字小文字を
   区別しないボリュームで、大文字小文字を変えて打ったパスがそれをすり抜けた
   （実装のレビュー）。新しいルートは、内側にある、レベルが高くない追加ルートを
   吸収する — read ルートの上の write ルート、またはより高いレベルの同じ
   ディレクトリ: 内側の項目を置き換え、注記がそれを名指す（そうしないと、write
   レーンはファイルツールが断るルートに書け、プローブは分かりにくい失敗をする）。
2. **開く。** パスで `os.Root` を開き、記述子から実パスを読み戻し（`F_GETPATH`）、
   判定したものと比べる。その間にパスを差し替えられるのは、どのレーンの外にも
   いるもの — MCP サーバ（ADR-0077）と無制限のコマンド — である。`RefuseRoot` が
   受け入れたルートには、サンドボックスの中のレーンが書ける祖先がないからである。
3. **付与のロックを取る。** すべての付与と、`/clear` の `rotateWorkDir` が持つ 1 つの
   mutex。見放した呼び出しの遅れた付与と組み立て直しが、それぞれ古いスナップショット
   から組み立てて、最後の差し替えが勝つことを防ぐ。その下で、呼び出しの context と
   セッションの epoch を確かめる — セッションが先へ進んだ付与や、取り消された
   呼び出しの付与は捨てて記録する — そして、今のプロジェクト・作業ディレクトリ・
   ルートから `Spec` を組み立てる。
4. **組み立てと検証。** 3 つのプロファイル、続けて変えたルートについての §7 の
   プローブ。プローブはセッションが閉じ込められているときだけ走る: `--no-sandbox` や
   無制限のセッション（`Enforcement{}`）では、付与はファイルツールにだけ届き、
   シェルのコマンドは引き続き聞くと注記が言う。組み立て直した `Enforcement` は
   今のものと等しくなければならない — 付与は read レーンを入れも切りもしない
   （`ReadLanePrompts` の選択は保つ） — そうでなければ付与を断る。
5. **スナップショット**: write ルートなら §10 の見張りのために、新しいプロファイルで
   書けるようになる前に取る。
6. **差し替え**: シェルの実行器、続けてレジストリのルート — 追加するか、昇格や吸収
   なら既存の項目を置き換える。古いハンドルは `UseWorkDir` と同じく退役させる。
   ファイル読み取りの子プロセス・判定・レビュアーへの入力・`@` メンションは
   レジストリを読むので、それについてくる。
7. **記録**: 使っている transcript に `added_directories` を書き、システムプロンプトに、
   次のターンの区切りでの作り直しの印を付ける。`SetSystem` はターンの合間の操作で
   ある。今この時点でモデルに知らせるのは、ツールの結果（§4）か注記（§11）である。
   作り直しは、skill の再読み込みと同じく、プロンプトのキャッシュを温め直す。

`/clear` は、レジストリのルート — 起動時・`/`・要請のどれも — から組み立て直し、
その記録を新しい transcript に書く。見張りはそれらを持ち越す。

名前は TUI の入口を通って操作者に届き、そこで文字は入ってくる場所で無害にされる
（ADR-0093 §2）— 承認のプロンプトも注記も `/dirs` も同じである。表示する場所で
もう一度除くことはしない。

なければならないテスト: 昇格がファイルツール・判定・プローブに効く。write による
read の吸収。検証の失敗は、実行器・レジストリ・プロンプト・見張りを変えない。
取り消された呼び出しや見放した呼び出しの付与は効かない。`/clear` と遅れた付与の
競合。read レーンの選択が付与の後も保たれる。`request_directory` が `a`・`never` の
ポリシー・`--allow request_directory --auto` の下でも操作者専用のままで、`Subset` に
入らない。リンクを通る `/add-dir` は聞く。`/clear` の記録が `/` と要請のルートを
含む。

## 検討した代替案

- **プロジェクトの `.gem-agent.toml` でディレクトリを追加できるようにする**
  — 却下、§3: リポジトリが自分の外への書き込みを自分に与えることになる。
- **追加ディレクトリの指示ファイルと `.mcp.json` を信頼確認つきで読む** —
  オペレータが却下、§2。ルートごとのピンも要り、§4 と組み合わさると
  モデルが指示を持ち込めるようになる。
- **`request_directory` にモデル層やセッションの許可リストが答える** —
  却下。そのディレクトリを欲しがっているモデルが自分の要請を判定すること
  になる: ADR-0020 §4 の「評価者が提案者」への反対そのものである。
- **承認した要請をファイルに残す** — 却下。一度きりの答えが、後のどの
  プロンプトにも見えない常設の権限になる。
- **要請でも `/clear` と同じく `buildExecFn` を使う** — 却下、§4: 検証に
  失敗するとセッションを無制限モードにする落ち方を持ち、モデルの要請で
  サンドボックスを下げられるようになる。
- **付与のときは既存の起動時プローブだけを走らせ直す** — 却下、§7: 檻を
  もう一度証明するだけで、新しいルートが檻のどこにあるかは証明しない。
- **read ルートに operator レーンが書けるようにする** — 却下、§1。`read` が
  オペレータの承認したすべてのコマンドへの書込権になり、「read」が言葉
  どおりの意味でなくなる。
- **追加ルートを環境変数で渡す** — ADR-0068 と同じ理由で却下: 環境は
  すべての子に届き、transcript には見えない。ルートはシステムプロンプトと
  ツールの結果で述べる。
- **オペレータのプロンプトでモデルの `reason` を nonce で包む** — 却下。
  nonce はモデルをデータから守るためのもので、オペレータはモデルではない。
  人間に要るのは、最初に実パスがあることと、行を書き換える文字がないこと
  である。
- **禁止するシステムディレクトリの一覧を置く** — 却下、§5。ずれていく
  一覧であり、守るものは SIP がすでに守っている。

## 帰結

- オペレータは、vault・ノート・隣のツリーを、`--no-sandbox` なしで書ける
  ようにしたまま、レーンの保護の下に置ける。ファイルツールもプロジェクトと
  同じように届く。
- 広いディレクトリ（`~/Documents`）への `write` を承認すると、自動承認
  モードでは以後そこへの書き込みが聞かれなくなる。それは与えた権限
  そのものであって穴ではない。プロンプトがそう述べ、少なく与えたいときの
  ために「read として承認」の答えがある。
- **残余: write ルートには永続ファイルをいつでも置け、それは断られず、知らされる。**
  名前は拒否されるが、write レーンのコマンドは scratch で `d/AGENTS.md` を作り、
  `d` をルートへ移せる（レビューで実測: 移動は成功し、直接の書き込みは拒否
  された）。後で `<root>/d/...` の下で起動したセッションは、それを祖先の指示
  ファイルとして確認なしに読み込み、移し込んだチェックアウトの `.git/hooks` は、
  操作者が次にそこで git を使ったときに走る。§10 は、そうしたファイルを次の
  `/clear` か終了時に（強制終了したセッションの後なら次の起動時に）、そのルートを
  足したプロジェクトのセッションにだけ知らせ、移動は止めない。受け入れる:
  止めるには、ルートへのすべての改名を拒否するか（ツリーに書くことの大半が
  それである）、祖先のファイルを信頼で絞るか（どのプロジェクトが何を読むかが
  変わる）しかない。gem-agent や Claude Code で開くプロジェクトの上位を
  write ルートにしないこと。注記が出たら読むこと。
- **残余: 追加ルートの中の走査には、プロジェクトの無視規則が効く。**
  `list_tree`・`list_files`・`search_files` は `.gitignore` をプロジェクトを
  起点に読むので、追加ルートではプロジェクトの規則がその中の項目に当たりうる。
  作業ディレクトリでも ADR-0058 以来同じである。いまは受け入れる。規則を
  いちばん内側のルートを起点にするのは、それ自体が別の変更である。
- **残余: write ルートは、他のプログラムがサンドボックスの外で走らせる
  ファイルを持ちうる** — `~/bin`・`~/.local/bin`、`~/.config` の下の
  シェルの設定など。§5 が断るのは `~/Library` とホームそのものであって、
  これらではない。受け入れる: オペレータはそこへの書き込みを、パスを見た
  うえで承認しており、そうしたディレクトリの一覧はずれていく（§5）。
- 付与のたびに、ルートごとのプローブが走る。`sandbox-exec` を数回、付与
  1 回につき 1 度である。
- lagent はレーンの設計を共有している。移植は別の変更として、そちらで
  判断する。
