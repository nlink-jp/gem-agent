# ADR-0037: agentic_file_search — 隔離コンテキストでの委任プロジェクト検索

| 項目 | 内容 |
|------|------|
| Status | **Accepted** |
| Date | 2026-08-21 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | オペレーター: 文脈負荷の削減が目的なら、汎用サブエージェントではなく、リテラルな search_files とは別の「エージェンティックファイルサーチ」に絞るほうが効率が良い |

## Context（背景）

モデルが読んだものは、以後の全ラウンドで再送される。「X はどこで
扱っているか？」に答えるには `list_tree` / `search_files` /
`read_file` を数ラウンド回す必要があり、外れだった読み込み——結局
無関係だったファイル——はセッションの残り全部の期間、履歴に残って
リクエストごとに再送され続ける。`search_files` はモデルが既に知って
いる文字列を見つける道具であり、質問には答えられない。

ADR-0014 は 1 ファイルについて既に処方を確立している: バイト列では
なく要約を返す。本 ADR はそれを 1 ファイルから 1 つの質問へ一般化
する。

汎用サブエージェント（「このタスクを子ループで実行」）を先に検討し、
意図的に絞った。理由は 3 つ: 子の mutating コールが承認ゲートに
当たると、オペレーターは見えない会話について判断させられる——文脈
なしの承認は承認ではない（同じ構造が、書き込みタスクを持つ
バックグラウンドエージェントを実際に全滅させた実測がある）; 汎用の
`task` 引数は開かれた指示チャネルであり、相応の注入面を持つ; そして
何でも委任できるツールは何でも委任したくなり、トークン消費を逆に
倍増させる。検索専用エージェントは隔離の利益を保ったまま、これらの
問題をすべて失う。汎用ツールが将来必要になっても、それは本機構の
真上位集合であり、その時に独自の ADR を得る。

## Decision（決定）

### 1. 読み取り専用ツール 1 つ: `agentic_file_search(question)`

**メインモデル**上の子エージェントループ（多ラウンドのツール判断が
仕事の本体であり、サマリモデルでは力不足）に、読み取り専用ツールの
**ポジティブ許可リスト**を与える: `list_files`・`list_tree`・
`search_files`・`read_file`・`file_info`・`read_document`・
`summarize_file` — 最後のものは `[model].summary` で動く。メイン
ループと同じ構成である。許可リストは `Registry.Subset` が構築し、
未知の名前はエラーになる: セキュリティに関わる許可リストのタイポが
ツールを黙って落としてはならない。

除外は、それぞれ意図的である: すべての mutating ツール（上記の
承認文脈問題）、`web_search`/`web_fetch`（エグレスはメインループの
ゲート配下に留める）、MCP ツール（gem-agent には意味が未知）、
`ask_user`（対話予算はメイン会話のもの）、`view_image`（テキストの
報告はピクセルを運べない）、`load_skill`（instruction-grade の結果は
狭く保つべき ADR-0010 の穴）、メモリツール（mutating）、そして
**自分自身** — 再帰とファンアウトはプロンプトによる取り締まりでは
なく構造的に不可能である。

### 2. 隔離、ただし有界

コールごとに新しいエージェントを構築する: 独自の履歴、独自の nonce
タグ、`MaxTurns` 10、自動コンパクションなし、トランスクリプトなし
— 子の内部過程は ADR-0014 のサイドコールとまったく同様に一時的で
あり、usage レコードを 1 件記録する。報告は通常のツール結果として
メイン会話に入り、したがって nonce ラップされる: ファイル内容から
導かれたものだから非信頼データであり、既存の機構がそのまま正しく
扱う。子の registry には mutating ツールが存在しないにもかかわらず、
全拒否の approver を渡す — 構成が将来変わっても、見えない文脈に
ついてオペレーターに問うのではなく、fail-closed で拒否される。

### 3. 出力契約は否定形の空間を名指しする

子のシステムプロンプトが報告の形を固定する: 質問への直接の回答;
`path:行範囲` + 短い原文引用による根拠; **見つからなかったもの・
検証できなかったものの明示** — 否定的結果の欠落は「報告することが
ない」と読まれる。それが検索結果の嘘のつき方である; そして範囲外の
観察の行き先として最大 1 行の `Note:`（禁止ではなく行き先 —
禁止は情報を失う。サブエージェント出力契約に関するナレッジベースの
教訓）。報告は質問の言語で書かれる。結果ヘッダはモデル名・ラウンド
数と「引用は lossy — 編集前に `read_file` で実文確認」を名指しする。

### 4. 委任は観測可能で、監査される

- 子はメインのバックエンドを共有するため、委任中も ADR-0033 の
  ストリームハートビートが追加コストなしで動き続ける — 委任の
  1 分間がハングに見えてはならない。
- 子のツールコールは TUI と素の REPL に `↳ tool` 行としてライブ
  表示され、オペレーターは検索の進行を見ていられる。
- テレメトリ（ADR-0035）に `Sink.Sub(label)` を追加: 子の全イベント
  — `tool.call`・`model.usage`・`turn.end` — が
  `agent="agentic_file_search"` を運ぶ。委任先が何を読んだかを失う
  監査証跡は監査証跡ではない。
- トークン消費は `summarize_file` と同様に `/usage` の集計に載る
  （カテゴリ別会計、ADR-0019）: コンテキストゲージはメイン会話
  だけを追い、子はそれに一切触れない。

キャンセルには何も新しいものが要らない: ターンの context がツール
コール経由で子ループへ流れるので、Ctrl+C（と ADR-0034 のラダー）は
他のすべてを中断するのとまったく同じに子を中断する。

## Consequences（帰結）

- 方向づけの質問は 1 コールで済み、1 つの報告が返る; 探索は——
  その外れも含めて——メイン履歴に一切入らない。
- モデルには説明文が与える使い分けが必要になる: リテラル文字列 →
  `search_files`、質問 → `agentic_file_search`。質問は「何を探すか」
  と「何を報告するか」の両方を言うこと。
- 単発 `-p` モードは変更なしで動く — ツールは読み取り専用である。
- 10 ラウンドを使い切った子は上限を名指しする明確なエラーで失敗
  する; 答えはより狭い質問であって、より大きな予算ではない。
- 並列ファンアウトと汎用サブエージェントは将来の ADR に残る;
  どちらも本機構を再利用することになる。
