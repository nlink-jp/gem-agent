# ADR-0104: ターンが操作者を待つときは端末を鳴らす — 何も止めず、Claude Code の承認プロンプトと同じ間合いで

| Field | Value |
|-------|-------|
| Status | **Accepted**（2026-11-04） |
| Date | 2026-11-04 |
| Binds | gem-agent |
| Decision makers | nlink-jp メンテナ |
| Triggered by | 第三者の利用概要（agent-report）: 承認プロンプトが数分単位で放置されることが月に何度もあった |
| Relates to | ADR-0044（ツール実行前フック。この ADR が足さないフックのイベント）、ADR-0069（実物の契約を先に測る）、ADR-0093（端末に届くもの）、ADR-0080（読み取り専用の上限）、ADR-0096 §7（RT7 の不採用）、ADR-0036（ask_user）、ADR-0040（ラウンド上限の介入） |

## 背景

gem-agent は、ターンの途中で操作者の答えを待つことがある。承認プロンプト、読み取り専用の上限の下での MCP 呼び出しの承認、上限を外すかの問い、`ask_user`、ラウンド上限の介入（ADR-0040）である。待っている間ターンは止まるが、それを画面の外に知らせる手段が無い。ランタイムは端末に BEL も OSC 9 も書かない（ソースで確認。書く OSC は iTerm2 の画像のシーケンスだけ）。

`pre_tool_use` フック（ADR-0044）で音を鳴らすことは今もできるが、時機が違う。承認の段より前に走るので、許可リストや自動承認がすぐ答える呼び出しも含めてすべての呼び出しで発火し、対話が開いたのか、操作者がもう画面を見ているのかを知らない。

2026-11 に第三者が agent-report v0.2.0 で 1 か月分を集計した（実測、その利用者の環境。数字はその利用者のもので、ここには載せない）:

- 承認プロンプトの典型的な待ちは数秒で、多くの場合は操作者が画面の前にいる。一方で月に 40 回以上は数分を超えて放置され、最も長い待ちは時間単位に及んだ。知らせれば縮む待ちである。
- 結果までの時間が最も長かった MCP 呼び出しは、その待ちのために長かっただけで、実行そのものは長くても 1 分ほどだった。
- ラウンド上限の介入と `ask_user` も起きていた。これらの待ち時間は集計に無い（承認の記録を伴わないため）。

同じ集計の lagent には、このような長い待ちは無かった。

Claude Code はこの場面を二つの仕組みで扱う。組み込みの通知（`preferredNotifChannel`、既定は `auto`）と、止めることも変えることもできない `Notification` フックである。いつ発火し何を運ぶかは実物で測った（「測定結果」参照）。

RT7（ADR-0096 §7）で採らなかったのは、ターン終了時に回答を照合して**止める**関門である。この ADR は何も止めない。知らせるだけで、ターンの進み方・承認の判断・記録は変わらない。

## 決定

### 1. 知らせる場面は「TUI で動いているターンが操作者の答えで止まったとき」だけ

知らせる対話（すべて TUI）:

- 承認プロンプト（許可リストや自動承認が答えた呼び出しは対話が開かないので知らせない）
- 読み取り専用の上限の下での MCP 呼び出しの承認（`ApproveOnce`、ADR-0080）
- 上限を外すかの問い（`ApproveLift`）
- 質問の対話: `ask_user`、ラウンド上限の介入、`/riskbook learn` の確認。最後のものは要約モデルの呼び出しの後に出て、その間に操作者が席を外せるだけの時間がかかる。同じ対話を使うので、同じに扱う。

**間合い**は Claude Code の `permission_prompt` で測ったとおりにする。対話が開いた時点から 6 秒ごとに確かめ、直前の 6 秒にキー入力が無かった最初の確認で知らせる。キー入力はタイマーを最初からやり直すのではなく、次の確認を見送らせる。答えたら取り消す。開いたままの対話に 2 回目は出さない。こうして、画面の前にいる操作者は鳴らさない。

**知らせないもの:**

- **plain REPL。** stdin か stdout が端末でないときの代わりの画面である。問いは cooked モードで行ごとに読むので、Enter の前のキー入力は見えず、上の間合いが作れない。stdin がパイプなら、待っている相手は人ではない。
- **ワンショット実行（`-p`）。** そこでは何も待たない。承認は聞かずに拒否し（`denyGate`）、`ask_user` はエラーを返し、ラウンド上限の介入には呼び出し先が無い。
- **終わったターン**（2026-11-04、利用者の判断）。空の入力欄での待ちは途中で止まったターンではなく、測った数字も無い。§代替案参照。

### 2. 知らせは端末に渡す: `[tui].notify`

通知を出すのは端末アプリの仕事である（OS の通知の許可を持つのは端末で、gem-agent は .app ではない）。`[tui].notify` で選ぶ:

- `"bell"` — BEL を 1 つ書く。
- `"osc9"` — 固定の本文を持つ OSC 9 のデスクトップ通知 `ESC ] 9 ; gem-agent needs your answer ESC \` を ST で終えて書き、続けて別に BEL を書く。OSC 9 を解さない所では表示されずに捨てられる（Terminal.app、および先へ渡さない tmux）ので、そこで届くのは BEL である。
- `"off"` — 何もしない。

**既定値は `"bell"`**（2026-11-04、利用者の判断）。何も設定しない操作者にも届く。BEL はどの端末も受けるよう作られた制御で、tmux が先へ渡すと実測できたのもこれだけである。iTerm2 は窓の題名に示した。6 秒の確認があるので、画面の前にいる操作者は鳴らさない。この既定は Claude Code より音が出やすい。tmux の下の Claude Code の `auto` は何も書かなかった（実測）し、その文書では Terminal.app のベルを鳴らすのはオーディブルベルが切られているときだけとしている。オーディブルベルが有効な Terminal.app では、gem-agent の既定は音を鳴らすかもしれない（その反応は観測していない）。`"off"` でこの ADR より前の振る舞いに戻る。

この設定は他の `[tui]` の設定と同じ所に置く。`[tui]` と同じくグローバル設定だけで（プロジェクトの設定からは変えられない）、`/settings` に出どころとともに表示し、`config.example.toml` に載せる。

**バイトを端末に届ける道。** 知らせはランタイムが自分で書く定数のバイト列で、外から来たものを含まない。だから外から来た文字を扱う ADR-0093 の対象ではなく、無害化も要らない。TUI の端末への書き込み口から、レンダラの書き出しと直列にした単独の書き込みとして 1 回書く。書き出しの途中にも、再描画のたびに出てしまう `View()` の中にも入れない。

### 3. 記録とテレメトリは足さない

知らせたことはトランスクリプトに書かない。効果は、操作者が agent-report の `operator_wait_sec` を導入の前後で比べれば分かる。計測のために記録を増やすことはしない。

## 測定結果（2026-11-04）

ADR-0069 と同じく、契約は文書でなく実物から取った。

**Claude Code 2.1.311** を対話モード・既定の承認モードで非公開の tmux サーバの中で動かし、`--settings` で `Notification`・`PermissionRequest`・`PreToolUse`・`Stop`・`UserPromptSubmit` の入力と時刻を書き留めるフックを登録した:

- **承認プロンプト。** `PermissionRequest` の 6.0 秒後に `permission_prompt` が届いた。`message` は `"Claude needs your permission"`。欄は `session_id`・`transcript_path`・`cwd`・`hook_event_name`・`message`・`notification_type` に、文書に無い `prompt_id`・`scratchpad_dir`。文書で省略可能とされる `title` は無かった。
- **キー入力。** プロンプトが開いて 4.3 秒後と 8.3 秒後にキーを押すと、知らせは 18.0 秒後に来た。6 秒ごとの 3 回目の確認、つまり直前の 6 秒にキー入力が無かった最初の確認である。
- **`AskUserQuestion`。** 他のツールと同じく `PermissionRequest` を通り、6.0 秒後に同じ `permission_prompt`・同じ `message` が届いた。75 秒開いたままにしても、届いたのはその 1 回だけだった。
- **ターン終了後。** `Stop` の 60.1 秒後に `idle_prompt`（`message` は `"Claude is waiting for your input"`）が届いた。2 回の試行の両方で同じで、それぞれ 1 回だけ。その後 80 秒は何も来なかった。
- **組み込みの通知。** tmux の中の Claude Code は、どの場面でも端末に BEL も OSC 9・99・777 も書かなかった（OSC は窓の題名だけ）。

フックの入力の形は、通知のフックを足すかもしれない後の ADR のためにここに残す（§代替案参照）。

**端末** には BEL、OSC 9（BEL 終端と ST 終端）、OSC 777 を送った（`tools/escprobe` の方法: 画面を読み戻し、クライアントが受け取るものをバイト単位で記録）:

| 端末 | BEL | OSC 9 | 本文が文字として表示されたか |
|---|---|---|---|
| tmux 3.8（既定: `bell-action any`・`allow-passthrough off`） | 外側の端末へ渡す | 食べて先へ渡さない（OSC 777 も同じ） | いいえ |
| Terminal.app | 観測していない | 捨てる。背後の窓からでも通知は出ない | いいえ |
| iTerm2（プロファイルの通知が有効） | 窓の題名に 🔔 | 背後の窓から出すと `Session <name>: <body>` の形の通知（日本語表示では `セッション …`） | いいえ |
| kitty 0.50.0 | 観測していない | 最初の 1 回で macOS が kitty を通知の送り手として登録した（初回の案内が出た）。通知そのものは確認できなかった | いいえ |

どの端末も、解さない OSC の本文を文字として表示しなかった。したがって `"osc9"` はどこに書いても害が無く、デスクトップ通知になるのは一部の端末だけで、tmux の下では BEL だけが届く。

**実装を本物の端末で確かめた結果**（tmux 3.8。ペインが受け取ったバイトを記録し、実際のターンで本物の承認プロンプトを出した）: 既定の `"bell"` では、プロンプトが出て約 6 秒後に BEL が 1 つ、レンダラの書き出しの直後に単独で届いた。`"osc9"` でプロンプトが出て 4.4 秒後にキーを押すと、知らせは 12 秒の確認で `ESC ] 9 ; gem-agent needs your answer ESC \` と BEL の形で届いた。

## 結果

- TUI の対話で止まったターンが、席を外した操作者に届く。届いた後の答えの速さは操作者次第で、この ADR が保証するものではない。
- **何も設定していない操作者の振る舞いが変わる:** 出荷後は、TUI の対話を 6 秒放置すると端末のベルが鳴る。リリースノートにそう書き、`[tui].notify = "off"` を案内する。
- 開いている対話ごとに確認のタイマーを 1 本使う。`notify = "off"` なら何も走らない。
- plain REPL とワンショット実行の振る舞いは変わらない。
- lagent は拘束しない。同じ集計で lagent に待ちの根拠は無い。移植するかは lagent 側で決める。

## 代替案

- **gem-agent が OS の通知を直接出す**（`osascript` の `display notification`、UserNotifications）— 不採用: 通知の許可と見え方は端末アプリが持つ。CLI が別の経路で出すと、操作者には出どころの違う通知が二系統見えることになる。
- **通知のフック**（Claude Code の `Notification` と同じ入力の `[[hooks.notification]]`）— 今回は採らない。ADR-0044 §1 はフックのイベントを需要が示されたときに足すとしている。集計が示すのは待ちが長いことで、それには組み込みの知らせが答える。フックの需要は示されていない。後の ADR で上の実測した形のまま足せる。その場合、非同期のフックを対話に答えたとき・セッション終了時・`/clear` のときにどうするか、失敗をどう知らせるかを決める必要がある。Claude Code の `terminalSequence` 出力もその問いに属する。
- **既存の `pre_tool_use` フックを使う** — 足りない: 承認の段より前に、すべての呼び出しで発火し、対話のこともキー入力のことも知らない。
- **ターン終了後に知らせる**（Claude Code の `idle_prompt`。ターン終了の 60 秒後に 1 回と実測）— 今回は採らない: 長い自律ターンの終わりを知らせる価値はありそうだが、その待ちを測った数字が無い。agent-report も今はこの待ちを集計しないので、まず別に測る必要がある。
- **plain REPL でも知らせる** — 採らない: §1 参照。
- **知らせを繰り返す・段階的に強める** — 不採用: 測ったのは「待ちが長い」ことだけで、1 回で足りないという根拠は無い。
- **ターン終了時の照合や停止**（RT7）— ADR-0096 §7 で不採用のまま。この ADR は止める仕組みを持たない。
