# ADR-0063: 図のフェンスはその場で描画し、ランタイムは図について何も語らない

| 項目 | 値 |
|-------|-----|
| ステータス | **Accepted** |
| 日付 | 2026-09-02 |
| 拘束範囲 | gem-agent |
| 廃止対象 | [ADR-0043](0043-diagram-tool.ja.md) |
| 改訂対象 | [ADR-0042](0042-terminal-diagrams.ja.md) |
| 決定者 | nlink-jp メンテナ |
| 契機 | オペレーター: ツール方式はターン数を増やし、応答の中にステータス行が混ざる — そして 2 ヶ月分のセッションが示したのは、チャットから図が消え、手描きの罫線アートに置き換わったという事実だった |

## Context（背景）

v0.40.0 が ADR-0043 を出荷してからの 2 ヶ月間の実測（記録された
76 セッション）:

- `render_diagram` の呼び出しは**1 回**。その 1 回は成功した — そして
  ツールの存在理由だったループ（拒否 → 修正 → 描画）は、事実上一度も
  行使されなかった。
- 指示どおり、mermaid フェンスは応答から消えた。置き換わったのは
  ツールではない: モデルは**素のフェンスの中に罫線アートを手描き**
  するようになった。応答にも、Markdown ファイルにも（08-23 以降で
  7 件）。手描きアートは検証されず、別の幅では崩れ、mermaid で
  あるべきファイルの図を汚染する。
- 機序は ADR-0020 §5 がメモリで実測したものと同じ: **具体的な禁止の
  隣に曖昧な推奨を置くと「めったにやるな」と読まれる。**
  「do NOT write a mermaid fence」は具体的で、「files are
  unaffected」は添え書きだった。モデルは禁止を過剰一般化し、誰も
  想定していなかった — そして禁止されてもいなかった — 第 3 の経路を
  発明した。

その間、ツールのコストは常時発生し続けた: 図 1 つにつき 1 ラウンド
の追加、応答に混ざるステータス行、そしてモデルの自然な学習済み挙動
（Markdown には mermaid フェンス）に乗るのではなく逆らって発火させ
なければならない契機。

ADR-0043 の正直さの論証 — 書いた本人に告げない拒否は正直ではない —
は正しかった。だが実践でループを閉じている経路は人間である:
オペレーターは画面を見て「単純にして」「描けてないよ」と言える。
これは標準トリアージ（教える / 検証して拒否 / 人間に見せる）の
(3) そのものだ。ツールが買った同一ターン内のフィードバックループは、
ほぼ一度も使われなかった。

## Decision（決定）

### 1. フェンス描画を復活させる（ADR-0043 §1 を廃止）

`diagram.Split` を TUI の Markdown レンダラ — 完成セグメントが必ず
通る唯一の場所 — で実行する: 回答を mermaid フェンスの周りで分割し、
描く。忠実に描けるフェンスはその位置で罫線アートとして表示し、
描けないものはソースのまま表示する。外側のフェンスの**内容**である
```` ```mermaid ```` 行（別のコードブロック内に引用された例示）は
データであり、決して描かない。素の REPL と単発モードは従来どおり
触らない。

これは**表示層**の関心事であり、それが ADR-0043 の「モデルが出した
ものを加工しない」との整合線になる: glamour は既に、印字する全応答を
再レンダリングしている — 見出しも、表も、コードブロックも。フェンス
を描くのは同じカテゴリだ。ただし条件がある: (a) トランスクリプトは
モデルのソースを逐語で保持する、(b) 描画前の変換は凍結済みの構文
テーブルのみ、(c) フォールバックは逐語のソース。ADR-0043 が正しく
葬った「意味を変える補正」は死んだままにする。

### 2. プロンプトとツール群は図について何も語らない

ツールなし、「mermaid で書け」なし、「アスキーアートを手描きするな」
なし、方言の段落もなし。上記の汚染は自前の禁止文から生まれた —
否定形の指示は過剰一般化する — し、肯定形の書式指示も同様に不要で
ある: モデルの自然な事前分布（Markdown の図は mermaid フェンス）が
既に望む挙動であり、この面でも、モデルが書く他のあらゆる面でも
同じだ。ランタイムは書かれるものを操縦するのではなく、届いたものを
描画する。

v0.38.0 の方言教育はこの節とともに引退する。凍結済み変換テーブルが
単独で負荷を担う。凍結時の実測: テーブルありで実ブロック 18 中 16 が
描画、なしで 13。テーブルは残り、プロンプトは消える。

不在はテストで固定する: システムプロンプトはどの面でも図に関する
文言を含まない。

### 3. FIT を削除する（ADR-0042 を改訂 — 残る規則は 2 つ）

幅ゲートなし、高さ上限なし。端末より広いアートはそこで折り返し、
画面より高いアートはスクロールする — スクロールバックの他の全てと
同じように。これを正直に成立させる実装上の事実が 1 つある:
**アートは glamour を迂回しなければならない**。最初のプローブ
（空白を含まない 132 セルの行を `WithWordWrap(80)` に通した）は
glamour がコードブロックの行を無加工で通すと示唆したが、独立
レビューが実物の罫線アート — 空白を含む — で再測定し、glamour は
コードブロックの行を**空白で語折り返し**して、端末に届く前に広い
図を断片の交互列に粉砕することを突き止めた。それは醜さではなく
間違いだ。よってアートのセグメントはシェル出力と同じ逐語レーンで
端末へ渡し、周囲の markdown は従来どおり glamour で描画する。TUI の
スクロールバック経路は折り返すだけで決して切り詰めず、端末自身の
折り返しははみ出した行を順番に割るだけ — 情報は失わない。残るのは
醜さであり、醜さは読み手の判断であってゲートではない: v0.37.4 で
ER 複雑さ上限をリバートしたのと同じ基準だ。

残るガードは「間違い」のガードで、不変: ソースの全ラベルはアートに
現れなければならない、flowchart の辺数は描かれた矢印頭数と一致し
なければならない、非 ASCII ラベルのシーケンス図はレンダラが整列を
崩すのでソースのまま。

### 4. 描こうとして失敗したブロックはフェンス + 1 行を残す

フェンスの後に `*diagram shown as source: <理由>*` を置く —
読み手向けであり、ループを閉じるのは読み手だ。モデルは画面を
見ない。非対応の図種別は無言で素通しする: チャットの gantt は
エラーではないし、その全部に注記を付けたらノイズになる。注記は
`warning:` 行と同様に英語（ADR-0029 はログ体裁のクロームを言語
カタログの対象外とした）。

### 5. ツールとともに削除するもの

`render_diagram`、`diagram.Budget`、`agent_info` の図予算行。

## Consequences（帰結）

- 図のコストは追加 0 ラウンドになり、応答はモデルが書いたとおりに
  読める。フェンスの位置にアートが入る。
- モデルはどこでも同じ図形式を書くようになり、ファイルには既定で
  本物の mermaid が入る。
- モデルは同一ターン内の描画フィードバックを失う。上記の実測に
  基づき受容する: ループの発火は 2 ヶ月で 1 回、機能している経路は
  人間だ。
- 手描きアートが習慣で残るなら、セッションログに現れる。答えは
  新しい実測であって、新しい禁止ではない。
- ADR-0042 の 3 規則は 2 つになる: TRANSLATE と VERIFY。
