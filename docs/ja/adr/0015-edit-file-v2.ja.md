## Context

`edit_file` は既に「一意性契約つきの完全一致文字列置換」であり、アンカーとしては
正しい。そして代替案に対するオペレータの直感も正しい: 行番号アドレッシングは、
ここで一番困る形で壊れる — 番号は編集のたびにずれ、モデルは数え間違え、
古い番号は**黙って**間違った場所に書く。文字列アンカーは、大きな音で失敗するか
正しく動くかのどちらかである。この性質は守る価値がある。

今日の編集を高くしているのはアンカーではなく、その周りのラウンドである:

1. **1 呼び出し 1 編集。** 5 箇所に触る変更は 5 ラウンドで、毎回履歴全体を
   再送する（ADR-0014 のコスト再び）。
2. **一括置換が無い。** リネームは多数の呼び出しか、`write_file` の全書き —
   オペレータが名指しした無駄そのもの — を強いる。
3. **失敗が診断されない。**「old_string not found」だけでは、モデルは原因究明の
   ためにファイルを再読しに戻る（しばしば全文）。実際の原因はタブ 1 個の違い
   だったりする。
4. **成功に証拠が無い。**「edited <path>」だけでは、慎重なモデルは再読して
   検証するしかない。

## Decision

アンカーは守り、経済を直す。`edit_file` に後方互換で追加する:

1. **一括編集 `edits: [{old_string, new_string, replace_all?}]`**。適用は
   **逐次**（各編集は先行編集の結果を見る — 人が躓く意味論なので説明文に明記）
   かつ**アトミック**: 全編集をメモリ上のコピーに適用して 1 回で書くか、
   何も書かずに「何番目の編集が・なぜ」失敗したかを名指すエラーを返す。
   半分だけ適用されたバッチは、誰も正確な姿を知らないファイルを残す。
   単発の `old_string`/`new_string` 形式は 1 編集の場合としてそのまま残る。
2. **編集ごとの `replace_all`** — リネーム用。一意性契約が既定のままで、
   replace_all は明示的な opt-out。報告には置換件数を含める。
3. **不一致は拒否だけでなく診断する。**「not found」時は空白を正規化して
   再検索する（インデントと空白連続の差 — モデルが実際に外す形）。近い一致が
   あれば行番号と**実際の**テキストを報告する。修正が再読ではなくコピペで
   済む。「N 回出現」時は出現行番号を列挙する — アンカーの一意化に必要なのは
   せいぜい窓読みであって全文読みではなくなる。
4. **成功は証拠を返す: 変更後の領域** — 新しいテキストを前後 2 行の文脈と
   行範囲つきで。範囲や見出しは注記側に置き、内容への行番号プレフィックスは
   決して付けない（ADR-0014 の規則: 番号付き内容はコピーされた瞬間に完全一致
   契約を毒する）。証拠が結果に入っていれば読み戻し検証ラウンドが消える。
   意図するループは「窓読み → 一括編集 → 結果で検証」である。

## Consequences

- オペレータが名指しした部分変更の無駄が端から端まで消える: 窓読みで入り、
  一括呼び出しで出て、検証は同梱。全文を読む・書くのは全文が論点のときだけ。
- 逐次バッチの意味論は驚きうる: 同一バッチ内の先行編集で変わったテキストを
  old_string にした編集は外れる。アトミックな失敗 + 近似一致診断がこれを
  大きな音にし、回復可能にする。説明文でも警告する。
- 近似一致検索はヒューリスティックである。影響するのは**エラーメッセージ
  だけ** — 適用は相変わらず完全一意一致を要求するので、外れた推測のコストは
  「ヒントが少し役に立たない」以上にならない。
- 結果ペイロードはスニペット分（上限つき）増える。置き換える再読より毎回安い。

## Alternatives considered

- **行番号・行範囲編集** — オペレータと同意見で却下。古い番号は黙って
  間違った場所に書く。文字列アンカーの失敗様式（大きな音の不一致）は、
  アドレッシングの失敗様式（静かな破損）より厳密に良い。
- **unified diff / パッチ入力** — 却下。モデルは壊れた hunk とずれた文脈行を
  日常的に出す。パッチパーサには誰も求めていない形式のための診断機構が
  別途必要になる。edits 配列は同じ情報を完全一致の意味論で運ぶ。
- **fuzzy 適用**（近似一致を自動適用）— 却下。完全一致契約の価値の全体は
  「モデルが文字どおり指定していないものをツールが決して書かない」ことに
  ある。近似一致はヒントであり、行動では決してない。
- **別ツール `multi_edit`** — 却下。同じ操作に 2 つ目の名前
  （ADR-0014 の read_lines と同じ論法）。
