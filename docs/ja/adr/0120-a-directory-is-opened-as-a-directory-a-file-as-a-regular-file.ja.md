# ADR-0120: ディレクトリはディレクトリとして、ファイルは通常ファイルとして開く

| 項目 | 値 |
|-------|-----|
| Status | **Accepted**（2026-11-17） — §8 は ADR-0122 で撤回 |
| Date | 2026-11-17 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | v0.104.0 の後の修正は、普通に開くと FIFO で待つプロジェクトのファイルを 4 つ見つけ、ほかの open は測らないまま残した。操作者: 残りを測り、名前を操作者自身が選んでいないものを直す |
| Amends | ADR-0119（その残余: 一覧するディレクトリには残らなくなった） |

## Context

FIFO を普通に開くと、相手側を誰かが開くまで待ちます。ADR-0119 は、プロジェクトが名前を決める 4 つのファイルでこれに当たり、通常ファイルのときだけ開くようにしました。ほかの open はそのとき測っていません。ここで測りました。どれも実際のコードで、その名前に FIFO を置いて呼び、2 秒で戻らなければ「待つ」と数えています（macOS 27.2、Go 1.27）。

相手側に誰もいない FIFO に対する、開き方ごとの結果:

| 開き方 | 結果 |
|---|---|
| `os.Open`、`os.ReadFile`、`Root.Open` | 待つ |
| `os.OpenRoot`、`Root.OpenRoot` | 待つ — 普通に開いてから種類を見る |
| 書き込みで開く（`os.WriteFile`） | 読み手が来るまで待つ |
| `O_DIRECTORY` を付ける | その場で「ディレクトリではない」と返る。リンク越しでも同じ |
| `O_NONBLOCK` を付ける | その場で開く |
| `Stat`、`os.ReadDir`、FIFO を途中に通るパス | その場で返る |

シェルのコマンドがルートそのものに対してできること（実際のプロファイルで実行）:

| | write レーン | operator レーン |
|---|---|---|
| `.claude/skills` や `AGENTS.md` を FIFO として作る | 名前で拒否される | できる |
| セッションの作業ディレクトリを消し、同じ名前で FIFO を置く | できる | できる |
| 書き込み可で追加したディレクトリで同じことをする | できる | できる |
| プロジェクトのディレクトリを別のルートへ移し、同じ名前で FIFO を置く | できる | できる |

つまり、モデルが選べるのはルートの中の名前だけではありません。ルートの名前そのものも選べます。

待ったもの:

| FIFO の場所 | 待った処理 | 誰が置けるか |
|---|---|---|
| `<project>/.claude/skills` | スキルの探索、信頼の質問の前の下調べ、ピン（起動時と、ツールが書いた後） | 操作者が承認したコマンド、またはランタイムの外の何か |
| セッションの作業ディレクトリ | 終了時と `/clear` の後片づけ、ファイルツールのルート、そこへの `@` 参照 | write レーン |
| 追加ディレクトリ | ファイルツールのルート（起動時、再開時、読み取りを実行する子プロセス）、そこへの `@` 参照 | write レーン |
| プロジェクトのディレクトリ | 指示ファイル、`.mcp.json`、ピン、ファイルツールのルート | write レーン |
| メモリ、メモリのディレクトリ、トランスクリプト、セッションのディレクトリ、`.project` マーカー、前回のセッションの 2 つのスナップショット、作業ディレクトリを収めるディレクトリ、`policy.toml`、`risk-rules.md`、プロジェクトの `rules.md`、操作者自身のスキルと指示ファイルのディレクトリ | それぞれの読み込み。多くは起動のたびに走る。FIFO の上へのメモリの保存は戻ってこなかった | 操作者、またはレーンの外で操作者として動くプロセス |
| 設定ファイル（`--config`）、`headers_file` | その読み込み | 操作者。名指すことで |

待たなかったもの: モデルが頼める読み取りのすべて（`read_file`、`search_files`、一覧、`view_image`、`show_image`、`edit_file`、`write_file` のコピー元）、ファイルへの `@` 参照、`/add-dir`。これらは待たずに開き、開いたものの種類を見ます（ADR-0072 §4.8）。スキルのディレクトリの各項目と、スキルの中のファイルも待ちませんでした（ADR-0119）。

## Decision

1. **一覧するディレクトリは、ディレクトリとして開きます**（`bounded.OpenDir`、`bounded.OpenDirIn`）。`O_DIRECTORY` を付けるので、ほかのものはカーネルが開く時点で、待たずに断ります。開く前に見るものが無いので、その間に差し替えられるものもありません。これは `os.ReadDir` 自身が渡しているフラグで、ディレクトリの開き方は何も変わりません。
2. **ルートは、見てディレクトリだったときだけパスで開きます**（`bounded.OpenRoot`）。`os.OpenRoot` はフラグを取らないので、見てから開く形になります。
3. **このランタイムが、自分で決めた名前で読むファイルは、通常ファイルのときだけ開きます**（`bounded.OpenRegularPath`。ADR-0119 がプロジェクトの 4 つにしたのと同じ）。メモリ、トランスクリプト、マーカー、スナップショット、`policy.toml`、`risk-rules.md` とプロジェクトの `rules.md` です。状態ディレクトリはレーンから書けませんが、含めます。理由は 3 つあります。その中の 1 つ、作業ディレクトリは、モデルが差し替えられる名前でした。これらのファイルが FIFO であるべき場面はありません。そして、ランタイム自身のツリーの中に例外の無い規則はテストで保てますが、名前ごとに判断していたことが、これらの open を取り残した原因でした。
4. **決まった名前で書くファイルは、通常ファイルの上にだけ書きます**（`bounded.WriteFile`）。メモリと、ポリシーファイルとプロジェクトのルールを保存するときの一時ファイルです。
5. **操作者が名指すものは、ここでは変えません。** `--config` で渡した設定ファイルと、設定が名指す `headers_file` は、FIFO なら何かが書くまで待ちます。そこに FIFO やプロセス置換を置くのは、操作者が意図したことかもしれません。断るかどうかは操作者の判断で、未決のまま残します。
6. **テストで保ちます**（`internal/archtest` の `TestOpensDoNotWait`）。`internal/bounded` の外に `os.Open`、`os.OpenFile`、`os.OpenRoot`、`os.Create`、`os.WriteFile`、`toml.DecodeFile` は無く、`Open`、`OpenFile`、`OpenRoot`、`Create`、`ReadFile`、`WriteFile` というメソッドの呼び出しもありません。例外は、待たない理由をテストが 1 つずつ挙げているものだけです。最初の形は `os.OpenFile` と `OpenFile` メソッドを見ておらず、変更のレビューが、そのために見えていなかったものを見つけました。
7. **ファイルは待たずに開きます。** Consequences に記録した観察の後で、操作者が決めました。`bounded.OpenRegular` と `bounded.OpenRegularPath` は、これまでどおり先に見てから、`O_NONBLOCK` で開き、開いたものをもう一度見て、ファイルを返す前にフラグを外します。ファイルツールの開き方と同じです。見てから開くまでの間に FIFO へ差し替えられた名前は、待たずに断ります。変更前に、名前をファイルと FIFO の間でディスクの許す限り速く差し替えながら測ると、見てから普通に開く形は 6 回中 6 回、10〜212 回開いたところで待ちました。変更後は、1.5 秒の実行ごとに約 11,000 回開き、35 万〜70 万回断り、待ったものはありませんでした。フラグは読む前に外すので、読み取りは変わりません。
8. **スキルを歩くときは、各階層を 1 つ上の階層から、待たない開き方で開きます。** この記録がスキルの下位ディレクトリに残した残余を閉じるよう、操作者が求めました。これまでは階層ごとに `os.Root` を持ち、次の階層を `Root.OpenRoot` で得ていました。これはフラグを取りません。一覧した後で名前を FIFO に差し替えられた下位ディレクトリは、歩きを止め、そのスキルの利用も止めていました。今は、階層をそのために開いたディレクトリ（`bounded.Dir`）として持ち、中のものを 1 つの名前で開きます。下位ディレクトリは `O_DIRECTORY` で、ファイルは `O_NONBLOCK` で開いて開いたものを確かめ、どちらもリンクは辿らず、パスや `..` である名前は開きません。変更前に、下位ディレクトリの名前をディレクトリと FIFO の間で 2.5 秒に約 3,400 回差し替えながら測ると、歩きは 6 回中 6 回待ちました。変更後は 6 回とも待ちませんでした。最初に提案した方法は、すべてをスキルのルートからのパスで名指すもので、階層ごとのハンドルが要りません。これは測って、採りませんでした。ルートはパスを open のたびに 1 要素ずつ解決するので、ADR-0119 の上限いっぱいの木を歩くのに、0.3 秒だったものが 8.2 秒かかりました。採った形では 0.3 秒です。digest は変わりません。ただし、そう言えるまでに見直しが 1 度要りました。この変更の最初の形は、階層の一覧を、ディレクトリ自身が名前ごとに記録している種類で作っていました。そのレビューが、その形では読み方が変わる木を見つけました。ACL で見ることを拒まれた名前（`deny readattr`）を含む木です。ルート経由の一覧は名前を 1 つずつ見て、見られない名前のところで止まります。ディスク上のピンはその一覧から取ったものなので、その後ろの名前はどのピンにも入っていません。`bounded.Dir` も同じ一覧の作り方にし、テストがその一覧をルートの一覧と名前ごとに突き合わせます。同じレビューは、最初の形が階層ごとに記述子を 2 つ持つことも見つけました。変更前の歩きは 1 つでした。今は、階層の一覧を専用の記述子で作り、下の階層へ降りる前に閉じます。そのうえで、変更前と変更後の歩きを、ピンが区別するあらゆる種類の木 — 各種のリンク、空白・改行・非 ASCII 文字を含む名前、255 バイトの名前が 32 階層続く木、FIFO、権限をモードごとに落としたファイルとディレクトリ、ファイルやディレクトリの権利を 1 つ拒む ACL を 3 つの階層それぞれに付けた木、拡張属性とファイルフラグ、大きさの上限を超えるファイル、各上限を超える木、残りの記述子が少ないときの歩き — と、実在の 19 の木（導入済みのスキルと、リポジトリ全体。ファイル数の上限 2,000 まで）で比べ、毎回同じ項目と同じ digest を得ました。12 の性質 — 普通の open それぞれ、開いたものの確認、フラグを外すこと、リンクそれぞれ、open とリンク先の読み取りそれぞれでの 1 つの名前、ルートと同じ一覧、その数の上限、専用の記述子、close-on-exec — を 1 つずつ元に戻すと、どれもテストが検出します。6 のテストは、`internal/bounded` の外の生の open（`unix.Open`、`unix.Openat`、`syscall.Open`、`syscall.Openat`）も落とします。
9. **リリース前のレビューが見つけた、さらに 3 つの open。** 1〜8 を書いていない読み手が変更全体を読み、まだ待つ open を 3 つ見つけました。2 つはそのレビューが再現し、3 つめはコードから明らかです。すでに使われている名前で結果を保存するときは、そこにあるファイルと比べます。そのファイルを、見てから普通に開いていました（`fileSHA256`）。7 が破られると測った形で、しかも作業ディレクトリの中の名前です。そこにはセッションのコマンドと MCP サーバが書けます。ファイルと FIFO の間で差し替えると、3 回中 3 回待ちました。終わりの無いファイルへのリンクに差し替えれば、比較も終わらなかったはずです。これは 6 の一覧に載っていて、理由として書かれていたのは「先に見ている」ことでした。それは open が待たない理由になりません。今は、待たずに、リンクを辿らずに開き（`bounded.OpenRegularPathNoFollow`）、種類と大きさを開いたものから読み、その大きさより多くは読みません。セッションの作業ディレクトリを消すときは、先にそのキャッシュを消します。`os.RemoveAll` は、最初の削除が失敗すると、消す対象の親を普通に開きます。キャッシュを収めるディレクトリ（状態ツリーの中で、3 が扱う種類です）が FIFO になっていると、操作者が確認した後の `workdirs clean` が止まりました。今は親をルートとして開き、そこから名前を消します（`bounded.RemoveAll`）。残るのは 2 の残余だけです。そして `bounded.WriteFile` は、見てから `os.WriteFile` を呼んでいました。コメントには間で差し替えられるとまだ待つと書いてあったのに、この記録は残余をルートだけとしていました。今は、待たずに開き、開いたものをもう一度見て、ファイルを空にするのはその後です。open では空にしません。6 のテストは `os.RemoveAll` と `os.OpenInRoot` も落とします。同じレビューは、1〜8 が変えたものを 1 つずつ元に戻し、そのうち 3 つをどのテストも検出しないことを見つけました。開けない下位ディレクトリの先へ歩きが進むこと、一覧した後に消えた名前を除くこと、open の前に見ること、の 3 つです。今はどれにもテストがあります。先に見ることには、それ自体の理由があります。FIFO は、待たずに開いても、反対側で待っている相手を通してしまいます。この決定の 13 の性質を 1 つずつ元に戻すと、どれもテストが検出します。

## Consequences

- `<project>/.claude/skills` が FIFO なら、スキルの無いプロジェクトとして扱います。ルートがあった場所が FIFO なら、そのルートは開けず、それを必要とした処理はその場でエラーを返します。
- `policy.toml` が FIFO なら、その名前を挙げたエラーで起動が止まります。これまでは何も言わずに止まっていました。`risk-rules.md` が FIFO なら読み込みません。読めないルールブックのときと同じ通知を出して起動は続き、判定はルールブック無しで行います。通常ファイルへのリンクは、これまでどおり読みます。
- 決まった名前のファイルが通常ファイルでなければ、書きません。FIFO の上へのメモリの保存はエラーになります。
- 残余: パスで開くルート（2）は見てから開くので、その間に FIFO へ差し替えられた名前では、まだ待ちます。削除のときに開く親（9）も、そういうルートです。ランタイム自身の open で残っているのはこれだけです。一覧するディレクトリには残余が無く、7 からは読むファイルにも、8 からはスキルを歩くときの下位ディレクトリにも、9 からは書くファイルにもありません。9 より前のこの記録にも同じことが書いてありましたが、事実ではありませんでした。リリース前のレビューが 3 つ見つけています。この差し替えには、ランタイムが開いている最中に名前を書き換え続けるプロセスが、すでに書ける場所で動いている必要があり、得られるのは待たせることだけです。
- これを閉じるのに、ファイルでは待たない open（`O_NONBLOCK`）が要りました。ルートではフラグを取る `os.OpenRoot` が要りますが、Go にありません。ファイルツールはすでに `O_NONBLOCK` で開いています（ADR-0072 §4.8）。クラウドフォルダのオンラインのみのファイルで、その open と読み取りがどう動くかは、これを決めた時点では、意図して観察したことがありませんでした。
- その後、iCloud Drive で観察しました（macOS 27.2。2 MiB のファイルと 18 バイトのファイルを、実行のたびに `brctl evict` でオンラインのみにして、2 巡）。open は、`O_NONBLOCK` があっても無くても、その場で返り、何もダウンロードしません。最初の read がダウンロードを待ち（0.8〜1.0 秒）、バイト列を返します。フラグを付けたままでも、open の後で外しても、`os.Root` 経由でも同じでした。毎回すべてのバイトを読め、読んだ後のファイルはディスク上にありました。観察していないもの: それ自体がオンラインのみのフォルダ（フォルダを退避させると中身が退避され、フォルダはそのままでした）、他社プロバイダのフォルダ、ダウンロードが失敗する場合。これを受けて、操作者が 7 を決めました。
- 8 を試す中で観察し、8 では変えていないこと: どこかのプロセスがディレクトリの名前を変え続けている間、ファイルを開くのが遅くなります。歩きだけでなく、そのボリュームでファイルを開くどのプログラムでも同じです。macOS 27.2（APFS）で、そういうループを 1 つ動かして測りました。open は名前の変更が途切れるまで待ち、1 回あたり約 155 ミリ秒かかりました。201 ファイルを歩くのに、8 ミリ秒だったものが 30 秒かかり、`cat` で 1 ファイルを読むのに 0.15 秒かかりました。名前を変えるディレクトリはスキルの中でなくても構いません。スキルの隣でも、ボリュームの別の場所でも、同じ結果でした。ディレクトリの一覧、名前を見ること、ディレクトリを開くこと、すでに開いているファイルを読むことは遅くなりません。ファイルの名前を変えるループでは起きません。読み取り用、書き込み用、イベント専用のどの開き方でも同じように待ちました。8 の前の歩きでも後の歩きでも同じです。いつまでも待つものは無く、照合していないものを読むこともありません。続くのはループが動いている間で、要るのはボリュームのどこかでディレクトリの名前を変えられるプロセスです。ランタイムが実行したコマンドが残した子プロセスも、そのコマンドが書ける場所があれば、それに当たります（サンドボックスが許す範囲からの推論で、サンドボックス越しには測っていません）。待っている open は同じ切れ目でまとめて通ります。同じファイルを 32 個ずつ同時に開くと 1.1 秒でした。この記録の以前の形は、ループがスキルの中に要ると書いていました。それは測っておらず、事実でもありません。操作者は、これに対しては何も変えず、残余として受け入れると決めました。これは歩きの性質ではなく、OS の性質です。ファイルを開くプログラムはどれも同じように待つので、歩きだけ速くしても、ファイルツールも、ランタイムが実行するコマンドも、その機械のほかのすべても遅いままです。そして、ループが終われば終わります。これと比べた案は Alternatives にあります。モデルによる利用は操作者を待たせ続けません。取り消された呼び出しは、どのツール呼び出しとも同じく 1 秒で見切られ、歩きはその裏で自分で終わります。操作者が打つ `/skill` は歩きが終わるのを待ち、3 回目の割り込みでプログラムが終わります（どちらもコードを読んだもので、実行して観察したものではありません）。

## Alternatives considered

- **状態ディレクトリはそのままにする** — 却下。理由は 3 のとおりです。
- **今すぐ、すべてのファイルを `O_NONBLOCK` で開く** — 採りません。これを決めた時点ではオンラインのみのファイルで観察しておらず、ADR-0119 が取り下げたのも同じ理由です。観察はその後に行い（Consequences）、そのうえで 7 として採りました。
- **`O_DIRECTORY` で開いた記述子から、`/dev/fd` 経由でルートを作る** — 却下。ルートの残余は閉じますが、デバイスノードがディレクトリをどう開き直すかに頼ることになり、どのエラーでもルートの名前が変わります。
- **スキルの中のものを、すべてスキルのルートからのパスで名指す** — 8 で却下。階層ごとのハンドルが要らず、`Root.OpenRoot` も要りませんが、歩きが 0.3 秒で済む木に 8.2 秒かかります。
- **`--config` に渡された FIFO を断る** — 操作者の判断に残します（5）。
- **スキルのファイルを複数同時に開く** — 採りません。測ったところでは 30 秒が 1.1 秒になりましたが、待っている open を OS がどう通すかに頼ることになり、それを述べた文書はありません。照合に並行処理と、開いたままの記述子の増加を持ち込みます。そして、速くなるのは歩きだけです。
- **スキルの歩きに時間の上限を付ける** — 採りません。数字の根拠が無く、遅い置き場にある、ピンを取ったときのままのスキルまで断ることになります。
- **操作者が打つ `/skill` を、取り消したら戻るようにする** — 今は採りません。操作者は、遅さを記録して何も変えないことを選びました。歩きが遅くなる原因が何であっても効くので、そこで待たされるのが困るようになったら、採るのはこれです。
