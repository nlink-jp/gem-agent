# ADR-0006: Context compaction

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-19 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | Operator request: implement conversation-history compaction |

## Context

A gem-agent session grows until it hits the model's input window, and
the way it hits it is unpleasant: a turn fails with an API error deep in
an agent loop, and the only recovery on offer is `/clear`, which throws
away everything. The footer added earlier makes the approach visible
(`ctx 812k/~1.0M`), which turns out to sharpen the problem rather than
solve it — the operator watches the number climb and can do nothing about
it except stop.

Tool output dominates the growth. A handful of `read_file` calls over a
large repository outweighs every message the operator typed, and most of
it stopped mattering several rounds ago.

## Decision

Summarise the older part of the conversation and replace it, keeping the
recent part verbatim.

1. **When.** Automatically when the observed prompt-token count reaches
   `[agent].compact_at_pct` (default 80) of the model's input window,
   checked between rounds of the agent loop — where long tool loops
   actually run out of room — and manually via `/compact`. Auto-compaction
   is on by default (`[agent].auto_compact`); it is not a weakening of any
   defense, and a tool whose sessions die at the window is not a backup
   tool.
2. **Where to cut.** The most recent `keepRecent` messages stay verbatim;
   everything older is summarised. The cut is then moved forward past any
   **tool result**, because Gemini requires every function call to be
   paired with its response in the same request: a cut landing on a
   result would leave the retained half starting with a response whose
   call had been summarised away — a 400. Every other message is a safe
   start, an assistant turn included, since its own results always follow
   it immediately.

   Cutting only at user messages is tidier and was the first rule
   written here. It was withdrawn during verification: one long agent
   loop contains exactly one user message, at the very beginning, so
   that rule could never compact the case this ADR exists for.
3. **How.** One LLM call, **with no tools offered**, whose input is the
   rendered transcript of the messages being replaced, **nonce-wrapped as
   untrusted data** (nlk/guard) with the defensive framing first. The
   transcript being summarised is full of tool output; a summariser that
   treated it as instructions would be an injection path straight into
   every subsequent turn. Individual tool results are clipped when
   rendered for this call — the summary does not need the bytes, and the
   call should be cheaper than the context it is buying back.
4. **What replaces it.** A single user-role message carrying the summary
   **as an attachment**, so the existing send-time wrapping quotes it as
   data rather than instructions. The summary is model-generated text
   derived from untrusted input; it is a set of facts to rely on, not a
   new set of orders.
5. **Fail safe, not fail small.** If the summarisation call errors, is
   filtered, or returns nothing, **the history is left exactly as it
   was** and the operator is told. Compaction that half-worked would
   silently delete a conversation. For the same reason a compaction that
   would not shrink anything (too few messages, no safe boundary) is
   declined with a message rather than performed.
6. **Recorded.** Each compaction writes a `compaction` record — the
   number of leading messages replaced, and the summary message itself —
   so a resumed session (ADR-0005) reconstructs the compacted history
   rather than the pre-compaction one.

## Consequences

- Long sessions survive. The cost is one extra LLM call per compaction
  and the loss of detail in the summarised half — stated plainly in the
  notice, because a model that has forgotten something must not look
  like a model that never knew it.
- The summary is a lossy artifact generated by the same model that may
  be having a bad day. `/compact` being manual as well as automatic
  gives the operator a way to compact at a natural boundary (end of a
  task) rather than mid-thought, which is when summaries are best.
- Auto-compaction depends on knowing the window. Vertex publisher
  metadata omits `inputTokenLimit`, so the value is often the family
  assumption (1M) already used by the footer; `[model].context_window`
  makes it exact. When no window is known at all, auto-compaction stays
  off and `/compact` still works.
- Compaction cannot shrink the system prompt or the instruction files.
  A project whose `CLAUDE.md` set is itself near the window is a
  different problem, and one this does not pretend to solve.

## Alternatives considered

- **Drop the oldest messages** (no summary) — rejected: cheap, and the
  agent silently forgets decisions it agreed to. The failure is invisible
  precisely where it matters.
- **Summarise into the system prompt** — rejected: the system prompt is
  the trusted channel, and this content is derived from untrusted tool
  output. It belongs in the conversation, quoted as data.
- **Compact only on demand** — rejected as the default: the operator is
  usually reading output, not the token counter, and the failure it
  prevents arrives mid-loop.
- **Summarise per tool result, continuously** (rolling compression) —
  rejected for now: more calls, more places to be wrong, and it discards
  detail that is still in use. Revisit if one compaction per session
  proves insufficient.
