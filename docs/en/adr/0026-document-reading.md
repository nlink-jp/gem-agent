# ADR-0026: Document reading — native PDF, extracted Office formats

| Field | Value |
|-------|-------|
| Status | **Accepted** |
| Date | 2026-08-20 |
| Binds | gem-agent |
| Decision makers | nlink-jp maintainers |
| Triggered by | Operator: can the common file types — Excel, Word, PowerPoint, PDF — be supported? Interpretation over creation |

## Context

The agent could read text and view images; the documents people
actually hand an assistant — PDFs, Word, Excel, PowerPoint — were
opaque (read_file refuses or garbles them, file_info only names them).
Gemini understands PDF natively as document parts; the Office XML
formats are not accepted by the API but are zip+XML that pure Go can
open.

## Decision

1. **Two-tier support by format.** PDF rides to the model as bytes —
   measured before designing: a PDF part is accepted both as a user
   message part and inside a multimodal function response, and the
   conversation continues past the tool round without the ADR-0012
   latent 400 (verified to round 3 against ground truth). The Office
   XML formats — .docx, .xlsx, .pptx — are extracted to text locally
   by a pure-Go package (`internal/docext`): word processing text in
   document order, sheets as tab-separated rows named per sheet,
   slides as numbered text blocks. Legacy binary formats (.doc, .xls,
   .ppt) are out of scope — reading them means a heavyweight
   dependency for formats two decades past their successor.
2. **Both access paths, per ADR-0012's "who chose the file" split.**
   The operator attaches with `@report.pdf` / `@data.xlsx` (project
   files, or absolute/~ paths — extended from images to documents on
   the same rationale: the operator typed the path themselves). The
   model reads with a new `read_document(path)` tool, project-confined
   like every reading tool: PDF returns as a multimodal function
   response part; Office formats return extracted text.
3. **Extraction is untrusted like any tool output** — nonce-wrapped
   text; a PDF part cannot be wrapped, so it inherits the image
   framing (visible text inside a document is content, never
   instructions — the system prompt already says so for images and now
   says documents too).
4. **Caps reported, never silent**: PDFs over the inline budget are
   refused with the size and the limit named; Office extraction stops
   at its text cap with a truncation note, and zip members are read
   through a decompression cap so a crafted archive cannot balloon
   memory.
5. Verification is ground-truth-first: a real PDF (generated by an
   independent producer, not by the code under test) with a known
   token, a real .docx from macOS textutil, and spec-conformant
   fixtures for .xlsx/.pptx, each answered correctly end-to-end.

## Consequences

- "Read this report" works for the four formats people actually send.
- The transcript stores PDF bytes like images (base64; resume keeps
  them); compaction summarises them as placeholders.
- Tokens: a PDF page costs what the model charges for document pages —
  /usage makes it visible.

## Alternatives considered

- **Local PDF text extraction** — rejected: pure-Go PDF text extraction
  is fragile (fonts, encodings, layout), and the model reads the real
  layout natively, tables and scans included.
- **A dependency for Office parsing** (excelize etc.) — rejected: the
  needed slice (text out) is small, and heavyweight deps cut against
  the fallback tool's zero-dependency posture.
- **Legacy binary formats** — out of scope, stated loudly in the tool's
  error message.
